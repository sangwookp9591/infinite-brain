# B0-a llama.cpp 내장 실험 보고서

2026-10-16 · 브랜치 `iron/spike-b0-llama` · 기준 문서: PRD v2 §5.8 F8.1~F8.3, §9 B0 행, §12 Q2 (`docs/superpowers/specs/2026-10-15-team-second-brain-prd.md`)

## 1. 결론 (한 문단)

**macOS(Apple silicon) 한정 조건부 채택을 권고한다. B0는 아직 완료되지 않았다.** PRD §9의 B0 출시 조건은 "OS별 CPU·메모리·속도·앱 크기 측정"인데 Windows·Linux·Intel Mac은 측정하지 못했다. Rust에서 llama.cpp를 앱 바이너리에 정적으로 넣어 EmbeddingGemma 2(GGUF)를 별도 런타임 없이 실행할 수 있음을 macOS(M5)에서 확인했다. 이 기기에서는 Metal로 문단 1개를 약 15ms, 100개를 약 1~2초에 처리한다. 바이너리 증가는 Metal 포함 약 9.0MiB, CPU 전용 약 3.7MiB다. 지금 crates.io의 `llama-cpp-2 0.1.160`에 들어 있는 llama.cpp는 EmbeddingGemma 2 구조(`gemma-embedding2`)를 모른다. `llama-cpp-rs` main도 같은 llama.cpp(v0.6.0)라서 git 핀으로는 해결되지 않는다. 이 실험은 llama.cpp를 최신 태그로 바꿔 끼운 사본으로 통과시켰고, 이 모델을 돌리는 길은 지금 **포크뿐**이다. 양자화는 **기본 Q8_0(약 310MB 내려받기)**, Q4_K_XL(약 180MB)은 B1 검색 품질 평가로 기준이 확정될 때까지 저사양 대안으로만 둔다(Q4는 BF16과 top-3 순서가 18~19/24만 일치, §4.6). Windows·Linux, 디스크 cold 상태, 배터리는 측정하지 못했고, B1 전에 처리할 항목은 §6에 모았다.

> 이 보고서는 독립 검증(`B0-LLAMA-VERIFY-opus.md`, 29f53af)을 반영해 고쳤다. 반영 내역과 반영하지 않은 항목은 맨 끝 "검증 반영 기록"에 있다.

**가정.** (a) "EmbeddingGemma 2 GGUF"는 Unsloth 배포본을 쓴다. 공식 모델명이 존재해서 대체 모델은 쓰지 않았다. (b) 앱 호환을 보려는 것이 아니라 실행 가능성과 비용을 보는 spike이므로 `src-tauri`에는 연결하지 않았다(의존성도 건드리지 않음). (c) Windows·Linux는 이 기기에서 잴 수 없어 B1 확인 항목으로 넘긴다.

**측정 신뢰도에 관한 주의.** 측정 중 이 기기에서 다른 워커와 OrbStack이 함께 돌아 load average가 7~89까지 흔들렸다고 기억하지만, **load average와 열 상태는 원자료에 기록하지 않았다**(`run-bench.sh`가 남기지 않음). 아래 "load 14~22"는 출력 근거가 없는 기억값이다. 설정마다 1회씩만 돌렸고 원자료(`matrix.out`, dump)는 저장소 밖 `~/.cache/infinite-brain-b0/`에만 있다. **Metal 수치는 GPU 위주라 비교적 안정적이다**(검증자 재실행에서 ±20% 안으로 재현). **CPU 수치는 부하에 크게 흔들릴 수 있어** 비율(예: Q4가 Q8보다 1.7배 빠름)은 신뢰하기 어렵고, 방향만 본다. 절대값이 아니라 자릿수와 상대 비교로 읽어야 한다.

- **정적 링크:** 가능하다. 기본이 정적이다(`llama-cpp-sys-2` `build.rs:484-488`에서 `dynamic-link` feature나 `LLAMA_BUILD_SHARED_LIBS=1`일 때만 공유 라이브러리). 실제로 `otool -L target/metal/release/bench`에 `libllama`·`libggml` 같은 동적 라이브러리가 없고 시스템 프레임워크(Foundation, Metal, MetalKit, Accelerate)와 `libc++`만 나온다.
- **CPU 명령어 최적화:** `GGML_NATIVE`는 `target-cpu=native`를 줄 때만 켜진다(`build.rs:808-816`). 기본은 꺼져 있어 빌드한 기기에 묶이지 않는다.
- **Metal:** macOS에서는 `metal` feature와 상관없이 **항상 켜진다.** `build.rs:894`는 watchOS에서만 끄고, `build.rs:1519-1521`은 watchOS가 아니면 Metal·MetalKit 프레임워크를 링크한다. 그래서 "CPU 전용" 비교용으로는 사본의 `build.rs`에 환경변수 `B0_NO_METAL=1` 스위치를 넣었다(`scripts/vendor-llama.sh`). 실행 때는 `n_gpu_layers`(0 또는 99)로 CPU/GPU를 고른다.
- **기타 feature:** `vulkan`, `cuda`, `opencl`, `webgpu`, `openmp` 등이 있다(`llama-cpp-2` Cargo.toml). Windows·Linux GPU는 Vulkan이 후보이나 이번에는 확인하지 못했다.
- **막힌 점 (중요):** 0.1.160이 번들한 llama.cpp는 `d81235049384534c167caea52b85a694f6103d14`(2026-10-05, 태그 `v0.6.0`)다. 이 시점에는 `LLM_ARCH_GEMMA_EMBEDDING`(1세대)만 있고 `gemma-embedding2`가 없다. 모델 파일의 `general.architecture`는 `gemma-embedding2`다. 지원 커밋은 `4fbc76dec5`(2026-10-06, "model: support embeddinggemma2")로 v0.6.0보다 23커밋 뒤이고, v0.7.0은 그보다 217커밋 뒤다. 검증자가 확인한 대로 `llama-cpp-rs` main(`224a1a3`, 0.1.161)의 서브모듈도 같은 `d81235049…`이다. 그래서 **릴리스된 crate로도, `llama-cpp-rs` git rev 핀으로도 이 모델을 못 돌린다.** 지금 경로는 서브모듈을 올리고 `timing.rs`를 패치한 **포크뿐**이다. 업스트림 서브모듈이 올라간 뒤에야 git rev 핀으로 바꿀 수 있다. 관련 이슈는 검색되지 않았다.
- **우회 (이번 실험에서 쓴 방법):** `scripts/vendor-llama.sh`가 `llama-cpp-sys-2`를 복사해 `llama.cpp`만 `v0.7.0`으로 바꾸고, 래퍼 `llama-cpp-2`도 복사해 새 C 구조체의 필드 추가에 맞게 한 곳(`src/timing.rs`의 `llama_perf_context_data`에 `n_reallocs_diff`, `n_reallocs_same` 0으로 추가)만 고친다. `Cargo.toml`의 `[patch.crates-io]`가 이 사본을 가리킨다. 사본(약 180MB)은 `.gitignore`로 막았다. 다른 호환 문제는 이 모델에서는 나오지 않았다.

1. Apache-2.0 모델에 카드가 붙인 "Prohibited Use Policy 준수" 요구가 법적 구속력을 갖는지, 앱 약관에서 사용자에게 이 의무를 넘겨야 하는지.
2. 자체 모델 미러(§6 내려받기)가 재배포에 해당해 Apache-2.0 §4(사본·고지 동봉) 의무를 만드는지.
3. UI에서 "Gemma" 상표를 표기하는 방식.
4. 우리가 직접 양자화한 파생물을 배포할 때의 고지.
5. 앱 서드파티 고지에 llama.cpp/ggml(MIT) 저작권 고지와 모델 Apache 2.0 전문·고지를 어디에 넣을지.

- **BF16은 CPU에서 쓸 수 없다**(문단 1개 2초 이상). 품질 기준(레퍼런스)으로만 썼다.
- **스레드 수 시험 (`matrix.out`, 설정당 1회. 모델은 Q4_K_XL로 기억하나 검증 문서가 모델을 적지 않아 확인하지 못함).** 4스레드 100문단 순차 10.4초(9.6/s, 위 표). 6스레드 16.2초(6.2/s). 10스레드(모든 코어)는 순차 54.3초(1.8/s), 묶음 11.7초(8.6/s)다. 이전 판이 10스레드 "168초"라고 쓴 값은 100문단 시간이 아니라 **프로세스 전체 시간(`total_wall_ms`=168,499ms)을 잘못 읽은 것**이어서 정정했다. 코어 수만큼 스레드를 쓰면 4스레드보다 순차 처리가 느려진다. 성능 코어 수 이하로 제한하고 낮은 우선순위로 돌려야 한다(앱 편집 지연 방지, §11 측정 정의와도 연결). 단, macOS에서 낮은 QoS(background)는 효율 코어에만 배치되므로 "성능 코어 수만큼 스레드"와 "낮은 우선순위"를 함께 쓰면 처리량이 표와 크게 다를 수 있다. B1에서 QoS 등급별로 재야 한다.
- **부하 민감도는 수치로 입증하지 못했다.** 이전 판에 적었던 "4스레드 재실행 19.1초(5.2/s)", "6스레드 187초(0.5/s), load 89", "9.8/s 재현", "6스레드는 20배 느려짐"은 **남은 원자료에 없어 기록 없음으로 처리하고 근거에서 뺐다.** 원자료의 6스레드 값은 16.2초다. 부하 때문에 CPU 수치가 흔들렸을 가능성은 있으나(load average가 크게 변했다는 기억), 얼마나 흔들리는지는 이번 자료로 말할 수 없다.
- 표의 Q4 CPU 값(9.6/s)은 설정당 1회 측정이다. 사용자 기기가 바쁠 때의 하한은 이 자료로 정할 수 없고, 조용한 기기에서 반복 측정이 필요하다.

### 4.4 메모리 해석

최대 RSS는 mmap된 모델 파일 페이지를 포함한다. 메모리 풋프린트(`peak memory footprint`)는 Metal에서 383~394MB로 BF16(532MiB 모델)에서도 모델 크기보다 작다. mmap된 모델 페이지가 footprint에 잡히지 않는다는 뜻이므로 **예산 기준은 RSS**로 삼는다. CPU 풋프린트는 Q4 542MB, Q8 593MB다. 앱의 메모리 예산은 보수적으로 **Q8 약 0.7GB, Q4 약 0.5GB**(RSS, 컨텍스트 4096 기준)로 잡고, 앱 자체 사용량과 합산해 B1에서 다시 잰다. 계산용 버퍼는 `n_ubatch=4096`에 비례하는데 이 값을 바꿔 보지 않았다. 메모리 예산은 chunk 상한과 함께 정한다.

### 4.5 출력 차원과 Matryoshka

- 출력 차원 768, 모든 값 유한(NaN 없음). **llama.cpp의 출력은 정규화되어 있지 않다**(첫 문단 L2 노름 483.9). 공식 sentence-transformers에는 `2_Normalize` 단계가 있는데 llama.cpp 경로에는 없으므로 **앱이 직접 L2 정규화해야 한다.**
- 앞 128·256·512·768차원을 자른 뒤 다시 정규화하는 `truncate_norm` 구현(앞 d개를 자른 뒤 L2로 나눔)은 맞다. 다만 출력의 `trunc*_norm_after=1.0000`은 **증거가 아니다.** 정규화하면 항상 1이 되는 항등식이다. 또 `cos()`가 내부에서 다시 정규화하므로 smoke의 256d 결과는 재정규화 여부와 무관하다. 노름이 0이면 NaN이 나는데 이를 막는 장치가 없으므로 앱 코드에서 막고 유한값을 검증한다(F8.4). 앱이 내적으로 순위를 낸다면 저장된 정규화 벡터로 내적 순위를 시험해야 한다. 카드가 안내하는 MRL 차원은 128/256/512/768이다.
- 카드의 보고값(MTEB 다국어 v2): 768d 61.36, 512d 61.17, 256d 60.41, 128d 57.89. 코드 MTEB는 768d 78.68 → 256d 76.18(−2.5점)로 다국어(−0.95점)보다 손실이 크다(검증자 확인). 이번 smoke에서는 256d와 768d의 검색 결과가 같았으나 변별력이 낮다(아래).

### 4.6 품질 smoke (한국어·영어)

모든 모델·빌드에서 결과가 사실상 같았다. 표는 Q4_K_XL 값이다(768d / 256d).

| 지표 | 768d | 256d |
|---|---|---|
| 문장 쌍 유사도, 같은 뜻 4쌍 평균(ko↔en) | 0.929 | 0.934 |
| 문장 쌍 유사도, 무관 4쌍 평균 | 0.720 | 0.721 |
| 차이(gap) | 0.209 | 0.213 |
| 한국어 문단 ↔ 같은 주제 영어 문단 평균 (12쌍) | 0.845 | 0.858 |
| 한국어 문단 ↔ 다른 주제 영어 문단 평균 (132쌍) | 0.590 | 0.611 |
| 짧은 검색어 24개 → 문단 24개, top-1 정답(같은 주제의 ko 또는 en) | 24/24 | 24/24 |

해석: 같은 뜻과 무관한 쌍이 분리되고 한·영 교차 검색이 된다. 다만 **무관한 쌍의 유사도도 0.72로 높다**(문장 유사도 prefix 사용). 임계값을 절대값으로 쓰지 말고 순위로만 써야 한다. 말뭉치가 작고(24문단) 주제가 뚜렷이 달라서 24/24는 변별력이 낮다. 양자화 간 품질 차이는 이 검색 smoke로는 구분되지 않아, 아래의 BF16 대비 벡터 코사인으로 비교했다.

**양자화 품질 (BF16 CPU 결과 대비 같은 입력 48개 벡터의 코사인)**

| 모델 | CPU 최소 / 평균 | Metal 최소 / 평균 |
|---|---|---|
| F16 | 0.99999 / 0.99999 | 0.99999 / 1.00000 |
| Q8_0 | 0.99971 / 0.99985 | 0.99985 / 0.99993 |
| Q4_K_XL | 0.97315 / 0.99343 | 0.97380 / 0.99383 |

Q8은 BF16과 거의 같다. Q4는 평균 0.993이지만 일부 벡터는 0.973까지 벗어났다.

**순위 영향: 평균 코사인이 가린다.** 같은 dump로 BF16과 **top-3 순서가 같은 질의 수**를 다시 세면(검증자 계산, 질의 24개) 다음과 같다.

| 모델 | 768d | 256d |
|---|---|---|
| Q8_0 | 23/24 | 24/24 |
| Q4_K_XL | 19/24 | 18/24 |

작고 쉬운 말뭉치에서도 Q4는 top-3 순서를 바꾼다(top-1은 24/24로 같아 구분되지 않는다). 이 값이 "GPU 없는 기기는 Q4" 권고를 접은 이유이고, Q4의 품질 비용으로 본다. 실제 노트에서의 영향은 B1 검색 평가(§11 지표)로 재야 한다.

**float16 경고.** "Run inference in bfloat16 or float32. Do not use float16" 경고의 출처는 Google 공식 카드이고 Unsloth 카드가 그대로 옮겼다. 경고 대상은 **활성값 범위**다. 이 llama.cpp(v0.7.0)에서 F16 **가중치** GGUF가 CPU·Metal 모두 정상(BF16과 코사인 0.99999)이었다고 해서 경고를 반박하지는 않는다. 백엔드가 활성값을 F16으로 계산하는 경로가 생기면 다시 확인한다. F16은 크기 이점이 없어 쓰지 않는다.

**이 smoke의 한계.** 말뭉치가 12개 글을 `(#i)`만 붙여 반복했고 평균 77토큰이다. 정답이 같은 주제의 ko·en 둘 중 하나라 쉬운 과제이고, 글쓴이와 평가자가 같다. top-1 24/24는 상한에 붙어 768d와 256d를 구분하지 못한다. "망가지지 않았다"는 뜻만 있다. PRD §11의 검색 품질 지표(정답 없음, 코드, 정확한 이름, hit@5, nDCG)는 하나도 측정하지 않았다. 또 기준으로 쓴 BF16도 llama.cpp 경로를 거친 결과여서, 확인한 것은 양자화 간 일관성뿐이다. BOS/EOS 처리(`tokenize(..., true, ...)`), mean pooling의 prompt 포함 여부, 512→768 투영이 sentence-transformers float32 출력과 같은지는 비교하지 않았다. B1 첫 단계에서 입력 50개 정도로 코사인 0.99 이상인지 확인한다.

## 5. 위험

1. **번들 llama.cpp가 모델보다 오래됐다.** 릴리스된 `llama-cpp-2`로도, `llama-cpp-rs` main의 git 핀으로도 이 모델이 로드되지 않는다(§3.1). 지금은 포크뿐이다. llama.cpp는 거의 매일 갱신되며 C 구조체가 바뀌면 래퍼 빌드가 깨진다(이번에도 한 필드 때문에 깨졌다). 포크 서브모듈은 태그와 **커밋 SHA**로 고정하고, 래퍼 패치는 업스트림 PR로 돌려보낼 계획이 필요하다.
2. **CPU 성능이 스레드 수와 기기 부하에 민감할 수 있다.** GPU가 없는 환경(또는 GPU 경로 실패)에서는 이 기기 기준 문단 5~10개/초 수준이다. 만 개 문단을 처음 색인하면 CPU로 약 17~33분, Metal로 약 1.5~3분이다(위 처리량으로 계산한 추정). **이 추정은 평균 77토큰 문단 기준의 하한이다.** 실제 chunk(256~512토큰)에서는 문단당 시간이 크게 늘어나므로 tok/s와 실제 길이 분포로 다시 내야 한다. 작업 큐, backpressure, 스레드 상한, 낮은 우선순위가 필수다(F8.3).
3. **첫 실행 지연.** Metal 셰이더를 첫 실행에서 런타임 컴파일한다(§4.2). 미리 데우기가 필요하다.
4. **빌드 환경.** cmake와 C++ 툴체인이 있어야 한다. 이 기기에는 cmake가 없어 pip로 따로 받았다(앱 개발자·CI 요건). bindgen용 `libclang`도 필요하다. Metal은 Xcode `metal` 도구가 필요 없다(§4.2).
5. **디스크 cold 로드 미측정.** `purge`에 sudo가 필요해 OS 페이지 캐시를 비우지 못했다. 로드 0.5~0.8초는 파일이 캐시에 있을 때의 값이다.
6. **라이선스·고지.** §3.2의 법무 확인 항목 5건과 고지문 배치. 두 HF repo에는 LICENSE 파일이 없다.
7. **입력 규칙.** 비대칭 prefix(검색어/문서)를 쓰는 모델이다. 색인 버전(F8.4)에 prefix 규칙을 포함해야 하고, 이번에는 prefix 유무 비교를 하지 않았다.
8. **긴 문단.** 이 모델은 비인과 어텐션이라 한 번에 넣는 토큰이 `n_ubatch` 이하여야 한다. 이번 말뭉치는 짧아(약 77토큰) 긴 문단·긴 노트 처리(chunker 상한)는 측정하지 못했다.
9. **x86 CPU 빌드가 AVX 없이 나간다(높음, 검증자 지적).** `llama-cpp-sys-2`는 `GGML_NATIVE=OFF`이고 `CARGO_CFG_TARGET_FEATURE`로만 SIMD를 켠다(`build.rs:832-850`). `x86_64-pc-windows-msvc`의 기본 feature는 `sse`~`sse3`, `x86_64-apple-darwin`은 `sse4.1`까지다(`rustc --print cfg`). 그래서 Windows·Linux·Intel Mac 빌드에는 AVX2·FMA·F16C가 없어 CPU 처리량이 위 M5 수치보다 훨씬 낮을 수 있다. 앱 전체에 `+avx2`를 주면 구형 CPU에서 시작하자마자 `SIGILL`로 죽는다. 대안은 (a) `GGML_CPU_ALL_VARIANTS`+`GGML_BACKEND_DL`(DLL 동적 로딩이라 "정적 단일 바이너리"와 충돌하고 DLL마다 서명·공증 필요), (b) AVX2 sidecar와 기본 sidecar 두 개, (c) 런타임 감지 후 비활성화다. B1 전에 정한다.
10. **Vulkan을 켜면 앱 전체가 Vulkan 로더에 의존한다(높음, 검증자 지적).** `build.rs:1043`(Windows)는 `vulkan-1`을, `build.rs:1066`(Linux)은 `vulkan`을 링크한다. 정적으로 넣으면 로더가 없는 기기(VM, 원격 데스크톱, 일부 Windows on ARM)에서 의미 검색만 꺼지는 것이 아니라 앱 자체가 시작하지 못할 수 있다. 빌드에는 `VULKAN_SDK`와 `glslc`도 필요하다.
11. **Windows CRT가 일치해야 한다.** `LLAMA_STATIC_CRT`·`config.static_crt`(`build.rs:501,917`)를 Tauri 앱의 CRT 설정과 맞추지 않으면 링크 오류(LNK2038)가 나거나 런타임이 섞인다.
12. **빌드 시간과 CI.** 릴리스 매트릭스는 4개(arm64·x86_64 macOS, ubuntu-22.04, windows)이고 한 번에 약 35~45분 걸린다(`release.yml` 주석). 여기에 대상마다 llama.cpp cmake 빌드와 bindgen이 더해진다. 러너에 cmake, libclang, (Vulkan을 쓰면) Vulkan SDK를 설치해야 하고 캐시도 커진다(이 spike의 `target/`만 513MB). 빌드 시간은 측정하지 않았다.
13. **같은 프로세스 안에서 실행할 때의 안정성(in-process abort).** ggml은 `GGML_ASSERT`/`GGML_ABORT`에서 프로세스를 끝낸다. 긴 입력, 메모리 부족, 드라이버 오류가 나면 편집 중인 앱이 통째로 종료된다. 디스크 쓰기는 원자적이지만 저장 전 편집 상태를 잃을 수 있다. sidecar 프로세스로 분리하면 장애와 메모리를 격리하고 우선순위도 따로 줄 수 있다. B1 설계에서 in-process와 sidecar를 비교한다.
14. **코드 서명·보안 도구.** 정적 링크라 macOS에서 추가로 서명할 dylib는 없다(`otool -L` 확인). `GGML_BACKEND_DL`을 쓰면 DLL·dylib마다 서명·공증이 필요하다. Windows는 지금 OS 서명이 없어(`release.yml` 주석) 네이티브 코드와 대용량 다운로드가 늘면 SmartScreen·백신 오탐 위험이 커진다.
15. **GGUF 파서가 공격면이다.** F8.2의 폐쇄망 수동 설치는 서명 manifest를 거치지 않으므로 임의의 GGUF를 로드하게 된다. 수동 설치에도 SHA-256 허용 목록 검증을 의무화한다.
16. **공급망.** `vendor-llama.sh`가 llama.cpp tarball을 SHA-256 검증 없이 받는다(태그는 옮길 수 있으므로 커밋 SHA로 고정해야 한다). 또 `UD-Q4_K_XL`은 Unsloth 고유 레시피여서 우리가 다시 만들 수 없고 제3자 파일에 의존한다.
17. **재현성.** 커밋된 트리를 깨끗한 디렉터리에 풀면 `cargo metadata --offline`이 `vendor/` 누락으로 실패하고, `vendor-llama.sh`는 `~/.cargo/registry/src`에 crate가 이미 풀려 있다고 가정한다. 처음 쓰는 기기에서는 순서가 꼬이고 README에 이를 푸는 단계가 없다. 원자료도 `~/.cache`에만 있다.
18. **PRD §11에서 측정하지 않은 항목.** 최소 사양 기기(M5 24GB는 고사양), 배터리·발열, 편집 지연, CPU 사용률(처리량만 쟀음), 색인 디스크 크기, cold 상태.

### B1 착수 전 처리 목록

1. **포크 결정:** `llama-cpp-rs` 포크로 서브모듈과 `timing.rs` 패치를 고정(태그+커밋 SHA)하고 업스트림 PR 계획을 세운다. `vendor-llama.sh`는 커밋 SHA와 tarball 해시로 고정하고 README에 깨끗한 checkout 절차(registry crate를 먼저 받는 방법)를 적는다(§5-16, 17).
2. **x86 AVX 미적용:** Windows·Linux·Intel Mac 빌드가 AVX2 없이 나가는 문제의 해법(ALL_VARIANTS+BACKEND_DL / sidecar 2종 / 런타임 감지)을 정한다(§5-9).
3. **Vulkan 로더 의존:** Vulkan을 정적으로 링크하면 로더 없는 기기에서 앱이 시작하지 못할 수 있다. 동적 로딩 또는 sidecar 분리로 앱 시작을 보호한다(§5-10).
4. **Windows CRT:** `LLAMA_STATIC_CRT`를 Tauri 앱 설정과 맞춘다(§5-11).
5. **CI 빌드 시간:** 4개 대상의 llama.cpp cmake·bindgen 빌드 시간과 캐시 크기를 측정하고 러너 설치 항목(cmake, libclang, Vulkan SDK)을 확정한다(§5-12).
6. **in-process abort:** 앱 안에서 직접 돌릴지 sidecar로 분리할지 비교하고 결정한다(§5-13).
7. **라이선스 고지·법무 확인:** §3.2의 법무 확인 5건을 처리하고 서드파티 고지(llama.cpp MIT, 모델 Apache-2.0)와 사용 정책 문구를 배포 조건으로 넣는다.
8. **검증 선행:** 공식 구현(sentence-transformers float32)과 입력 50개 정도로 코사인 0.99 이상인지 확인하고, 실제 노트·실제 chunk 길이로 검색 평가(양자화·차원 기준 확정)와 처리량 재추정을 한다(§4.6, §5-2).
9. **OS별 측정:** Windows·Linux·Intel Mac의 CPU·메모리·속도·앱 크기, 최소 사양 기기, 배터리·발열, 편집 지연, cold 상태를 잰다(PRD §9 B0 출시 조건).

### Windows·Linux에서 확인할 것

1. 정적 링크 빌드가 되는지(MSVC + 정적 CRT, Linux는 `libstdc++` 동적 의존 문제: `build.rs`가 Linux에서 기본 `dylib=stdc++`로 링크함). 바이너리 증가분.
2. CPU 최소 사양: 기본 빌드는 AVX2·FMA·F16C 없이 나간다(§5-9). 해법별로 문단 처리량, 최대 메모리, 구형 CPU의 지원 하한을 잰다.
3. GPU: Vulkan feature 빌드와 동작(Intel/AMD/NVIDIA 드라이버 유무), 실패 시 CPU로 자동 복귀하는지, 첫 실행 지연.
4. 메모리가 작은 기기(8GB 이하)에서 §4.4의 예산이 맞는지.
5. 백신·SmartScreen 등 OS 보안 도구와의 상호작용(모델 파일 mmap).
6. Tauri 앱에 실제로 링크했을 때의 충돌(`rusqlite` bundled SQLite와의 심볼, C++ 런타임). 이 spike는 앱과 분리되어 있어 확인하지 않았다.

### 이번에 하지 않은 것

`src-tauri` 연동, Windows·Linux·Intel Mac(B0 출시 조건 미충족), 공식 구현(sentence-transformers)과의 출력 비교, 디스크 cold 로드(`sudo purge` 후 `scripts/run-bench.sh` 재실행으로 가능), 배터리·발열, 긴 문단, prefix 유무 비교, 실제 노트 말뭉치와 BM25 혼합 순위(F8.6), 편집 중 동시 부하, Q5/Q6 XL 양자화, 조용한 기기에서의 CPU 재측정.

## 7. 재현 방법

`app/apps/desktop/spikes/b0-llama/README.md` 참고. 요약: 모델을 `~/.cache/infinite-brain-b0/models/`에 받고(위 표의 revision), cmake를 PATH에 두고 `scripts/vendor-llama.sh` → `B0_NO_METAL=1 cargo build --release --target-dir target/cpu` 및 `cargo build --release --target-dir target/metal` → `scripts/matrix.sh`. 양자화 품질은 `bench --dump`로 쓴 파일을 `cmpdump`로 비교한다. 새 소스 파일에는 Apache-2.0 SPDX 헤더를 넣었다.
