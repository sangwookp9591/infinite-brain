# 사내 협업 동기화를 위한 논문과 구현 조사

조사·출처 확인일: 2026-10-21. **설계 제안이며 구현·보안 감사·사용성 검증 결과가 아니다.** 산출물: [PRD](../specs/06-office-collaboration-prd.md), [전체 아키텍처](../specs/07-office-collaboration-architecture.md).

**직원이 IP나 서버 명령을 몰라도, 별명을 설정하고 근처 작업 공간에 참여하는 제품을 만들 수 있다.** 권고는 회사 내부에서 앱이 관리하는 단일 권한 허브를 두고, 자동 발견과 승인으로 연결하는 방식이다. 허브는 팀 그룹, 폴더 권한, 변경 이력과 저장 확인을 맡고 각 직원의 앱은 오프라인 편집을 유지한다. 사람의 별명은 화면에서 알아보는 용도로 쓰며 기기 키와 승인된 구성원 ID가 실제 신원을 연결한다. 기존 Yjs·Markdown bridge·Hono/Hocuspocus·Postgres를 재사용하고 발견·기기 인증·운영 계층을 추가한다. 완전한 다중 마스터 P2P보다 회사의 구성원 회수와 폴더 권한을 일관되게 다루기 쉽다는 판단이다. 다만 서버 런타임과 실제 Postgres를 비개발자용 설치물로 묶는 작업은 아직 검증되지 않았으며, 이를 첫 구현 진입 조건으로 삼아야 한다.

## 주소는 자동으로 찾고 사람은 별명과 승인으로 구별한다

mDNS는 일반 DNS 서버 없이 로컬 링크의 이름을 해석하며 DNS-SD는 서비스 인스턴스와 연결 정보를 발견한다. 직원에게 IP를 입력받지 않는 표준 기반이다. 기업망에서는 라우터·VLAN을 넘어 발견되지 않을 수 있고 같은 와이파이의 단말 간 연결도 제한될 수 있다. 따라서 ‘근처’는 물리적 거리나 같은 회사라는 인증이 아니라 **접근 가능한 네트워크에서 발견한 후보**라는 뜻이어야 한다. 발견 실패에는 endpoint가 포함된 초대 링크·파일을 제공하되 네트워크 자체의 연결 차단을 우회한다고 설명해서는 안 된다. ([RFC 6762](https://www.rfc-editor.org/rfc/rfc6762.html), [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763.html), [기업망 요구 RFC 7558](https://www.rfc-editor.org/rfc/rfc7558.html))

LocalSend는 alias, fingerprint, port 등을 포함한 로컬 발견과 서버 없는 파일 전송의 실용 사례다. Syncthing은 사람이 읽는 기기 이름과 TLS 인증서 지문으로 만든 기기 ID를 분리한다. 여기서 가져올 설계는 ‘민수 · 기획팀 · 7K2P’ 같은 익숙한 표시와 변하지 않는 신원을 결합하는 것이다. 별명 변경이 작성자나 권한을 바꾸어서는 안 되며, 같은 이름의 새 허브나 기기를 자동 신뢰해서도 안 된다. LocalSend는 장기 협업 ACL이나 회사 인명록을 제공하는 기반이라고 해석하지 않는다. ([LocalSend protocol](https://github.com/localsend/protocol/blob/main/README.md), [Syncthing device IDs](https://docs.syncthing.net/dev/device-ids.html), [Syncthing 보안 원칙](https://docs.syncthing.net/users/security.html))

페어링 연구인 Kumar·Saxena·Uzun의 *Alice Meets Bob*은 두 사람이 각자 자기 기기를 조작하면서 짧은 확인 문구를 비교하는 방식을 연구했다. 40명의 주로 대학생 표본에서 문구 비교 평균은 11.44초였지만 한국 직장인의 성공률·소요 시간으로 일반화할 수 없다. 실무 통찰은 IP나 기기를 서로 넘기지 않고 두 화면의 신뢰 정보를 확인하도록 만드는 것이다. arXiv 제출은 2009년이며 PDF 표지의 날짜 차이가 있으므로 ‘최근 실증’으로 소개하지 않는다. ([논문 원문 §4–5](https://arxiv.org/pdf/0907.4743))

초대에는 허브 endpoint와 공개키 pin, 충분한 무작위 단회 토큰, 만료와 관리자 승인을 결합한다. 숫자 코드만으로 상대 주소를 찾거나 인증을 끝내지 않는다. SPAKE2 같은 PAKE는 검토 후보지만 RFC 9382는 Informational이며 특정 구현의 안전성을 보증하지 않는다. Magic Wormhole도 PAKE를 활용하지만 기본 rendezvous/mailbox 서버를 사용하므로 그대로 가져와 ‘외부 서버 없음’이라고 할 수 없다. 미승인 발견 광고는 공유자가 공개에 동의한 최소 별명·팀 표시만 허용하고 폴더·문서·사원 명단은 내려주지 않는다. ([RFC 9382](https://www.rfc-editor.org/rfc/rfc9382.html), [Magic Wormhole API](https://github.com/magic-wormhole/magic-wormhole/blob/master/docs/api.rst))

## CRDT는 유지하고 회사의 권한 확정점을 하나로 둔다

2019년 local-first 논문은 오프라인 작업·협업·사용자 소유권을 함께 다룬다. 이는 서버를 무조건 없애라는 요구가 아니라 사용자가 서버 연결 없이도 자기 자료로 일할 수 있게 만드는 설계 방향이다. Yjs는 binary update의 교환·결합·멱등과 state vector를 제공하지만 팀 승인, ACL, 폴더 이동 순서를 결정하지 않는다. replicated tree 연구 역시 동시 폴더 이동에서 사이클과 구조 유효성을 따로 다루어야 함을 보여 준다. 본문 CRDT의 수렴과 회사 정책의 확정은 다른 문제다. ([Local-first software](https://martin.kleppmann.com/papers/local-first.pdf), [Yjs updates](https://docs.yjs.dev/api/document-updates), [replicated tree 연구](https://martin.kleppmann.com/2021/10/07/crdt-tree-move-operation.html))

현재 저장소는 Markdown↔Y.Text bridge와 binary sync, stable doc_id, Rust atomic write를 갖고 있다. 반면 공유 API principal은 `user|org`이며 API의 `groups` 인자는 팀 그룹이 아닌 조회 묶음이다. resolver에는 개인 vault 수준, deny, private, 잠금과 관리자 shortcut의 예외가 이미 있다. **신규 팀 그룹을 별도 권한 엔진으로 추가하면 읽기 목록과 쓰기 판정이 달라질 위험이 있다.** 새 그룹 grant는 하나의 resolver에 합치고 HTTP·WebSocket·blob·MCP·검색·presence와 동일한 결론을 내도록 해야 한다. ([현재 불변 조건](../../CLAUDE.md), [공유 API](../../app/apps/server/src/http/routes/shares.ts), [resolver](../../app/apps/server/src/permissions/resolver.ts))

| 사례·방법 | 가져올 통찰 | 이번 기준안에서의 판단 |
|---|---|---|
| LocalSend / mDNS·DNS-SD | 별명 기반 발견, IP 없는 참여 | 채택 방향. 신뢰·ACL은 별도 구현 |
| Syncthing | 키 기반 기기 식별, 충돌 사본, 발견/relay 분리 | 패턴 참고. 같은 vault에 별도 동기화 엔진을 겹쳐 실행하지 않음 |
| Yjs / Hocuspocus | 기존 binary 협업·오프라인 bridge | 유지. 회사 신원·권한 계층 확장 |
| Iroh | native 연결·로컬 탐색 후보 | 보류. 현재 HTTPS/WS를 대체할 이득을 실측 후 결정 |
| Automerge | heads와 fork/merge, 과거 시점 조회 | 참고. 이번 기능에 엔진 전환을 필수화하지 않음 |
| AnySync | CRDT/DAG와 별도 ACL 제어 계층 | 비교 사례. 현 데이터 모델 대체 근거 부족 |
| Keyhive / NextGraph | 오프라인 권한·암호화 협업 연구 | 관찰. 현재 성숙도와 통합 비용 때문에 1차 기반에서 제외 |

Iroh의 로컬 탐색은 선택 기능이고 일부 preset에는 공용 DNS와 relay가 포함된다. LAN 전용이면 외부 경로를 명시적으로 끈 구성이 필요하다. AnySync가 별도 ACL consensus node를 둔다는 사실은 ‘P2P가 권한 순서까지 저절로 해결한다’는 해석을 반박한다. Keyhive는 pre-alpha·미감사·production 사용 금지라고 명시하며 NextGraph Framework는 alpha early preview다. 대안의 가능성과 현재 제품에 즉시 도입 가능한 정도를 분리해야 한다. ([Iroh local lookup](https://docs.iroh.computer/connecting/local-address-lookup), [Iroh Builder](https://docs.rs/iroh/1.3.0/iroh/endpoint/struct.Builder.html), [AnySync GitHub](https://github.com/anyproto/any-sync), [Keyhive GitHub](https://github.com/inkandswitch/keyhive), [NextGraph](https://docs.nextgraph.org/en/framework/), [Automerge history](https://automerge.org/automerge-swift/documentation/automerge/changesandhistory/))

## 형상관리 경험은 자동 공유와 확정 버전을 구분해야 한다

Ink & Switch의 Patchwork Edit Groups는 관련 편집과 이유를 묶고 diff로 검토하는 경험을 연구한다. Simple branching은 공유 편집과 별도의 대안을 다루는 다른 모델이다. 비개발자에게는 ‘버전 남기기·지난 버전과 비교·이 버전으로 복원’이 적합하다. **자동 공유 중인 내용은 이미 팀에 보이며, 이름 붙인 버전은 승인 전 비공개 초안이 아니다.** 승인 후 배포를 원한다면 branch/publication 엔진을 후속 범위로 설계해야 한다. ([Edit Groups](https://www.inkandswitch.com/patchwork/notebook/2024-version-control/05/), [Simple branching](https://www.inkandswitch.com/patchwork/notebook/2024-version-control/06/), [Universal Version Control](https://www.inkandswitch.com/universal-version-control/), [연구 코드](https://github.com/inkandswitch/tiny-essay-editor))

현재 checkpoint는 vault 구조·본문·blob pinning과 forward restore의 기반을 제공하지만 후속 content top-up과 여러 단계 복원을 포함한다. 이미 엄격한 불변 snapshot이나 여러 문서의 단일 ACID 복원을 제공한다고 주장할 수 없다. 제안하는 확정 버전은 준비 중 manifest를 검증한 뒤 완성 상태로 전환하고, 완성 manifest와 참조 blob을 바꾸지 않는다. 복원은 미리 비교하고 현재 Yjs에 새 작업으로 적용하며 단계별 진행과 재시도를 남긴다. ([현재 checkpoints](../../app/apps/server/src/versions/checkpoints.ts), [현재 revert](../../app/apps/server/src/versions/revert.ts))

Office/PDF 같은 binary는 CRDT에 넣지 않고 이전 digest/revision을 조건으로 교체한다. 동시에 저장하면 두 버전을 보존해 선택한다. Syncthing도 동시 수정과 삭제·수정 충돌에서 사본 보존을 사용하며, 자체 버전 관리가 모든 로컬 편집을 포괄하지 않는다고 설명한다. 동기화·변경 이력·백업은 각각 다른 보장이다. 회수된 직원이 이미 받은 평문을 보유할 수 있다는 한계도 숨겨서는 안 된다. ([Syncthing sync](https://docs.syncthing.net/users/syncing.html), [versioning](https://docs.syncthing.net/users/versioning.html), [Keyhive 위협 모델](https://github.com/inkandswitch/keyhive/blob/main/design/threat_model.md))

## 설치와 장애 복구가 회사용 제품의 검증 관문이다

Tauri sidecar는 OS별 실행 파일 동봉을 지원하지만 서비스 수명주기, DB 업그레이드와 복원을 대신하지 않는다. 현재 서버는 Node·native Argon2·pg pool과 session advisory lock을 사용한다. PGlite socket은 단일 연결 위 multiplexing과 SSL 미지원 제약을 명시하므로 즉시 대체 가능한 Postgres라고 확정할 수 없다. 이번 기준안은 **실제 Postgres와 기존 서버 의미론의 유지**를 우선하고 Windows/macOS 설치·강제 종료·migration·복원 spike를 선행한다. ([Tauri sidecar](https://v2.tauri.app/develop/sidecar/), [PGlite socket](https://pglite.dev/docs/pglite-socket), [서버 manifest](../../app/apps/server/package.json), [migration lock](../../app/apps/server/src/db/migrate.ts), [Postgres upgrade](https://www.postgresql.org/docs/current/upgrading.html))

작은 팀은 한 직원의 앱에서 공유를 시작하고, 정식 운영은 상시 켜진 사내 장비로 옮기는 흐름이 적합하다. 호스트가 꺼져도 로컬 편집은 가능하지만 다른 직원과의 동기화·신규 가입·권한 변경 확정은 중단된다. 이전 때는 DB·Yjs·registry·blob·ACL·신원·감사의 일관된 백업과 구 호스트의 쓰기 차단이 필요하다. 자동 리더 선출은 V1에서 제외한다. 백업 후 ACK된 변경의 재해 손실 가능성과 실제 RPO/RTO는 복원 실험으로 정한다. ([Postgres backup](https://www.postgresql.org/docs/current/backup.html))

회사 내부 협업은 외부 relay·OAuth·SMTP가 필수여서는 안 된다. 그러나 이를 ‘앱의 외부 통신이 전혀 없다’와 동일시하지 않는다. 엄격 오프라인 정책에서는 updater, 원격 AI, telemetry, 모델 다운로드와 원격 이미지까지 차단하거나 내부 대체하고 packet capture로 검증해야 한다. Windows 방화벽과 macOS 로컬 네트워크 권한은 배포 앱에서 각각 확인해야 하며 브라우저 시뮬레이터로 검증할 수 없다. 실제 인원·파일량·VLAN·IT 정책은 아직 미확인이다. ([Microsoft 방화벽](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules), [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy))

## 결론: 사람을 찾는 화면과 정책을 지키는 구조를 함께 설계한다

제품에서 없애야 하는 것은 직원의 서버 운영 부담이다. 회사 데이터의 확정점까지 없애면 팀 그룹과 접근 회수의 복잡성이 각 PC로 이동한다. 따라서 발견 화면은 ‘기획팀 · 민수 · 공유 중’을 보여 주되, 실제 연결은 승인된 회사 신원과 허브 키를 확인하고 권한 있는 폴더만 전달해야 한다.

첫 실험의 성공 조건은 자동 발견 화면의 완성이 아니라 비개발자 첫 참여, 동시 편집, 권한 회수, 호스트 장애 후 복원까지 하나의 흐름으로 입증하는 것이다. 이 결과가 없으면 사용 인원 상한이나 ‘데이터 손실 없음’을 출시 보장으로 내세우지 않는다. [PRD](../specs/06-office-collaboration-prd.md)와 [아키텍처](../specs/07-office-collaboration-architecture.md)는 이 검증 순서와 미결정을 함께 기록한다.
