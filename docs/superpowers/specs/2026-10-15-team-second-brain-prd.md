# PRD: 팀용 세컨드 브레인 (서버 모드 + 서버 없는 공유 + 기기 안 의미 검색)

관련 문서: [[STATUS]], [[superpowers/specs/2026-10-15-ui-redesign-color-design]], `CLAUDE.md`(불변 조건)

## 0. 한 줄 요약

Infinite Brain을 **개인이 아니라 팀과 조직이 함께 쓰는 세컨드 브레인**으로 만든다. 팀은 **지금처럼 서버를 띄워 쓰는 방식(허브 모드)** 과 **서버 없이 기기끼리 직접 공유하는 방식(P2P 모드)** 중에서 고를 수 있고, 두 방식 모두 같은 Markdown + Yjs 기반 위에서 동작한다. 검색은 앱 안에 내려받는 임베딩 모델(EmbeddingGemma 2)로 뜻까지 찾는다.

## 1. 배경과 문제

- 지금 앱은 Baalda에서 물려받은 **서버 중심 구조**다. 공유하려면 Hono + Hocuspocus + Postgres 서버가 있어야 한다.
- 팀 기능은 한 조직 안에서만 동작한다.
  - 역할은 owner/admin/member뿐이고, 게스트 역할이 없다(`server/src/http/routes/members.ts:424-427`).
  - 공유는 같은 조직 안에서만 된다. 다른 조직의 리소스는 "Resource is outside this vault"로 거부한다(`shares.ts:394`). 공유받는 사람도 vault 멤버여야 한다(`shares.ts:397-404`).
  - 참가 코드는 만료와 재발급이 없다(`orgs.ts:479-520`). 도메인 자동 합류와 가입 승인 대기열도 없다.
  - 감사 로그는 AI 변경 기록(`ai_change_ledger`)뿐이다. SSO/SCIM은 없다.
- 검색은 이름만 의미 검색이다.
  - 서버 임베더는 256차원 단어 해시 방식이다(`server/src/index/embedder.ts:14-15`). 모델을 바꿔 끼우는 `setEmbedder`는 한 번도 호출되지 않는다.
  - 데스크톱은 SQLite FTS5와 trigram의 bm25 순위만 쓰고 벡터는 없다(`desktop/src-tauri/src/index.rs:346-521, 1896-1963`).
- 사용자 요구는 다음과 같다.
  1. 팀과 조직이 함께 쓰는 세컨드 브레인
  2. 조직 간 연결과 초대가 간편할 것
  3. 서버 없이도 공유할 것: 운영 부담 없이, 데이터가 남의 서버에 저장되지 않게, 오프라인과 사내망에서도
  4. 그러면서도 Baalda처럼 서버를 띄워 쓰는 방식도 계속 지원할 것

## 2. 목표와 비목표

### 2.1 목표
- **G1:** 두 가지 배포 형태를 모두 1급으로 지원한다. 허브 모드(서버를 띄움)와 P2P 모드(서버 없음)가 같은 앱, 같은 문서 형식으로 동작한다.
- **G2:** 작은 팀은 앱 설치와 초대 링크 하나만으로 5분 안에 공유를 시작한다.
- **G3:** 외부 협력자를 게스트로 폴더 범위만 보이게 초대할 수 있다.
- **G4:** 두 조직이 함께 쓰는 "연결된 vault"를 만들 수 있다. 각자의 내부 vault는 비공개로 남는다.
- **G5:** 같은 Wi-Fi에서는 인터넷 없이도 동기화된다.
- **G6:** 검색이 뜻으로 찾는다. 예를 들어 "회의록"으로 검색해도 "미팅 노트"가 나온다. 노트는 기기 밖으로 나가지 않는다.
- **G7:** 기업용 안전장치를 둔다. 외부 공유 정책, 감사 로그, 외부 접근 일괄 회수.

### 2.2 비목표 (이번 PRD 범위 밖)
- 모바일 앱. 데스크톱(macOS/Windows/Linux)만 다룬다.
- 블루투스 동기화. 데스크톱에는 불필요하다.
- 탈중앙 그룹 키 합의(DCGKA/BeeKEM)와 MLS. 연구 단계이거나 순서 보장 서버가 필요하다. 향후 과제로 둔다.
- 하나의 vault 안에서 허브 모드와 P2P 모드를 섞는 것. vault마다 한 가지 모드만 쓴다.
- SSO/SCIM. 기업 확장 단계에서 별도 PRD로 다룬다.

## 3. 사용자

| 사용자 | 상황 | 주로 쓸 모드 |
|---|---|---|
| 작은 팀 (2~15명) | 서버 관리자가 없고 비용을 피하고 싶다 | P2P 모드 |
| 현업 부서 | 회사 IT의 승인이 필요하다. 사내망을 쓴다 | P2P 모드(사내망) 또는 사내에 설치한 허브 |
| 기업 | SSO, 감사, 세밀한 권한, AI 연결(MCP)이 필요하다 | 허브 모드 |
| 외부 협력자 | 고객사, 외주. 특정 폴더만 보면 된다 | 게스트 (두 모드 모두) |
| 파트너 조직 | 공동 프로젝트를 한다 | 연결된 vault (허브 모드부터) |

## 4. 핵심 설계 결정

### D1. 배포 형태 2가지가 공존한다 (vault 단위로 선택)

| | 허브 모드 (지금의 Baalda 방식) | P2P 모드 (신규) |
|---|---|---|
| 서버 | 필요하다(Hono + Hocuspocus + Postgres). 직접 설치하거나 관리형으로 쓴다 | 필요 없다. 공개 중계 또는 직접 설치한 중계를 선택적으로 쓴다 |
| 서버가 내용을 읽나 | 읽는다 | 읽지 못한다(종단간 암호화) |
| 권한 | 노트·폴더 단위로 세밀하다(지금의 resolver) | vault 또는 폴더 단위다(키 단위) |
| 권한 회수 | 즉시 | 키 교체 이후의 내용만 막는다(이미 받은 내용은 남는다) |
| 외부 AI 연결(MCP) | 서버 엔드포인트로 연결한다 | 각 기기의 로컬 엔드포인트로 연결한다(5.6절) |
| 검색 | 서버 검색과 기기 검색 | 기기 검색 |
| 감사 로그 | 서버에 기록한다 | 각 기기의 로컬 기록만 남는다 |
| 오프라인과 같은 Wi-Fi | 오프라인에서는 편집만 하고, 다시 연결되면 동기화한다 | 같은 Wi-Fi끼리 바로 동기화된다 |

- vault를 만들 때 모드를 고른다. 나중에 P2P에서 허브로 옮기는 기능을 제공한다(5.7절).
- 두 모드 모두 문서 정체성(`doc_id`), 디스크의 Markdown, `Y.Text("content")`, 이진 Yjs 업데이트라는 CLAUDE.md 불변 조건을 그대로 지킨다.

### D2. P2P 연결은 단계적으로 시도한다
같은 Wi-Fi(mDNS) → 인터넷 직접 연결(홀펀칭) → 중계 → (있으면) 항상 켜진 노드 순서로 시도한다. 구현은 **Iroh 1.0**으로 하고, 같은 Wi-Fi 탐색은 공식 플러그인 `iroh-mdns-address-lookup`을 쓴다. mDNS를 직접 구현하지 않는다.

### D3. 종단간 암호화는 secsync 방식으로 한다
- Yjs 상태를 **스냅샷과, 그 스냅샷을 참조하는 업데이트 묶음** 으로 나누고, 각각을 vault 키로 암호화(AEAD)한 봉투로 주고받는다.
- 업데이트마다 서명하는 방식(BFT CRDT 논문)은 쓰지 않는다. 그 논문은 해시로 이어진 작업 그래프를 전제로 하는데, Yjs에는 그런 구조가 없다.
  - 인증은 두 층으로 한다. 직접 연결 구간은 Iroh 연결이 상대 기기 키를 인증한다. 저장 후 전달 구간(중계·노드)은 봉투에 보낸 기기의 서명을 붙인다.

### D4. 키 관리는 단순하게 시작한다
vault마다 대칭 키를 하나 두고, 멤버를 내보내면 키를 교체한다. 새 스냅샷을 만들고 예전 봉투를 폐기한 뒤, 남은 멤버에게 새 키를 각 기기 공개키로 암호화해 전달한다. 폴더 단위 권한은 폴더마다 키를 따로 두는 방식으로 2단계에서 다룬다.

### D5. 의미 검색은 기기 안에서 한다
앱 안의 모델 목록에서 EmbeddingGemma 2(텍스트 전용)를 내려받아 기기에서 실행한다. Google AI Edge Gallery처럼 내려받기만 하면 쓸 수 있게 한다. 허브 모드에서는 서버도 같은 모델을 선택적으로 쓸 수 있다.

### D6. 권한 판정은 모든 경로에서 일치해야 한다 (불변 조건 유지)
허브 모드의 게스트·연결된 vault 변경은 아래 경로 전부에 같은 규칙으로 들어가야 한다. 하나라도 빠지면 출시하지 않는다.
- resolver: `effectivePermission`(`resolver.ts:1229`), `loadAccessIndex`(:376)
- 읽기 가능 목록: `vault-docs.ts`(`vaultAccess`, `listReadableDocsInVault`, `listDeletedReadableDocsInVault`, `listVisibleFolders`), `readable-cache.ts`
- HTTP 게이트: `http-gates.ts`
- 동기화: `sync/hocuspocus.ts:228`의 `onAuthenticate`
- 첨부: `canReadAttachment`, `filterReadableBlobs`, `canWriteBlob`
- MCP: `mcp/service.ts:613, 651, 1278, 1346`

## 5. 기능 요구사항

### 5.1 F1 — 팀 합류를 쉽게 (두 모드 공통)
- **F1.1 초대 링크와 참가 코드(기존 개선)**
  - 허브 모드: 참가 코드에 만료와 재발급을 추가한다. 지금은 조직당 코드가 하나이고 만료가 없다. 초대 링크(`/invite/<id>`, `infinitebrain://invite/<id>`)는 그대로 쓴다.
  - P2P 모드: 초대는 **티켓 하나**로 한다. 티켓에는 vault ID, 초대한 기기의 공개키와 연결 정보(Iroh 주소), 1회용 초대 비밀이 들어 있고, 기본 유효기간은 7일이다. 링크, QR, 기존 CodeSlots 입력 중 무엇으로든 받을 수 있다.
- **F1.2 도메인 자동 합류 (허브 모드, 신규)**
  - 관리자가 `@company.com` 같은 도메인을 등록하면, 그 도메인으로 로그인한 사용자는 바로 member로 합류한다.
  - 전제: 지금은 이메일 인증이 꺼져 있다(`auth.ts:136`). 자동 합류는 **이메일 인증이 된 계정에만** 허용한다.
- **F1.3 가입 승인 대기열 (신규)**
  - 허브 모드: 링크나 코드로 들어온 사람을 "대기"로 두고, owner/admin이 승인한다. vault마다 켜고 끈다.
  - P2P 모드: 티켓을 쓴 기기는 초대한 사람(또는 관리 권한 기기)이 승인해야 vault 키를 받는다.
- **완료 기준:** 새 팀원이 링크를 누르고 5분 안에 첫 노트를 연다. 만료된 코드와 티켓은 거부되고, 그 이유가 화면에 표시된다.

### 5.2 F2 — 게스트 (두 모드 공통)
- **허브 모드**
  - 새 역할 `guest`를 추가한다. 초대할 때 member/admin/guest 중에서 고른다.
  - 게스트에게는 조직 전체 기본 권한(baseline)이 적용되지 않는다. **명시적으로 공유받은 폴더와 노트만** 볼 수 있다.
  - 게스트에게는 owner/admin 지름길과 "만든 사람 규칙"이 적용되지 않는다. vault 목록, 멤버 목록, 다른 폴더 이름도 보이지 않는다.
  - 공유 대상 검사(`shares.ts:397-404`)에 guest를 member로 인정한다. 게스트는 다른 사람을 초대하거나 공유할 수 없다.
- **P2P 모드:** 게스트에게는 공유된 폴더의 키만 준다. 폴더 키(D4 2단계)가 생기기 전까지 P2P 게스트는 "vault 전체 읽기 전용"으로만 제공한다.
- **완료 기준:** 게스트가 공유받지 않은 노트를 볼 수 없다. D6의 모든 경로(목록, HTTP, 동기화, 첨부, MCP, 검색)를 통합 테스트로 확인한다.

### 5.3 F3 — 연결된 vault: 조직 대 조직 (허브 모드 먼저)
- 조직 A가 vault를 만들고 "연결"로 조직 B를 초대한다. 초대는 B의 admin에게 가고, B의 admin이 수락한다.
- 각 조직의 admin이 자기 쪽에서 참여할 멤버를 정한다. B의 멤버는 연결된 vault에서 **파트너 멤버** 로 표시된다.
- 데이터는 vault를 만든 조직 A가 소유한다. 어느 쪽이든 연결을 끊을 수 있고, 끊으면 B 멤버의 접근이 즉시 사라진다.
- 데이터 모델은 `vault_connections(vault_id, host_org_id, partner_org_id, state, created_by, …)`이고, 파트너 멤버 지정은 별도 테이블로 둔다. `principal_type='org'`는 지금처럼 "자기 조직 전체"라는 뜻만 유지하고, 다른 조직을 가리키는 데 재사용하지 않는다.
- P2P 모드의 연결된 vault는 "두 조직의 기기가 같은 vault 키를 공유하는 것"과 같다. 그래서 별도 기능 없이 F1의 티켓과 승인으로 만들 수 있다. 다만 조직 단위 관리(한쪽 admin이 자기 멤버를 정하는 것)는 허브 모드에서만 제공한다.
- **완료 기준:** 연결을 끊은 직후 B 멤버의 동기화 세션이 끊기고, 어떤 경로로도 다시 읽을 수 없다.

### 5.4 F4 — 관리자 정책과 감사 (허브 모드)
- 외부 공유 정책: `끔 / 허용한 도메인만 / 허용`. 게스트 초대, 연결, 공개 링크에 모두 적용한다.
- 감사 로그 테이블을 새로 만든다. 멤버·게스트 추가와 제거, 역할 변경, 공유 변경, 연결과 해제, 공개 링크 생성, 외부 접근 일괄 회수를 기록한다. 보존 기간은 설정할 수 있다.
- "외부 접근 모두 회수": 버튼 하나로 게스트, 파트너 멤버, 공개 링크를 모두 끊는다.
- P2P 모드에서는 각 기기에 로컬 감사 로그만 남는다. 이 한계를 설정 화면에 명시한다.

### 5.5 F5 — 서버 없는 공유 (P2P 모드, 신규)
- **F5.1 신원:** 기기마다 Ed25519 키 쌍을 만든다. 비밀키는 OS 키체인에 저장한다(지금의 keychain 사용 경로를 재사용). 사용자 이름과 아바타는 vault 안의 메타데이터로 둔다.
- **F5.2 연결**
  - Iroh 1.0 엔드포인트를 Rust(`src-tauri`)에서 실행하고, 같은 Wi-Fi 탐색 플러그인을 켠다.
  - 중계는 기본적으로 Iroh 공개 중계를 쓰고, 설정에서 직접 설치한 중계 주소로 바꿀 수 있다. 중계는 암호문만 전달한다.
- **F5.3 동기화 프로토콜**
  - 문서마다 스냅샷 봉투와 업데이트 봉투를 주고받는다(D3).
  - 연결되면 서로 가진 스냅샷 ID와 업데이트 범위를 비교해 빠진 것만 보낸다.
  - 기존 브리지의 두 가지 반사 방지 장치(디스크에서 온 변경은 다시 내보내지 않음, `lastWrittenHash`와 같은 내용은 다시 들이지 않음)와 지연 시간(감시·수신 약 150ms, 내보내기 약 300ms)을 그대로 지킨다.
- **F5.4 항상 켜진 노드 (선택)**
  - 같은 앱을 화면 없이 실행하는 모드다(`--headless-node`). 팀원 PC나 작은 서버에서 돌리며, 암호문 봉투를 보관했다가 오프라인이던 기기에 전해 준다. 내용은 읽지 못한다.
  - 노드가 없으면, 두 기기가 동시에 켜져 있을 때만 동기화된다. 화면에 "마지막 동기화: 2시간 전 (Mina의 기기)"처럼 표시한다.
- **F5.5 멤버 제거와 키 교체:** D4의 키 교체를 실행한다. 제거된 기기는 새 키를 받지 못한다. 이미 받은 내용은 남는다는 사실을 제거 확인 화면에 명시한다.
- **F5.6 플랫폼 권한**
  - macOS: Info.plist에 `NSLocalNetworkUsageDescription`과 `NSBonjourServices`를 넣는다. 권한 요청 창이 뜨지 않는 경우가 보고되어 있으므로, 같은 Wi-Fi 탐색이 실패하면 "시스템 설정 → 개인정보 보호 → 로컬 네트워크"로 안내하고 인터넷 경로로 넘어간다.
  - Windows: 처음 실행할 때 방화벽 확인 창이 뜨며, 이를 안내한다.
  - 회사·게스트 Wi-Fi는 기기끼리의 통신을 막는 경우가 많다. 이때도 자동으로 중계로 넘어간다.
- **F5.7 첨부 파일:** 첨부 파일도 같은 봉투 방식(파일 키)으로 기기끼리 전송한다. 지금의 스트리밍 다운로드와 SHA-256 검증 경로(`attachments.rs:629`)를 재사용한다.
- **완료 기준**
  - 인터넷을 끈 상태에서 같은 Wi-Fi의 두 기기가 10초 안에 편집을 주고받는다.
  - 서로 다른 네트워크의 두 기기가 중계를 거쳐서라도 동기화된다.
  - 중계와 노드의 저장소에 평문이 없다(테스트로 확인).

### 5.6 F6 — 외부 AI 연결(MCP)과 모드
- 허브 모드: 지금 그대로다(서버 MCP, scope 검사, AI 변경 기록).
- P2P 모드: 각 기기의 앱이 **로컬 MCP 엔드포인트**(127.0.0.1)를 연다. 이미 CSP가 localhost 연결을 허용한다(`tauri.conf.json:28`). 외부 AI는 그 기기의 사용자 권한으로만 읽고 쓰며, AI 변경 기록은 기기에 남는다.

### 5.7 F7 — 모드 전환
- P2P에서 허브로: 관리자가 허브 서버 주소를 지정하면, 한 기기가 복호화한 상태를 허브에 올리고 vault 모드를 바꾼다. 다른 기기는 다음 연결 때 허브로 넘어간다. `doc_id`는 유지한다.
- 허브에서 P2P로: 서버에 맡기던 세밀한 권한이 거칠어지므로, 전환 전에 경고하고 권한 차이를 보여 준다. 1차 범위에서는 이 방향을 제공하지 않을 수 있다(열린 질문).

### 5.8 F8 — 기기 안 의미 검색 (두 모드 공통)
- **F8.1 모델 목록과 내려받기**
  - 설정 → "AI 모델"에서 EmbeddingGemma 2(텍스트 전용, 메모리 약 191MB)를 보여 준다. 내려받기, 일시정지, 삭제가 가능하고, 진행률은 kit의 ProgressDial로 보여 준다.
  - 모델 파일은 앱 로컬 데이터 디렉터리(`app_local_data_dir`)에 저장한다. 지금은 큰 파일을 여기에 두지 않으므로 새 경로를 만든다.
  - 내려받기는 기존 reqwest 스트리밍과 SHA-256 검증, 임시 파일에서 이름 바꾸기 패턴을 재사용한다. 모델 목록(URL, 크기, 해시)은 앱에 내장하고, 서명된 업데이트 채널로 갱신한다.
- **F8.2 실행:** Rust에서 실행한다. 런타임(ONNX Runtime `ort` 또는 llama.cpp 계열)은 열린 질문이다. 출력은 768차원 중 앞쪽 256차원만 잘라 쓴다(Matryoshka). 서버의 `EMBED_DIM=256`과 맞춘다.
- **F8.3 색인**
  - 노트를 문단 단위로 잘라 `<vault>/.context/index.sqlite`에 벡터 테이블을 추가한다. `.context/`는 동기화에서 제외되는 비공개 영역이라는 불변 조건을 지킨다.
  - 모델 버전이 바뀌면 다시 색인한다(서버의 `embed_version` 개념과 같다).
- **F8.4 순위:** 지금의 bm25 결과와 벡터 유사도를 섞어 순위를 매긴다(하이브리드). 고유명사와 코드는 bm25가 강하기 때문이다. "관련 노트" 패널에도 같은 벡터를 쓴다.
- **F8.5 권한:** 기기에는 그 사용자가 읽을 수 있는 노트만 동기화되어 있다는 전제 위에서, 색인도 그 노트들만 대상으로 한다. 게스트 기기에는 공유된 범위만 있다. 이 전제는 구현 계획에서 검증한다.
- **F8.6 허브 모드 서버:** 서버에도 같은 모델을 선택적으로 붙인다(`embedder.ts`의 `setEmbedder` 연결). MCP 검색이 의미 검색이 된다. 기본값은 지금 방식을 유지한다.
- **F8.7 모델이 없을 때:** 모델을 내려받지 않은 기기는 지금의 bm25와 trigram 검색만 쓴다. 기능이 줄어들 뿐, 막히지는 않는다.
- **선행 확인:** EmbeddingGemma 2의 라이선스를 Hugging Face 모델 카드에서 확인한다. 기사에서는 Apache 2.0이라고 하지만, Gemma 계열은 별도 약관을 써 왔다. 배포에 문제가 있으면 다른 오픈 모델(예: BGE-M3, Qwen3 Embedding)로 대체한다.

## 6. 비기능 요구사항

| 항목 | 요구 |
|---|---|
| 보안 | P2P의 중계·노드에 평문 0. 비밀키는 OS 키체인. 티켓 비밀은 1회용. 허브 모드 권한 판정은 D6 경로 전부에서 일치 |
| 성능 | 같은 Wi-Fi 편집 전파 p95 1초 이하. 노트 1만 개의 첫 색인이 일반 노트북에서 30분 안에 끝나고, 앱 사용을 막지 않음(백그라운드). 검색 응답 p95 300ms 이하 |
| 오프라인 | 두 모드 모두 오프라인 편집 가능. P2P는 같은 Wi-Fi에서 인터넷 없이 동기화 |
| 데이터 보존 | 디스크의 Markdown이 원본이라는 원칙 유지. 모드 전환과 키 교체 중 데이터 손실 0 (삭제·복구·대량 작업 가드 유지) |
| 접근성 | 새 화면은 kit 컴포넌트와 키보드 조작, 모션 줄이기 설정 지원 |
| 플랫폼 | macOS·Windows·Linux. macOS 로컬 네트워크 권한과 Windows 방화벽 대응 |

## 8. 단계별 로드맵

| 단계 | 내용 | 모드 | 의존 |
|---|---|---|---|
| **A** | F1(코드 만료, 승인 대기열, 도메인 자동 합류) + F2 게스트 + F4 최소(정책, 감사 로그) | 허브 | 없음 |
| **B** | F8 기기 안 의미 검색 (모델 내려받기, 색인, 하이브리드 순위) | 공통 | 없음. A와 병렬 가능 |
| **C** | F5 P2P 최소 기능: 기기 키, 티켓 초대, 같은 Wi-Fi 탐색, 직접 연결과 중계, 봉투 동기화, vault 키 하나 | P2P | B와 병렬 가능 |
| **D** | F5.4 항상 켜진 노드, F5.5 키 교체, F5.7 첨부, P2P 게스트(폴더 키), F6 로컬 MCP | P2P | C |
| **E** | F3 연결된 vault | 허브 | A |
| **F** | F7 모드 전환(P2P에서 허브로) | 공통 | C, A |
| **장기** | 허브를 P2P와 같은 프로토콜을 쓰는 피어로 통합할지 검토. 그룹 키 합의(DCGKA/BeeKEM, MLS) | 공통 | D |

각 단계는 별도 스펙 → 계획 → 구현 주기를 거친다. 허브 모드(지금의 Baalda 방식)는 모든 단계에서 계속 지원하며 중단하지 않는다.

## 9. 성공 지표
- 새 팀이 공유를 시작하기까지 걸리는 시간: 중앙값 5분 이하 (G2)
- 게스트 권한 누출: 0건 (D6 통합 테스트, 보안 리뷰)
- 같은 Wi-Fi 편집 전파 p95 1초 이하, 인터넷 경유 p95 3초 이하 (G5)
- 의미 검색: 한국어·영어 혼합 테스트 세트(유의어·바꿔 쓴 표현 50쌍)에서 상위 5위 적중률 80% 이상. 지금 방식과 비교한다 (G6)
- P2P 중계·노드 저장소의 평문: 0 (자동 테스트)

## 10. 위험과 완화

| 위험 | 영향 | 완화 |
|---|---|---|
| 동기화 경로가 두 개(Hocuspocus, P2P)가 된다 | 버그와 권한 불일치가 늘어난다 | vault마다 한 모드만 허용한다. 공통인 Yjs와 브리지 계층은 그대로 두고 전송만 바꾼다. 장기적으로 통합을 검토한다 |
| P2P에서는 권한 회수가 즉시 되지 않는다 | 제거된 사람이 이미 받은 내용을 계속 갖는다 | 화면에 명시한다. 즉시 회수가 필요한 조직에는 허브 모드를 권한다 |
| 회사·게스트 Wi-Fi가 기기 간 통신을 막는다 | 같은 Wi-Fi 동기화가 실패한다 | 자동으로 중계로 넘어간다. 진단 화면을 둔다 |
| macOS 로컬 네트워크 권한 요청 창이 안 뜬다 | 탐색이 실패한다 | 안내 화면을 두고, 인터넷 경로로 넘어간다 |
| 게스트 추가가 권한 경로 하나에서 빠진다 | 정보가 새어 나간다 | D6 체크리스트와 경로별 통합 테스트를 출시 조건으로 둔다 |
| 모델 라이선스 또는 크기 문제 | 배포가 막힌다 | 선행 확인(F8)하고, 대체 모델을 준비한다 |
| Iroh 공개 중계에 의존한다 | 외부 서비스가 바뀌면 영향받는다 | 직접 설치한 중계 주소를 설정할 수 있게 한다. 중계는 암호문만 다룬다 |
| 이메일 인증이 꺼져 있다 | 도메인 자동 합류가 악용된다 | 자동 합류는 인증된 이메일에만 허용한다 |

## 11. 열린 질문
1. P2P 모드의 첫 출시에서 폴더 단위 게스트(폴더 키)까지 할지, vault 전체 읽기 전용 게스트로 시작할지.
2. 허브에서 P2P로 바꾸는 기능을 1차 범위에 넣을지.
3. 임베딩 런타임: ONNX Runtime(`ort`)과 llama.cpp 계열 중 무엇을 쓸지. 앱 크기, 플랫폼별 GPU 가속, 빌드 복잡도를 기준으로 고른다.
4. 항상 켜진 노드를 공식 서비스로 운영할지, 사용자가 직접 띄우게만 할지.
5. 연결된 vault를 P2P 모드에서도 조직 단위로 관리할지(조직 정체성을 P2P에서 어떻게 표현할지).
6. NextGraph(Yjs를 지원하는 E2EE 동기화 엔진)를 가져다 쓸지, Iroh 위에 직접 만들지. C 단계 착수 전에 평가한다.
7. 제품 이름의 "vault"와 P2P의 "space" 개념을 하나로 볼지(현재 안: 둘 다 vault).
