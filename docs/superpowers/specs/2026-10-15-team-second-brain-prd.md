# PRD v2: 팀용 세컨드 브레인 (서버 모드 + 서버 없는 공유 + 기기 안 의미 검색)

관련 문서: [[STATUS]], [[reports/PRD-REVIEW-team-second-brain-astra]] (v1 독립 리뷰, 판정 rework), `CLAUDE.md`(불변 조건)

> **v2에서 바뀐 것.** v1은 서버가 하던 권한·순서·삭제·복구 판단을 전송 방식만 바꾸면 대체할 수 있다고 과소평가했다. v2는 다음을 PRD의 필수 계약으로 올렸다.
> - P2P의 멤버십 순서와 키 교체 권한
> - 오프라인 변경 보존 규칙
> - 모든 영속 변경의 작성자 서명과 쓰기 권한 검증
> - 암호화된 registry/control 프로토콜
> - 허브 모드 게스트의 전체 권한 경로
> - 기기 신원과 복구
> - 모델과 색인의 버전 관리
> - 내보내기, 백업, 보존 같은 운영 요구
>
> 로드맵에는 설계 검증 단계(A0, B0, C0)를 앞에 두었다. 각 항목 옆의 `[R#]`, `[S#]`, `[F#]`, `[#n]`은 리뷰 보고서의 항목 번호다.

## 0. 한 줄 요약

Infinite Brain을 **팀과 조직이 함께 쓰는 세컨드 브레인**으로 만든다. vault마다 **허브 모드(지금처럼 서버를 띄움)** 와 **P2P 모드(서버 없이 기기끼리)** 중 하나를 고르고, 두 모드 모두 같은 Markdown + Yjs 기반에서 동작한다. 검색은 앱 안에 내려받는 임베딩 모델로 뜻까지 찾는다. 허브 모드는 모든 단계에서 1급으로 지원하며 중단하지 않는다.

## 0.1 최우선 원칙: 개발을 모르는 사람도 쓸 수 있어야 한다

이 PRD의 모든 기능은 **명령줄, 별도 프로그램 설치, 기술 용어 없이** 앱 화면만으로 끝나야 한다. 설계가 이 원칙과 부딪히면 원칙이 이긴다.

| 하지 않게 할 것 | 대신 이렇게 한다 |
|---|---|
| Ollama, Python, 런타임을 따로 설치하기 | 실행 엔진(llama.cpp)을 앱 안에 함께 넣는다. 사용자는 모델 파일만 버튼 하나로 받는다 |
| 모델 이름, 양자화, 차원 같은 것을 고르기 | 앱이 기기 사양을 보고 알맞은 모델 하나를 고른다. 화면에는 "스마트 검색 켜기"와 용량만 보여 준다 |
| 포트, 중계 주소, IP를 입력하기 | 기본값으로 자동 연결한다. 고급 설정은 접힌 "관리자용" 영역에만 둔다 |
| 키, 복구 키 파일을 직접 다루기 | 복구 키는 "복구 코드 저장하기" 한 화면으로 안내한다(인쇄, 파일 저장, 비밀번호 관리자) |
| 오류 코드를 해석하기 | 무엇이 안 됐고 지금 무엇을 누르면 되는지 한 문장으로 알려 준다 |

**용어 원칙:** 화면에는 "임베딩", "GGUF", "P2P", "epoch", "relay" 같은 말을 쓰지 않는다. 각각 "스마트 검색", "검색 모델", "서버 없이 공유", "보안 갱신", "연결 도우미"처럼 하는 일을 말로 쓴다. 기술 용어는 관리자용 세부 정보에서만 쓴다.

**완료 기준(모든 단계 공통):** 개발 경험이 없는 테스트 사용자 5명이 안내 없이 다음 과제를 끝낸다. 각 과제의 성공률과 걸린 시간, 막힌 지점을 기록한다.
1. 앱을 설치하고 스마트 검색을 켠다.
2. 팀원을 초대하고, 초대받은 쪽에서 첫 노트를 연다.
3. 같은 Wi-Fi에서 인터넷 없이 서로의 편집을 본다.
4. 팀원을 내보내고, 그 결과를 이해한다.

## 1. 배경과 현재 상태 (v1 사실 오류 정정)

경로 약어: `S/` = `app/apps/server/src/`, `D/` = `app/apps/desktop/src/`, `R/` = `app/apps/desktop/src-tauri/src/`.

- **구조:** Baalda에서 물려받은 서버 중심 구조다(Hono + Hocuspocus + Postgres). 한 조직은 여러 vault를 가질 수 있지만, 제품에서 보이는 vault는 Better Auth 조직이다. 한 사용자는 여러 조직에 속할 수 있다.
- **역할:** owner/admin/member뿐이고 게스트가 없다. 초대는 member/admin만 받는다(`S/http/routes/members.ts:425-427`).
- **공유 [F01, #1]**
  - 권한 요약 API(`/orgs/:orgId/access/summary`)는 다른 조직의 리소스를 "Resource is outside this vault"로 거부하고, 선택한 사람이 멤버인지 검사한다(`S/http/routes/shares.ts:395, 397-404`).
  - 그러나 **실제 공유 생성 API(`POST /shares`, 472행~)는 대상이 멤버인지 일괄 검사하지 않고 저장한다(524-575행).** 이 사실만으로 비멤버가 실제로 접근할 수 있다고 단정할 수는 없다(접근하려면 별도로 조직 접근이 있어야 한다). 다만 게스트를 도입하기 전에 대상 검증을 명시적 계약으로 만든다(A0).
- **합류**
  - 참가 코드는 조직당 하나이고 만료와 재발급이 없다(`S/http/routes/orgs.ts:479-560`). 이메일 초대는 `expiresAt`(기본 7일)을 쓴다.
  - 도메인 자동 합류와 가입 승인 대기열은 없다.
- **이메일 인증 [F02, #1]:** 인증 메일 발송과 인증 절차는 이미 있다(`S/auth/auth.ts:161-172`). 다만 `requireEmailVerification: false`(`S/auth/auth.ts:136`)라서 **미인증 계정도 로그인할 수 있다.** 인증 절차를 새로 만들 필요는 없다.
- **기록 [F11, #2]:** 기록은 세 가지가 흩어져 있다. AI 변경 기록(`ai_change_ledger`), 일반 편집 버전의 작성자(`migrations/016_versioning.sql`), 멤버 활동과 초대 이벤트다. **멤버·공유·정책 변경을 일관되게 남기는 통합 보안 감사 로그는 없다.** SSO/SCIM도 없다.
- **검색 [F10, #2]**
  - 서버: "의미 검색"이라는 이름과 달리 256차원 단어 해시 방식이다(Unicode 정규화와 CJK bigram 포함, `S/index/embedder.ts:14-15`). `setEmbedder`는 정의만 있고 호출되지 않는다.
  - 데스크톱: FTS5 bm25, trigram, 짧은 CJK 부분 문자열(`LIKE`) 분기, 노트와 파일을 합친 순위를 쓴다(`R/index.rs:1857-1883, 1896-1971`). 벡터는 없다. **이 동작들은 새 하이브리드 검색의 회귀 기준으로 유지한다.**
- **회수 [F03, #3]:** 허브의 권한 회수는 새 요청과 열린 연결에만 즉시 적용된다. 이미 발급된 첨부 다운로드 URL은 기본 300초 동안 유효하고(`S/blobs/config.ts:225`), 기기에 이미 받은 평문은 회수할 수 없다. 엄격한 회수가 필요한 조직을 위해 다운로드 프록시 옵션(`S3_PROXY_DOWNLOADS`)이 이미 있다.

**사용자 요구:**
1. 팀·조직이 함께 쓰는 세컨드 브레인
2. 조직 간 연결과 초대가 간편할 것
3. 서버 없이도 공유할 것: 운영 부담 없이, 데이터 주권을 지키며, 오프라인과 사내망에서도
4. Baalda처럼 서버를 띄우는 방식도 계속 지원할 것

## 2. 목표와 비목표

### 2.1 목표
- **G1:** 허브 모드와 P2P 모드를 모두 1급으로 지원한다. vault마다 하나를 선택한다.
- **G2:** 작은 팀은 설치와 초대만으로 협업을 시작한다(측정 정의는 §11).
- **G3:** 외부 협력자를 게스트로 초대한다. 게스트는 공유받은 범위만 본다.
- **G4:** **같은 허브 안에서** 두 조직이 함께 쓰는 연결된 vault를 만든다. 서로 다른 허브 간 연합은 범위 밖이다.
- **G5:** 같은 Wi-Fi에서는 인터넷 없이 동기화된다(환경 제약은 F5.6).
- **G6 [#3]:** 검색이 뜻으로 찾는다. **임베딩 계산을 위해 노트 내용을 외부로 보내지 않는다.** 단, 사용자가 연결한 외부 AI(MCP)에 내용이 전달되는 것은 별개이며, 화면에 구분해 표시한다.
- **G7:** 기업용 안전장치를 둔다. 외부 공유 정책, 통합 감사 로그, 외부 접근 일괄 회수.

### 2.2 비목표
- 모바일 앱, 블루투스 동기화
- 서로 다른 허브 간 조직 연합
- 한 vault 안에서 두 모드를 섞어 운영하는 것. 단, 모드 전환 중의 일시 상태는 허용한다(F7).
- **MLS(RFC 9420)와 탈중앙 그룹 키 합의(DCGKA/BeeKEM) [§사실 보충]**
  - MLS는 IETF 표준이지만, 그룹 변경(commit)의 순서를 정하는 전달 서비스가 필요하다. 이번 범위의 단순한 epoch 권한 모델(D4)로 같은 요구를 더 싸게 충족하므로 제외한다.
  - DCGKA/BeeKEM은 연구 단계라서 제외한다. 둘 다 향후 재검토한다.
- SSO/SCIM. 별도 PRD로 다룬다. **이 PRD만으로 기업 도입 요구를 모두 충족한다고 보지 않는다.**

|---|---|---|
| 작은 팀 (2~15명) | 서버 관리자가 없고 비용을 피하고 싶다 | P2P |

| 파트너 조직 | 공동 프로젝트를 한다 | 같은 허브의 연결된 vault |

## 4. 핵심 설계 결정

### D1. 배포 형태 2가지 (vault 단위)

| | 허브 모드 | P2P 모드 |
|---|---|---|
| 서버 | 필요(Hono + Hocuspocus + Postgres) | 없음. 공개 또는 자체 중계와 선택형 저장 노드 |
| 서버가 내용을 읽나 | 읽는다 | 읽지 못한다(종단간 암호화). 단, 관측 메타데이터는 남는다(D7) |
| 권한 | 노트·폴더 단위로 세밀하다 | vault 단위. 폴더 단위는 D 이후 |
| 회수 [F03] | 새 요청과 열린 세션은 즉시. 발급된 URL은 TTL 동안 유효(엄격하면 프록시 모드). 기기의 사본은 회수 불가 | 새 epoch 이후의 내용과 쓰기를 막는다. 이미 받은 내용은 회수 불가 |
| 외부 AI(MCP) | 서버 MCP | 기기의 로컬 MCP. 로컬 클라이언트만 연결 가능(F6) |
| 감사 | 서버의 통합 감사 로그 | 기기의 로컬 기록만 |

두 모드 모두 CLAUDE.md 불변 조건을 지킨다. 안정된 `doc_id`, 디스크의 Markdown이 원본, `Y.Text("content")`가 실시간 원본, 이진 Yjs 업데이트, `.context/` 비공개, 삭제·회수·복구·대량 작업 가드가 그것이다.

### D2. P2P 연결: 연결과 저장을 분리한다 [F04, R10, #4]
- **연결**
  - Iroh 1.x(확인 시점 최신 1.3.0)의 주소 탐색과 경로 선택에 맡긴다. Iroh는 보통 중계로 먼저 연결한 뒤 가능하면 직접 경로로 바꾸고, 같은 Wi-Fi 탐색은 공식 플러그인(`iroh-mdns-address-lookup`)으로 한다.
  - 연결 순서를 직접 구현하지 않는다.
- **저장:** 항상 켜진 노드는 연결 경로가 아니다. **데이터를 보관하는 별도의 피어**다(F5.4).
- **사내망 전용 모드:** 공개 주소 조회와 공개 중계를 끈다. 이때는 같은 망 안의 탐색, 수동 피어 주소, 사내 중계만 쓴다.

### D3. 동기화 프로토콜: secsync에서 봉투 형식만 참고한 새 프로토콜 [F05, F06, R07, #5, #6]
- secsync는 **스냅샷과 업데이트의 순서를 정하는 중앙 서버를 전제**로 한다. 그래서 P2P에는 그대로 쓸 수 없다. secsync에서는 봉투 형식만 참고하고, 순서·충돌·복구는 D4와 C0에서 새로 설계한다.
- **모든 영속 봉투**(스냅샷, 업데이트, registry 변경)에는 작성 기기 서명이 붙는다.
  - 수신 기기는 경로(직접 연결이든 중계·노드든)와 관계없이 서명과 **해당 epoch의 쓰기 권한**을 검증한 뒤에만 Yjs에 적용한다.
  - 서명은 작성자를 인증하는 것이다. Yjs를 BFT CRDT로 만들어 주지는 않는다.
- **봉투의 인증 대상(AAD):** protocol version, vault ID, doc ID, epoch, 부모 스냅샷 증거, 작성 기기, 단조 증가 카운터, payload 해시. nonce 재사용을 막고, 받은 카운터와 최신 확인 지점을 재시작 후에도 유지한다.
- **누락이나 분기를 감지하면** 조용히 성공으로 처리하지 않는다. "동기화 미완료"로 표시한다.
- **위협 모델:**
  - 막는 것: 악성 중계·노드의 위조, 재전송, 과거 상태로 되돌리기, 그리고 쓰기 권한이 없는 멤버의 쓰기.
  - 막지 못하는 것: 쓰기 권한이 있는 악의적인 멤버의 정상 서명 편집(되돌리기는 가능), 그리고 모든 경로를 막는 공격자에 의한 가용성 저하.

### D4. 멤버십 epoch와 키 교체 [R01, R02, R03, #7]
- **순서 권한:** vault마다 "멤버십 권한 기기" 집합을 하나로 지정한다. 처음에는 vault를 만든 관리자의 기기이고, 이양할 수 있다.
  - 가입 승인, 제거, 역할 변경, 키 교체는 **권한 기기만 순서대로 발행**한다(멤버십 epoch).
  - 권한 기기가 오프라인이면 이런 변경은 대기한다. **일반 편집은 계속 가능하다.**
  - 여러 관리자가 연결이 끊긴 채 동시에 변경하는 것은 1차 범위 밖이다. 권한은 한 번에 한 기기 집합만 가진다.
- **읽기 권한과 쓰기 권한의 분리 [R03]:** vault 콘텐츠 키는 읽기 권한이다. 쓰기는 "관리자가 서명한 epoch 멤버십 문서에 쓰기 역할로 등록된 기기의 서명"으로만 인정한다. **이 검증이 없으면 P2P 읽기 전용 게스트를 출시하지 않는다.**
- **키 교체 3단계 [R02]**
  1. **준비:** 새 epoch를 만들고, 새 스냅샷에 포함된 변경의 watermark를 기록한다.
  2. **배포:** 남은 기기마다 새 키를 감싸 전달하고, 받았는지 확인을 모은다.
  3. **확정:** 모두 받으면 확정한다. 구 epoch 봉투는 **보존 기한**(기본 30일) 동안 남겨 둔다.
  - 현역 기기의 미전송 변경은 권한을 재검증한 뒤 새 epoch로 병합한다. 병합할 수 없으면 복구 사본으로 남긴다.
  - **기준 시점:** "제거가 확정된 epoch 이후"에 제거된 기기가 보낸 변경은 자동으로 받지 않는다. 그 전에 작성된 변경은 관리자 확인을 거쳐 받을 수 있다.
  - 키 배포 중 장애가 나거나 같은 요청이 다시 와도 원래 상태로 복구할 수 있어야 한다.
- **스냅샷 [R06, #11]**
  - 스냅샷은 **Yjs 구조를 보존하는 이진 상태 스냅샷**이다. Markdown에서 다시 만들어 압축하는 방식은 쓰지 않는다. 그렇게 하면 기존 연산 ID를 잃는다.
  - 업데이트는 스냅샷에 포함된 것(watermark 이하)만 지운다. 이미 있는 `R/index.rs` `save_yjs_snapshot`의 `id <= up_to` 원리를 봉투 저장소에도 적용한다.
  - Yjs의 삭제 내용 GC는 압축과 별개다.
  - 문서 상태 크기, 로그 크기, 압축 빈도, 오프라인 복귀 한도(구 epoch 보존 기한)에 상한을 둔다.
- **스냅샷 작성자가 오프라인이어도:** 다른 기기가 **같은 검증된 이력**(같은 부모 증거와 watermark)을 가지고 있으면 스냅샷을 만들 수 있다. 그렇지 않으면 업데이트만 쌓고 기다린다.

### D5. 기기 안 의미 검색
앱 안의 모델 목록에서 임베딩 모델을 내려받아 기기에서 실행한다. 1차 후보는 EmbeddingGemma 2이고, 멀티모달 모델의 텍스트 인코더만 쓴다(F8). 모델이 없으면 기존 검색으로 동작한다.

### D6. 권한 판정 일치 (허브 모드 출시 조건) [S01, #13]
게스트와 연결된 vault는 **"이 vault에 활성 관계로 참여할 수 있는가"** 와 **"이 리소스에서 무엇을 할 수 있는가"** 를 분리해 판정한다.
- guest와 partner는 다음을 상속하지 않는다: 조직 전체 기본 권한(baseline), 가입 시점 스냅샷(join snapshot), 개인 vault 권한, 조직 단위 공유(`principal_type='org'`), 만든 사람 규칙, 관리 기능.
- `orgRole`이 partner를 member로 돌려주는 방식은 쓰지 않는다. `organizationId`와 `vaultId`를 바꿔 쓰지 않는다. 지금 vault 단위 공유의 `resource_id`가 실제로는 조직 ID라는 기존 계약(`S/permissions/lookup.ts:40-57`)을 문서화한다.

### D7. 메타데이터 보호 (P2P) [R09]
- **암호화하는 것:** 제목, 경로(`rel_path`), 폴더 이름, 첨부 파일 이름, 멤버 프로필, presence, 링크·백링크 관계, 검색 snippet.
- **평문으로 두는 것:** 봉투의 불투명 ID(vault, 문서, 봉투).
- **남는 관측 정보:** IP, 연결 시각, 트래픽 크기, 기기 공개키, 그리고 mDNS가 같은 망에 알리는 기기 존재. 이 한계를 설정 화면과 문서에 명시한다.

## 5. 기능 요구사항

### 5.1 F1 — 팀 합류
- **F1.1 허브: 초대와 참가 코드**
  - 참가 코드에 만료, 재발급, 시도 횟수 제한을 둔다.
  - 참가 코드로 게스트를 member로 승격시킬 수 없다. 코드는 member로만 합류시키고, 게스트는 개별 초대로만 만든다.
  - 기존 초대 링크(`/invite/<id>`, `infinitebrain://invite/<id>`)는 그대로 쓴다.
- **F1.0 비개발자 기준 초대 흐름 (두 모드 공통)**
  - 초대하는 사람: [초대하기] → 링크 복사 또는 QR 표시. 화면에 "이 링크를 받은 사람이 들어오면 내가 승인합니다"를 함께 보여 준다.
  - 초대받는 사람: 링크를 누르면 앱이 열린다(앱이 없으면 설치 안내 페이지). → 이름 입력 → "승인을 기다리는 중" → 승인되면 바로 vault가 열린다.
  - 승인하는 사람에게는 앱 안 알림으로 [승인]과 [거절]을 보여 준다.
- **F1.2 P2P: 초대 티켓 [S03, #12]**
  - 티켓에는 다음이 들어간다: 발급자 서명, 충분히 긴 무작위 비밀, vault ID, 역할, 범위, epoch, 만료, 초대 ID, 발급 기기의 주소.
  - **소비는 발급 기기(또는 멤버십 권한 기기)가 원자적으로 확정한다.** 발급 기기가 오프라인이면 "승인 대기"로 표시한다. 같은 요청을 다시 보내도 결과가 같아야 한다(idempotency). 승인은 요청한 기기의 공개키에 묶는다.
  - 티켓은 링크나 QR로 **통째로** 전달한다. CodeSlots의 8자리 짧은 코드는 허브의 참가 코드 전용이다. P2P의 짧은 코드는 온라인 만남 서버나 별도 페어링 방식이 필요하므로 1차 범위 밖이다.
  - 로그, 클립보드, URL에 티켓 비밀이 남지 않게 한다. 만료는 1회용 보장을 대신하지 않는다.
- **F1.3 가입 승인 대기열:** 허브는 vault마다 켜고 끈다. P2P는 항상 승인이 필요하다(F1.2).
- **F1.4 도메인 자동 합류 (A2로 분리) [S05, #16]**
  - **기본값은 꺼짐이다.**
  - 도메인 소유를 DNS TXT 레코드로 확인한다. 같은 도메인은 한 조직만 등록할 수 있다. 공용 메일 도메인(gmail.com 등)은 등록할 수 없다.
  - 정규화한 정확한 도메인으로 비교하고, **서버가 확인한 현재 이메일 인증 상태**만 인정한다. 이메일을 바꾸면 다시 인증해야 한다.
  - 게스트를 member로 승격하지 않는다. 합류 시점의 좌석 한도를 적용한다.
  - 우선순위는 하나로 고정한다: 외부 공유 정책 → 신원 확인 → 승인 대기 → 역할 부여. 모든 합류 경로가 이 순서를 쓴다.
- **완료 기준:** 만료되거나 이미 쓴 코드·티켓은 거부되고 이유가 표시된다. 모든 합류 경로가 같은 우선순위 계약을 쓴다는 것을 경로별 테스트로 확인한다.

### 5.2 F2 — 게스트
- **허브 게스트 (A1)**
  - 새 역할 `guest`를 둔다. 판정은 D6의 "관계와 리소스 권한 분리"를 따른다.
  - 게스트는 명시적으로 공유받은 폴더와 노트만 읽거나 쓴다. 다른 사람의 이름과 이메일, 내부 vault 이름, 다른 폴더 이름을 받지 못한다. 자기에게 공유된 진입점은 받는다.
  - 쓰기 게스트가 만든 노트를 공유 범위 밖으로 옮겨도, 만든 사람 규칙으로 접근이 유지되지 않는다.
  - 게스트는 초대, 공유, 공개 링크를 만들 수 없다.
- **`POST /shares` 대상 검증 [F01]:** 대상이 해당 vault의 활성 member나 guest인지 검증한다.
- **기존 데이터 migration [#22]:** 게스트 도입 전의 member, 초대, 참가 코드, 기본 권한(baseline), join snapshot은 지금과 같은 권한을 유지해야 한다. 기존 vault가 게스트 규칙을 잘못 물려받지 않음을 migration 테스트로 확인한다.
- **P2P 게스트 (C2 이후):** D4의 쓰기 권한 검증을 충족한 뒤 "vault 전체 읽기 전용"으로 시작한다. 폴더 단위는 폴더 키 계약(F5.8)을 갖춘 뒤에 제공한다.
- **완료 기준:** 역할 × 리소스 × 경로(D6 표) × 이력·삭제 × 회수 × 기존 토큰 조합의 기대 거부가 모두 통과해야 출시한다.

### 5.3 F3 — 연결된 vault (같은 허브, E 단계) [S02, #14]
- **연결 절차:** 조직 A가 vault를 만들고 조직 B의 admin에게 연결을 요청한다. B의 admin이 수락하고, 자기 쪽 참여 멤버를 정한다.
- **유효 권한은 다음의 교집합이다:** 호스트가 허용한 최대 권한, 활성 연결, B 조직에서의 현재 멤버십, 명시적 참여자 지정, 리소스 공유.
  - 어느 쪽 admin도 상대 조직의 내부 권한을 관리할 수 없다.
  - 두 조직의 정책이 충돌하면 더 제한적인 쪽을 적용한다.
- **연결 해제:** 연결마다 세대(generation)와 공유의 출처(provenance)를 기록한다. 연결을 끊으면 그 연결에서 생긴 공유, 초대, 세션, MCP 토큰을 함께 무효화한다. 다시 연결해도 예전 공유가 되살아나지 않는다.
- **수명주기:**
  - B 조직에서 퇴사하면 연결된 vault 접근도 사라진다.
  - 호스트 조직이 폐쇄되거나 탈퇴하면 vault는 호스트 소유로 남는다.
  - 소유권 이전은 양측 admin이 합의해야 한다.
  - 좌석과 요금은 참여자가 속한 조직이 부담한다.
- **데이터 모델:** `vault_connections(vault_id, host_org_id, partner_org_id, state, generation, …)`, `vault_connection_members`. `principal_type='org'`는 지금처럼 자기 조직 전체라는 뜻만 유지한다.
- **P2P 모드:** 조직 단위 관리는 하지 않는다. 별도의 협업 vault를 공유 경계로 쓴다.

### 5.4 F4 — 관리자 정책과 감사 (허브) [S07, #15]
- **외부 공유 정책:** 끔 / 허용한 도메인만 / 허용. **"허용한 도메인만"일 때 익명 공개 링크는 만들 수 없다.** 방문자의 도메인을 확인할 수 없기 때문이다. 대신 인증된 제한 공유 링크를 쓴다.
- **통합 감사 로그:** 수행자, 대상, 이전 권한과 이후 권한, 결과, 시각, 요청 상관 ID를 남긴다. 기존 기록(AI 변경, 버전 작성자, 멤버 활동)과의 관계를 정의한다. 보존 기간은 설정할 수 있다.
- **외부 접근 일괄 회수:** 게스트, 파트너 멤버, 공개 링크, 관련 MCP 토큰을 한 번에 끊는다. 부분 실패와 완료 상태를 보여 주고, 다중 서버 인스턴스에 전파한다.

### 5.5 F5 — 서버 없는 공유 (P2P)
- **F5.1 신원과 기기 [R08, #8]**
  - 신원 구조는 `사용자 → 승인된 기기 → vault 멤버십과 역할`이다. 사용자 전체 제거와 기기 하나 제거를 구분한다.
  - 기기 키는 두 종류로 나눈다: 서명 키(Ed25519)와 키 감싸기용 암호화 키(X25519 기반 HPKE). 둘은 기기 인증서로 서로 묶는다. 비밀키는 OS 키체인(`R/keychain.rs`)에 저장한다. 키체인은 저장 수단일 뿐 이 프로토콜을 대신하지 않는다.
  - **기기 추가:** 기존에 승인된 기기에서 확인하거나 관리자가 승인한다.
  - **관리자 승계:** 마지막 관리자는 제거할 수 없다. 권한 기기를 이양할 수 있다.
  - **복구:** vault를 만들 때 복구 키를 발급한다(오프라인 보관을 권장). 모든 키를 잃으면 내용을 복구할 수 없다는 사실을 만들 때 고지한다.
  - **디스크 복원으로 기기가 복제되는 경우:** 카운터와 nonce 재사용을 막기 위해 기기 키를 다시 발급한다.
- **F5.2 연결:** D2를 따른다. 중계 주소는 설정할 수 있다. 사내망 전용 모드를 둔다.
- **F5.3 registry/control 프로토콜 [R04, #9]**
  - 문서 본문 외에 다음을 암호화된 control 봉투로 주고받는다: 노트·폴더 생성, 이름 변경과 이동, tombstone과 복구, 권한 변경, 수신 확인(ACK), 보존 주체.
  - **목록에 없다는 것은 삭제의 증거가 아니다.** 지금 허브 프로토콜의 `empty`, `behind`, `revoked`, `tombstones`, `covered`(`D/lib/sync/vaultProtocol.ts:72-141`)에 해당하는 신호와 삭제 가드(`D/lib/sync/inbound.ts:90-136`)를 P2P에서도 보장한다.
  - **충돌 규칙:** 같은 경로에 다른 `doc_id`가 있을 때, 대소문자나 Unicode 정규화만 다를 때, 폴더를 지우는 중에 새 파일이 생겼을 때, 바이너리가 충돌할 때(CRDT가 아니므로 사본으로 남긴다)를 각각 정의한다.
  - `.context/`는 로컬 저장소로만 쓰고 통째로 동기화하지 않는다. 공유할 메타데이터는 별도 구조로 정의한다.
- **F5.4 브리지 연결 계약 [R05, #10]**
  - **디스크에서 온 변경은 디스크로 다시 쓰지만 않을 뿐, 네트워크로는 보낸다.** 예를 들어 AI가 파일을 바꾼 변경도 동료에게 전달된다.
  - 받은 이진 업데이트는 같은 `doc_id`의 **같은 실시간 Y.Doc**에 적용한다. 원격, 디스크, persistence 재생을 구분한다.
  - `lastWrittenHash`는 디스크로 다시 쓰는 것을 막는 값일 뿐이다. 네트워크 ACK나 스냅샷이 같다는 증거로 쓰지 않는다.
  - 다음을 그대로 유지한다: 디스크 쓰기 완료 후 해시 갱신, `diskBase`와 복구 사본, 시드 전에 먼저 받아오기(pull-before-seed), 동시 디스크 읽기 보호(`D/lib/bridge/noteBridge.ts:712-728`), 감시·수신 약 150ms와 내보내기 약 300ms 지연.
  - **P2P bootstrap 완료 기준:** 여러 피어 중 첫 빈 응답을 "전역 빈 문서"로 보지 않는다. 권한 기기나 저장 노드가 상태를 확인했거나, 일정 수 이상의 피어가 같은 상태를 보고할 때 완료로 본다.
- **F5.5 멤버 제거와 키 교체:** D4를 따른다. **C2(공개 베타)의 출시 조건이다.** 제거 확인 화면에 "이미 받은 내용은 남는다"를 명시한다.
- **F5.5a 비개발자 기준 화면 표현**
  - 연결 상태는 세 가지 말로만 보여 준다: "실시간으로 함께 편집 중", "다른 사람이 켜면 전달됨", "이 기기에만 저장됨".
  - 같은 Wi-Fi 권한이 막혔을 때는 OS별로 어디를 눌러야 하는지 그림과 함께 안내하고, 그동안은 인터넷 경로로 계속 동기화한다.
  - 보안 갱신(키 교체)은 "팀원이 나가서 보안을 새로 고치는 중" 진행 표시로만 보여 준다.
- **F5.6 플랫폼과 네트워크**
  - macOS: `NSLocalNetworkUsageDescription`과 `NSBonjourServices`를 설정하고, 권한 요청 창이 뜨지 않을 때를 위한 안내 화면을 둔다.
  - Windows: 방화벽 안내.
  - Linux: 비밀 저장소가 없을 때 안내.
  - 다음 환경에서는 "설명 가능한 실패"를 보여 준다: 회사·게스트 Wi-Fi의 기기 간 통신 차단(AP isolation), UDP 차단, 프록시, 절전 후 재개. 수동으로 피어 주소를 넣는 기능을 둔다.
- **F5.7 첨부 [#17]:** 파일마다 키를 두고, 조각(chunk) 단위로 무결성을 검사하고, 이어받기를 지원한다. 경로와 크기에 상한을 둔다. 키를 교체하면 **새 버전에는 새 파일 키를 쓴다.** 이미 받은 파일 키로는 새 버전을 열 수 없어야 한다. C 단계가 첨부를 지원하지 않는다면, 그 단계는 새 텍스트 전용 vault로만 제한한다. 기존 첨부를 조용히 빼지 않는다.
- **F5.8 폴더 키 (D 단계):** 이동, 상속, 재공유, 여러 폴더에서 같은 첨부를 참조하는 경우, 교체 규칙을 정의한 뒤에 도입한다.
- **F5.9 저장 노드 [R10, #17]**
  - 노드는 **콘텐츠 키를 갖지 않고 평문 처리(bridge, indexer, Markdown 생성)를 실행하지 않는 암호문 저장소**다. 같은 Rust 공통 코드를 쓰되, 데스크톱 전체 초기화 경로는 쓰지 않는다.
  - 업로드하는 피어를 인증한다. 할당량, 보존·삭제 권한, 체크섬과 서명 검증, durable ACK, 복제 수, 저장 공간 부족 처리를 정의한다.
  - 화면에 세 상태를 구분해 보여 준다: "내 기기에 저장됨", "다른 기기가 받음", "노드에 보존됨".

### 5.6 F6 — 외부 AI 연결(MCP) [S04, F09, #18]
- **허브 모드:** 지금 그대로다(서버 MCP, scope 검사, AI 변경 기록).
- **P2P 모드: 로컬 MCP**
  - **로컬 MCP 클라이언트만 지원한다.** 예: Claude Desktop, Claude Code, Codex CLI. 클라우드 AI 서비스는 사용자 PC의 `127.0.0.1`에 닿을 수 없다.
  - stdio를 우선한다. HTTP를 쓴다면 MCP 명세의 보안 요구를 따른다: loopback 바인딩, 연결마다 토큰, Origin과 Host 검증, 와일드카드 CORS 금지, 요청 크기와 동시 실행 한도.
  - 연결마다 최소 scope, vault 선택, 만료, 철회를 둔다.
  - MCP의 변경은 같은 실시간 Y.Doc과 AI 변경 기록·revision 보호를 거쳐 반영한다. 기록과 반영이 따로 실패하지 않게 한다.
- **CSP의 localhost 허용은 WebView가 밖으로 나가는 연결 정책일 뿐이다.** endpoint 보안의 근거가 아니다.

### 5.7 F7 — 모드 전환 (P2P → 허브) [R11, #19]
- **절차:** migration ID를 발급하고 다음 순서로 진행한다.
  1. 지원하는 기기 버전인지 확인한다.
  2. 관리자 권한과 대상 허브의 TLS 신뢰를 확인한다.
  3. 이진 CRDT, registry, 첨부 manifest를 단계적으로 올린다. 중간에 끊겨도 이어서 올릴 수 있다.
  4. 올린 내용을 검증한다.
  5. cutover epoch를 확정한다.
  6. 늦게 돌아온 기기의 미전송 변경은 허브로 다시 올리거나, 기한이 지나면 수동 복구로 넘긴다.
- **동의와 안전장치:** 전환하면 서버가 평문을 읽게 된다는 데 명시적으로 동의받는다. 전환 전에 백업과 내보내기(§6.1)를 먼저 한다. 실패하면 되돌린다.
- **혼합 운용:** 계속 섞어 쓰는 것은 금지한다. 전환 중의 중복 저장과 제한된 복구 상태만 허용한다.
- **허브 → P2P:** 1차 범위 밖이다.
- **의존:** C, D(첨부, 키, 보존, 복구), §6.1.

### 5.8 F8 — 기기 안 의미 검색 [F07, F08, R12, S06, #20, #21]
- **F8.1 모델 (B0에서 확정)**
  - 1차 후보는 EmbeddingGemma 2다. 공식 모델 카드에 Apache 2.0이 명시되어 있고 사용 정책 안내도 있다.
  - **배포할 아티팩트의 revision, 변환·양자화 결과물, 라이선스 파일을 고정**하고 고지를 기록한다.
  - 멀티모달 모델의 텍스트 인코더만 쓴다. "191MB"는 Pixel에서 양자화한 텍스트 가중치의 수치일 뿐이다. 실제 아티팩트 크기와 최대 메모리는 B0에서 OS별로 측정한다.
- **F8.2 내려받기:** 서명된 manifest(URL, 크기, 필수 SHA-256)를 쓰고, 경로 탈출을 막고, 실패한 내려받기를 정리하고, 디스크 부족을 처리하고, 프록시를 지원한다. 폐쇄망을 위해 수동 설치를 지원한다. 일시정지와 이어받기는 서버가 Range와 ETag를 지원할 때만 완료 기준에 넣는다. 기존 `attachments.rs` 다운로드 함수는 vault 내부 경로 전용이고 해시가 선택 사항이므로, 원리만 재사용하고 모델용 경로는 따로 만든다.
- **F8.3 실행 (2026-10-15 결정)**
  - 1순위는 **llama.cpp를 앱 바이너리 안에 정적으로 함께 넣고 GGUF 모델을 실행**하는 것이다. EmbeddingGemma 2는 GGUF 배포본이 이미 있다(Unsloth).
  - 사용자는 런타임을 따로 설치하지 않는다(§0.1). Google AI Edge Gallery가 쓰는 LiteRT-LM은 관찰 후보로 둔다. 공식 Rust 바인딩이 없고 Bazel 빌드가 부담이기 때문이다. ONNX Runtime은 공식 ONNX 변환본이 나오면 재검토한다.
  - B0에서 확인할 것: GGUF 파일 목록과 양자화 종류, Rust 바인딩 crate의 상태, OS별 GPU(Metal, Vulkan) 지원, 앱 크기 증가분, CPU 속도와 메모리 예산.
  - 작업 큐와 backpressure를 두어 편집과 동기화를 막지 않는다.
- **F8.3a 첫 실행 안내 (Google AI Edge Gallery 방식)**
  - 앱을 처음 열면 "스마트 검색을 켤까요? 뜻이 비슷한 노트까지 찾아 줍니다. 약 ○○MB를 내려받고, 노트는 이 기기 밖으로 나가지 않습니다."를 묻는다. 선택지는 [켜기]와 [나중에]다.
  - [나중에]를 고르면 지금의 단어 검색으로 동작한다. 검색창 옆의 작은 안내로 다시 켤 수 있다.
  - 설정 → "스마트 검색"에서 켜기·끄기, 사용 용량, 지우기를 제공한다. 지우면 모델 파일과 그 모델로 만든 색인을 함께 지워 공간을 돌려준다.
  - 기기 사양이 부족하면(메모리, 디스크) 켜기 전에 이유와 함께 알려 주고, 단어 검색을 계속 쓰게 한다.
- **F8.4 색인 버전:** 색인 버전은 하나의 묶음으로 기록한다: 모델 revision, tokenizer, 입력 prefix(검색어용과 문서용을 구분), chunker 설정, 차원, 양자화.
  - 차원은 모델 출력을 자른 뒤 정규화한다(Matryoshka). 서버의 256이라는 숫자에 맞추는 것은 벡터 호환이 아니다.
  - 버전이 다른 벡터 공간을 섞지 않는다. 재색인 중에는 기존 키워드 검색으로 동작한다. 벡터가 유한한 값인지 검증한다.
- **F8.5 저장:** `<vault>/.context/index.sqlite`에 문단(chunk) 벡터 테이블을 둔다. 이 DB에는 CRDT 상태도 들어 있으므로, 스키마 변경 시 기존 테이블을 건드리지 않는다.
- **F8.6 순위:** 기존 검색(bm25, trigram, 짧은 CJK, 파일)과 벡터 유사도를 섞는다. 같은 노트의 결과 중복을 없애고, 이름과 경로가 정확히 맞는 결과는 우선한다. 기존 검색의 동작을 회귀 기준으로 유지한다.
- **F8.7 색인 수명주기와 권한 [S06]**
  - **로컬에 파일이 있다는 것이 현재 권한의 증거는 아니다.** 예전 권한으로 받은 파일이나 직접 가져온 문서가 남아 있을 수 있다.
  - 검색과 MCP 결과는 vault와 계정, 그리고 현재 알려진 권한 상태로 거른다.
  - 노트를 삭제하거나 권한이 회수되면 원문 FTS, chunk 벡터, 캐시, 추천 결과를 함께 지운다.
  - 재색인 작업이 시작할 때의 문서 revision과 접근 세대(access generation)를 확인한다. 그래서 회수된 결과가 다시 들어오지 않게 한다.
  - 오프라인에서 확인할 수 있는 권한의 한계와 보호할 수 없는 기존 사본을 명시한다.
- **F8.8 모델이 없을 때:** 기존 검색만 쓴다. 모델을 삭제하면 그 버전의 벡터도 지운다.
- **F8.9 허브 서버 의미 검색 (B2, 별도 단계):** `setEmbedder`를 연결하고, `EMBED_VERSION`을 모델 묶음 버전으로 바꾸고, 전체를 재색인한다. 요청 처리와 자원을 다투지 않도록 작업 큐를 둔다. 지금 `Embedder.embed`는 동기 함수이므로 인터페이스를 비동기로 바꿔야 한다.

## 6. 운영 요구사항 (신규) [#22]

### 6.1 내보내기와 백업
- **내보내기:** Markdown, 첨부, 폴더, frontmatter, 링크, 안정 ID를 내보내고 다시 가져올 수 있게 한다. 사용자용 문서 내보내기와 운영 백업(CRDT, 키, ACL 포함)을 구분한다. `.context/`를 통째로 다른 팀에 넘기는 방식은 금지한다.
- **백업:** RPO와 RTO를 정의한다(허브: 운영자, P2P: 관리자 기기와 선택형 노드). 백업의 주기, 암호화, 복원 권한, 복구 훈련 절차를 정한다. **동기화와 저장 노드는 백업이 아니다.**

### 6.2 보존 기간
감사 로그, AI 변경, 문서 버전, 휴지통, P2P 구 epoch, 오프라인 미전송 변경 각각에 기본 보존 기간과 삭제 권한을 정한다. legal hold는 1차 범위 밖이라고 명시한다.

### 6.3 기기 관리
기기 목록, 마지막 접속, 승인, 분실 처리, 퇴사자 일괄 회수, 한 사용자의 여러 기기, 계정 전환, 공용 PC. P2P 신원과 허브 사용자 ID의 대응 관계(모드 전환용).

### 6.4 용량과 남용 방지
vault, 문서, 첨부, 기기 수, 봉투, 큐, 중계 대역폭에 상한을 둔다. 압축 해제와 파싱에도 한도를 둔다. 승인되지 않은 연결에는 rate limit을 건다. 할당량을 넘거나 디스크가 부족할 때 읽기·편집·동기화가 각각 어떤 상태가 되는지 정한다.

### 6.5 호환성
프로토콜 버전과 기능 협상(capability negotiation), 구버전 클라이언트와 서버가 섞인 상태, 단계적 출시와 롤백.

### 6.6 오프라인 충돌 UX
본문은 자동으로 병합한다. 다음은 수동 복구로 구분한다: 파일 이름 충돌, 폴더 이동 충돌, 바이너리 충돌, 키 교체 후의 미전송 변경. 원본 사본, 비교, 선택 화면을 두고, "아직 다른 기기나 노드에 저장되지 않음"을 표시한다.

### 6.7 개인정보와 진단
진단 로그와 지원 번들에 본문, 티켓, 키를 넣지 않는다. 측정은 동의를 받아서만 한다. 중계·노드 운영자가 볼 수 있는 관측 정보를 설명한다. 로컬 색인이 평문에서 나온 데이터라는 점을 알린다. E2EE가 분실 기기의 디스크 암호화를 대신하지 않는다는 점도 알린다.

## 7. 비기능 요구사항

| 항목 | 요구 |
|---|---|
| 보안 | P2P 중계·노드에 평문과 콘텐츠 키가 없다. 모든 영속 봉투에 서명과 쓰기 권한 검증. 허브는 D6 경로 전체가 일치 |
| 데이터 보존 | 디스크의 Markdown이 원본. 키 교체, 모드 전환, 스냅샷 중 장애에서 **확인 응답을 받은(acknowledged) 데이터는 복구 가능**. durable ACK 전에 유일한 로컬 사본을 잃는 것은 별도 위험으로 표시 |
| 성능 | 수치 목표는 §11의 측정 정의에 따른다. B0와 C1에서 현재 기준선을 먼저 측정한다 |
| 접근성 | kit 컴포넌트, 키보드 조작, 모션 줄이기 설정 |
| 플랫폼 | macOS, Windows, Linux. 최소 지원 사양은 B0와 C0에서 정한다 |

## 10. 위험과 완화

| 위험 | 완화 |
|---|---|
| 동기화 경로가 두 개가 된다 | vault마다 한 모드만 쓴다. Yjs와 브리지 계층을 공유한다. 장기적으로 통합을 검토한다 |
| P2P에서 순서 권한을 가진 기기가 오프라인이면 멤버 변경이 멈춘다 | 일반 편집은 계속된다. 권한 이양과 기다리는 상태 표시 |
| 게스트 추가가 한 경로에서 빠진다 | D6 표와 경로별 테스트를 출시 조건으로 둔다 |
| 회수의 한계(사본, 발급된 URL) | D1에 명시한다. 엄격한 조직에는 다운로드 프록시를 쓰게 한다 |
| 회사 망이 기기 간 통신을 막는다 | 중계로 넘어가고, 설명 가능한 실패와 수동 피어 주소를 둔다 |
| 모델의 크기나 라이선스 문제 | B0에서 확정하고 대체 모델을 준비한다 |
| 키를 모두 잃는다 | 복구 키와 관리자 승계. 만들 때 고지한다 |

## 11. 성공 지표 (측정 정의 포함) [#23]

| 지표 | 측정 계약 |
|---|---|
| 협업 시작 시간 | "설치 시작 → 두 번째 사람이 첫 편집을 받음"을 모드·네트워크 조건별로 측정한다. 중앙값, p90, 실패율. 내용은 수집하지 않는다 |
| 권한 누출 | 출시 조건: 역할 × 리소스 × D6 경로 × 이력·삭제 × 회수 × 기존 토큰 조합의 기대 거부가 100% 통과. 운영 사고 건수는 결과 지표로 따로 추적한다 |
| P2P 전파 | 연결된 피어 기준으로 "입력 → 상대 화면 반영"과 "입력 → 상대 디스크 저장"을 나눠 p95로 측정한다. 처음 연결, 초대, 절전 복귀는 따로 p95와 실패율로 측정한다 |
| 같은 망 탐색 | 순수 LAN, 기기 간 통신 차단(client isolation), 수동 연결, UDP 차단 각각의 성공률과 설명 가능한 실패율 |
| 색인·검색 성능 | 최소 장비와 OS, 총 토큰 수와 chunk 수, 언어 분포, 모델 revision, cold/warm 조건을 고정한다. 최대 메모리, CPU, 디스크, 배터리, 편집 지연을 함께 측정한다. 목표 수치는 B0의 기준선 측정 후에 정한다 |
| 검색 품질 | 독립 평가 질의와 방해 문서를 갖춘 corpus(한국어, 영어, 혼합, 코드, 정확한 이름, 정답 없음)로 측정한다. hit@5, nDCG 또는 MRR, 오탐률, 언어별 결과를 지금 방식과 비교한다. 유의어 50쌍은 smoke 테스트로만 쓴다 |
| 평문 비노출 | 본문, 제목, 경로, 첨부 이름 canary가 중계·노드 저장소와 로그에 없는지 검사한다. 위조, 재전송, 구 epoch 봉투가 거부되는지 테스트한다. 노드에 콘텐츠 키가 없는 구조를 검토한다 |
| 데이터 손실 | 반복·역순·중복 전달, 오프라인 편집 중 키 교체, 스냅샷 중 장애, 디스크 부족, 기기 분실, migration 중단에서 확인 응답을 받은 데이터가 복구되는지 테스트한다 |

"테스트에서 0건"을 운영상 무결함의 증명으로 표현하지 않는다.

## 12. 열린 질문
1. **C0의 기술 선택:** NextGraph, Iroh 위 직접 구현 등. 평가 기준은 Yjs 이진 이력 보존, 순수 LAN 오프라인, 라이선스, 지원 플랫폼, 게스트와 회수, 데이터 내보내기다.
2. **B0의 런타임:** llama.cpp(GGUF, 앱에 함께 넣기)를 1순위로 정했다(F8.3). B0 측정에서 앱 크기, 속도, 메모리가 예산을 넘으면 LiteRT-LM을 재검토한다.
3. 저장 노드를 공식 서비스로 운영할지, 사용자가 직접 띄우게만 할지.
4. P2P 멤버십 권한을 여러 관리자 기기가 동시에 가질 수 있게 확장할지. 지금은 한 번에 한 집합이다.
5. 구 epoch 보존 기한의 기본값. 지금은 30일이다.
6. 허브에서 P2P로 바꾸는 기능의 필요성.
