# C0: 서버 없는 공유(P2P) 설계 검증

관련 문서: PRD v2 §4 D1~D4·D7, §5.5 F5, §5.7 F7, §9 C0, §12 Q1·Q4·Q5. v1 독립 리뷰 `docs/reports/PRD-REVIEW-team-second-brain-astra.md`(이하 "리뷰", 항목 번호 `R#`, `S#`, `F#`). 코드 경로 약어는 PRD와 같다. `S/` = `app/apps/server/src/`, `D/` = `app/apps/desktop/src/`, `R/` = `app/apps/desktop/src-tauri/src/`. 줄 번호는 커밋 `c10a7ea` 기준이다.

이 문서는 코드를 바꾸지 않는다. C1(같은 망 실험)을 시작해도 되는지 판단하는 데 필요한 계약을 정한다.

## 0. 결론 요약

1. **기술 선택(§3, Q1):** **Iroh 1.x를 연결 계층으로만 쓰고, 봉투·멤버십·registry 프로토콜은 직접 구현한다.** NextGraph는 기각한다. v0.1.2-alpha.1 릴리스 노트(2025-11-08)가 "다른 사용자와 문서를 공유할 수 없다"고 적고 있고 그 뒤 릴리스 노트에도 이를 해소했다는 내용이 없으며, broker가 필수이며, 데이터 모델과 신원 체계가 우리 계약(`doc_id`, 디스크 Markdown 원본, 브리지)과 다르다. Automerge 계열(automerge-repo/samod + Keyhive/Subduction)은 Yjs 이력을 보존할 수 없어 기각한다. p2panda는 구조가 가장 잘 맞지만 0.x API이고 암호화 crate가 감사 전이라 채택하지 않는다. 설계 참고 대상으로 두고 1.0과 감사가 나오면 다시 평가한다.
2. **신뢰 구조(§4, §5):** 멤버십은 **권한 기기 한 대가 순서대로 쓰는 서명된 해시 체인**이다. 복구 코드는 그 위의 루트로, 권한 기기를 잃었을 때 권한을 넘기고 모든 epoch 키를 복호화할 수 있다. 여러 관리자 기기의 동시 발행은 하지 않는다. 대신 예비 권한 기기 한 대를 지정할 수 있게 한다(Q4).
3. **쓰기 권한(§5.2):** 봉투는 작성 기기 서명, 멤버십 기록상의 쓰기 역할, 제거 기준점(cutoff)을 모두 통과해야 Yjs에 적용된다. 콘텐츠 키를 가졌다는 사실은 쓰기 권한이 아니다(리뷰 R03).
4. **키 교체(§5.3):** 준비·배포·확정의 3단계다. 준비는 권한 기기 안에서 원자적으로 저장되고, 배포가 시작된 뒤에는 되돌리지 않고 앞으로만 재시도한다. 키를 받은 기기는 바로 새 epoch로 쓴다. 키를 못 받은 기기의 감싼 키는 기한 없이 보존한다.
5. **봉투(§6):** 헤더 전체가 AEAD의 인증 대상이다. 서명은 봉투 ID(헤더와 암호문의 해시)에 붙는다. 작성 기기별 단조 카운터와 직전 봉투 해시로 누락·되돌리기·분기를 탐지한다. 스냅샷은 Yjs 이진 상태이고, 업데이트는 **이 기기가 직접 검증한 스냅샷이 덮는 것만** 지운다.
6. **삭제(§7):** 목록에 없다는 것은 삭제가 아니다. 삭제는 서명된 tombstone 연산으로만 일어나고, 지금 허브 경로의 대량 삭제 상한을 P2P에도 그대로 적용한다. 제거된 멤버의 기기는 동기화와 키를 지우지만 디스크의 Markdown은 지우지 않는다.
7. **브리지(§8):** P2P 어댑터는 Hocuspocus provider 자리에 들어간다. `NoteBridge`, 에코 가드 두 개, 150/300ms 지연, `.context/` 비공개 규칙은 바꾸지 않는다. 디스크에서 온 변경도 네트워크로 보낸다.
8. **Q5(§9):** 30일은 **구 epoch 봉투 본문의 보관 정책**이지 오프라인 복귀의 데이터 손실 경계가 아니다. 키는 vault 수명 동안 보존한다.
9. **C1(§10):** 텍스트 전용 새 vault, 2~3대, 인터넷과 중계를 끈 같은 망에서 수렴, 손실 없음, 부정 테스트, 브리지 회귀, 비개발자 과제 3을 판정한다.

### 2.3 신뢰 경계
```
┌ 기기 ───────────────────────────────────────────────┐
│ WebView(TS): 평문 Y.Doc, 에디터, NoteBridge          │
│        │ 타입 있는 IPC: 평문 Yjs 업데이트와 상태만.  │
│        │ 비밀키는 넘어가지 않는다            [경계 B1]│
│ Rust 코어: 키체인, 봉투 서명·암호화·검증,            │
│            봉투 저장소(.context), Iroh 엔드포인트    │
└────────────────────────┬────────────────────────────┘
                         │ QUIC/TLS, EndpointId 인증  [경계 B2]
      ┌──────────────────┼───────────────────┐
  다른 멤버 기기 [B3]   중계(선택)        저장 노드(D, 키 없음)
  신뢰 루트: 복구 코드 ⟶ 권한 기기 ⟶ 멤버십 체인 [B4]
```
- **B1 (Rust ↔ WebView):** 비밀키는 Rust에만 있다. WebView는 자기 기기의 로컬 편집에 대해서만 서명을 요청할 수 있다. 노트 HTML 렌더링이 뚫리면 그 기기 이름으로 편집이 서명될 수 있으므로 기존 HTML sanitization과 CSP 경계(CLAUDE.md)는 P2P에서도 보안 경계다.
- **B2 (기기 ↔ 네트워크):** 네트워크로 나가는 것은 봉투(암호문)와 연결 메타데이터뿐이다.
- **B3 (멤버 ↔ 멤버):** 다른 멤버는 "인증됐지만 정직하다고 가정하지 않는" 상대다. 받은 모든 영속 봉투는 경로와 관계없이 서명과 권한을 검증한다.
- **B4 (신뢰 루트):** 멤버십은 권한 기기가 정하고, 권한 기기는 복구 코드가 정한다.

### 2.4 막지 못하는 것
1. 이미 받은 평문과 사용자가 복사한 내용. 회수는 미래의 내용과 쓰기만 막는다(PRD D1).
2. 쓰기 권한이 있는 멤버의 정상 서명 편집. 되돌리기와 책임 추적만 가능하다(PRD D3).
3. 권한 기기나 복구 코드를 손에 넣은 공격자. 이것이 루트다.
4. 관측 메타데이터: IP, 연결 시각, 트래픽 크기, 기기 공개키, mDNS가 같은 망에 알리는 기기 존재(PRD D7). Iroh 기본 DNS 주소 조회는 EndpointId를 키로 한 기록을 평문으로 게시한다(§3.3).
5. 모든 경로를 막는 공격자에 의한 가용성 저하. 이때 최신 상태가 존재하지 않는다는 증명은 불가능하고, 탐지는 정직한 피어와 다시 만날 때만 된다.
6. 기기의 디스크. `.context/index.sqlite`의 색인과 CRDT 상태는 평문에서 나온 데이터다. OS 디스크 암호화와 로그인 잠금은 사용자와 조직이 책임진다(PRD §6.7).
7. Yjs 수준의 비잔틴 행위 전체. 서명은 작성자를 인증할 뿐이다. 이중 발행은 탐지만 한다.

### 3.3 결론과 근거
**Iroh 1.x 위 직접 구현을 채택한다.** 근거는 세 가지다.
1. 평가 기준 중 Yjs 이력 보존과 순수 LAN을 둘 다 충족하는 후보는 직접 구현과 p2panda뿐이다. NextGraph는 broker 없이 기기끼리 동기화하는 경로가 문서에 없고 공유 자체가 아직 연결되지 않았다. Automerge 계열은 CRDT 교체가 필요하다.
2. p2panda는 우리와 같은 Iroh 위에 있어 기술적으로 가깝다. 그러나 p2panda-net은 2024-12의 0.1.0 이후 0.x로만 12개 버전이 나왔고, API 안정성을 약속하지 않는다. p2panda-auth의 동시 관리자 해결 규칙은 우리가 일부러 피하기로 한 다중 권한 모델(Q4)이다. p2panda-encryption은 감사 전이며 README가 고위험 용도를 권하지 않는다. 바이트 로그 위에 우리 봉투를 다시 얹으면 헤더와 서명이 이중이 된다. 지금 의존하면 얻는 것보다 따라가야 할 변경이 크다.
3. 직접 구현에서 우리가 새로 만드는 것은 봉투, 단일 작성자 멤버십 체인, registry 연산이다. 셋 다 이미 허브 모드에서 서버가 하던 판단을 서명과 체인으로 옮기는 일이고, 지금 브리지·삭제 가드·SQLite 로그를 그대로 쓴다.

**쓰는 Iroh 구성:** `iroh` 1.3.x(Endpoint, Router, ALPN별 프로토콜), `iroh-mdns-address-lookup` 0.6.x(같은 망 탐색), `RelayMode::Disabled`(C1, 사내망 전용) 또는 `RelayMode::Custom`(사내 중계). 초대 티켓 안의 주소 표현은 Iroh의 티켓 crate(`iroh-tickets` 1.0.0, "Tickets as signaling for iroh")를 쓸 수 있는지 C1에서 확인한다.

**쓰지 않는 Iroh 구성:** `iroh-docs`(0.101.0, 자체 복제 key-value 모델이고 우리 멤버십·암호화와 겹친다), `iroh-gossip`(0.101.0, 영속 데이터를 gossip에 맡기지 않는다. 15명 규모는 온라인 피어 직접 연결로 충분하다. presence 같은 일시 메시지용으로만 나중에 검토한다), `iroh-blobs`(첨부는 D. 2026-10-08에 보안 수정이 있었으므로 D에서 다시 평가한다).

**Iroh의 메타데이터 주의점:** 기본 DNS 주소 조회는 EndpointId를 키로 한 기록을 평문으로 게시한다. Iroh 팀의 "blinded address lookup"은 아직 개념 증명이며 공개키를 비밀로 만드는 것은 로드맵에 없다고 밝혔다. 그래서 (1) C1과 사내망 전용 모드는 DNS 주소 조회를 쓰지 않는다. (2) 전송 키를 기기 서명 키와 분리하고 vault마다 따로 둔다(§4.1). (3) C2에서 공개 DNS 게시 여부를 다시 정한다. 기본안은 게시하지 않고 초대 티켓과 vault 안의 암호화된 주소 교환으로 상대 주소를 얻는 것이다.

**재평가 조건:** p2panda 1.0과 암호화 감사 공개, Keyhive·Subduction의 감사와 Yjs 지원 확인, NextGraph의 공유 기능과 안정 포맷. 셋 중 하나라도 생기면 C2 착수 전에 같은 표로 다시 본다.

**직접 구현의 위험과 완화:** 프로토콜 설계 오류가 가장 큰 위험이다. 표준 구성(Ed25519, RFC 9180 HPKE, XChaCha20-Poly1305, BLAKE3)만 쓰고, 멤버십을 단일 작성자 체인으로 작게 유지하고, C1에서 속성 기반 테스트와 장애 주입을 하고, C2 전에 외부 보안 리뷰를 받는다.

## 4. 기기 신원과 복구 키

### 4.1 키 구성
| 키 | 방식 | 용도 | 보관 | 교체 |
|---|---|---|---|---|
| 기기 마스터 비밀 | 256비트 무작위 | vault별 기기 키를 파생하는 뿌리 | OS 키체인 | 복제 감지나 분실 시 새로 만든다 |
| 기기 서명 키 | Ed25519, 마스터에서 HKDF(`"ib/p2p/sign/v1" ‖ vault_id`)로 파생 | 봉투, 멤버십 요청, ACK 서명. `device_id` = 공개키 | 파생 결과는 메모리에만 | 마스터와 함께 |
| 기기 암호화 키 | X25519, 같은 방식으로 파생. HPKE(RFC 9180) DHKEM(X25519, HKDF-SHA256) / HKDF-SHA256 / ChaCha20-Poly1305 | epoch 키를 감싸 받기 | 메모리 | 마스터와 함께 |
| 전송 키 | Ed25519(Iroh EndpointId) | QUIC/TLS 연결 인증 | OS 키체인 | 서명 키와 **독립적으로** 바꿀 수 있다(추적 방지) |
| epoch 콘텐츠 키 | 256비트 대칭, XChaCha20-Poly1305 | 봉투 payload 암호화 | 기기 암호화 키로 감싸 `.context`에, 또는 키체인 | 제거·강등·의심 시 새 epoch |
| 복구 키 | 256비트 비밀. HKDF로 Ed25519 복구 서명 키와 X25519 복구 암호화 키를 파생 | 권한 이양, 모든 epoch 키 복호화 | **사용자가 오프라인 보관.** 앱에는 공개키만 | 권한 기기가 교체할 수 있다 |

- **vault별 파생 이유:** 한 기기가 여러 vault에 있어도 노드·중계 운영자가 같은 기기임을 연결하지 못하게 한다. 키체인 항목은 마스터 하나로 끝난다. 서명 키와 전송 키를 나누는 이유도 같다. 전송 키는 mDNS와 DNS 조회에 공개되지만 서명 키는 봉투에만 나타난다.
- **보관:** 지금 `R/keychain.rs`의 OS 비밀 저장소를 재사용한다(서비스 이름 `com.infinitebrain.desktop`, `R/keychain.rs:29`). 이 모듈은 지금 세션 토큰 저장용이다. OS 비밀 저장소가 없어 메모리 대체본으로 떨어지는 경우를 이미 감지한다(`R/keychain.rs:43-62`). **P2P는 이 경우 기기 키를 만들지 않는다.** 화면에는 "이 기기에는 안전한 저장 공간이 없어 서버 없이 공유를 켤 수 없습니다"와 OS별 해결 방법을 보여 준다(PRD F5.6 Linux).
- **기기 인증서:** `DeviceCert{vault_id, user_id, device_id, hpke_pk, transport_id, created_at, self_sig}`. 자기 서명으로 세 공개키를 서로 묶고, 권한 기기가 멤버십 체인의 `AddDevice` 레코드로 승인한다. 기기 이름과 사용자 프로필은 암호화된 멤버십 본문에만 들어간다(D7).

### 4.2 사용자와 기기
- 구조는 PRD F5.1대로 `사용자 → 승인된 기기 → vault 멤버십과 역할`이다. `user_id`는 합류 때 정하는 128비트 무작위 값이다. 사용자 단위 키는 두지 않는다. 멤버십 체인이 기기와 사용자의 관계를 정하므로 따로 필요하지 않다.
- **기기 하나 제거**는 `RemoveDevice`, **사용자 전체 제거**는 그 사용자의 모든 기기를 한 레코드로 지우는 `RemoveUser`다. 둘 다 키 교체를 일으킨다(§5.3).
- **같은 사용자의 새 기기:** 기존 기기에서 [기기 추가] → 새 기기가 QR이나 링크로 받은 기기 연결 티켓으로 요청 → 기존 기기가 보증 서명 → 권한 기기가 `AddDevice`. vault 정책에 따라 "같은 사용자의 보증이면 자동 승인"을 켤 수 있다.
- **마지막 관리자 제거 금지, 권한 기기 이양**은 PRD F5.1대로다. 이양은 `TransferAuthority` 레코드다.

### 4.3 복제·디스크 복원 감지
디스크를 백업에서 복원하거나 기기를 통째로 복제하면 같은 기기 키와 옛 카운터로 서명이 다시 시작된다. 대응은 두 겹이다.
1. **nonce 재사용을 구조적으로 없앤다.** 봉투는 192비트 무작위 nonce를 쓰는 XChaCha20-Poly1305로 암호화한다. 카운터가 되돌아가도 nonce는 겹치지 않는다.
2. **카운터 분기를 탐지한다.** 연결할 때 피어가 "내가 가진 당신의 마지막 봉투(카운터, 해시)"를 알려 준다. 로컬 head보다 앞서 있거나 같은 카운터에 다른 해시면 이 기기는 복원본이다. 기기는 서명을 멈추고, 새 마스터 비밀을 만들고, 권한 기기에 `ReplaceDevice{old, new}`를 요청한다(같은 사용자의 다른 기기 보증 또는 관리자 승인). 화면에는 "이 기기를 다시 등록해야 합니다"만 보여 준다.
3. 오프라인 중에 이미 서명한 봉투는 버리지 않는다. 복원본이 새로 만든 Yjs 연산은 새 세션의 clientID를 쓰므로 Yjs ID가 겹치지 않는다. 수신 측은 체인 분기를 "복원 또는 이중 발행"으로 표시하고, 두 가지의 Yjs ID 범위가 겹치지 않으면 둘 다 받는다. 겹치면 이중 발행으로 보고 나중에 온 쪽을 격리한다(§6.3).

### 4.4 초대 티켓 (F1.2, 리뷰 S03)
- **내용:** `{vault_id, invite_id, role, expires_at, issuer_device_id, issuer_addr(EndpointAddr), membership_head(seq, hash), secret(32B)}`에 발급 기기가 서명한다. 링크(`infinitebrain://` 딥링크의 fragment)나 QR로 통째로 전달한다. 짧은 코드는 쓰지 않는다(PRD F1.2).
- **합류:** 새 기기는 티켓의 주소와 EndpointId로 발급 기기에 직접 연결한다(같은 망은 mDNS, C2부터 중계). TLS가 EndpointId를 확인하므로 중간자가 끼어들 수 없다. 새 기기는 `JoinRequest{invite_id, DeviceCert, MAC(secret, DeviceCert)}`를 보낸다.
- **소비:** 발급 기기가 MAC을 확인하고 SQLite 트랜잭션 하나로 티켓을 "사용됨"으로 바꾼다. 같은 `(invite_id, device_id)` 재요청은 같은 결과를 돌려준다. 다른 기기가 같은 티켓을 쓰면 "이미 사용된 초대"로 거절한다. 발급 기기가 권한 기기가 아니면 승인 요청을 권한 기기에 전달하고, 새 기기는 "승인을 기다리는 중"을 본다.
- **승인:** 관리자가 [승인]을 누르면 권한 기기가 `AddDevice`를 쓰고, 현재까지의 **모든** epoch 키를 새 기기의 HPKE 공개키로 감싸 보낸다. vault 단위 읽기 권한은 이력 전체를 포함하기 때문이다(허브에서 새 멤버가 기존 노트를 모두 읽는 것과 같다). 승인 전에는 키를 주지 않는다.
- **신선도:** 새 기기는 티켓의 `membership_head`보다 오래된 멤버십 체인을 받아들이지 않는다. 이것이 처음 들어오는 기기의 되돌리기 방어다.
- **노출 방지:** 티켓 비밀은 로그, 지원 번들, 클립보드 기록에 남기지 않는다. 사용 후 클립보드를 비운다. 만료는 1회 사용을 대신하지 않는다.
- **선택 확인:** 같은 장소에서 합류할 때는 두 화면에 같은 그림 4개를 보여 주고 같은지 묻는다. 원격 합류는 요청자 이름만 보여 준다.

### 4.5 복구 키
- **발급:** vault를 만들 때 복구 키를 만든다. 화면은 PRD §0.1의 "복구 코드 저장하기" 한 장이다(인쇄, 파일 저장, 비밀번호 관리자). 마지막 몇 단어를 다시 입력해 저장했는지 확인한다. 표시 형식(단어 24개 등)은 C2 UX에서 정한다.
- **genesis 레코드:** `{vault_id, creator_device, recovery_sign_pk, recovery_hpke_pk, authority = creator_device}`에 생성 기기와 복구 키가 함께 서명한다. 이 레코드가 vault의 신뢰 루트다.
- **할 수 있는 일:** (1) `TransferAuthority`에 서명해 새 권한 기기를 정한다. (2) 모든 epoch 키는 복구 공개키로도 감싸 두므로, 복구 코드와 암호문(다른 멤버, 노드, 백업 어디서든)만 있으면 내용을 복원한다.
- **쓰면 일어나는 일:** 복구 코드로 권한을 넘기면 즉시 새 epoch로 키를 교체하고 모든 기기에 알린다. 복구 코드가 새어 나갔을 가능성을 기본으로 가정하기 때문이다.
- **교체:** 권한 기기가 새 복구 키를 만들고 옛 복구 키와 함께 서명해 바꾼다. 옛 복구 코드는 이미 감싼 옛 epoch 키를 계속 열 수 있다. 이것은 막을 수 없다.
- **모두 잃은 경우:** 권한 기기와 예비 권한 기기와 복구 코드를 모두 잃으면 멤버십은 영구히 멈춘다. 남은 멤버는 현재 epoch에서 계속 편집할 수 있지만 누구도 추가·제거하지 못한다. 탈출구는 "새 vault로 복사"다. 아무 멤버나 Markdown을 내보내 새 vault를 만들고 다시 초대한다. 이 사실을 vault를 만들 때 고지한다(PRD F5.1).

## 5. 멤버십 epoch와 3단계 키 교체

### 5.1 용어와 멤버십 체인
PRD의 "멤버십 epoch"를 두 값으로 나눈다.
- **멤버십 seq:** 멤버십 레코드마다 1씩 증가한다. 기기 추가처럼 키를 바꾸지 않는 변경도 seq를 올린다.
- **키 epoch:** 키 교체 때만 증가한다. 봉투 헤더는 epoch 번호와 `key_id`(그 epoch를 연 `RotateBegin` 레코드의 해시 앞 16바이트)를 함께 담는다. 번호만으로는 §5.4의 분기 상황에서 같은 번호가 두 번 생길 수 있기 때문이다.

멤버십 체인은 권한 기기 한 대만 쓰는 append-only 해시 체인이다. 레코드는 `{vault_id, seq, prev_hash, epoch, kind, body(암호화), signer, sig}`다. 헤더는 불투명 값만 담고, 누가 어떤 역할인지는 epoch 키로 암호화된 본문에 있다. 본문은 그 레코드가 속한 epoch 키로 암호화하되, `RotateBegin` 이후의 본문(새 멤버 목록 포함)은 새 epoch 키로 암호화한다. 제거된 기기가 남은 멤버 목록을 읽지 못하게 하기 위해서다. 새 기기는 합류 때 받은 epoch 키들로 본문을 열고, 헤더의 서명과 해시 체인은 genesis부터 검증한다.

레코드 종류: `Genesis`, `AddDevice`, `RemoveDevice`, `RemoveUser`, `ChangeRole`, `ReplaceDevice`, `TransferAuthority`, `SetStandby`(예비 권한 기기 지정, §9.2), `RotateBegin`, `RotateCommit`, `RecoveryRotate`, `SetPolicy`(보존 기한 등).

역할: `admin`(관리 요청 가능, 권한 기기 후보), `editor`(쓰기), `reader`(읽기 전용, C2 이후 게스트). 권한 기기는 admin 중 한 기기다.

### 5.2 쓰기 권한 검증 (리뷰 R03)
수신 기기는 영속 봉투를 다음 순서로 검사하고, 모두 통과해야 Yjs나 registry에 적용한다. 값싼 검사부터 한다.
1. 크기 상한, 프로토콜 버전, `vault_id`가 맞는가.
2. 작성 기기 서명이 맞는가.
3. 작성 기기가 헤더의 `roster_seq` 시점 멤버십에서 활성이고 그 종류의 봉투를 쓸 역할(편집·registry는 editor 이상)을 가졌는가. `roster_seq`는 수신 기기가 아는 head 이하여야 한다. 더 크면 멤버십을 먼저 받아 온다.
4. **제거·강등 기준점:** 작성 기기가 나중에 제거되거나 reader로 강등됐다면, 그 레코드에 적힌 기준점(그 시점에 권한 기기가 알던 그 기기의 체인 head, 즉 카운터와 해시) 이하이고 그 체인 위에 있는 봉투만 자동으로 받는다. 기준점 이후의 봉투는 **격리**하고 관리자에게 "확인이 필요한 변경"으로 보여 준다(PRD D4 "그 전에 작성된 변경은 관리자 확인"). 제거된 기기가 옛 `roster_seq`를 주장해도 기준점은 기기 단위라서 우회할 수 없다.
5. 헤더의 `key_id`에 해당하는 키를 갖고 있는가. 없으면 "키 대기"로 보관했다가 키가 오면 다시 검사한다.
6. 작성자 체인(§6.3)에 맞는가. 누락이 있으면 적용은 하되 "동기화 미완료"로 표시하고 빠진 봉투를 요청한다.
7. 복호화하고, Yjs 업데이트 파싱 한도(크기, 구조 수)를 확인한다.

이 검증이 없으면 P2P 읽기 전용 게스트를 출시하지 않는다(PRD D4). C1은 reader 역할을 만들지 않지만, editor를 reader로 강등하는 시나리오로 4번을 시험한다(§10).

### 5.3 키 교체 상태 기계 (리뷰 R02)
| 상태 | 들어가는 조건 | 하는 일 | 저장 | 실패·재시도 |
|---|---|---|---|---|
| **안정(e)** | 처음, 또는 확정 후 | epoch e 키로 읽고 쓴다 | — | — |
| **준비(e→e+1)** | 제거·강등·복구 사용·관리자의 수동 갱신 | 새 키 K(e+1) 생성. `RotateBegin{rotation_id, from e, to e+1, 사유, 제거 기기별 기준점, 새 멤버 목록}` 작성. 남은 기기 각각, 그리고 복구 공개키와 예비 권한 기기용으로 K(e+1)을 HPKE로 감싼 `KeyPackage` 생성 | 위 전부를 권한 기기의 SQLite 트랜잭션 하나로 저장한 뒤에야 밖으로 보낸다 | 아무것도 보내기 전이면 취소하고 안정(e)로 돌아갈 수 있다. 재시작하면 저장된 상태에서 이어간다 |
| **배포(e+1)** | 첫 `RotateBegin`이 밖으로 나감 | `RotateBegin`과 `KeyPackage`를 온라인 기기에 직접, 오프라인 기기 몫은 다른 멤버(와 D의 노드)에 맡겨 보낸다. 받은 기기는 서명된 `KeyAck{rotation_id, device_id}`를 돌려주고 **곧바로 e+1로 쓰기 시작한다**. 아직 키가 없는 기기는 e로 계속 쓰고, e+1 봉투는 보관했다가 키를 받으면 연다 | 보낸 `KeyPackage` 바이트를 그대로 보관해 재전송한다(HPKE는 무작위라 다시 만들면 바이트가 달라진다). 수신 측은 `(rotation_id, device_id)`로 중복을 거른다 | **되돌리지 않는다.** 앞으로만 재시도한다. 권한 기기가 이 상태에서 사라져도 K(e+1)이 복구 공개키와 예비 권한 기기 몫으로 감싸져 있어 이어받을 수 있다 |
| **확정(e+1)** | 남은 기기 전원 ACK, 또는 관리자가 기다리지 않기로 고르고 기한(기본 7일)이 지남 | `RotateCommit{rotation_id, ACK한 기기, 미수령 기기, 제거 기기별 최종 기준점, 구 epoch 봉투 보존 기한}` 작성 | 체인에 추가 | 미수령 기기의 `KeyPackage`는 **기한 없이** 보존한다. 그 기기가 제거되기 전까지 지우지 않는다 |

규칙:
- **새 키를 아는 기기는 구 epoch로 새 봉투를 만들지 않는다.** 아직 보내지 못한 자기 봉투(outbox)는 작성자 자신이 e+1로 다시 봉인해 새 서명을 붙인다. 다른 기기가 남의 봉투를 다시 봉인하지는 않는다. 작성자 서명이 깨지기 때문이다.
- **현역 기기의 구 epoch 봉투는 언제 와도 받는다.** 서명과 멤버십이 맞으면 epoch e 봉투라도 받는다. 수신 기기는 구 epoch 키를 vault 수명 동안 보존한다(§9.3). 이 봉투는 멤버가 아닌 상대에게 전달하지 않는다. 그래서 제거된 기기가 그 암호문을 얻을 경로는 멤버의 협조뿐이다.
- **연속 제거:** 배포 중에 또 제거가 생기면 권한 기기는 `RotateBegin(e+2)`를 바로 쓴다. e+1은 "대체됨"으로 확정되고, e+1 `KeyPackage`는 새로 제거된 기기를 뺀 기기에게만 계속 전달한다. 배포 중 e+1로 쓰인 봉투를 열려면 e+1 키가 필요하기 때문이다.
- **멱등성:** 모든 단계는 `rotation_id`로 식별한다. 같은 요청이 다시 와도 결과는 같다. PRD D4의 "원래 상태로 복구할 수 있어야 한다"는 준비 단계의 취소와, 배포 단계의 저장된 바이트 재전송으로 충족한다.
- **화면:** 진행 중에는 "팀원이 나가서 보안을 새로 고치는 중"만 보여 준다(PRD F5.5a). 미수령 기기가 있으면 관리자에게만 "○○님의 기기가 켜지면 마무리됩니다"를 보여 준다.

### 5.4 권한 기기가 오프라인일 때
- **일반 편집은 계속된다.** 멤버십과 무관하기 때문이다.
- **멤버십 변경은 요청으로 쌓인다.** 다른 admin은 서명된 `ChangeRequest{request_id, ...}`를 보내고, 권한 기기가 켜지면 받은 순서대로 처리한다. 화면에는 "관리자 기기(○○의 노트북)가 켜지면 처리됩니다".
- **합류 요청**은 발급 기기가 티켓을 소비한 뒤 "승인 대기"로 남는다.
- **권한 기기를 오래 쓸 수 없으면** 예비 권한 기기가 인수하거나(§9.2), 복구 코드로 `TransferAuthority`를 쓴다(§4.5).

### 5.5 동시 변경 충돌 해결
작성자가 한 기기뿐이라 정상 상태의 멤버십 체인은 직선이다. 충돌은 아래 경우에만 생기고, 규칙은 모두 결정적이다.
| 상황 | 규칙 | 결과 |
|---|---|---|
| 같은 seq에 두 레코드, 하나는 복구 키 서명 | 복구 키 레코드가 이긴다 | 진 쪽 이후 레코드는 무효. 그 내용은 새 권한 기기에 "다시 요청"으로 올라간다 |
| 같은 seq에 두 레코드, 하나는 예비 권한 기기의 인수(`TransferAuthority` by standby) | 인수 레코드가 이긴다(사전에 `SetStandby`로 지정된 기기만) | 위와 같다 |
| 같은 seq에 두 레코드, 둘 다 같은 권한 기기 서명 | 이중 발행이나 권한 기기 복제로 본다 | **멤버십 변경을 멈추고** 관리자에게 "보안 문제 감지"를 알린다. 편집은 마지막 공통 epoch에서 계속된다. 복구 키 레코드가 한쪽을 고를 때까지 유지한다 |
| 무효가 된 가지에서 추가된 기기가 이미 쓴 봉투 | 버리지 않고 격리한다 | 이긴 가지에서 그 기기가 추가되면 다시 검사해 받는다 |
| 무효가 된 가지의 epoch 키로 쓰인 봉투 | `key_id`로 구분해 그 키를 보존하고 연다 | 내용 손실 없음. 이긴 가지의 다음 교체가 새 키를 정한다 |
| admin들의 충돌하는 요청(같은 사람 제거와 승격) | 권한 기기가 받은 순서대로 적용하고, 나중 것은 바뀐 상태에서 다시 검증한다 | 거절된 요청은 이유와 함께 돌려준다 |
| 멤버십 변경과 동시 편집 | §5.2의 `roster_seq`와 기준점 규칙 | 현역 기기 편집은 받고, 제거 기기의 기준점 이후 편집은 격리 |
| 같은 초대 티켓을 두 기기가 사용 | 발급 기기의 원자적 소비 | 두 번째는 "이미 사용된 초대" |

## 6. 봉투 형식, 스냅샷 경쟁, watermark 삭제

### 6.1 봉투 종류
`update`(Yjs 업데이트), `snapshot`(Yjs 상태), `registry`(§7 연산), `control`(ACK, 보유 알림, 정리 요청), `membership`(§5.1 레코드), `keypkg`(감싼 epoch 키). 일시 메시지(presence, 커서)는 epoch 키로 암호화하고 서명하지만 체인에 넣지 않고 저장하지 않는다.

### 6.2 헤더와 암호화 (PRD D3, 리뷰 R07)
| 필드 | 크기(바이트) | 설명 |
|---|---|---|
| `magic`, `version` | 4 | 프로토콜 식별과 버전. 능력 협상은 연결 hello에서 한다(PRD §6.5) |
| `suite` | 1 | 암호 묶음. v1 = Ed25519 / XChaCha20-Poly1305 / BLAKE3 / HPKE(X25519, HKDF-SHA256, ChaCha20-Poly1305) |
| `kind` | 1 | 위 종류 |
| `vault_id` | 16 | 무작위 |
| `doc_id` | 16 | 지금 문서 ID와 같은 UUID v4(`R/index.rs:1424`). 무작위라 생성 시각이 드러나지 않는다. registry·membership 봉투는 0 |
| `epoch`, `key_id` | 4 + 16 | §5.1 |
| `roster_seq` | 4 | 작성자가 본 멤버십 seq |
| `author` | 32 | 작성 기기 서명 공개키 |
| `counter` | 8 | 작성 기기별 vault 단위 단조 증가 값 |
| `prev` | 32 | 같은 작성자의 직전 봉투 ID(작성자 해시 체인) |
| `parent` | 32 | snapshot: 부모 스냅샷 ID. update: 작성 시점에 알던 그 문서의 최신 스냅샷 ID(없으면 0) |
| `nonce` | 24 | 무작위 |
| `ct_len` | 4 | 암호문 길이 |

- **암호화:** `ciphertext = XChaCha20-Poly1305(K(epoch), nonce, payload, AAD = 헤더 전체)`. 헤더의 어느 값을 바꿔도 복호화가 실패한다.
- **봉투 ID와 서명:** `envelope_id = BLAKE3(헤더 ‖ ciphertext)`, `sig = Ed25519(author, "ib/p2p/env/v1" ‖ envelope_id)`. 암호문에 서명하므로 키가 없는 저장 노드도 작성자를 확인하고 업로드를 인증할 수 있다(F5.9). PRD D3이 요구한 "payload 해시"는 봉투 ID에 들어 있다.
- **payload:** 종류별 본문, 작성 시각(화면 표시용이며 신뢰하지 않음), 그리고 크기를 감추기 위한 padding. padding 구간은 C1 측정 후 정한다.
- **인코딩:** 헤더는 고정 순서의 이진 형식으로 하나의 표현만 허용한다. 해시와 서명이 표현 차이에 흔들리지 않게 하기 위해서다.
- **평문으로 남는 것:** 불투명 ID(vault, 문서, 봉투), 종류, 크기, 작성 기기 공개키, 시각. PRD D7이 허용한 범위다. 제목, 경로, 폴더 이름, 멤버 프로필은 모두 payload 안에 있다.

### 6.3 되돌리기·누락·분기 방어
수신 기기는 다음 상태를 봉투 저장과 **같은 SQLite 트랜잭션**으로 `.context/index.sqlite`의 새 테이블에 저장한다. 기존 테이블은 건드리지 않는다(PRD F8.5).
- 멤버십 head(seq, 해시)와 알고 있는 epoch 키 목록
- 작성 기기별 연속 head(카운터, 봉투 ID)와 분기 표시
- 문서별로 받아들인 스냅샷(ID, watermark)과 Yjs state vector
- 마지막 "최신 확인" 기록: 언제, 누구와 head가 일치했는가

규칙:
1. **줄어들지 않는다.** 멤버십 head보다 오래된 체인은 받아들이지 않는다. seq가 같고 해시가 다르면 §5.5의 분기다.
2. **누락 탐지:** 작성자별 카운터가 n+1인 봉투는 n이 필요하다. 없으면 적용은 하되 빠진 것을 요청하고, 일정 시간 안에 못 받으면 "일부 변경을 아직 받지 못했습니다"를 보여 준다. 조용히 성공 처리하지 않는다(PRD D3).
3. **분기 탐지:** 같은 작성자에게서 같은 카운터와 다른 해시가 오면 분기다. 두 가지가 담은 Yjs 연산의 (clientID, clock) 범위가 겹치지 않으면 복원으로 보고 둘 다 받은 뒤 `ReplaceDevice`를 기다린다(§4.3). 겹치면 이중 발행으로 보고 나중에 받은 가지를 격리하고 관리자에게 알린다.
4. **신선도:** 권한 기기나 서로 다른 피어 두 대 이상과 head가 일치하면 "최신"이다. 그렇지 못하면 PRD F5.5a의 표현 중 "다른 사람이 켜면 전달됨" 또는 "이 기기에만 저장됨"을 쓴다. 처음 들어온 기기는 티켓의 멤버십 head가 하한이다(§4.4).

### 6.4 스냅샷
- **내용:** `Y.encodeStateAsUpdate(doc)`(Yjs v1 이진), 그 상태의 state vector, watermark W. W는 "작성 기기 → 이 문서에 대해 포함한 가장 큰 카운터"이고, 그 작성자가 이 문서에 쓴 봉투 중 W 이하는 **모두** 포함했다는 뜻이다. 작성자 체인 헤더에 `doc_id`가 평문으로 있어 어떤 카운터가 어느 문서 것인지 수신 측이 확인할 수 있다.
- **Markdown에서 다시 만들지 않는다.** 그렇게 하면 기존 연산 ID를 잃는다(PRD D4, 리뷰 R06). Yjs의 삭제 내용 GC는 Yjs 안에서 따로 일어나며 연산 ID 구조는 유지된다.
- **누가 만드나:** 아무 editor 기기나 만들 수 있다. 조건은 (1) 부모 스냅샷과 W에 든 그 문서의 봉투를 모두 적용했고, (2) 그 문서에 해결되지 않은 누락·분기·격리가 없고, (3) 마지막 스냅샷 이후 봉투가 일정 수를 넘은 경우다. 만들 기기를 따로 정하지 않는다. 경쟁은 아래 규칙으로 안전하게 처리되므로 조정 비용이 더 크다. 동시에 만드는 일을 줄이려고 무작위 지연만 둔다. 스냅샷 작성자가 오프라인이어도 같은 검증된 이력을 가진 다른 기기가 만들 수 있다(PRD D4).
- **로컬 압축과의 관계:** 지금 로컬 Yjs 로그의 압축 기준(업데이트 64개 또는 1MB, `D/lib/bridge/types.ts:209-212`)은 그대로 둔다. 네트워크 스냅샷은 봉투 저장소에 대한 별도 단계다. 기준값은 C1에서 정한다.

### 6.5 스냅샷 경쟁
같은 부모에서 두 기기가 다른 W로 스냅샷 S1, S2를 동시에 만들 수 있다. 처리는 다음과 같다.
1. **둘 다 유효하다.** 각각 자기 W만큼의 정확한 상태다. Yjs 상태는 합칠 수 있으므로 어느 쪽을 받아도 내용은 같아진다.
2. **다음 스냅샷의 부모는 결정적으로 고른다.** W가 다른 쪽을 지배하면 그쪽을, 아니면 W 합계가 큰 쪽을, 같으면 봉투 ID가 작은 쪽을 고른다. 모든 기기가 같은 답을 낸다. 고르지 않은 쪽은 다음 스냅샷이 덮으면 지울 수 있다.
3. **받은 스냅샷은 검증한다.** 스냅샷을 압축 기준으로 쓰기 전에, 그 스냅샷이 덮는다고 주장하는 업데이트 중 내가 가진 것을 스냅샷 상태에 적용해 보고 상태가 바뀌지 않는지(멱등) 확인한다. state vector만으로는 삭제 집합의 포함 여부를 알 수 없기 때문이다. 바뀌면 그 스냅샷은 압축 기준으로 쓰지 않고 작성 기기를 표시한다.

### 6.6 watermark 삭제
업데이트 봉투 u(문서 d)를 지우는 조건은 모두 만족해야 한다.
1. 이 기기가 §6.5의 방법으로 **직접 검증한** 스냅샷 S가 u를 덮는다(W_S[u.author] ≥ u.counter).
2. S의 저장과 u의 삭제를 SQLite 트랜잭션 하나로 한다. 지금 `R/index.rs:2424-2475`의 `save_yjs_snapshot`이 `id <= up_to`인 행만 지우는 원리를 봉투 저장소에 그대로 쓴다. 스냅샷을 만드는 동안 들어온 봉투는 남는다.
3. u가 격리 중이거나 해결되지 않은 분기에 속하지 않는다.
4. u가 구 epoch 봉투면 보존 기한(§9.3)이 지났다.
5. 저장 노드(D)는 키가 없어 1을 할 수 없다. 노드는 editor가 서명한 정리 요청을 받아도 **보존 기한이 지난 뒤에만** 실제로 지운다. 악성 editor가 가짜 스냅샷으로 노드의 이력을 지우게 하는 것을 막기 위해서다.

스냅샷은 동기화 상태를 줄이는 장치일 뿐 백업이 아니다(PRD §6.1). 문서 상태 크기, 봉투 로그 크기, 스냅샷 빈도의 상한은 C1 측정으로 정한다(PRD D4).

## 7. 암호화된 registry/control 프로토콜과 삭제·복구 계약

### 7.1 registry 연산 (PRD F5.3, 리뷰 R04)
registry는 vault의 문서·폴더 목록이다. 모든 연산은 `registry` 봉투(서명, 암호화)다. 연산은 작성자가 본 registry head 목록(`deps`)과 Lamport 값을 담아 인과 DAG를 이룬다. 각 기기는 같은 연산 집합을 결정적인 위상 순서(같은 순위는 봉투 ID 순)로 접어 같은 상태를 계산한다.

| 연산 | 내용(모두 암호화) | 필요한 역할 |
|---|---|---|
| `CreateDoc` | `doc_id`, 경로, 폴더 ID | editor |
| `CreateFolder` | `folder_id`, 이름, 부모 | editor |
| `Move` | `doc_id` 또는 `folder_id`, 이전 위치, 새 위치 | editor |
| `Tombstone` | `doc_id` 목록 또는 `folder_id`와 **그 시점에 아는 하위 항목 목록** | editor |
| `Restore` | `doc_id`/`folder_id` | editor |
| `Purge` | 보존 기한 전 영구 삭제 | admin |

컨트롤 메시지(`control` 봉투):
- `Heads`: 연결할 때 서로의 멤버십 head, 작성자별 체인 head, registry head를 교환한다.
- `HeldAck{doc_id, state_vector_digest, holder}`: "이 상태를 내가 영속 저장했다"는 서명된 확인. 권한 기기, 다른 기기, 노드가 보낸다.
- `PruneRequest`: §6.6의 노드용 정리 요청.

### 7.2 충돌 규칙
| 상황 | 규칙 | 화면 |
|---|---|---|
| 같은 경로에 다른 `doc_id`(동시 생성, 각자 같은 파일을 가져옴) | 둘 다 유지하고 자동 병합하지 않는다. registry 상태에서 결정적으로 "표시 경로"를 계산해 나중 순위 문서에 ` (2)` 같은 접미사를 붙인다. 모든 기기가 같은 결과를 내므로 이름 바꾸기가 오가지 않는다 | "같은 이름의 노트가 두 개 생겨 하나의 이름을 바꿨습니다" |
| 대소문자나 Unicode 정규화만 다른 경로 | 지금 `D/lib/pathIdentity.ts:25`의 `pathKey`로 같은 경로로 본다(macOS·Windows는 대소문자를 구분하지 않는다). 위 규칙을 적용한다 | 위와 같음 |
| 같은 항목을 동시에 다른 곳으로 이동 | Lamport가 큰 쪽, 같으면 봉투 ID가 큰 쪽이 이긴다. 진 이동은 기록에 남긴다 | 없음 |
| 이동과 삭제가 동시 | 삭제가 이긴다. 복원하면 마지막 이동 위치로 돌아간다 | 휴지통 표시 |
| 삭제와 동시 편집 | 문서는 휴지통 상태로 두고 편집은 CRDT에 보존한다. 허브의 휴지통이 삭제된 노트의 오프라인 변경을 받는 것과 같다 | "삭제된 노트에 새 변경이 있습니다 [복원]" |
| 폴더 삭제 중 그 폴더에 새 문서 | 폴더 `Tombstone`은 그 시점에 알던 하위 항목만 지운다. 새 문서는 살고, 폴더는 그 문서를 위해 남는다 | "다른 기기에서 이 폴더에 새 노트를 만들어 폴더를 남겼습니다" |
| 폴더 이름 변경과 하위 새 문서 | 폴더는 `folder_id`로 식별하므로 새 문서는 바뀐 이름 아래 생긴다 | 없음 |
| 바이너리 파일 | C는 텍스트 전용이라 동기화하지 않는다. Rust 확장자 목록, TS 형식 registry, 동기화 확장자 목록을 계속 같게 유지한다(CLAUDE.md). D의 첨부는 CRDT가 아니므로 충돌하면 사본을 남긴다 | "이 파일은 아직 공유되지 않습니다" |

### 7.3 "부재 ≠ 삭제" 계약
1. 피어가 보낸 목록이나 registry 상태에 문서가 없다는 것은 그 피어가 뒤처졌다는 뜻이다. 로컬 문서를 지우지 않고, 상대에게 없는 연산을 보낸다.
2. 피어가 "그 문서의 내용이 없다"고 해도 빈 문서로 다루지 않는다. 내용을 가진 기기가 나타날 때까지 "내용을 가진 기기를 기다리는 중"으로 둔다. 빈 상태로 시드하지 않는다(§8 pull-before-seed).
3. 삭제는 서명되고 권한이 검증된 `Tombstone` 연산으로만 일어난다.
4. 멤버 제거는 권한 기기가 서명한 멤버십 레코드로만 일어난다. 어떤 피어의 멤버 목록에 내가 없다는 것은 제거가 아니다.
5. 저장 노드나 피어가 봉투를 주지 않는 것은 삭제가 아니다.

지금 허브 프로토콜 신호(`D/lib/sync/vaultProtocol.ts:72-141`)와의 대응은 다음과 같다.
| 허브 신호 | 뜻 | P2P에서의 대응 |
|---|---|---|
| `empty` | 서버에 그 문서 내용이 없다 | 연결 때 `Heads`로 문서별 보유 상태를 알린다. 상대에게 없는 내용을 보낸다 |
| `behind` | 내 기기에 서버가 모르는 연산이 있다 | 작성자별 체인 head를 비교해 상대에게 없는 봉투를 보낸다 |
| `revoked` | 문서 읽기 권한이 회수됐다(서버가 이름을 명시) | vault 단위 회수만 있다. 근거는 권한 기기의 `RemoveDevice`/`RemoveUser` 서명 레코드뿐이다. 문서 단위 회수는 폴더 키(D) 이후 |
| `tombstones` | 소프트 삭제됨 | 서명된 `Tombstone` 연산 |
| `covered` | 서버가 내가 보낸 state vector를 모두 보관했다(삭제 게이트용 확인) | `HeldAck`. 지금 `D/lib/sync/ackedSv.ts:1-14`가 서버 확인 state vector를 문서별로 늘려 가며 기록하는 것과 같은 방식으로, "다른 곳에 영속 저장된 것으로 확인된 state vector"를 기록한다 |

### 7.4 대량 변경 가드
지금 허브 경로의 받는 쪽 가드(`D/lib/sync/inbound.ts:376-398`)를 P2P registry 적용에도 그대로 쓴다. 한 번에 들어온 삭제가 `max(5, 20%)`, 이동이 `max(20, 30%)`를 넘으면 디스크에 반영하지 않고 사용자에게 묻는다. 허브에서는 서버 목록이 잘린 경우를 막는 장치였다. P2P에서는 악성이거나 고장 난 멤버의 정상 서명 대량 삭제를 막는 장치가 된다. registry 상태 자체는 수렴하고, 디스크 반영만 보류한다. 화면에는 "○○님이 노트 120개를 지웠습니다. 이 기기에도 적용할까요?"를 보여 준다.

### 7.5 삭제·복구 계약
- **삭제:** `Tombstone`을 받으면 파일을 지금과 같은 `.context/trash`(`R/checks.rs:78`)로 옮긴다. CRDT 상태와 봉투는 남긴다.
- **아직 확인받지 않은 로컬 변경:** 삭제할 파일에 `HeldAck`로 덮이지 않은 로컬 변경이 있으면 휴지통으로 옮기기 전에 그 변경을 먼저 내보내고, 복구 사본을 남긴다. 지금 허브의 삭제 게이트와 같은 원칙이다(`D/lib/sync/ackedSv.ts:4-8`).
- **보존:** 휴지통 항목은 기본 30일 뒤 각 기기에서 지운다(PRD §6.2). admin의 `Purge`는 기한 전 영구 삭제다.
- **복원:** `Restore` 연산. 원래 경로가 차 있으면 §7.2의 경로 충돌 규칙을 쓴다.
- **격리된 봉투:** 제거된 기기의 기준점 이후 봉투, 이중 발행으로 판정된 가지는 "확인이 필요한 변경"으로 관리자에게 보여 준다. 관리자가 받거나 버린다. 보존 기한이 지나면 기록만 남기고 지운다.
- **제거된 멤버의 기기:** 서명된 제거 레코드를 받은 정직한 클라이언트는 동기화를 멈추고 그 vault의 키와 P2P 봉투 저장소를 지운다. **디스크의 Markdown 파일은 지우지 않는다.** 평문은 어차피 회수할 수 없고, 위조되거나 탈취된 권한 기기의 제거로 사용자의 파일을 지우는 위험이 더 크기 때문이다. 화면에는 "이 vault에서 나갔습니다. 파일은 이 기기에 남아 있습니다 [이 기기에서 지우기]"를 보여 준다. 허브는 회수된 노트를 로컬에서 지운다(`D/lib/sync/inbound.ts:380-392`의 설명). P2P가 다르게 동작하는 이유를 제거 확인 화면에 적는다(PRD F5.5 "이미 받은 내용은 남는다").

### 7.6 P2P bootstrap 완료 기준 (PRD F5.4)
새 기기는 다음을 모두 만족해야 vault가 준비됐다고 본다.
1. 멤버십 head가 티켓의 head 이상이고 체인 검증을 통과했다.
2. registry head를 권한 기기에서 받았거나, 서로 다른 두 기기(D에서는 노드 포함)가 같은 head를 보고했다. 첫 빈 응답 하나로 끝내지 않는다.
3. registry의 각 문서에 대해 내용을 받았거나 "내용을 가진 기기를 기다리는 중"으로 표시했다.

합류할 폴더는 비어 있어야 한다. 비어 있지 않으면 합류를 거절하거나, 합류 뒤 기존 파일을 새 문서로 가져오는 선택지를 준다. 기존 로컬 파일을 이미 있는 `doc_id`에 시드하지 않는다.

### 7.7 `.context/` 처리
P2P의 봉투 저장소, head, 멤버십 체인, registry 상태, 격리 목록은 `.context/index.sqlite`의 **새 테이블**에 둔다. `.context/` 전체를 동기화하지 않고, 공유하는 것은 위에서 정의한 봉투뿐이다. `.context`는 지금처럼 트리 탐색과 감시에서 빠진다(`R/vault.rs:10`, `R/vault.rs:84`). 파일 신원 맵은 로컬 전용으로 남는다. 키는 `.context`가 아니라 키체인에 둔다(§4.1).

## 8. 기존 브리지 계약 유지 방법 (PRD F5.4, 리뷰 R05)

### 8.1 끼우는 자리
```
디스크 Markdown ⇄ [Rust 감시 150ms] ⇄ NoteBridge(Y.Doc, Y.Text "content") ⇄ 네트워크 어댑터
                                         (바꾸지 않음)                 허브: HocuspocusProvider
                                                                       P2P: P2P 문서 세션(신규)
```
P2P 문서 세션은 지금 `HocuspocusProvider`가 있는 자리(`D/lib/sync/syncManager.ts:260`)에 같은 역할로 들어간다. `NoteBridge`는 한 줄도 바꾸지 않는 것이 목표다.

### 8.2 지키는 계약
| 계약 | 지금 코드 | P2P에서 지키는 방법 |
|---|---|---|
| 디스크 Markdown이 영속 진실 | Rust 원자적 쓰기, 브리지 egest | P2P 계층은 Markdown을 직접 쓰지 않는다. 받은 내용은 항상 Y.Doc을 거쳐 브리지 egest(300ms)로만 디스크에 간다 |
| `Y.Text("content")`가 실시간 진실 | `D/lib/bridge/noteBridge.ts:190` | 받은 업데이트와 스냅샷 모두 같은 `doc_id`의 **같은 실시간 Y.Doc**에 `applyRemote`(`noteBridge.ts:1267-1268`, origin `remote`)로 적용한다. 별도 Y.Doc에 시드하지 않는다 |
| 에코 가드 1: 디스크 origin은 egest하지 않음 | `noteBridge.ts:249` | 그대로. 이 가드는 디스크로 다시 쓰는 것만 막는다 |
| 디스크 origin은 네트워크로 **보낸다** | 허브 provider는 origin과 관계없이 문서 업데이트를 보낸다 | P2P 세션은 origin이 `remote`이거나 `"persistence"`(로컬 로그 재생)인 트랜잭션만 빼고 모두 보낸다. 디스크, 에디터, AI 변경이 모두 동료에게 간다. `remote`를 다시 보내지 않는 이유는 에코 때문만이 아니다. 남의 연산을 내 서명으로 보내면 작성자가 바뀌기 때문이다 |
| 에코 가드 2: `lastWrittenHash` | `noteBridge.ts:778`, 쓰기 확인 후 해시 갱신 `noteBridge.ts:1041-1057` | 그대로. P2P는 이 값을 네트워크 ACK나 스냅샷 일치의 증거로 쓰지 않는다. 네트워크 확인은 `HeldAck`다 |
| 동시 디스크 읽기 보호 | `noteBridge.ts:712-728` | 그대로. 원격 업데이트가 디스크 읽기와 겹쳐도 지금과 같은 경로를 탄다 |
| 지연 시간 | 감시 150ms(`R/watcher.rs:46`), 수신 150ms·내보내기 300ms(`D/lib/bridge/types.ts:207-208`) | 바꾸지 않는다. P2P는 **송신 쪽에만** 짧은 묶음 창(가설 50ms, C1에서 측정 후 결정)을 둔다 |
| pull-before-seed | 로그인한 vault의 빈 문서는 받아오기 전에 시드하지 않는다(`noteBridge.ts:340-346`) | P2P vault는 "로그인한 vault"와 같이 다룬다. 받아오기 완료는 §7.6 기준을 쓴다. 로컬 전용 시드는 vault를 만드는 기기의 첫 시드에만 허용한다 |
| `diskBase`와 복구 사본 | `noteBridge.ts:52`, `402-409` | 그대로 |
| `.context/` 비공개 | `R/vault.rs:10` | §7.7 |
| 바이너리는 노트 CRDT에 들어가지 않음 | 확장자 목록 일치(CLAUDE.md) | C는 텍스트 전용. registry도 노트 확장자 문서만 다룬다 |

### 8.3 보내기와 받기의 원자성
- **보내기:** 로컬 업데이트는 지금처럼 평문 Yjs 로그에 먼저 저장된다. P2P 세션은 "봉투로 만든 state vector"를 문서별로 기록한다. 앱이 그 사이에 꺼져도 다시 켤 때 `Y.encodeStateAsUpdate(doc, 봉투로 만든 state vector)`로 빠진 부분을 봉투로 만든다. 봉투 생성 대기열을 따로 믿지 않는 것은 `ackedSv`가 서버 확인을 state vector로 기록하는 것과 같은 이유다.
- **받기:** Rust가 검증·복호화한 뒤 봉투와 head를 저장하고, 그다음에 WebView로 평문 업데이트를 넘긴다. WebView 적용 전에 꺼져도 다음 실행 때 저장된 봉투에서 다시 적용한다. Yjs 적용은 멱등이다.
- **저장 공간:** 평문 로컬 로그와 암호화된 봉투 저장소를 둘 다 둔다. 로컬 로그는 지금 계약(빠른 로드, 호환)을 위해, 봉투 저장소는 다른 기기에 전달하기 위해서다. 두 배 가까운 공간이 들 수 있으므로 C1에서 측정한다.

### 8.4 바뀌지 않음을 확인하는 방법
기존 데스크톱 테스트(`pnpm test`, `cargo test`)를 그대로 통과해야 한다. 여기에 C1의 브리지 시나리오(§10.4의 5번)를 더한다. 원격 편집 한 번에 받는 기기의 디스크 쓰기는 정확히 한 번이고, 10분 동안 편집이 없으면 쓰기가 0번이어야 한다(되먹임 없음). 외부 프로그램이 파일을 바꾸면 동료 화면에 반영되어야 한다.

## 9. 열린 질문 권고

### 9.1 Q1: C0의 기술 선택
§3의 결론대로 **Iroh 1.x 위 직접 구현**을 권고한다. p2panda는 재평가 후보로 두고, NextGraph와 Automerge 계열은 기각한다. C2 착수 전에 §3.3의 재평가 조건을 다시 확인한다.

### 9.2 Q4: 여러 관리자 기기의 동시 권한
**권고: C·D 동안 동시 다중 발행은 하지 않는다. 대신 "예비 권한 기기" 한 대를 지정할 수 있게 한다.**
- 동시 발행을 허용하면 끊긴 상태의 두 관리자가 서로 다른 멤버십과 키를 만든다. 이를 풀려면 p2panda-auth 같은 DAG 해결 규칙이나 MLS의 순서 서비스가 필요하다(리뷰 R01). 2~15명 팀이 얻는 이득에 비해 프로토콜과 검증 비용이 크다.
- 실제 불편은 "권한 기기가 꺼져 있으면 멤버 변경이 멈춘다"이다. 이것은 동시 권한 없이 다음으로 푼다.
  1. 다른 admin의 요청 대기열(§5.4)
  2. 권한 기기의 자발적 이양(`TransferAuthority`)
  3. **예비 권한 기기:** 권한 기기가 `SetStandby`로 다른 admin 기기 하나를 지정한다. 예비 기기는 관리자의 명시적 조작으로 즉시 인수할 수 있다. 인수 레코드는 같은 seq의 옛 권한 기기 레코드보다 우선한다(§5.5). 예비 기기는 모든 epoch 키를 함께 받는다.
  4. 복구 코드(§4.5)
- **재검토 기준:** C2 베타에서 "멤버십 요청이 24시간 넘게 대기한 비율"과 "예비 권한 기기 인수 횟수"를 기록한다. 대기가 흔하면 E 이후에 DAG 기반 다중 관리자(p2panda-auth의 strong removal 규칙, 또는 감사된 Keyhive)를 다시 평가한다.

### 9.3 Q5: 구 epoch 보존 기한
**권고: 기본 30일을 유지한다. 단, 무엇을 30일 보존하는지 다시 정의한다.**
- **30일 보존 대상은 구 epoch 봉투의 본문**이다. 새 epoch의 스냅샷이 그 봉투들을 덮고(§6.6), 그 스냅샷이 다른 곳에 영속 저장됐다는 `HeldAck`가 있을 때만 30일 뒤에 지운다.
- **epoch 키는 vault 수명 동안 보존한다.** 키는 작다. 현역 기기가 오래 꺼져 있다 돌아와 구 epoch로 만든 미전송 변경을 보내도 열 수 있어야 하고, 이력 보기와 내보내기, F7 전환에도 필요하다. 제거된 기기는 옛 키를 이미 갖고 있으므로 현역 기기가 키를 계속 보관해도 새로 새는 것은 없다.
- **미수령 기기의 `KeyPackage`는 기한 없이 보존한다**(§5.3).
- **그래서 30일은 데이터 손실 경계가 아니다.** 30일 넘게 꺼져 있던 현역 기기도 (1) 자기 미전송 변경을 새 epoch로 다시 봉인해 보내고, (2) 최신 스냅샷으로 따라잡는다. 30일이 지나 잃는 것은 제거된 기기의 기준점 이후 격리 봉투를 관리자가 검토할 기회뿐이다. PRD D4·§6.2의 "오프라인 복귀 한도"라는 표현을 이렇게 고친다.
- **관리자 설정 범위:** 7~365일. 디스크가 부족하면 기한 전 정리를 묻는다. legal hold는 범위 밖이다(PRD §6.2).

## 10. C1 같은 망(LAN) 실험 계획

### 10.1 목표
§4~§8의 계약이 실제 기기 2~3대에서 성립하는지, 그리고 비개발자가 같은 Wi-Fi에서 인터넷 없이 서로의 편집을 볼 수 있는지 확인한다. 결과는 `docs/reports/`에 C1 실험 보고서로 남긴다.

### 10.2 범위
| 포함 | 제외(이후 단계) |
|---|---|
| 텍스트 전용 새 vault 하나, 기기 2~3대 | 중계와 인터넷 경로(C2) |
| 기기 키, 복구 코드 생성과 내부 복구 시험 | 저장 노드(D) |
| 초대 티켓(링크·QR)과 승인, 단일 권한 기기 | 첨부(D) |
| 봉투 v1, 작성자 체인, 쓰기 권한 검증 | 게스트(reader) 출시(C2 이후). 단, 강등으로 검증 경로는 시험 |
| 멤버십 체인, 제거 1회와 3단계 키 교체 | 로컬 MCP(D), 허브 전환(F) |
| registry 연산과 충돌 규칙, 대량 변경 가드 | 여러 vault 동시 사용 다듬기, 모바일 |
| 스냅샷, 경쟁, watermark 삭제 | 공개 DNS 주소 게시 |
| 브리지 연결(§8), 화면의 연결 상태 3종 | |

네트워크 설정: `RelayMode::Disabled`, DNS 주소 조회 끔, `iroh-mdns-address-lookup` 켬, 수동 피어 주소 입력 가능.

### 10.3 환경
- 기기: macOS 15 이상(Apple silicon), Windows 11, Ubuntu 24.04 LTS 각 1대 이상. 같은 OS 두 대 조합도 시험한다.
- 망: (a) 인터넷 선을 뺀 가정용 공유기, (b) 기기 간 통신 차단(AP isolation)을 켠 AP, (c) 휴대폰 핫스팟, (d) 방화벽으로 UDP 차단, (e) Wi-Fi와 유선 혼합, (f) 절전 후 재개.
- macOS 로컬 네트워크 권한: macOS 15부터 앱의 같은 망 접근에 사용자 승인이 필요하고, 권한 요청 창이 뜨지 않는 사례가 Apple 개발자 포럼에 보고돼 있다(§13). `NSLocalNetworkUsageDescription`·`NSBonjourServices` 설정(PRD F5.6), 승인, 거부, 창이 뜨지 않음 세 경우를 모두 시험한다. 시험 기기는 깨끗한 상태로 준비한다.

측정 로그에는 본문, 제목, 티켓, 키를 넣지 않는다(PRD §6.7). 가설 값으로 LAN 편집 전파 p95 1초 이하, 발견 10초 이하를 두지만 목표 수치는 C1 기준선 측정 뒤에 정한다(PRD §11).

### 10.6 C1에서 정할 값
송신 묶음 창, 네트워크 스냅샷 기준(봉투 수와 바이트), padding 구간, 봉투·문서 크기 상한, 휴대폰 핫스팟과 AP isolation에서의 안내 문구, 수동 주소 입력 UX.

### 10.7 중단 기준
다음 중 하나면 C2 계획 전에 설계를 다시 본다. 흔한 가정용 공유기에서 mDNS 발견 실패가 잦다(수동 페어링 UX를 1급으로 올린다). 저장 공간이 평문 로그의 3배를 넘는다(봉투 저장소와 로컬 로그 통합을 검토한다). 2번 시나리오에서 확인된 편집 손실이 한 번이라도 나온다.

## 11. PRD 반영 제안과 리뷰 대응

### 11.1 PRD v2에 반영할 변경 제안
1. **D4:** "멤버십 epoch"를 멤버십 seq와 키 epoch(번호와 `key_id`)로 나눈다.
2. **D4:** 확정 조건을 "전원 ACK, 또는 관리자 선택과 기한 경과"로 바꾸고, 미수령 기기의 감싼 키는 기한 없이 보존한다고 적는다.
3. **D4, §6.2, Q5:** 30일은 구 epoch 봉투 본문의 보존 기한이며 키는 vault 수명 동안 보존한다. "오프라인 복귀 한도"라는 표현을 바꾼다.
4. **D4:** 제거·강등 레코드에 기기별 기준점을 넣고, 기준점 이후 봉투는 격리 후 관리자 확인으로 처리한다.
5. **F5.1:** 기기 키를 vault별로 파생하고, 전송 키를 서명 키와 분리한다. 복구 키를 권한 기기 위의 루트로 명시한다. OS 비밀 저장소가 없으면 P2P를 켜지 않는다.
6. **F5.3:** 제거된 멤버의 기기는 Markdown을 지우지 않고 동기화와 키만 지운다. 허브와 다른 이유를 적는다.
7. **F5.3:** 대량 변경 가드(`D/lib/sync/inbound.ts:376-398`)를 P2P에도 적용한다.
8. **Q4:** 동시 다중 권한 대신 예비 권한 기기 한 대.
9. **D2, D7:** C1과 사내망 전용 모드에서 DNS 주소 조회를 끈다. Iroh 기본 DNS 조회가 EndpointId 기록을 평문으로 게시한다는 사실을 관측 정보 목록에 넣는다.

## 12. 이 문서가 검증하지 않은 것
- 프로토타입, 테스트, 성능 측정, 실기기 네트워크 시험은 하지 않았다. 모든 수치 목표는 C1 이후에 정한다.
- 암호 crate(ed25519-dalek, x25519-dalek, hpke)의 감사 여부는 확인하지 않았다. C2 보안 리뷰에서 확인한다.
- NextGraph의 broker 없는 기기 간 동기화가 코드에 있는지는 확인하지 않았다. 문서와 릴리스 노트만 근거로 했다.
- Iroh mDNS의 Windows·Linux 동작과 macOS 권한 창 동작은 공식 문서에 없어 C1에서 확인한다.
- Yjs 14로 올라갈 때 업데이트 형식이 바뀌는지 확인하지 않았다(A6).
