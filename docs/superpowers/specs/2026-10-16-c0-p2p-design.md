# C0: 서버 없는 공유(P2P) 설계 검증

관련 문서: PRD v2 §4 D1~D4·D7, §5.5 F5, §5.7 F7, §9 C0, §12 Q1·Q4·Q5. v1 독립 리뷰 `docs/reports/PRD-REVIEW-team-second-brain-astra.md`(이하 "리뷰", 항목 번호 `R#`, `S#`, `F#`). 코드 경로 약어는 PRD와 같다. `S/` = `app/apps/server/src/`, `D/` = `app/apps/desktop/src/`, `R/` = `app/apps/desktop/src-tauri/src/`. 줄 번호는 커밋 `c10a7ea` 기준이다.

이 문서는 코드를 바꾸지 않는다. C1(같은 망 실험)을 시작해도 되는지 판단하는 데 필요한 계약을 정한다.

r2: 독립 검증 보고서(`docs/reports/C0-VERIFY-opus.md`, 이하 "검증", 항목 `H#`·`M#`·`L#`)의 상 4건과 중 11건을 반영했다. 상 4건은 각각 공격 시나리오 → 설계 변경 → 남는 한계 순으로 쓴 절이 있다(H1 §5.3.1, H2 §5.5.1, H3 §4.5.1, H4 §6.6.1). 항목별 반영 위치는 §14에 있다.

r3: 재검증 보고서(`docs/reports/C0-REVERIFY-opus.md`, 이하 "재검증", 항목 `N#`)의 상 2건(N1, N2)과 중·하 11건을 반영했다. 새 직접 구성을 늘리지 않고 규칙을 줄이는 쪽을 골랐다. (1) 복구 키는 권한 기기보다 엄격히 위이고, 복구 키는 복구 키로만 바꾼다(N1, §4.5.1). (2) 스냅샷은 작성자 서명 봉투를 결정적으로 재생한 결과와 같을 때만 쓴다. 기존 기기는 스냅샷을 live doc에 넣지 않는다(N2, §6.5). (3) 뒤집힐 수 있는 판정에는 되돌릴 수 없는 자동 조치를 붙이지 않는다. 격리 봉투는 자동으로 지우지 않고, 제거를 받은 기기는 봉인만 한다(N3~N5, §7.5). 반영 기록은 §14.5다.

r4: 3차 검증 보고서(`docs/reports/C0-REVERIFY2-opus.md`, 이하 "3차 검증")의 새 상 3건(N14~N16)만 반영했다. (1) 복구 인수는 멤버십 기준점을 갖고, 그 뒤 진 가지의 옛 권한·예비 기기 레코드는 보류 목록으로 간다. 동결 판정을 평가 순서에 넣는다(N14, §5.5.1-4·9). (2) 교체를 모르는 같은 세대 단독 복구 키 레코드는 무효이고, 같은 세대 이중 사용은 해소 레코드로 풀 수 있다(N15, §4.5.1-5). (3) 상태 해시 D는 통합 순서의 정규 인코딩이고, 받는 쪽이 스냅샷 본문에서 직접 다시 계산한다(N16, §6.4, §6.5-3, §7.6-4). 반영 기록은 §14.6이다.

## 0. 결론 요약

1. **기술 선택(§3, Q1):** **Iroh 1.x를 연결 계층으로만 쓰고, 봉투·멤버십·registry 프로토콜은 직접 구현한다.** NextGraph는 기각한다. v0.1.2-alpha.1 릴리스 노트(2025-11-08)가 "다른 사용자와 문서를 공유할 수 없다"고 적고 있고 그 뒤 릴리스 노트에도 이를 해소했다는 내용이 없으며, broker가 필수이며, 데이터 모델과 신원 체계가 우리 계약(`doc_id`, 디스크 Markdown 원본, 브리지)과 다르다. Automerge 계열(automerge-repo/samod + Keyhive/Subduction)은 Yjs 이력을 보존할 수 없어 기각한다. p2panda는 구조가 가장 잘 맞지만 0.x API이고 암호화 crate가 감사 전이라 채택하지 않는다. 설계 참고 대상으로 두고 1.0과 감사가 나오면 다시 평가한다.
2. **신뢰 구조(§4, §5):** 멤버십은 **권한 기기 한 대가 순서대로 쓰는 서명된 해시 체인**이다. 복구 코드는 그 위의 루트로, 권한 기기를 잃었을 때 권한을 넘기고 모든 epoch 키를 복호화할 수 있다. 여러 관리자 기기의 동시 발행은 하지 않는다. 대신 예비 권한 기기 한 대를 지정할 수 있게 한다(Q4). 멤버십 분기는 서명자 등급과 "제거·강등은 어느 가지에 있든 남는다"는 합집합 규칙으로 결정적으로 푼다. 예비 기기의 인수는 옛 권한 기기나 복구 키가 확인하기 전까지 잠정이고, 제거를 되돌리지 못한다(§5.5.1). 복구 키는 복구 키로만 바꾼다. 권한 기기는 몇 명이 함께 서명해도 복구 키를 이기지 못한다. 코드 없이 보유자가 나가면 권한 기기는 이후 epoch 키를 복구 키로 감싸지 않는다(§4.5.1).
3. **쓰기 권한(§5.2):** 봉투는 작성 기기 서명, 멤버십 기록상의 쓰기 역할, 제거 기준점(cutoff)을 모두 통과해야 Yjs에 적용된다. 콘텐츠 키를 가졌다는 사실은 쓰기 권한이 아니다(리뷰 R03).
4. **키 교체(§5.3):** 준비·배포·확정의 3단계다. 준비는 권한 기기 안에서 원자적으로 저장되고, 배포가 시작된 뒤에는 되돌리지 않고 앞으로만 재시도한다. 감싼 키(`KeyPackage`)는 권한 기기가 서명하고 HPKE 문맥에 vault·회전·수신자를 묶는다. 받은 기기는 서명과 `RotateBegin`의 키 확인값을 확인한 뒤에만 새 epoch로 쓴다(§5.3.1). 키를 못 받은 기기의 감싼 키는 기한 없이 보존한다.
5. **봉투(§6):** 헤더 전체가 AEAD의 인증 대상이다. 서명은 봉투 ID(헤더와 암호문의 해시)에 붙는다. 작성 기기별 단조 카운터와 직전 봉투 해시로 누락·되돌리기·분기를 탐지한다. 스냅샷은 Yjs 이진 상태다. 스냅샷은 부모 스냅샷과 작성자 서명 봉투를 결정적으로 재생한 결과와 상태 해시가 같을 때만 유효하고, 기존 기기는 스냅샷을 live doc에 적용하지 않고 압축 기준으로만 쓴다(§6.5). 업데이트는 **이 기기가 재생으로 검증한 스냅샷이 덮고, 작성자의 서명된 checkpoint가 그 뒤에 있는 것만** 지운다. 새 기기는 작성자별 checkpoint부터 체인을 검증한다(§6.6.1). Yjs clientID는 문서별로 처음 쓴 작성 기기에 묶는다(§6.3).
6. **삭제(§7):** 목록에 없다는 것은 삭제가 아니다. 삭제는 서명된 tombstone 연산으로만 일어나고, 지금 허브 경로의 대량 삭제 상한을 P2P에도 그대로 적용한다. 제거를 받은 기기는 동기화를 멈추고 봉인만 한다. 키, 봉투, outbox, Markdown을 자동으로 지우지 않는다. 격리 봉투도 자동으로 지우지 않는다(§7.5).
7. **브리지(§8):** P2P 어댑터는 열린 노트의 Hocuspocus provider 자리와 vault 동기화 엔진의 `DocUpdateSink` 자리(닫힌 노트의 hot·cold 경로) 둘 다에 들어간다. 봉투에는 이 기기의 로컬 트랜잭션만 담는다. `NoteBridge`, 에코 가드 두 개, 150/300ms 지연, `.context/` 비공개 규칙은 바꾸지 않는다. 디스크에서 온 변경도 네트워크로 보낸다.
8. **Q5(§9):** 30일은 **구 epoch 봉투 본문의 보관 정책**이지 오프라인 복귀의 데이터 손실 경계가 아니다. 키는 vault 수명 동안 보존한다.
9. **C1(§10):** 텍스트 전용 새 vault, 2~3대, 인터넷과 중계를 끈 같은 망에서 수렴, 손실 없음, 부정 테스트, 브리지 회귀(열린·닫힌 노트), 키 교체, 비개발자 과제 3(5명 중 5명), 가지치기 뒤 새 기기 합류를 판정한다.

### 2.2 공격자
| 공격자 | 할 수 있는 것 | 막는 방법 | 남는 위험 |
|---|---|---|---|
| **외부 네트워크** (같은 Wi-Fi 도청자, 경로상 능동 공격자) | 패킷 관찰·변조·차단, mDNS 응답 위조 | Iroh의 QUIC/TLS가 상대의 EndpointId(공개키)를 확인한다. 동기화 프로토콜은 멤버십에 등록된 전송 키만 받는다. 봉투 자체도 AEAD와 서명으로 보호된다 | mDNS로 기기 존재와 로컬 주소가 같은 망에 알려진다. 트래픽 시각과 크기. 차단에 의한 가용성 저하 |
| **중계** (공개 n0 중계, 사내 중계) | 암호화된 QUIC 패킷 전달, EndpointId·IP·시각·양 관찰, 전달 거부 | 중계는 종단 TLS 안쪽을 보지 못하고, 봉투는 그 안에서 한 번 더 암호화된다 | 관측 메타데이터, 가용성. **C1은 중계를 끈다** |
| **저장 노드** (D, 암호문 보관) | 봉투 저장과 제공, 누락, 지연, 과거 상태 제공, 그룹별로 다른 상태 보여 주기, 디스크 채우기 공격의 표적 | 서명으로 위조를 막는다. 작성 기기별 해시 체인과 카운터로 누락과 분기를 탐지한다. 멤버십 head는 줄어들지 않는다. 업로드와 **다운로드** 모두 멤버십에 있는 기기 공개키로 인증한다(§2.3 B5) | 다른 경로가 모두 막히면 최신 상태가 따로 있다는 것을 증명할 수 없다. 이때는 "동기화 미완료"로 표시만 한다 |
| **제거된 멤버** | 구 epoch 키와 이미 받은 평문 보유. 수정한 클라이언트로 구 epoch 봉투를 만들거나 옛 멤버십을 주장 | 새 epoch 키를 받지 못한다. 제거 기준점 이후의 봉투는 자동으로 받지 않고 격리한다(§5.2). 전송 키가 멤버십에서 빠져 연결이 거부된다 | 이미 받은 내용. 제거가 확정되기 전에 생긴 유출. 관측 가능한 메타데이터 |
| **분실·도난 기기** | 키체인이 잠금 해제된 상태로 빼앗기면 그 기기의 모든 키를 쓸 수 있다 | 관리자가 기기를 제거하면 키 교체가 일어난다(§5.3). 권한 기기를 잃었으면 예비 권한 기기나 복구 코드로 넘긴다 | 제거 전까지의 읽기와 쓰기. 디스크의 평문. E2EE는 디스크 암호화를 대신하지 않는다(PRD §6.7) |
| **악성 멤버 (읽기 전용)** | 수정한 클라이언트로 쓰기 시도 | 수신 기기가 역할을 검증해 거부한다(§5.2). 로컬 UI의 읽기 전용 표시(`D/lib/bridge/readOnlyDocs.ts:18-23`)는 편의일 뿐 보안 경계가 아니다 | 없음(읽기는 허용된 권한) |
| **악성 멤버 (쓰기 가능)** | 정상 서명으로 삭제·훼손. 같은 Yjs ID에 서로 다른 내용을 담아 피어마다 다르게 보내기(이중 발행) | 작성자 서명으로 책임을 남긴다. 대량 삭제는 받는 쪽에서 상한에 걸려 확인을 받는다(§7.4). 이중 발행은 작성자 해시 체인에서 탐지해 그 기기를 격리하고 관리자에게 알린다 | 정상 서명 편집 자체는 막지 못한다(되돌리기만 가능). 탐지 전에 이미 적용된 이중 발행은 피어 간 상태 차이를 남길 수 있다. Yjs는 BFT CRDT가 아니다 |
| **악성 멤버 (clientID 사칭, 스냅샷 위조)** | 피해자 V의 Yjs clientID와 다음 clock 범위로 자기 서명 업데이트를 먼저 보내 V의 진짜 연산을 중복으로 버려지게 하기. 남의 clientID 연산이나 삭제를 넣은 스냅샷 퍼뜨리기 | clientID를 문서별로 처음 쓴 작성 기기에 고정하고, 충돌하면 격리한다(§6.3-5). 스냅샷은 서명 봉투 재생 결과와 같을 때만 쓰고, 기존 기기는 live doc에 넣지 않는다(§6.5) | 먼저 도착한 기기에서는 V의 연산이 격리된다. 조용한 손실은 막지만 관리자 확인이 필요하다 |
| **악성 관리자(권한 기기)** | 아무나 멤버로 추가해 엿보기 | 막지 못한다. 권한 기기는 멤버십의 신뢰 루트다. 대신 모든 멤버십 변경이 모든 기기에 "보안 갱신" 알림으로 보인다 | 루트 신뢰 |
| **예비 권한 기기 탈취** | 권한 인수, 공격자 기기 추가, 전원 제거 | 확정되지 않은 인수는 권한 기기의 `RevokeStandby`로 무효가 된다. 인수는 제거를 되돌리지 못한다. 제거를 받은 기기는 봉인만 하므로 무효가 되면 그대로 돌아온다(§5.5.1, §7.5). 공지 후 24시간 대기는 정직한 클라이언트의 관례일 뿐 방어가 아니다 | 권한 기기가 반응하기 전까지는 루트와 같다(§2.4-3) |
| **권한 기기 탈취** | 멤버 추가·제거, 허수아비 admin 만들기, 과거 지점에서 분기한 레코드 쓰기 | 복구 키 레코드는 권한 기기 서명(공동 서명 포함)에 늘 이긴다. 복구 키 교체에는 현재 복구 키 서명이 필요하다(§4.5.1) | 복구 코드로 되찾기 전까지는 루트다. 이후 epoch 키를 복구 키로 감싸지 않게 바꿀 수는 있다(가용성 저하, §4.5.1) |
| **복구 코드를 가진 퇴사자, 새어 나간 복구 코드** | 복구 공개키로 감싼 epoch 키 열기, 권한 인수 | 보유자 기록. 보유자 제거 때 코드로 `RecoveryRotate`, 코드가 없으면 이후 epoch 키를 복구 키로 감싸지 않는다(§4.5.1) | 탐지되지 않은 유출은 다음 교체까지 유효(§2.4-8). 교체되지 않은 코드를 가진 사람은 권한을 가져갈 수 있다. 교체된 옛 코드로 교체 이전에서 분기한 레코드는 무효다(§4.5.1-5) |
| **초대 링크를 가로챈 사람** | 링크로 합류 요청, 요청자 이름 사칭 | 1회 사용, 관리자 승인, 원격 합류에도 짧은 지문 확인(§4.4) | 관리자가 지문 확인 없이 승인하면 막지 못한다 |
| **정상 멤버의 자원 고갈** | 봉투·스냅샷·checkpoint를 대량으로 만들어 저장 공간과 대역폭 소모 | 봉투·문서 크기 상한, 작성자별 저장 quota(값은 C1, §10.6) | quota 안의 낭비 |
| **앱 업데이트 채널** | 악성 바이너리 배포 | 범위 밖(A3). 앱 updater 서명 키가 사실상 모든 기기의 루트다 | — |

### 2.3 신뢰 경계
```
┌ 기기 ───────────────────────────────────────────────┐
│ WebView(TS): 평문 Y.Doc, 에디터, NoteBridge          │
│        │ 타입 있는 IPC: 평문 Yjs 업데이트와 상태만.  │
│        │ 비밀키는 넘어가지 않는다            [경계 B1]│
│ Rust 코어: 키체인, 봉투 서명·암호화·검증,            │
│            봉투 저장소(.context), Iroh 엔드포인트    │
└────────────────────────┬────────────────────────────┘
                         │ QUIC/TLS, EndpointId 인증  [경계 B2]
      ┌──────────────────┼───────────────────┐
  다른 멤버 기기 [B3]   중계(선택)        저장 노드(D, 키 없음)
  신뢰 루트: 복구 코드 ⟶ 권한 기기 ⟶ 멤버십 체인 [B4]
```
- **B1 (Rust ↔ WebView):** 비밀키는 Rust에만 있다. WebView는 자기 기기의 로컬 편집에 대해서만 서명을 요청할 수 있다. 노트 HTML 렌더링이 뚫리면 그 기기 이름으로 편집이 서명될 수 있으므로 기존 HTML sanitization과 CSP 경계(CLAUDE.md)는 P2P에서도 보안 경계다.
- **B2 (기기 ↔ 네트워크):** 네트워크로 나가는 것은 봉투(암호문)와 연결 메타데이터뿐이다.
- **B3 (멤버 ↔ 멤버):** 다른 멤버는 "인증됐지만 정직하다고 가정하지 않는" 상대다. 받은 모든 영속 봉투는 경로와 관계없이 서명과 권한을 검증한다.
- **B4 (신뢰 루트):** 멤버십은 권한 기기가 정하고, 권한 기기는 복구 코드가 정한다. 이 순서는 뒤집히지 않는다. 권한 기기가 서명한 레코드는 공동 서명이 있어도 복구 키 레코드를 이기거나 복구 키를 바꾸지 못한다(§4.5.1). 예비 권한 기기는 권한 기기가 철회하지 않는 한 권한 기기를 대신할 수 있고, 인수가 확정되면 철회할 수 없다(§5.5.1).
- **B5 (저장 노드 다운로드):** 노드는 업로드뿐 아니라 다운로드도 멤버십에 있는 기기 전송 키로 인증한다. "구 epoch 봉투를 멤버가 아닌 상대에게 주지 않는다"(§5.3)는 규칙은 노드에도 똑같이 적용된다. 구현은 D다.

### 2.4 막지 못하는 것
1. 이미 받은 평문과 사용자가 복사한 내용. 회수는 미래의 내용과 쓰기만 막는다(PRD D1).
2. 쓰기 권한이 있는 멤버의 정상 서명 편집. 되돌리기와 책임 추적만 가능하다(PRD D3).
3. 권한 기기, 예비 권한 기기, 복구 코드를 손에 넣은 공격자. 셋이 루트다. 예비 기기는 확정 전에 권한 기기가 철회하면 무효가 되고 제거를 되돌리지 못하지만(§5.5.1), 권한 기기가 반응하지 않는 동안은 루트와 같다. 권한 기기 도둑은 복구 코드를 무력화하지 못한다. 복구 코드로 권한을 되찾을 때까지 루트이고, 이후 epoch를 복구 코드로 열 수 없게 만들 수는 있다(§4.5.1). 복구 코드 사본을 가진 사람이 둘이면 서로 막을 수 있을 뿐 이길 수 없다. 이때 멤버십은 동결되고 탈출구는 "새 vault로 복사"다.
4. 관측 메타데이터: IP, 연결 시각, 트래픽 크기, 기기 공개키, mDNS가 같은 망에 알리는 기기 존재(PRD D7). Iroh 기본 DNS 주소 조회는 EndpointId를 키로 한 기록을 평문으로 게시한다(§3.3).
5. 모든 경로를 막는 공격자에 의한 가용성 저하. 이때 최신 상태가 존재하지 않는다는 증명은 불가능하고, 탐지는 정직한 피어와 다시 만날 때만 된다.
6. 기기의 디스크. `.context/index.sqlite`의 색인과 CRDT 상태는 평문에서 나온 데이터다. OS 디스크 암호화와 로그인 잠금은 사용자와 조직이 책임진다(PRD §6.7).
7. Yjs 수준의 비잔틴 행위 전체. 서명은 작성자를 인증할 뿐이다. 이중 발행은 탐지만 한다. Yjs의 삭제 범위(delete set)에는 삭제한 사람이 없으므로, 봉투 서명은 "이 기기가 이 삭제 범위를 보냈다"까지만 증명한다.
8. 탐지되지 않은 복구 코드 유출. 다음 `RecoveryRotate`까지의 모든 epoch를 연다. 옛 복구 코드는 교체 전 epoch를 계속 연다(§4.5.1).
9. 각 기기가 제거를 알기 전까지의 유출. 오프라인이던 기기 O가 제거 사실을 모른 채 제거된 X와 먼저 만나면, O가 그사이 쓴 내용이 X에게 간다. 연결할 때 멤버십을 먼저 맞추는 규칙(§7.1 `Heads`)은 이 창을 줄일 뿐 없애지 못한다.
10. 키 교체가 있었다는 사실과 그 시각. 멤버십 레코드 헤더와 `keypkg` 봉투로 드러난다.

## 3. 기술 선택 평가 (Q1)

모든 버전과 날짜는 2026-10-16에 crates.io API, npm registry, 공식 문서·저장소에서 직접 확인했다(출처는 §13).

### 3.1 후보
- **NextGraph:** 자체 commit DAG, 지갑 신원, broker 망을 가진 local-first 플랫폼. Yjs와 Automerge를 브랜치 모델로 지원한다.
- **Iroh 1.x 위 직접 구현:** Iroh는 연결(주소 탐색, 경로 선택, QUIC/TLS)만 맡고, 봉투·멤버십·registry는 우리가 정의한다.
- **p2panda 0.7.1:** Iroh 기반 Rust 모듈 묶음. CRDT와 무관한 바이트 로그, 그룹 권한(p2panda-auth), 그룹 암호화(p2panda-encryption)를 제공한다.
- **Automerge 계열:** automerge-repo(JS)와 Rust 구현 samod, 접근 제어 Keyhive(BeeKEM), 동기화 Subduction.

조사 중 확인했지만 비교에서 뺀 것: secsync(npm 최신 0.5.0이 2024-06-04, 중앙 서버 전제), y-sync(crates.io 0.4.0이 2023-11-17, 서버-클라이언트 동기화 프로토콜이고 E2EE·멤버십 없음), iroh-willow(0.0.1, 2025-02-07).

### 3.3 결론과 근거
**Iroh 1.x 위 직접 구현을 채택한다.** 근거는 세 가지다.
1. 평가 기준 중 Yjs 이력 보존과 순수 LAN을 둘 다 충족하는 후보는 직접 구현과 p2panda뿐이다. NextGraph는 broker 없이 기기끼리 동기화하는 경로가 문서에 없고 공유 자체가 아직 연결되지 않았다. Automerge 계열은 CRDT 교체가 필요하다.
2. p2panda는 우리와 같은 Iroh 위에 있어 기술적으로 가깝다. 그러나 p2panda-net은 2024-12-06의 0.1.0을 포함해 0.x로만 12개 버전이 나왔고(auth·encryption은 2025-07-07의 0.4.0부터 8개), API 안정성을 약속하지 않는다. p2panda-auth의 동시 관리자 해결 규칙은 우리가 일부러 피하기로 한 다중 권한 모델(Q4)이다. p2panda-encryption은 감사 전이며 README가 고위험 용도를 권하지 않는다. 바이트 로그 위에 우리 봉투를 다시 얹으면 헤더와 서명이 이중이 된다. 지금 의존하면 얻는 것보다 따라가야 할 변경이 크다.
3. 직접 구현에서 우리가 새로 만드는 것은 봉투, 단일 작성자 멤버십 체인, registry 연산이다. 셋 다 이미 허브 모드에서 서버가 하던 판단을 서명과 체인으로 옮기는 일이고, 지금 브리지·삭제 가드·SQLite 로그를 그대로 쓴다. 검증 반영으로 비용이 더 붙었다. Rust 쪽 Yjs 파싱(clientID 고정 §6.3-5, 파싱 한도 §5.2-7), 작성자 checkpoint(§6.6.1), `KeyPackage` 인증(§5.3.1), 분기 규칙(§5.5.1)이다. 그래도 p2panda를 따라가는 비용보다 작다고 본다. 재평가 때는 p2panda의 mDNS crate 버전(0.5)이 우리 쪽(0.6)과 다르다는 점도 함께 본다.

**쓰는 Iroh 구성:** `iroh` 1.3.x(Endpoint, Router, ALPN별 프로토콜), `iroh-mdns-address-lookup` 0.6.x(같은 망 탐색), `RelayMode::Disabled`(C1, 사내망 전용) 또는 `RelayMode::Custom`(사내 중계). 초대 티켓 안의 주소 표현은 Iroh의 티켓 crate(`iroh-tickets` 1.0.0, "Tickets as signaling for iroh")를 쓸 수 있는지 C1에서 확인한다.

**Iroh 밖에서 더 쓰는 구성:** Rust에서 Yjs 업데이트의 struct와 clientID를 읽기 위해 `yrs` 0.28.x를 쓴다(MIT). 적용은 지금처럼 WebView의 JS Yjs가 하고, Rust는 검사만 한다. JS Yjs 13.6의 v1 인코딩과 같은 결과를 내는지 C1에서 왕복 테스트로 고정한다.

**vault별 전송 키의 비용(검증 L5):** 전송 키를 vault마다 두면 Iroh endpoint와 mDNS 광고도 vault 수만큼 생긴다. 같은 망에서는 한 기기가 가진 vault 수가 드러나고 소켓도 늘어난다. C1은 vault 하나라 영향이 없다. C2 전에 "vault마다 endpoint"와 "endpoint 하나에 vault별 ALPN"(기기 연결성은 드러나지만 소켓은 하나)을 비교한다.

**쓰지 않는 Iroh 구성:** `iroh-docs`(0.101.0, 자체 복제 key-value 모델이고 우리 멤버십·암호화와 겹친다), `iroh-gossip`(0.101.0, 영속 데이터를 gossip에 맡기지 않는다. 15명 규모는 온라인 피어 직접 연결로 충분하다. presence 같은 일시 메시지용으로만 나중에 검토한다), `iroh-blobs`(첨부는 D. 2026-10-08에 보안 수정이 있었으므로 D에서 다시 평가한다).

**Iroh의 메타데이터 주의점:** 기본 DNS 주소 조회는 EndpointId를 키로 한 기록을 평문으로 게시한다. Iroh 팀의 "blinded address lookup"은 아직 개념 증명이며 공개키를 비밀로 만드는 것은 로드맵에 없다고 밝혔다. 그래서 (1) C1과 사내망 전용 모드는 DNS 주소 조회를 쓰지 않는다. (2) 전송 키를 기기 서명 키와 분리하고 vault마다 따로 둔다(§4.1). (3) C2에서 공개 DNS 게시 여부를 다시 정한다. 기본안은 게시하지 않고 초대 티켓과 vault 안의 암호화된 주소 교환으로 상대 주소를 얻는 것이다.

**재평가 조건:** p2panda 1.0과 암호화 감사 공개, Keyhive·Subduction의 감사와 Yjs 지원 확인, NextGraph의 공유 기능과 안정 포맷. 셋 중 하나라도 생기면 C2 착수 전에 같은 표로 다시 본다.

**직접 구현의 위험과 완화:** 프로토콜 설계 오류가 가장 큰 위험이다. 표준 구성(Ed25519, RFC 9180 HPKE, XChaCha20-Poly1305, BLAKE3)만 쓰고, 멤버십을 단일 작성자 체인으로 작게 유지하고, C1에서 속성 기반 테스트와 장애 주입을 하고, C2 전에 외부 보안 리뷰를 받는다.

**표준을 그대로 쓰는 부분과 직접 구성:**
- 표준 그대로: Ed25519 서명, HPKE Base 모드(RFC 9180) DHKEM(X25519, HKDF-SHA256)/HKDF-SHA256/ChaCha20-Poly1305, XChaCha20-Poly1305 AEAD, BLAKE3 해시와 `derive_key`, HKDF. 서명과 공개키 암호화에 레이블과 문맥을 붙이는 방식은 MLS의 `SignWithLabel`·`EncryptWithLabel`(RFC 9420 §5.1.2, §5.1.3)을 따른다.
- **직접 구성(외부 리뷰 우선 대상):** (1) 단일 작성자 멤버십 체인과 분기 규칙(§5.5.1, p2panda-auth의 strong removal 원칙을 참고), (2) `KeyPackage` 서명과 키 확인값(MLS Welcome과 `confirmation_tag`를 본뜸, §5.3.1), (3) 복구 키 에스크로와 교체(§4.5.1), (4) 작성자 해시 체인·문서별 연결·checkpoint(§6.6.1), (5) clientID 고정(§6.3-5), (6) 예비 인수 확정(§5.5.1-8, MLS의 커밋 확정을 순서 서비스 없이 옮김), (7) 스냅샷의 재생 검증과 상태 해시(§6.4, §6.5). (6)(7)은 r3에서 더했다. 대신 r2의 규칙 여섯 개(복구 키 교체의 두 사람 서명과 단독 서명 예외, 인수의 notice 해시 조건, 복구 키 이중 사용의 해시 선택, checkpoint clientID 목록, 격리 만료 삭제, 제거 시 자동 삭제)를 지웠다.
- MLS 자체를 쓰는 안: OpenMLS(0.9.1, 2026-10-07)로 권한 기기를 유일한 committer(순서 서비스)로 두면 키 교체와 멤버십을 표준으로 맞출 수 있다. C1에서는 쓰지 않는다. MLS 그룹 상태, Yjs 봉투, 오프라인 수령 기한 없는 보관(§5.3)을 함께 맞추는 비용이 크고, C1의 질문은 연결과 브리지이기 때문이다. C2 보안 리뷰 때 이 안을 직접 구성 (1)(2)의 대안으로 함께 검토한다.

## 4. 기기 신원과 복구 키

### 4.1 키 구성
| 키 | 방식 | 용도 | 보관 | 교체 |
|---|---|---|---|---|
| 기기 마스터 비밀 | 256비트 무작위 | vault별 기기 키를 파생하는 뿌리 | OS 키체인 | 복제 감지나 분실 시 새로 만든다 |
| 기기 서명 키 | Ed25519, 마스터에서 HKDF(`"ib/p2p/sign/v1" ‖ vault_id`)로 파생 | 봉투, 멤버십 요청, ACK 서명. `device_id` = 공개키 | 파생 결과는 메모리에만 | 마스터와 함께 |
| 기기 암호화 키 | X25519, 같은 방식으로 파생. HPKE(RFC 9180) DHKEM(X25519, HKDF-SHA256) / HKDF-SHA256 / ChaCha20-Poly1305 | epoch 키를 감싸 받기 | 메모리 | 마스터와 함께 |
| 전송 키 | Ed25519(Iroh EndpointId) | QUIC/TLS 연결 인증 | OS 키체인 | 서명 키와 **독립적으로** 바꿀 수 있다(추적 방지) |
| epoch 콘텐츠 키 | 256비트 대칭, XChaCha20-Poly1305 | 봉투 payload 암호화 | 기기 암호화 키로 감싸 `.context`에, 또는 키체인 | 제거·강등·의심 시 새 epoch |
| 복구 키 | 256비트 비밀. HKDF로 Ed25519 복구 서명 키와 X25519 복구 암호화 키를 파생 | 권한 이양, 모든 epoch 키 복호화 | **사용자가 오프라인 보관.** 앱에는 공개키만 | 권한 기기가 교체할 수 있다 |

- **vault별 파생 이유:** 한 기기가 여러 vault에 있어도 노드·중계 운영자가 같은 기기임을 연결하지 못하게 한다. 키체인 항목은 마스터 하나로 끝난다. 서명 키와 전송 키를 나누는 이유도 같다. 전송 키는 mDNS와 DNS 조회에 공개되지만 서명 키는 봉투에만 나타난다.
- **보관:** 지금 `R/keychain.rs`의 OS 비밀 저장소를 재사용한다(서비스 이름 `com.infinitebrain.desktop`, `R/keychain.rs:29`). 이 모듈은 지금 세션 토큰 저장용이다. OS 비밀 저장소가 없어 메모리 대체본으로 떨어지는 경우를 이미 감지한다(`R/keychain.rs:43-62`). 다만 `store_persists()`는 `UntilReboot`도 영속으로 친다(`R/keychain.rs:43-48`). 지금 빌드는 Secret Service만 켜 있어 문제가 없지만, keyutils(`UntilReboot`)를 켜면 재부팅마다 기기 마스터 비밀이 사라지고 기기 신원이 조용히 바뀐다. **P2P 기기 키는 지속성이 `UntilDelete`인 저장소에만 만들고, 이 조건을 단위 테스트로 고정한다(검증 M7). 조건을 못 맞추면 기기 키를 만들지 않는다.** 화면에는 "이 기기에는 안전한 저장 공간이 없어 서버 없이 공유를 켤 수 없습니다"와 OS별 해결 방법을 보여 준다(PRD F5.6 Linux).
- **기기 인증서:** `DeviceCert{vault_id, user_id, device_id, hpke_pk, transport_id, created_at, self_sig}`. 자기 서명으로 세 공개키를 서로 묶고, 권한 기기가 멤버십 체인의 `AddDevice` 레코드로 승인한다. 기기 이름과 사용자 프로필은 암호화된 멤버십 본문에만 들어간다(D7).

### 4.2 사용자와 기기
- 구조는 PRD F5.1대로 `사용자 → 승인된 기기 → vault 멤버십과 역할`이다. `user_id`는 합류 때 정하는 128비트 무작위 값이다. 사용자 단위 키는 두지 않는다. 멤버십 체인이 기기와 사용자의 관계를 정하므로 따로 필요하지 않다.
- **기기 하나 제거**는 `RemoveDevice`, **사용자 전체 제거**는 그 사용자의 모든 기기를 한 레코드로 지우는 `RemoveUser`다. 둘 다 키 교체를 일으킨다(§5.3).
- **같은 사용자의 새 기기:** 기존 기기에서 [기기 추가] → 새 기기가 QR이나 링크로 받은 기기 연결 티켓으로 요청 → 기존 기기가 보증 서명 → 관리자 승인 → 권한 기기가 `AddDevice`. `AddDevice` 본문에 보증한 기기(`vouched_by`)를 남긴다.
- **자동 승인은 C에서 두지 않는다(검증 M8).** "같은 사용자의 보증이면 자동 승인"을 켜면, 노트북 L을 훔친 사람이 L2를 추가한 뒤 관리자가 L만 제거해도 L2가 남는다. D 이후 다시 검토할 때는 `RemoveDevice` 확인 화면에 그 기기가 보증한 기기를 함께 보여 주고 기본값으로 함께 제거한다.
- **마지막 관리자 제거 금지, 권한 기기 이양**은 PRD F5.1대로다. 이양은 `TransferAuthority` 레코드다.

### 4.3 복제·디스크 복원 감지
디스크를 백업에서 복원하거나 기기를 통째로 복제하면 같은 기기 키와 옛 카운터로 서명이 다시 시작된다. 대응은 두 겹이다.
1. **nonce 재사용을 구조적으로 없앤다.** 봉투는 192비트 무작위 nonce를 쓰는 XChaCha20-Poly1305로 암호화한다. 카운터가 되돌아가도 nonce는 겹치지 않는다.
2. **카운터 분기를 탐지한다.** 연결할 때 피어가 "내가 가진 당신의 마지막 봉투(카운터, 해시)"를 알려 준다. 로컬 head보다 앞서 있거나 같은 카운터에 다른 해시면 이 기기는 복원본이다. 기기는 서명을 멈추고, 새 마스터 비밀을 만들고, 권한 기기에 `ReplaceDevice{old, new}`를 요청한다(같은 사용자의 다른 기기 보증 또는 관리자 승인). 화면에는 "이 기기를 다시 등록해야 합니다"만 보여 준다.
3. 오프라인 중에 이미 서명한 봉투는 버리지 않는다. 복원본이 새로 만든 Yjs 연산은 새 세션의 clientID를 쓰므로 Yjs ID가 겹치지 않는다. 수신 측은 체인 분기를 "복원 또는 이중 발행"으로 표시하고, 두 가지의 Yjs ID 범위가 겹치지 않으면 둘 다 받는다. 겹치면 이중 발행으로 보고 §6.3 규칙 3으로 처리한다.
4. `ReplaceDevice` 때 권한 기기는 옛 기기 몫의 미수령 `KeyPackage`와 지금까지의 모든 epoch 키를 새 기기의 HPKE 공개키로 다시 감싸 보낸다(§5.3.1 형식, 검증 L2). 옛 기기는 `RemoveDevice`와 같이 취급한다.

### 4.4 초대 티켓 (F1.2, 리뷰 S03)
- **내용:** `{vault_id, invite_id, role, expires_at, issuer_device_id, issuer_addr(EndpointAddr), membership_head(seq, hash), secret(32B)}`에 발급 기기가 서명한다. 링크(`infinitebrain://` 딥링크의 fragment)나 QR로 통째로 전달한다. 짧은 코드는 쓰지 않는다(PRD F1.2).
- **합류:** 새 기기는 티켓의 주소와 EndpointId로 발급 기기에 직접 연결한다(같은 망은 mDNS, C2부터 중계). TLS가 EndpointId를 확인하므로 중간자가 끼어들 수 없다. 새 기기는 `JoinRequest{invite_id, DeviceCert, MAC(secret, DeviceCert)}`를 보낸다.
- **소비:** 발급 기기가 MAC을 확인하고 SQLite 트랜잭션 하나로 티켓을 "사용됨"으로 바꾼다. 같은 `(invite_id, device_id)` 재요청은 같은 결과를 돌려준다. 다른 기기가 같은 티켓을 쓰면 "이미 사용된 초대"로 거절한다. 발급 기기가 권한 기기가 아니면 승인 요청을 권한 기기에 전달하고, 새 기기는 "승인을 기다리는 중"을 본다.
- **승인:** 관리자가 [승인]을 누르면 권한 기기가 `AddDevice`를 쓰고, 현재까지의 **모든** epoch 키를 새 기기의 HPKE 공개키로 감싸 보낸다. vault 단위 읽기 권한은 이력 전체를 포함하기 때문이다(허브에서 새 멤버가 기존 노트를 모두 읽는 것과 같다). 승인 전에는 키를 주지 않는다. 감싸는 방식과 받는 규칙은 §5.3.1이다. 키마다 그 epoch `RotateBegin`의 키 확인값으로 확인한다.
- **신선도:** 새 기기는 티켓의 `membership_head` 레코드를 포함하지 않는 멤버십 레코드 집합을 받아들이지 않는다. 그 레코드가 분기의 진 쪽에 있더라도 집합 안에 있어야 하고, head는 §5.5.1 규칙으로 고른다. 이것이 처음 들어오는 기기의 되돌리기 방어다.
- **노출 방지:** 티켓 비밀은 로그, 지원 번들, 클립보드 기록에 남기지 않는다. 사용 후 클립보드를 비운다. 만료는 1회 사용을 대신하지 않는다.
- **지문 확인:** 같은 장소에서 합류할 때는 두 화면에 같은 그림 4개를 보여 주고 같은지 묻는다. 원격 합류에도 같은 그림 4개를 보여 주고, 요청자가 전화나 메신저 같은 다른 경로로 같은 그림을 알려 주도록 관리자에게 안내한다(검증 L4). 요청자 이름은 요청자가 스스로 적는 값이라 확인 근거가 아니다.

### 4.5 복구 키
- **발급:** vault를 만들 때 복구 키를 만든다. 화면은 PRD §0.1의 "복구 코드 저장하기" 한 장이다(인쇄, 파일 저장, 비밀번호 관리자). 마지막 몇 단어를 다시 입력해 저장했는지 확인한다. 표시 형식(단어 24개 등)은 C2 UX에서 정한다.
- **genesis 레코드:** `{vault_id, creator_device, recovery_gen = 0, recovery_sign_pk, recovery_hpke_pk, authority = creator_device, key_confirm(epoch 0)}`에 생성 기기와 복구 키가 함께 서명한다. epoch 0은 `RotateBegin`이 없으므로 genesis가 그 역할을 한다. epoch 0의 `key_id`는 genesis 해시 앞 16바이트이고, `key_confirm`은 §5.3.1-3 식에서 `rotation_id` 자리에 genesis 해시를 넣는다(재검증 N9). 이 레코드가 vault의 신뢰 루트다. 암호화된 본문의 `recovery_holders`에 생성자를 넣는다(§4.5.1).
- **할 수 있는 일:** (1) `TransferAuthority`에 서명해 새 권한 기기를 정한다. (2) 각 epoch 키는 **현재 세대**의 복구 공개키로도 감싸 두므로, 복구 코드와 암호문(다른 멤버, 노드, 백업 어디서든)만 있으면 그 세대 이후 내용을 복원한다. 교체 때 만드는 `RecoveryArchive`로 이전 이력도 연다. `recovery_escrow = off`인 동안의 epoch는 열지 못한다(§4.5.1-3).
- **쓰면 일어나는 일:** 복구 코드로 권한을 넘기면(`TransferAuthority`) 새 권한 기기는 바로 다음 레코드로 같은 코드를 써서 `RecoveryRotate`를 하고 새 epoch로 키를 교체하며, 모든 기기에 알린다. 복구 코드가 새어 나갔을 가능성을 기본으로 가정하기 때문이다. 두 레코드는 이어지므로(`RecoveryRotate`가 인수 레코드를 안다) 같은 세대의 이중 사용이 아니다.
- **교체:** §4.5.1. 옛 복구 코드는 이미 감싼 옛 epoch 키를 계속 열 수 있다. 이것은 막을 수 없다.
- **모두 잃은 경우:** 권한 기기와 예비 권한 기기와 복구 코드를 모두 잃으면 멤버십은 영구히 멈춘다. 남은 멤버는 현재 epoch에서 계속 편집할 수 있지만 누구도 추가·제거하지 못한다. 탈출구는 "새 vault로 복사"다. 아무 멤버나 Markdown을 내보내 새 vault를 만들고 다시 초대한다. 이 사실을 vault를 만들 때 고지한다(PRD F5.1).

#### 4.5.1 복구 키 보유자가 나갈 때 (검증 H3)
**공격 시나리오.** 복구 코드는 vault를 만든 관리자 개인이 종이나 파일로 보관한다. 그 관리자가 퇴사해 `RemoveUser`가 되어도 r1에서는 복구 키가 바뀌지 않았다(교체는 "할 수 있다"였다). 새 epoch 키는 모두 같은 복구 공개키로도 감싸므로, 퇴사자는 암호문만 얻으면(공모 멤버, D의 노드) 미래 내용을 계속 읽는다. 복구 키 레코드는 분기에서 이기므로 언제든 권한도 가져갈 수 있다. 사진으로 찍혀 새어 나간 복구 코드도 같다. 아무도 모르게 영구적인 읽기 권한이 생긴다.

**설계 변경.**
1. **보유자 기록:** 멤버십 본문에 `recovery_holders`(user_id 목록)를 둔다. 앱이 복구 코드를 화면에 보여 준 사용자(생성자, 교체 때 새 코드를 저장한 admin)는 자동으로 들어간다. 앱은 복구 비밀을 저장하지 않아 종이를 본 사람을 알 수 없으므로, 관리자가 "이 코드를 맡긴 사람"을 직접 추가할 수 있게 한다.
2. **epoch 키 래핑:** epoch 키는 **현재 세대(`recovery_gen`)의 복구 공개키로만** 감싼다. `RotateBegin`이 `recovery_gen`을 담고, 복구용 `KeyPackage`는 §5.3.1과 같이 권한 기기가 서명하며 HPKE 문맥에 `recovery_gen`을 묶는다. `RecoveryRotate{gen g→g+1, 새 recovery_sign_pk, 새 recovery_hpke_pk}`는 (a) 새 공개키를 체인에 올리고, (b) 그때까지의 모든 epoch 키를 새 복구 공개키로 감싼 `RecoveryArchive` 하나를 만들어 새 코드만으로 전체 이력을 열 수 있게 하고, (c) 그 뒤 epoch 키를 옛 공개키로 감싸지 않는다. 옛 세대의 복구용 패키지는 지운다. 이미 가져간 사람에게는 소용없지만 이후 유출 범위를 줄인다.
3. **보유자 제거:** `recovery_holders`에 있는 사용자를 `RemoveUser`하는 화면은 남은 admin에게 복구 코드 입력을 요청한다. (a) 코드를 입력하면 권한 기기는 같은 준비 트랜잭션(§5.3)에 `RecoveryRotate`를 넣고, K(e+1)은 새 복구 공개키로만 감싼다. 새 코드는 "복구 코드 저장하기" 흐름으로 안내하고 저장 확인 전까지 관리자 화면에 경고를 둔다. (b) 코드를 입력할 수 없으면(보유자가 유일한 사본을 갖고 나감) 같은 트랜잭션에 `SetPolicy{recovery_escrow = off}`를 넣는다. 그 뒤 epoch 키는 어떤 복구 공개키로도 감싸지 않는다. 퇴사자가 암호문을 얻어도 새 epoch는 열지 못한다. 화면에는 "복구 코드를 바꾸지 못했습니다. 이 사람은 코드로 관리 권한을 가져갈 수 있습니다. 코드를 돌려받거나 새 vault로 복사하세요"를 보여 준다. 다른 기기는 이 규칙을 강제하지 않는다(제거 자체를 막는 쪽이 더 위험하다). 대신 보유자 제거에 둘 다 빠져 있으면 모든 admin에게 "복구 코드가 바뀌지 않았습니다"를 띄운다.
4. **교체 서명(재검증 N1):** `RecoveryRotate`는 **현재 세대 복구 키**와 권한 기기가 함께 서명한다. 권한 기기 단독 서명이나 다른 admin의 공동 서명으로는 쓸 수 없다. r2의 "(b) 다른 admin 공동 서명"과 "admin 한 명이면 단독 서명" 예외는 없앤다. 루트를 그보다 낮은 자격으로 바꿀 수 있게 하면 루트 순서(B4)가 뒤집히기 때문이다. `SetPolicy{recovery_escrow}`는 복구 키를 바꾸지 않으므로 권한 기기 혼자 쓸 수 있고, 켜는 것은 그것을 아는 `RecoveryRotate`로만 한다.
5. **복구 등급 안의 순서(3차 검증 N15):** 복구 키 레코드는 권한 기기·예비 기기가 서명한 어떤 레코드보다 우선한다(§5.5.1-3). 권한 기기 레코드가 복구 키 레코드를 무효로 만드는 경우는 없다. 같은 세대 g 안에서는 다음과 같이 정한다. r3의 "(교체 포함) 이중 사용이면 동결"은 정상 교체된 옛 코드를 영구 동결 스위치로 만들었으므로 없앤다.
   (a) **두 자격 교체:** `RecoveryRotate(g→g+1)`(RR)는 g 키와 권한 기기가 함께 서명한다(4). 이때 공동 서명한 권한 기기가 그 RR이 아는 세대 g 인수로 권한을 얻은 기기라면, 그 RR은 코드 하나로 만든 것이므로 (b)의 단독 레코드로 센다. 그래서 코드만 가진 사람도, 기기만 가진 사람도 두 자격 RR을 만들 수 없다.
   (b) **단독 레코드는 무효:** 두 자격 RR을 모르는 같은 세대 g 단독 레코드(g로 서명한 인수·확정, 그 인수로 생긴 권한 기기와 쓴 RR)는 이중 사용이 아니라 **무효**다. 교체된 옛 코드로 RR 직전에서 분기한 레코드가 이렇게 진다. r2의 "옛 코드는 진다"를 되살린 것이다. RR에는 g 서명이 필수이므로 N1은 다시 열리지 않는다.
   (c) **같은 세대 안의 해소:** (b)로 정해지지 않고 서로 모르는 세대 g 사용이 둘 이상 남으면 이중 사용이다. 해시로 고르지 않고 멤버십을 동결한다(§5.5.1-3). 같은 세대 g 복구 키로 양쪽을 아는 **해소 레코드**를 써서 한쪽을 고르면 동결이 풀린다. 해소 레코드가 다시 갈리면 동결을 유지한다. 정직한 재입력(기기 P1에서 코드를 입력했지만 전파되지 않아 P2에서 다시 입력)은 이렇게 풀린다. 다시 갈리는 것은 현재 코드 보유자가 둘인 진짜 분쟁이고, 탈출구는 새 vault로 복사다(§2.4-3).
   (d) `RecoveryRotate(g→g+1)`를 아는 레코드에서는 (c)의 해소 레코드를 빼고 세대 g 서명이 더 이상 유효하지 않다.
   (a)의 "인수로 생긴 권한 기기" 조건은 보고서 문장에 더한 것이다. 이것이 없으면 옛 코드 보유자가 자기 가지에서 g 인수로 권한 기기를 만들고 RR까지 쓴 뒤 해소 레코드를 계속 갈라 시나리오 a의 영구 동결을 되살릴 수 있다.
6. **정기 교체 알림:** 기본 1년마다 admin에게 교체를 권한다. 값은 C2에서 정한다.

**N1 공격과 이 규칙의 결과(재검증 N1).** 도둑이 권한 기기 A를 가졌고, 소유자는 복구 코드로 인수 레코드 R(prev = h)을 쓴다. r2에서는 도둑이 R을 본 뒤 prev = h인 `RecoveryRotate`를 단독 서명(admin 한 명 vault)이나 허수아비 admin 공동 서명으로 써서 R을 영구히 이길 수 있었다. r3에서는 도둑이 현재 세대 복구 키 없이 `RecoveryRotate`를 쓸 수 없고, A가 쓴 다른 레코드는 R에 진다. 그래서 §4.5.1-5와 §5.5.1-4는 더 이상 충돌하지 않는다. 앞의 것은 복구 등급끼리의 순서이고, 뒤의 것은 복구 등급이 권한 기기 등급을 이길 때의 처리다. r4에서는 R이 모르는 A의 레코드(R 이후에 미리 서명해 둔 축소 묶음, A의 포크 포함)가 R의 기준점에 따라 보류 목록으로 가고 동결도 일으키지 않는다(§5.5.1-4·9, 3차 검증 N14). 도둑이 할 수 있는 것은 R 이전에 쓴 `recovery_escrow = off`로 이후 epoch를 복구 코드로 열 수 없게 만드는 것뿐이다. 이것은 가용성 문제다. R 뒤의 새 권한 기기가 그 사이 epoch 키를 갖지 못했으면, 그 기간 내용은 다른 멤버가 새 epoch로 만든 스냅샷으로 따라잡는다(§7.6-4).

**남는 한계.**
- 탐지되지 않은 유출은 다음 교체까지의 모든 epoch를 연다(§2.4-8). 앱은 종이나 사진의 유출을 알 수 없다.
- 옛 코드는 교체 전 epoch를 계속 연다. 그 기간의 암호문을 얻는 경로가 있으면 읽힌다.
- **코드 없이 보유자를 제거하면(3-b) 그 사람은 계속 루트다.** 새 epoch는 열지 못하지만 언제든 과거 지점에서 분기해 권한을 가져갈 수 있다(모든 기기에 알림). r2는 권한 기기와 다른 admin의 서명으로 이를 막으려 했지만, 그 규칙이 N1을 만들었다. 순서 서비스 없이 "누가 먼저였는가"를 가릴 수 없으므로 루트는 루트로만 바꾼다. 방법은 코드 회수, 협조 퇴사(퇴사 전에 코드를 입력해 교체), 새 vault로 복사다.
- 교체된 옛 코드 사본만으로는 동결시키지 못한다. 교체 이전에서 분기한 레코드는 무효다(5-b). 다만 권한 기기를 훔친 사람이 그 옛 코드도 가졌다면 교체 이전에서 두 자격 RR을 만들어 같은 세대 분쟁을 일으킬 수 있다. 이때 동결은 서비스 거부이고 탈출구는 새 vault로 복사다.
- 보유자 기록은 앱이 보여 준 사용자와 관리자의 신고에 기댄다. 기록에 없는 사람이 코드를 봤다면 3이 일어나지 않는다.
- 복구 키는 루트다. 유효한 코드로 권한을 가져가는 일은 막지 못하고 모든 기기에 알릴 뿐이다.
- 이 래핑·교체 방식은 **직접 구성**이다(§3.3).

## 5. 멤버십 epoch와 3단계 키 교체

### 5.1 용어와 멤버십 체인
PRD의 "멤버십 epoch"를 두 값으로 나눈다.
- **멤버십 seq:** 멤버십 레코드마다 1씩 증가한다. 기기 추가처럼 키를 바꾸지 않는 변경도 seq를 올린다.
- **키 epoch:** 키 교체 때만 증가한다. 봉투 헤더는 epoch 번호와 `key_id`(그 epoch를 연 `RotateBegin` 레코드의 해시 앞 16바이트, epoch 0은 genesis)를 함께 담는다. 번호만으로는 §5.4의 분기 상황에서 같은 번호가 두 번 생길 수 있기 때문이다.

멤버십 체인은 권한 기기 한 대만 쓰는 append-only 해시 체인이다. 레코드는 `{vault_id, seq, prev_hash, epoch, kind, body(암호화), signer, sig}`다. 헤더는 불투명 값만 담고, 누가 어떤 역할인지는 epoch 키로 암호화된 본문에 있다. 본문은 그 레코드가 속한 epoch 키로 암호화하되, `RotateBegin` 이후의 본문(새 멤버 목록 포함)은 새 epoch 키로 암호화한다. 제거된 기기가 남은 멤버 목록을 읽지 못하게 하기 위해서다. 새 기기는 합류 때 받은 epoch 키들로 본문을 열고, 헤더의 서명과 해시 체인은 genesis부터 검증한다.

레코드 종류: `Genesis`, `AddDevice`, `RemoveDevice`, `RemoveUser`, `ChangeRole`, `ReplaceDevice`, `TransferAuthority`(서명자: 현재 권한 기기, 예비 기기의 인수, 복구 키 중 하나), `SetStandby`(예비 권한 기기 지정, §9.2), `RevokeStandby`, `ConfirmTakeover`(예비 기기 인수 확정, 서명자: 옛 권한 기기 또는 복구 키, §5.5.1), `RotateBegin`, `RotateCommit`, `RecoveryRotate`(서명자: 현재 세대 복구 키와 권한 기기, §4.5.1), `SetPolicy`(보존 기한, 최소 suite·version, `recovery_escrow` 등). 체인 밖의 서명된 control 메시지로 `TakeoverNotice`(예비 기기 인수 공지, §5.5.1)가 있다.

**보안 축소 레코드:** `RemoveDevice`, `RemoveUser`, 역할을 낮추는 `ChangeRole`, `RevokeStandby`, `RecoveryRotate`, `SetPolicy{recovery_escrow = off}`, 그리고 이들에 적힌 기준점. §5.5.1의 합집합 규칙이 적용된다.

**서명 전 동기화(재검증 N13):** 권한 기기는 시작한 뒤(특히 §4.3의 복원 감지 뒤) 피어 한 대 이상과 멤버십 head를 맞추기 전에는 멤버십 레코드에 서명하지 않는다. 백업에서 복원한 권한 기기가 옛 head에서 이중 발행을 만들어 멤버십을 동결시키지 않게 하기 위해서다. 피어가 하나도 없으면 관리자에게 "다른 기기와 연결한 뒤 처리됩니다"를 보여 준다. 복구 키 레코드(복구 코드로 쓰는 인수·확정·`RecoveryRotate`·해소 레코드)에도 같은 규칙을 적용한다. 전파되지 않은 입력을 다른 기기에서 다시 해 같은 세대 이중 사용을 만드는 일을 줄이기 위해서다(3차 검증 N15, §4.5.1-5).

역할: `admin`(관리 요청 가능, 권한 기기 후보), `editor`(쓰기), `reader`(읽기 전용, C2 이후 게스트). 권한 기기는 admin 중 한 기기다.

### 5.2 쓰기 권한 검증 (리뷰 R03)
수신 기기는 영속 봉투를 다음 순서로 검사하고, 모두 통과해야 Yjs나 registry에 적용한다. 값싼 검사부터 한다.
1. 크기 상한, 프로토콜 버전, `vault_id`가 맞는가. `suite`와 `version`이 vault 정책(`SetPolicy`)의 하한 이상인가(검증 L6).
2. 작성 기기 서명이 맞는가.
3. 작성 기기가 헤더의 `roster_seq` 시점 멤버십에서 활성이고 그 종류의 봉투를 쓸 역할(편집·registry는 editor 이상)을 가졌는가. `roster_seq`는 수신 기기가 아는 head 이하여야 한다. 더 크면 멤버십을 먼저 받아 온다.
4. **제거·강등 기준점:** 작성 기기가 나중에 제거되거나 reader로 강등됐다면, 그 레코드에 적힌 기준점(그 시점에 권한 기기가 알던 그 기기의 체인 head, 즉 카운터와 해시) 이하이고 그 체인 위에 있는 봉투만 자동으로 받는다(지워진 구간은 §6.6.1-5로 건너뛴다). 기준점은 §5.5.1의 합집합 규칙에 따라 어느 가지에서 왔든 가장 이른 것을 쓴다. 기준점 이후의 봉투는 **격리**하고 관리자에게 "확인이 필요한 변경"으로 보여 준다(PRD D4 "그 전에 작성된 변경은 관리자 확인"). 제거된 기기가 옛 `roster_seq`를 주장해도 기준점은 기기 단위라서 우회할 수 없다.
5. 헤더의 `key_id`에 해당하는 키를 갖고 있는가. 없으면 "키 대기"로 보관했다가 키가 오면 다시 검사한다.
6. 작성자 체인(§6.3, checkpoint 이전 구간은 §6.6.1)에 맞는가. 누락이 있으면 적용은 하되 "동기화 미완료"로 표시하고 빠진 봉투를 요청한다.
7. 복호화하고, Rust에서 Yjs 업데이트를 파싱해 한도(크기, 구조 수)와 clientID 고정(§6.3-5)을 확인한다.

이 검증이 없으면 P2P 읽기 전용 게스트를 출시하지 않는다(PRD D4). C1은 reader 역할을 만들지 않지만, editor를 reader로 강등하는 시나리오로 4번을 시험한다(§10).

### 5.3 키 교체 상태 기계 (리뷰 R02)
| 상태 | 들어가는 조건 | 하는 일 | 저장 | 실패·재시도 |
|---|---|---|---|---|
| **안정(e)** | 처음, 또는 확정 후 | epoch e 키로 읽고 쓴다 | — | — |
| **준비(e→e+1)** | 제거·강등·복구 사용·관리자의 수동 갱신 | 새 키 K(e+1) 생성. `RotateBegin{rotation_id, from e, to e+1, 사유, 제거 기기별 기준점, 새 멤버 목록, key_confirm, recovery_gen}` 작성. 남은 기기 각각, 그리고 현재 세대 복구 공개키와 예비 권한 기기용으로 K(e+1)을 감싼 `KeyPackage`를 §5.3.1 형식으로 생성. 제거 대상이 복구 코드 보유자면 코드를 입력받아 `RecoveryRotate`, 입력할 수 없으면 `SetPolicy{recovery_escrow = off}`를 함께(§4.5.1-3) | 위 전부를 권한 기기의 SQLite 트랜잭션 하나로 저장한 뒤에야 밖으로 보낸다 | 아무것도 보내기 전이면 취소하고 안정(e)로 돌아갈 수 있다. 재시작하면 저장된 상태에서 이어간다 |
| **배포(e+1)** | 첫 `RotateBegin`이 밖으로 나감 | `RotateBegin`과 `KeyPackage`를 온라인 기기에 직접, 오프라인 기기 몫은 다른 멤버(와 D의 노드)에 맡겨 보낸다. 맡는 쪽은 §5.3.1-4 (a)(b)의 서명 검사를 통과한 패키지만 보관하고 전달한다(재검증 N12). §5.3.1의 받는 규칙을 통과한 기기는 서명된 `KeyAck{rotation_id, device_id, key_confirm}`을 돌려주고 **곧바로 e+1로 쓰기 시작한다**. 아직 키가 없는 기기는 e로 계속 쓰고, e+1 봉투는 보관했다가 키를 받으면 연다 | 보낸 `KeyPackage` 바이트를 그대로 보관해 재전송한다(HPKE는 무작위라 다시 만들면 바이트가 달라진다). 수신 측은 **검증을 통과한 패키지만** `(rotation_id, device_id)`로 중복을 거른다 | **되돌리지 않는다.** 앞으로만 재시도한다. 권한 기기가 이 상태에서 사라져도 K(e+1)이 복구 공개키와 예비 권한 기기 몫으로 감싸져 있어 이어받을 수 있다 |
| **확정(e+1)** | 남은 기기 전원 ACK, 또는 관리자가 기다리지 않기로 고르고 기한(기본 7일)이 지남 | `RotateCommit{rotation_id, ACK한 기기, 미수령 기기, 제거 기기별 최종 기준점, 구 epoch 봉투 보존 기한}` 작성 | 체인에 추가 | 미수령 기기의 `KeyPackage`는 **기한 없이** 보존한다. 그 기기가 제거되기 전까지 지우지 않는다 |

규칙:
- **새 키를 아는 기기는 구 epoch로 새 봉투를 만들지 않는다.** 아직 보내지 못한 자기 봉투(outbox)는 작성자 자신이 e+1로 다시 봉인해 새 서명을 붙인다. 다른 기기가 남의 봉투를 다시 봉인하지는 않는다. 작성자 서명이 깨지기 때문이다.
- **현역 기기의 구 epoch 봉투는 언제 와도 받는다.** 서명과 멤버십이 맞으면 epoch e 봉투라도 받는다. 수신 기기는 구 epoch 키를 vault 수명 동안 보존한다(§9.3). 이 봉투는 멤버가 아닌 상대에게 전달하지 않는다. 그래서 제거된 기기가 그 암호문을 얻을 경로는 멤버의 협조뿐이다.
- **연속 제거:** 배포 중에 또 제거가 생기면 권한 기기는 `RotateBegin(e+2)`를 바로 쓴다. e+1은 "대체됨"으로 확정되고, e+1 `KeyPackage`는 새로 제거된 기기를 뺀 기기에게만 계속 전달한다. 배포 중 e+1로 쓰인 봉투를 열려면 e+1 키가 필요하기 때문이다.
- **멱등성:** 모든 단계는 `rotation_id`로 식별한다. 같은 요청이 다시 와도 결과는 같다. PRD D4의 "원래 상태로 복구할 수 있어야 한다"는 준비 단계의 취소와, 배포 단계의 저장된 바이트 재전송으로 충족한다.
- **화면:** 진행 중에는 "팀원이 나가서 보안을 새로 고치는 중"만 보여 준다(PRD F5.5a). 미수령 기기가 있으면 관리자에게만 "○○님의 기기가 켜지면 마무리됩니다"를 보여 준다.

### 5.3.1 KeyPackage 인증과 키 확인 (검증 H1)
이름은 MLS의 KeyPackage와 같지만 역할은 MLS Welcome의 `GroupSecrets`(RFC 9420 §12.4.3.1)에 가깝다. 감싼 epoch 키 하나를 수신자 하나(기기, 또는 복구 키 세대)에게 전한다.

**공격 시나리오.** 제거된 X는 남은 기기 V의 HPKE 공개키를 옛 멤버십 본문에서 안다. HPKE Base 모드는 송신자를 인증하지 않으므로(RFC 9180 §9.1, §9.8) X는 자기가 고른 키 K′를 `{rotation_id, device_id=V}`로 감싸 V에게 먼저 보낼 수 있다. r1의 수신 규칙은 `(rotation_id, device_id)`로 중복을 걸렀으므로 먼저 온 가짜가 남고 진짜가 버려진다. V는 K′를 e+1 키로 믿고 곧바로 e+1로 쓰기 시작하며, X는 V가 제거 이후 쓴 내용을 모두 읽는다. 가짜 `rotation_id` 하나로 진짜 교체를 방해하는 서비스 거부도 된다.

**설계 변경.**
1. **서명:** `KeyPackage = {vault_id, rotation_id, epoch, recipient(device_id 또는 recovery_gen), BLAKE3(recipient_hpke_pk), hpke_enc, ct}`이고, 권한 기기가 MLS `SignWithLabel`(RFC 9420 §5.1.2)과 같은 방식으로 레이블 `"ib/p2p/keypkg/v1"`을 붙여 서명한다. 서명자는 그 `RotateBegin`을 쓴 권한 기기여야 한다. 인수(§5.5.1) 뒤 재배포는 새 권한 기기가 서명한다.
2. **문맥 결합:** 암호화는 MLS `EncryptWithLabel`(RFC 9420 §5.1.3)과 같은 방식이다. `SealBase(pk_recipient, info = EncryptContext{label = "ib/p2p/keywrap/v1", context = (vault_id, rotation_id, epoch, recipient_type, recipient)}, aad = "", K)`. 다른 회전, 다른 수신자, 다른 vault의 패키지를 옮겨 붙이면 열리지 않는다.
   **인코딩(재검증 N10):** 서명 입력과 HPKE `info`는 `‖` 연결이 아니라 MLS와 같은 길이 접두 구조(RFC 9420의 TLS 표기 `opaque label<V>; opaque content<V>;`, 서명은 `SignContent`, 암호화는 `EncryptContext`)로 직렬화한다. `context` 안의 각 필드도 길이 접두로 넣고, `recipient_type`(1바이트: 기기 = 1, 복구 세대 = 2)으로 `device_id`와 `recovery_gen`을 구분한다. 봉투 서명(§6.2)의 `"ib/p2p/env/v1" ‖ envelope_id`도 같은 `SignContent`로 바꾼다.
3. **키 확인값:** `RotateBegin`에 `key_confirm = BLAKE3-derive_key("ib/p2p/keyconfirm/v1", vault_id ‖ rotation_id ‖ epoch ‖ K)`를 넣는다(각 필드는 고정 길이). `key_confirm`은 **평문 서명 헤더**에 둔다. 받는 기기가 본문을 열기 전에 4(d)에서 비교하기 때문이다. `RotateBegin`은 권한 기기가 서명한 체인 레코드이므로 이 값은 위조할 수 없다. MLS의 `confirmation_tag`(RFC 9420 §6.1)를 본떴지만 같은 성질은 아니다. 원본은 비밀 키로 만든 MAC이고, 이 값은 키에서 파생한 공개 commitment다. "이 K가 권한 기기가 정한 K다"까지만 확인한다.
4. **받는 규칙:** V는 다음을 모두 만족할 때만 K를 e+1 키로 받는다. (a) 서명이 맞고, 서명자가 V가 검증한 체인에서 그 회전의 권한 기기다. (b) 해당 `RotateBegin`이 V의 검증된 체인에 있다. 패키지와 같이 오면 체인부터 검증한다. (c) HPKE가 위 문맥으로 열린다. (d) K로 계산한 값이 `key_confirm`과 같다. 그다음 `RotateBegin` 본문을 K로 연다. 넷을 통과하기 전에는 e+1로 쓰지 않는다.
5. **중복 제거:** `(rotation_id, recipient)` 중복 제거는 검증을 통과한 패키지에만 적용한다. 실패한 패키지는 "본 것"으로 기록하지 않고 버리며, 보낸 연결을 기록하고 연결당 실패 횟수를 제한한다.
6. **수령 표시:** `KeyAck`에 `key_confirm`을 넣어 서명한다. 권한 기기는 확인값이 맞는 ACK만 센다. `key_confirm`은 공개값이므로 이 ACK는 키 보유 증명이 아니라 "어느 회전을 받았다고 주장하는가"의 표시다(재검증 N9). 받지 못한 기기가 거짓 ACK를 보내면 그 기기만 손해를 본다.
7. **같은 규칙을 쓰는 곳:** 합류 승인 때 모든 epoch 키 전달(§4.4), 예비 권한 기기용·복구용 패키지와 `RecoveryArchive`(§4.5.1), `ReplaceDevice` 때의 재래핑(§4.3-4), 진 가지 키의 재배포(§5.5.1-7). 옛 epoch 키를 한꺼번에 보낼 때는 키마다 그 epoch `RotateBegin`의 `key_confirm`으로 확인한다.

**남는 한계.**
- 권한 기기(또는 유효한 예비 기기, 복구 키)의 서명 키를 가진 공격자는 유효한 패키지를 만든다. 루트 신뢰다(§2.4-3).
- 기기 HPKE 키는 기기 마스터에서 파생하는 고정 키다. 마스터가 새면 그 기기에 보낸 모든 패키지가 열린다. MLS의 UpdatePath 같은 자동 갱신이 없고 `ReplaceDevice`로만 바꾼다.
- 가짜 패키지를 계속 보내는 상대는 수신 기기의 CPU를 쓰게 할 수 있다. 서명 검사가 가장 먼저라 비용은 작다. 멤버십에서 빠진 전송 키는 연결 단계에서 거부된다(단, 제거를 아직 모르는 기기는 예외, §2.4-9).
- 서명 + 레이블 HPKE + 키 확인값의 조합은 MLS 부품을 빌린 **직접 구성**이다(§3.3).

### 5.4 권한 기기가 오프라인일 때
- **일반 편집은 계속된다.** 멤버십과 무관하기 때문이다.
- **멤버십 변경은 요청으로 쌓인다.** 다른 admin은 서명된 `ChangeRequest{request_id, ...}`를 보내고, 권한 기기가 켜지면 받은 순서대로 처리한다. 화면에는 "관리자 기기(○○의 노트북)가 켜지면 처리됩니다".
- **합류 요청**은 발급 기기가 티켓을 소비한 뒤 "승인 대기"로 남는다.
- **권한 기기를 오래 쓸 수 없으면** 예비 권한 기기가 인수하거나(§9.2), 복구 코드로 `TransferAuthority`를 쓴다(§4.5).

### 5.5 동시 변경 충돌 해결
작성자가 한 기기뿐이라 정상 상태의 멤버십 체인은 직선이다. 분기는 (1) 예비 기기나 복구 키의 인수가 옛 권한 기기의 레코드와 겹칠 때, (2) 권한 기기 복제나 이중 발행일 때만 생긴다. 규칙은 §5.5.1이고 모두 결정적이다.

#### 5.5.1 분기 규칙과 되돌리기 방어 (검증 H2, M10)
**공격 시나리오.**
- 모순: r1의 §6.3 규칙 1은 "멤버십 head보다 오래된 체인은 받지 않는다"였고, 이 절은 "같은 seq에서 인수 레코드가 이긴다"였다. 권한 기기 A가 오프라인에서 seq n+1..n+3을 썼고 일부 기기가 n+3을 받아들였다고 하자. 예비 기기 S가 seq n에서 인수하면 S 쪽 체인(head n+1)은 그 기기들에게 "더 오래된" 체인이다. 규칙 1을 따르면 거부하고 이 절을 따르면 채택한다. 기기마다 다른 체인을 따르게 되고 분기가 영구화된다.
- 롤백: 인수 레코드가 어느 seq에서든 이긴다면, 예비 기기를 훔친 공격자는 `RemoveDevice`보다 앞선 seq에서 분기해 이미 제거된 기기를 되살릴 수 있다. 예비 기기는 관리자 조작 한 번으로 즉시 인수하고 모든 epoch 키를 갖는데도 r1의 루트 목록(§2.4-3)에 없었다.

**설계 변경.**
1. **용어:** 레코드 R이 레코드 Q의 조상이면(`prev_hash`로 닿으면) "Q는 R을 안다"고 한다. 서로 모르면 "동시"다.
2. **보안 축소 레코드는 합집합이다.** §5.1의 보안 축소 레코드는 그 가지의 정당한 서명자가 썼다면 **어느 가지에 있든** 모든 기기에 적용된다. 그것을 모르는 동시 레코드는 그 효과를 되돌리지 못한다. 되돌리려면 그 레코드를 아는 새 레코드가 필요하다. 제거된 기기는 새 `device_id`로 다시 합류한다. p2panda-auth의 strong removal과 같은 원칙이다. 예외는 복구 기준점이다(아래 4). 복구 기준점 이후 진 가지의 옛 권한·예비 기기 레코드는 정당한 서명자의 것이 아니므로 합집합에 들어가지 않는다.
3. **head 선택:** 가지가 갈라지면 **공통 조상 이후 그 가지에 있는 가장 높은 등급의 유효한 레코드**로 고른다. **복구 키 > 유효한 예비 기기 인수 > 권한 기기.** r2는 "공통 조상 다음 첫 레코드"로 골랐다. 그러면 더 이른 지점에서 갈라진 예비 인수가 권한 기기 가지 깊은 곳의 복구 인수를 묻었다(재검증 N8). 예비 기기 인수가 유효하려면 (a) 인수 레코드가 아는 체인에서 그 기기가 `SetStandby`로 지정돼 있고, (b) 인수가 확정되지 않았다면, 그 지정을 끝내는 `RevokeStandby`가 어느 가지에도 없거나 인수 레코드가 그 `RevokeStandby`를 알아야 한다. 확정은 8이다. r2의 "(c) `TakeoverNotice` 해시 포함" 조건은 뺀다. 도둑도 notice와 인수를 한꺼번에 만들 수 있어 보안 성질이 없다(재검증 N6).
   **이중 발행과 동결:** 같은 등급의 서명자가 서로 모르는 두 레코드를 만들면(권한 기기 복제, §4.5.1-5b로 무효가 되지 않은 같은 세대 복구 키 두 번 사용, 같은 예비 기기의 두 인수) 이중 발행이다. 해시나 도착 순서로 고르지 않는다. 서명자가 해시 값을 고를 수 있기 때문이다(재검증 N7). 멤버십을 **동결**하고 "보안 문제 감지"를 띄운다. 동결은 평가 순서 ②에서, ①을 통과한 레코드 중 **최고 등급**에서만 판정한다(9). 상위 등급 가지가 있으면 하위 등급의 포크는 동결을 일으키지 않는다. 동결 중에는 공통 조상 상태에 양쪽 축소 레코드의 합집합만 더해 쓴다. 어느 가지의 추가·승격도 적용하지 않는다. 새 epoch 키는 복구 공개키로 감싸지 않는다. 편집은 계속되지만 합집합 제거 대상이 가진 epoch 키로는 봉인하지 않는다. 그런 키밖에 없으면 편집은 outbox에 남고 "이 기기에만 저장됨"을 보여 준다. 권한 기기 이중 발행은 복구 키 레코드가 양쪽을 알고 한쪽을 고르거나, 복구 인수의 기준점(4)이 포크를 빼면 풀린다. **복구 키 이중 사용으로 동결된 동안에는 분쟁 가지의 제거를 합집합에 넣지 않고 보류한다(3차 검증 N15).** 보류된 제거는 봉인을 일으키지 않고, 공통 조상 시점의 멤버는 현재 epoch로 계속 봉인해 쓴다. 이 동결은 같은 세대 해소 레코드로 풀리고(§4.5.1-5c), 해소가 다시 갈리면 탈출구는 "새 vault로 복사"다(§4.5).
4. **복구 기준점(3차 검증 N14):** 복구 인수 R(복구 키가 서명한 `TransferAuthority`)과 복구 키가 확정한 예비 인수 T(8b)는 옛 권한 기기와 예비 기기에 대한 **멤버십 기준점**을 갖는다. 기준점은 그 인수가 참조하는 마지막 확정 지점, 즉 R.prev(T.prev)다. R이 모르는 옛 권한 기기·예비 기기의 레코드, 곧 기준점 이후 진 가지에서 그 기기들이 쓴 레코드는 ①에서 정당한 서명자의 것이 아니다. 체인에 시각이 없어 R 이후에 쓴 레코드도 R과 "동시"로 보이기 때문이다. 그 축소 레코드는 자동으로 적용하지 않는다. 새 권한 기기에 **보류 목록**으로 보여 주고, 관리자가 고른 것만 새 권한 기기가 다시 쓴다. 새 권한 집합이 재확인한 것만 효력을 갖는다. 진 가지의 추가·승격·정책 변경도 같은 보류 목록으로 간다(7). r3의 "진 가지의 제거를 기본값으로 다시 적용"을 뒤집은 것이다. 그러면 도둑이 미리 서명해 둔 `RemoveDevice(새 권한 기기)`, `RemoveUser(전원)`, `SetPolicy{recovery_escrow = off}` 묶음을 R 이후에 풀어도 아무 기기도 봉인하지 않는다. §5.2-4의 봉투 기준점과 같은 원리다. 대가로 복구와 동시에 일어난 정직한 옛 권한 기기의 제거도 새 관리자가 확인할 때까지 보류된다. 복구는 옛 권한 기기를 쓸 수 없을 때 하므로 대가는 작다. 기준점 이전 레코드(R이 아는 것)는 그대로 유효하다. 보류 목록은 자동으로 지우지 않는다(§7.5). 진 가지의 `RecoveryRotate`와 그 밖의 복구 키 레코드는 복구 등급이므로 이 규칙의 대상이 아니라 §4.5.1-5를 따른다.
5. **되돌리기 방어(§6.3 규칙 1)를 이렇게 바꾼다.** 내 head를 아는 체인(연장)은 검증 후 받는다. 내 head의 조상에서 끝나는 체인(짧은 접두부)은 무시한다. 내 head와 동시인 가지는 3으로만 판정한다. 어느 경우든 **제거 집합, 기준점, 철회된 예비 지정은 줄어들지 않는다.** head는 분기 규칙으로만 옮겨 간다.
6. **예비 기기 인수 절차:** 예비 기기는 먼저 서명된 `TakeoverNotice{known_head}`를 모든 기기에 보낸다. 정직한 클라이언트는 24시간 기다린 뒤 `TransferAuthority`(prev = 그때 아는 최신 head)를 쓴다. 그사이 권한 기기가 notice를 받으면 관리자에게 알리고, 관리자는 `RevokeStandby`로 인수를 막는다. 즉시 인수는 복구 키가 함께 서명할 때만 허용한다. 받는 기기는 24시간도, notice와 인수 `prev`의 일치도 강제하지 않는다(A4, 시계를 믿지 않는다). 24시간 대기와 notice는 **정직한 인수의 관례이자 조기 경보**이고 방어가 아니다(재검증 N6). 안전성은 2의 철회 규칙과 8의 확정 규칙에서 나온다.
7. **진 가지의 처리(검증 M10, 재검증 N4):** 진 가지나 무효가 된 인수 가지에서 추가된 기기, 승격, 정책 변경은 그 자리에서 효력을 잃는다. 새 권한 기기의 정직한 클라이언트는 이것을 **기본값으로 다시 적용**하고, 관리자가 해제한 항목만 뺀다. 단, 복구 기준점(4) 이후 옛 권한·예비 기기가 쓴 레코드는 다시 적용하지 않고 4의 보류 목록으로 보낸다. 오래된 head에서 인수해 옛 권한 기기의 추가가 진 경우와, 몇 달 운영한 인수가 철회돼 인수 기간의 추가가 무효가 된 경우의 손실을 이것으로 줄인다. 그 기기들의 봉투는 다시 적용될 때까지 격리하고, 이 격리는 자동으로 지우지 않는다(§7.5). 진 가지의 축소 레코드는 2에 따라 남는다. 진 가지에서 만든 epoch 키는 `key_id`로 보존해 그 가지에서 쓰인 봉투를 연다. 이 키는 **이긴 가지의 현재 멤버이면서 진 가지에서도 그 키를 받을 자격이 있던 기기**에게만 §5.3.1 방식으로 다시 감싸 보낸다. 진 가지에서 빠졌던 기기(예: 진 가지가 제거한 X)는 받지 못한다. 합집합 제거 대상이 이긴 가지의 현재 epoch 키를 갖고 있으면 새 권한 기기는 곧바로 키를 교체한다.
8. **인수 확정(재검증 N4):** 예비 기기 인수 T는 쓰인 뒤 **잠정**이다. T를 아는 `ConfirmTakeover`를 (a) 옛 권한 기기가 서명하거나 (b) 복구 키가 서명하면 **확정**된다. 보안 상태를 바꾸는 판정의 최종성에는 권한 기기나 복구 경로의 명시적 확인이 필요하다는 원칙이다. 시계로 확정하지 않는다(A4). 확정된 T는 T를 모르는 `RevokeStandby`로 무효가 되지 않는다. 옛 권한 기기의 정직한 클라이언트는 다시 켜져 T를 보면 관리자에게 "○○ 기기가 관리 권한을 넘겨받았습니다 [인정] [막기]"를 묻는다. [막기]는 T가 오래됐을수록(T를 아는 레코드가 많을수록) 잃는 것을 함께 보여 준다. 옛 권한 기기를 영영 쓸 수 없으면 관리자는 복구 코드로 확정한다. 화면은 "복구 코드로 확정하면 옛 관리자 기기가 돌아와도 되돌릴 수 없습니다"다. MLS(RFC 9420)에서 커밋이 순서 서비스에 받아들여져야 epoch가 확정되는 것을 순서 서비스 없이 옮긴 것이다. 그 역할을 옛 권한 기기나 복구 키의 서명이 맡는다.
9. **평가 순서(재검증 N4, 3차 검증 N14):** 모든 기기는 같은 레코드 집합에 대해 다음 순서로 계산한다.

   | 단계 | 계산 | 규칙 |
   |---|---|---|
   | ① 유효성 | 인수 레코드의 지정(3a), 철회(3b), 확정(8), 복구 키 세대와 단독 레코드(§4.5.1-5). 복구 기준점: 기준점 이후 R이 모르는 옛 권한·예비 기기 레코드를 보류 목록으로 빼고 ②~④에 넣지 않는다 | 4 |
   | ② 동결 판정 | ①을 통과한 레코드 중 **최고 등급**에서만 이중 발행을 판정한다. 상위 등급 가지가 있으면 하위 등급의 포크는 동결을 일으키지 않는다 | 3 |
   | ③ head | 유효한 레코드만으로 가지 등급과 head를 고른다. 동결이면 공통 조상에 머문다 | 3 |
   | ④ 합집합 | 각 가지에서 **그 시점에 정당한 서명자**가 쓴 축소 레코드의 합집합을 적용한다. 복구 키 이중 사용 동결이면 분쟁 가지의 제거는 보류한다 | 2, 3 |
   | ⑤ 목록 | 복구 기준점의 보류 목록(4)과 다시 적용 목록(7)을 반영한다 | 4, 7 |

   무효가 된 인수 뒤에 그 인수자가 쓴 레코드는 정당한 서명자의 것이 아니므로 ④에 들어가지 않는다. ①은 ③·④의 결과에 의존하지 않는다. 철회의 정당성은 철회한 권한 기기의 조상 체인만으로, 기준점은 인수 레코드의 `prev`만으로 정해지기 때문이다.

**남는 한계.**
- 훔친 예비 기기는 권한 기기가 반응하기 전까지 루트와 같다. 그사이 추가한 기기는 철회 뒤 무효가 되지만, 그 가지의 epoch 키로 정직한 기기가 쓴 내용은 이미 읽혔다. 그래서 예비 기기를 루트 목록(§2.4-3)에 넣는다. 그사이 한 제거는 철회 뒤 효력을 잃고, 제거를 받은 기기는 봉인만 했으므로 그대로 돌아온다(§7.5, 재검증 N5).
- 권한 기기 도둑은 `RevokeStandby`로 확정되지 않은 예비 인수를 무력화할 수 있다. 권한 기기 도난은 복구 키로만 되찾는다. 예비 기기는 보안 장치가 아니라 가용성 장치다.
- 확정되지 않은 인수는 옛 권한 기기가 돌아와 [막기]를 누르면 몇 달 뒤에도 무효가 된다. 인수 기간의 추가는 7에 따라 기본값으로 다시 적용되고 봉투는 지워지지 않지만, 관리자가 다시 확인해야 한다. 오래 쓸 인수는 복구 코드로 확정하도록 안내한다.
- 늦게 돌아온 권한 기기가 진 가지 레코드를 내놓거나 철회하면 기기들의 head가 한 번 더 바뀐다. 화면에는 "관리 기록이 정리되었습니다. 다시 적용한 항목 n개"를 보여 준다.
- 합집합 규칙과 등급 규칙의 조합은 **직접 구성**이다(§3.3). C1 속성 기반 테스트로 "어떤 수신 순서에서도 같은 head와 같은 제거 집합"을 확인한다.

## 6. 봉투 형식, 스냅샷 경쟁, watermark 삭제

### 6.1 봉투 종류
`update`(Yjs 업데이트), `snapshot`(Yjs 상태), `registry`(§7 연산), `control`(ACK, 보유 알림, 정리 요청), `membership`(§5.1 레코드), `keypkg`(감싼 epoch 키와 `RecoveryArchive`, §5.3.1), `checkpoint`(작성자 체인의 서명된 checkpoint, §6.6.1). 일시 메시지(presence, 커서)는 epoch 키로 암호화하고 서명하지만 체인에 넣지 않고 저장하지 않는다.

### 6.2 헤더와 암호화 (PRD D3, 리뷰 R07)
| 필드 | 크기(바이트) | 설명 |
|---|---|---|
| `magic`, `version` | 4 | 프로토콜 식별과 버전. 능력 협상은 연결 hello에서 한다(PRD §6.5) |
| `suite` | 1 | 암호 묶음. v1 = Ed25519 / XChaCha20-Poly1305 / BLAKE3 / HPKE(X25519, HKDF-SHA256, ChaCha20-Poly1305). vault 정책의 하한보다 낮은 suite·version은 거부한다(§5.2-1) |
| `kind` | 1 | 위 종류 |
| `vault_id` | 16 | 무작위 |
| `doc_id` | 16 | 지금 문서 ID와 같은 UUID v4(`R/index.rs:1424`). 무작위라 생성 시각이 드러나지 않는다. registry·membership 봉투는 0 |
| `epoch`, `key_id` | 4 + 16 | §5.1 |
| `roster_seq` | 4 | 작성자가 본 멤버십 seq |
| `author` | 32 | 작성 기기 서명 공개키 |
| `counter` | 8 | 작성 기기별 vault 단위 단조 증가 값 |
| `prev` | 32 | 같은 작성자의 직전 봉투 ID(작성자 해시 체인) |
| `doc_prev` | 32 | 같은 작성자가 같은 문서에 쓴 직전 봉투 ID(없으면 0, §6.6.1). `doc_id`가 이미 평문이라 새로 드러나는 것은 없다 |
| `parent` | 32 | snapshot: 부모 스냅샷 ID. update: 작성 시점에 알던 그 문서의 최신 스냅샷 ID(없으면 0) |
| `nonce` | 24 | 무작위 |
| `ct_len` | 4 | 암호문 길이 |

- **암호화:** `ciphertext = XChaCha20-Poly1305(K(epoch), nonce, payload, AAD = 헤더 전체)`. 헤더의 어느 값을 바꿔도 복호화가 실패한다.
- **봉투 ID와 서명:** `envelope_id = BLAKE3(헤더 ‖ ciphertext)`, `sig = Ed25519(author, SignContent{label = "ib/p2p/env/v1", content = envelope_id})`(길이 접두 구조, §5.3.1-2). 암호문에 서명하므로 키가 없는 저장 노드도 작성자를 확인하고 업로드를 인증할 수 있다(F5.9). PRD D3이 요구한 "payload 해시"는 봉투 ID에 들어 있다.
- **payload:** 종류별 본문, 작성 시각(화면 표시용이며 신뢰하지 않음), 그리고 크기를 감추기 위한 padding. padding 구간은 C1 측정 후 정한다.
- **인코딩:** 헤더는 고정 순서의 이진 형식으로 하나의 표현만 허용한다. 해시와 서명이 표현 차이에 흔들리지 않게 하기 위해서다.
- **평문으로 남는 것:** 불투명 ID(vault, 문서, 봉투), 종류, 크기, 작성 기기 공개키, 카운터와 체인 연결. 작성 시각은 payload 안에 있어 평문이 아니다. 다만 관찰자는 봉투가 오간 시각을 본다. PRD D7이 허용한 범위다. 제목, 경로, 폴더 이름, 멤버 프로필은 모두 payload 안에 있다.

### 6.3 되돌리기·누락·분기 방어
수신 기기는 다음 상태를 봉투 저장과 **같은 SQLite 트랜잭션**으로 `.context/index.sqlite`의 새 테이블에 저장한다. 기존 테이블은 건드리지 않는다(PRD F8.5).
- 멤버십 head(seq, 해시)와 알고 있는 epoch 키 목록
- 합집합 제거 집합, 기기별 기준점, 철회된 예비 지정, 인수 확정 여부, 동결 상태, 복구 기준점과 보류 목록(§5.5.1)
- 작성 기기별 연속 head(카운터, 봉투 ID), 최신 checkpoint(§6.6.1), 분기 표시
- 문서별로 받아들인 스냅샷(ID, watermark, 상태 해시, 재생 검증했는지 채택 조건으로 받았는지)과 Yjs state vector
- (문서, Yjs clientID) → 작성 기기 표(아래 5)
- 마지막 "최신 확인" 기록: 언제, 누구와 head가 일치했는가

규칙:
1. **줄어들지 않는다.** §5.5.1-5다. 멤버십 head는 연장이나 분기 규칙으로만 바뀌고, 제거 집합·기준점·철회된 예비 지정은 줄어들지 않는다.
2. **누락 탐지:** 작성자별 카운터가 n+1인 봉투는 n이 필요하다. 작성자의 최신 checkpoint 이전 구간은 checkpoint로 갈음한다(§6.6.1). 없으면 적용은 하되 빠진 것을 요청하고, 일정 시간 안에 못 받으면 "일부 변경을 아직 받지 못했습니다"를 보여 준다. 조용히 성공 처리하지 않는다(PRD D3).
3. **분기 탐지:** 같은 작성자에게서 같은 카운터와 다른 해시가 오면 분기다. 두 가지가 담은 Yjs 연산의 (clientID, clock) 범위가 겹치지 않으면 복원으로 보고 둘 다 받은 뒤 `ReplaceDevice`를 기다린다(§4.3). 겹치면 이중 발행이다. 수신 순서는 기기마다 다르므로 "나중에 받은 쪽"을 고르지 않고 **결정적으로 처리한다(검증 M4).** 분기점 이후 두 가지 모두에서 새로 받는 봉투를 격리하고, 그 작성 기기를 관리자에게 알린다. 이미 Yjs에 적용된 부분은 되돌릴 수 없으므로 `Heads`로 "이중 발행 적용됨"을 알리고 관리자 화면에 "되돌릴 수 없는 변경"으로 표시한다. 관리자는 기준 기기의 내용을 새 문서로 다시 만들 수 있다(옛 문서는 휴지통).
4. **신선도:** 권한 기기나 서로 다른 피어 두 대 이상과 head가 일치하면 "최신"이다. 그렇지 못하면 PRD F5.5a의 표현 중 "다른 사람이 켜면 전달됨" 또는 "이 기기에만 저장됨"을 쓴다. 처음 들어온 기기는 티켓의 멤버십 head가 하한이다(§4.4).
5. **clientID 고정(검증 M3, 재검증 N2·N3):** 수신 기기는 문서별 Yjs clientID마다 처음 쓴 작성 기기를 기록한다(`(doc_id, clientID) → author`, 봉투 저장과 같은 트랜잭션). Yjs clientID는 Y.Doc마다 따로 뽑으므로 문서별로 묶는다. 묶는 근거는 **실제 update 봉투**와 채택한 스냅샷의 표(§6.5-4)뿐이다. 자기 신고 목록으로 묶지 않는다. update 봉투는 자기 작성자에게 묶인 clientID나 아직 묶이지 않은 clientID의 struct만 담을 수 있다. 다른 작성자에게 묶인 clientID가 나오면 그 봉투만 격리한다. 아직 묶이지 않은 clientID를 두 작성자의 update 봉투가 쓰는 것이 드러나면 그 clientID의 두 작성자 봉투를 모두 격리하고 알린다. 이 격리는 자동으로 지우지 않는다(§7.5). delete set은 삭제한 사람을 알 수 없어 이 검사에서 빠진다(§2.4-7). 스냅샷은 이 검사를 따로 받지 않는다. 스냅샷은 이 검사를 통과한 봉투의 재생 결과와 같을 때만 쓰기 때문이다(§6.5). 송신 쪽은 §8.3에 따라 자기 트랜잭션만 봉인하므로 정상 기기는 이 규칙에 걸리지 않는다.
   남는 한계: 악성 editor가 아직 묶이지 않은 V의 clientID를 V보다 먼저 일부 기기에 전하면 그 기기들에서는 V의 진짜 연산이 격리된다. 조용한 손실은 막지만 기기 간 차이가 남고 관리자 확인이 필요하다. 격리된 V의 봉투는 지워지지 않는다. clientID는 문서를 열 때마다 새로 뽑는 32비트 무작위 값이라 정직한 충돌(검증 L7)도 같은 격리를 부른다. 문서별로 묶으므로 충돌은 같은 문서 안에서만 센다. 충돌 확률은 C1 보고서에서 추정한다.

### 6.4 스냅샷
- **내용:** `Y.encodeStateAsUpdate(doc)`(Yjs v1 이진), 그 상태의 state vector, watermark W, 상태 해시 D, 이 문서의 `clientID → author` 표. W는 "작성 기기 → 이 문서에 대해 포함한 가장 큰 카운터"이고, 그 작성자가 이 문서에 쓴 봉투 중 W 이하는 **모두**, 그리고 그것**만** 포함했다는 뜻이다. 작성자 체인 헤더에 `doc_id`가 평문으로 있어 어떤 카운터가 어느 문서 것인지 수신 측이 확인할 수 있다.
- **상태 해시 D(3차 검증 N16):** Yjs 상태의 **통합 순서**를 정규 인코딩한 값의 BLAKE3 해시다. Rust가 `yrs`로 계산한다. 루트 타입을 이름순으로 하나씩, 각 타입 안을 문서 순서대로 걷는다. clock 단위마다 `(client, clock, deleted)`를 내보내고, 삭제되지 않은 단위에는 `origin`, `rightOrigin`, `parent`(`parentSub` 포함), 내용을 더한다. 삭제된 단위는 내용 없이 순서상 위치만 넣는다. 연속 구간은 결정적으로 합친다. 여기에 정규화한 delete set(client·clock 순, 구간 병합)과 `clientID → author` 표를 더한다. 모든 필드는 길이 접두 구조(§5.3.1-2)로 직렬화한다. struct 목록을 그대로 쓰지 않는 이유는 둘이다. struct 분할·병합과 삭제 내용 GC는 이력에 따라 달라서 같은 연산 집합에서도 목록이 달라질 수 있다. 그리고 r3 정의에는 `rightOrigin`과 `parent`가 없어 동시 삽입의 위치만 바꾼 위조가 같은 값을 냈다. 수렴한 복제본은 같은 통합 순서를 가지므로 같은 값이 나오고, 위치·내용·삭제를 바꾼 위조는 값이 달라진다. 정규화 규칙은 C1에서 JS Yjs·`yrs` 왕복 테스트로 고정한다(§10.4 #1도 같은 값을 쓴다).
- **D는 본문에서 계산한다:** payload의 D 필드는 선언일 뿐이다. 스냅샷을 검증하거나 채택하는 쪽은 받은 본문 바이트(`Y.encodeStateAsUpdate` 결과)를 임시 Y.Doc에 넣어 D를 직접 다시 계산한다(§6.5-3, §7.6-4).
- **만드는 방법:** live doc을 그대로 내보내지 않는다. 부모 스냅샷 상태에 W 이하의 봉투를 임시 Y.Doc에서 재생해 만든다. live doc에는 W 밖의 원격 봉투나 아직 봉인하지 않은 로컬 편집이 섞여 있을 수 있기 때문이다. 검증도 같은 재생으로 한다(§6.5-3).
- **Markdown에서 다시 만들지 않는다.** 그렇게 하면 기존 연산 ID를 잃는다(PRD D4, 리뷰 R06). Yjs의 삭제 내용 GC는 Yjs 안에서 따로 일어나며 연산 ID 구조는 유지된다.
- **누가 만드나:** 아무 editor 기기나 만들 수 있다. 조건은 (1) 재생으로 검증한 부모 스냅샷과 W에 든 그 문서의 봉투를 모두 갖고 있고, (2) W에 넣는 구간에 누락·분기·격리가 없고(격리된 봉투가 있는 작성자는 W를 그 봉투 바로 앞에서 멈춘다. 격리 하나가 문서 전체의 스냅샷을 막지 않게 하기 위해서다, 재검증 N11), (3) 마지막 스냅샷 이후 봉투가 일정 수를 넘은 경우다. 만들 기기를 따로 정하지 않는다. 경쟁은 아래 규칙으로 안전하게 처리되므로 조정 비용이 더 크다. 동시에 만드는 일을 줄이려고 무작위 지연만 둔다. 스냅샷 작성자가 오프라인이어도 같은 검증된 이력을 가진 다른 기기가 만들 수 있다(PRD D4).
- **로컬 압축과의 관계:** 지금 로컬 Yjs 로그의 압축 기준(업데이트 64개 또는 1MB, `D/lib/bridge/types.ts:209-212`)은 그대로 둔다. 네트워크 스냅샷은 봉투 저장소에 대한 별도 단계다. 기준값은 C1에서 정한다.

### 6.5 스냅샷 경쟁
같은 부모에서 두 기기가 다른 W로 스냅샷 S1, S2를 동시에 만들 수 있다. 처리는 다음과 같다.
1. **둘 다 유효하다.** 각각 자기 W만큼의 정확한 상태다. Yjs 상태는 합칠 수 있으므로 어느 쪽을 받아도 내용은 같아진다.
2. **다음 스냅샷의 부모는 결정적으로 고른다.** W가 다른 쪽을 지배하면 그쪽을, 아니면 W 합계가 큰 쪽을, 같으면 봉투 ID가 작은 쪽을 고른다. 모든 기기가 같은 답을 낸다. 고르지 않은 쪽은 다음 스냅샷이 덮으면 지울 수 있다.
3. **받은 스냅샷은 결정적 재생으로만 검증한다(재검증 N2).** 스냅샷은 "부모 스냅샷 + 작성자 서명 봉투 중 W 이하"의 캐시일 뿐이다. 기존 기기는 자기가 재생으로 검증했거나 채택한(4) 부모 스냅샷 상태에, 자기가 가진 W 이하 봉투(§5.2 검사와 clientID 고정을 통과한 것)를 임시 Y.Doc에서 재생해 상태 해시 D_r을 계산한다. 그리고 받은 스냅샷 본문 바이트에서 D_c를 직접 다시 계산한다(§6.4). **D_r, D_c, payload의 D 필드가 모두 같을 때만** 받는다(3차 검증 N16). 필드만 비교하면 정직한 D 필드에 위조 본문을 붙인 스냅샷이 통과한다. 받으면 압축 기준으로는 **자기 재생 결과**를 저장하고 받은 본문은 쓰지 않으며, `HeldAck{snapshot_id, D_r}`를 보낸다. 다르면 쓰지 않고 작성 기기를 표시한다. W 이하 봉투 중 빠진 것이 있으면 검증하지 않고 빠진 봉투를 요청한다. 이 비교는 스냅샷에 **빠진 것과 더해진 것을 모두** 잡는다. r2의 멱등 검사(내 업데이트를 적용해도 바뀌지 않는가)는 빠진 것만 잡았다. 남의 clientID로 된 struct나 남의 글을 지우는 delete set을 더한 스냅샷, W를 부풀려 봉투를 빠뜨린 스냅샷 모두 해시가 달라진다. 비용은 스냅샷 간격만큼의 재생이다.
4. **기존 기기는 스냅샷을 live doc에 적용하지 않는다.** 재생 검증을 통과한 스냅샷은 이미 live doc에 있는 봉투들의 결과이므로 적용할 것이 없다. 그래서 스냅샷은 새 연산을 들여오는 통로가 되지 못한다. 재생으로 검증할 수 없는 기기(새 기기, 오래 꺼져 있는 사이 필요한 봉투가 모든 곳에서 지워진 기기)만 §7.6-4의 채택 조건을 거친 뒤 스냅샷을 live doc에 넣고, 그 스냅샷의 `clientID → author` 표로 자기 표를 채운다. 채택 전에는 live doc과 디스크에 넣지 않는다. Y.Doc에 들어간 연산은 되돌릴 수 없기 때문이다.

### 6.6 watermark 삭제
업데이트 봉투 u(문서 d)를 지우는 조건은 모두 만족해야 한다.
1. 이 기기가 §6.5-3의 재생으로 **직접 검증했거나** §7.6-4로 채택한 스냅샷 S가 u를 덮는다(W_S[u.author] ≥ u.counter).
2. S의 저장과 u의 삭제를 SQLite 트랜잭션 하나로 한다. 지금 `R/index.rs:2424-2475`의 `save_yjs_snapshot`이 `id <= up_to`인 행만 지우는 원리를 봉투 저장소에 그대로 쓴다. 스냅샷을 만드는 동안 들어온 봉투는 남는다.
3. u가 격리 중이거나 해결되지 않은 분기에 속하지 않는다.
4. u가 구 epoch 봉투면 보존 기한(§9.3)이 지났다.
5. u의 작성자가 u보다 카운터가 큰 checkpoint를 썼고, 이 기기가 그 checkpoint를 저장하고 있다(§6.6.1-3).
6. 저장 노드(D)는 키가 없어 1을 할 수 없다. 노드는 editor가 서명한 정리 요청을 받아도 **보존 기한이 지난 뒤에만** 실제로 지운다. 악성 editor가 가짜 스냅샷으로 노드의 이력을 지우게 하는 것을 막기 위해서다.

스냅샷은 동기화 상태를 줄이는 장치일 뿐 백업이 아니다(PRD §6.1). 문서 상태 크기, 봉투 로그 크기, 스냅샷 빈도의 상한은 C1 측정으로 정한다(PRD D4).

#### 6.6.1 작성자 checkpoint: 가지치기 뒤의 체인 연속성 (검증 H4)
**공격 시나리오.** 작성자 A의 카운터는 vault 전체에서 하나로 오르고 `prev`가 직전 봉투를 가리킨다. 문서 d1의 업데이트 1~500이 스냅샷에 덮여 지워진 뒤 새 기기 N이 합류한다. N이 받는 것은 스냅샷과 남은 봉투(카운터 501~)뿐이고, 501의 `prev`가 가리키는 봉투는 어디에도 없다. 규칙 2(§6.3)를 따르면 N은 영구히 "일부 변경을 아직 받지 못했습니다"를 띄운다. 규칙을 풀면 노드나 피어가 봉투를 빼돌리는 누락 공격이 다시 열린다. 카운터가 vault 단위라 다른 문서의 봉투만 지워져도 같다. §5.2-4의 "그 체인 위에 있는가" 검사도 지워진 조상을 거칠 수 없다.

**설계 변경.**
1. **문서별 연결:** 헤더에 `doc_prev`(같은 작성자가 같은 문서에 쓴 직전 봉투 ID)를 둔다(§6.2).
2. **checkpoint 봉투:** 작성자는 봉투 N개마다(가설 256, C1에서 정한다), 그리고 `PruneRequest`를 받았을 때 `checkpoint` 봉투를 자기 체인에 쓴다. 일반 봉투처럼 카운터·`prev`·서명을 갖고, 암호화된 본문에 (a) 이 작성자가 지금까지 쓴 문서마다 `(doc_id, 그 문서의 마지막 봉투 카운터, 봉투 ID)`, (b) 직전 checkpoint ID를 담는다. r2에 있던 "지금까지 쓴 Yjs clientID 목록"은 뺀다. 자기 신고 목록이라 악성 editor가 남의 clientID를 적어 피해자 봉투를 격리시킬 수 있었다(재검증 N3). 새 기기의 clientID 표는 채택한 스냅샷의 표와 실제 update 봉투로 채운다(§6.3-5, §6.5-4).
   **요청 제한(재검증 N11):** `PruneRequest` 때문에 쓰는 checkpoint는 작성자마다 일정 간격(가설 24시간, C1에서 정한다)에 한 번으로 묶는다. 그 사이 새 봉투가 없으면 쓰지 않는다. 요청자별 `PruneRequest`도 같은 간격으로 제한한다. 아무 멤버나 요청을 되풀이해 모든 작성자에게 큰 checkpoint를 쓰게 하는 대역폭·저장 소모를 막는다.
3. **지우는 조건:** 작성자 A의 봉투 u는 A의 checkpoint 중 카운터가 u보다 큰 것이 저장돼 있을 때만 지운다(§6.6-5). checkpoint는 더 새 checkpoint가 있을 때만 지운다. 그래서 **각 작성자의 최신 checkpoint 이후 체인은 늘 끊김 없이 남는다.**
4. **검증을 checkpoint에서 다시 시작한다:** 새 기기는 작성자마다 최신 checkpoint를 받아 서명과 그 시점 멤버십을 검증하고, 그 뒤 봉투를 `prev`로 잇는다. checkpoint 이전 구간은 문서별로 확인한다. 문서 d에 대해 checkpoint 표의 마지막 봉투에서 `doc_prev`를 따라 내려가며, 받아들인 스냅샷의 W[A]보다 큰 봉투가 모두 있는지 본다. W[A] 이하는 스냅샷이 덮는다. 문서 하나를 통째로 빼돌려도 checkpoint 표에 그 문서가 있으므로 드러난다.
5. **기준점 검사(§5.2-4):** 기준점 이하 봉투가 그 체인 위에 있는지는 기준점에서 `prev`를 따라가되, 지워진 구간은 checkpoint와 `doc_prev`로 건너뛴다. 제거된 기기는 더 이상 checkpoint를 쓰지 못하므로 그 기기의 마지막 checkpoint부터 기준점까지의 봉투는 지우지 않는다. 양은 checkpoint 간격으로 묶인다.
6. **checkpoint를 믿는 근거:** checkpoint는 작성자 자신의 서명이라 남이 위조할 수 없다. 작성자가 서로 다른 checkpoint를 내면 같은 카운터의 분기이므로 §6.3-3으로 탐지한다. 스냅샷 내용이 맞는지는 checkpoint가 증명하지 않는다. 그것은 재생 검증(§6.5-3)이나 §7.6-4의 채택 조건으로 받는다. 4의 "W[A] 이하는 스냅샷이 덮는다"는 그렇게 받은 스냅샷에만 쓴다. 재생 검증은 W를 부풀린 스냅샷을 해시 불일치로 떨어뜨리므로, 누락을 덮는 스냅샷이 채택되려면 정직한 검증자가 해시를 잘못 보고해야 한다(재검증 N2 4단계).

**남는 한계.**
- checkpoint 표는 작성자가 쓴 문서 수만큼 커진다(문서 1만 개면 수백 KB). C1에서 크기를 재고, 크면 직전 checkpoint와의 차분으로 바꾼다.
- 오래 꺼진 작성자의 봉투는 그 작성자의 마지막 checkpoint까지만 지울 수 있어 저장 공간이 늘 수 있다.
- 모든 경로가 어떤 작성자의 최신 checkpoint와 그 뒤 봉투를 감추면 새 기기는 "그 작성자 동기화 미완료"만 안다(§2.4-5).
- 작성자 해시 체인 + 문서별 연결 + checkpoint는 **직접 구성**이다(§3.3). C1 #9(가지치기 뒤 새 기기 합류)와 C2 외부 리뷰로 검증한다.

## 7. 암호화된 registry/control 프로토콜과 삭제·복구 계약

### 7.1 registry 연산 (PRD F5.3, 리뷰 R04)
registry는 vault의 문서·폴더 목록이다. 모든 연산은 `registry` 봉투(서명, 암호화)다. 연산은 작성자가 본 registry head 목록(`deps`)과 Lamport 값을 담아 인과 DAG를 이룬다. 각 기기는 같은 연산 집합을 결정적인 위상 순서(같은 순위는 봉투 ID 순)로 접어 같은 상태를 계산한다.

| 연산 | 내용(모두 암호화) | 필요한 역할 |
|---|---|---|
| `CreateDoc` | `doc_id`, 경로, 폴더 ID | editor |
| `CreateFolder` | `folder_id`, 이름, 부모 | editor |
| `Move` | `doc_id` 또는 `folder_id`, 이전 위치, 새 위치 | editor |
| `Tombstone` | `doc_id` 목록 또는 `folder_id`와 **그 시점에 아는 하위 항목 목록** | editor |
| `Restore` | `doc_id`/`folder_id` | editor |
| `Purge` | 보존 기한 전 영구 삭제 | admin |

**입력 검증(검증 L1):** 받는 쪽은 서명과 권한이 맞는 연산이라도 다음을 어기면 디스크에 반영하지 않고 격리한다. 경로는 Rust의 `resolve_in_vault`(`R/vault.rs:183-210`, `..`와 절대경로 거부)를 통과해야 한다. 무시 경로(`.context/`, `.git` 등 `rel_path_is_ignored`), Windows 예약 이름(`R/checks.rs`), 노트 확장자 목록 밖의 확장자, 경로 길이 상한을 거부한다.

컨트롤 메시지(`control` 봉투):
- `Heads`: 연결할 때 서로의 멤버십 head, 작성자별 체인 head와 최신 checkpoint, registry head를 교환한다. **내용 교환 전에 멤버십부터 맞춘다(검증 M9).** 상대 head가 더 새 것이면 멤버십을 먼저 받아 검증하고, 그 결과 어느 한쪽이 제거됐으면 내용을 교환하지 않고 연결을 끊는다.
- `HeldAck`: 서명된 확인이고 두 가지 뜻이 있다. 섞어 쓰지 않는다. (a) 문서용 `HeldAck{doc_id, state_vector_digest, holder}`는 "이 state vector까지의 상태를 내가 영속 저장했다"이고 삭제 게이트(§7.5)에 쓴다. (b) 스냅샷용 `HeldAck{snapshot_id, D, holder}`는 "이 스냅샷을 §6.5-3의 재생으로 검증했고 상태 해시가 D로 같았으며 보관한다"이고 스냅샷 채택(§7.6-4)에 쓴다. 재생 검증을 하지 않은 기기는 (b)를 보내지 않는다. 노드는 키가 없어 (b)를 보내지 못한다.
- `PruneRequest`: §6.6의 노드용 정리 요청. 요청자별 속도 제한이 있다(§6.6.1-2).

### 7.2 충돌 규칙
| 상황 | 규칙 | 화면 |
|---|---|---|
| 같은 경로에 다른 `doc_id`(동시 생성, 각자 같은 파일을 가져옴) | 둘 다 유지하고 자동 병합하지 않는다. registry 상태에서 결정적으로 "표시 경로"를 계산해 나중 순위 문서에 ` (2)` 같은 접미사를 붙인다. 모든 기기가 같은 결과를 내므로 이름 바꾸기가 오가지 않는다 | "같은 이름의 노트가 두 개 생겨 하나의 이름을 바꿨습니다" |
| 대소문자나 Unicode 정규화만 다른 경로 | 지금 `D/lib/pathIdentity.ts:25`의 `pathKey`로 같은 경로로 본다(macOS·Windows는 대소문자를 구분하지 않는다). 위 규칙을 적용한다 | 위와 같음 |
| 같은 항목을 동시에 다른 곳으로 이동 | Lamport가 큰 쪽, 같으면 봉투 ID가 큰 쪽이 이긴다. 진 이동은 기록에 남긴다 | 없음 |
| 이동과 삭제가 동시 | 삭제가 이긴다. 복원하면 마지막 이동 위치로 돌아간다 | 휴지통 표시 |
| 삭제와 동시 편집 | 문서는 휴지통 상태로 두고 편집은 CRDT에 보존한다. 허브의 휴지통이 삭제된 노트의 오프라인 변경을 받는 것과 같다 | "삭제된 노트에 새 변경이 있습니다 [복원]" |
| 폴더 삭제 중 그 폴더에 새 문서 | 폴더 `Tombstone`은 그 시점에 알던 하위 항목만 지운다. 새 문서는 살고, 폴더는 그 문서를 위해 남는다 | "다른 기기에서 이 폴더에 새 노트를 만들어 폴더를 남겼습니다" |
| 폴더 이름 변경과 하위 새 문서 | 폴더는 `folder_id`로 식별하므로 새 문서는 바뀐 이름 아래 생긴다 | 없음 |
| 바이너리 파일 | C는 텍스트 전용이라 동기화하지 않는다. Rust 확장자 목록, TS 형식 registry, 동기화 확장자 목록을 계속 같게 유지한다(CLAUDE.md). D의 첨부는 CRDT가 아니므로 충돌하면 사본을 남긴다 | "이 파일은 아직 공유되지 않습니다" |

### 7.3 "부재 ≠ 삭제" 계약
1. 피어가 보낸 목록이나 registry 상태에 문서가 없다는 것은 그 피어가 뒤처졌다는 뜻이다. 로컬 문서를 지우지 않고, 상대에게 없는 연산을 보낸다.
2. 피어가 "그 문서의 내용이 없다"고 해도 빈 문서로 다루지 않는다. 내용을 가진 기기가 나타날 때까지 "내용을 가진 기기를 기다리는 중"으로 둔다. 빈 상태로 시드하지 않는다(§8 pull-before-seed).
3. 삭제는 서명되고 권한이 검증된 `Tombstone` 연산으로만 일어난다.
4. 멤버 제거는 권한 기기가 서명한 멤버십 레코드로만 일어난다. 어떤 피어의 멤버 목록에 내가 없다는 것은 제거가 아니다.
5. 저장 노드나 피어가 봉투를 주지 않는 것은 삭제가 아니다.

지금 허브 프로토콜 신호(`D/lib/sync/vaultProtocol.ts:72-141`)와의 대응은 다음과 같다.
| 허브 신호 | 뜻 | P2P에서의 대응 |
|---|---|---|
| `empty` | 서버에 그 문서 내용이 없다 | 연결 때 `Heads`로 문서별 보유 상태를 알린다. 상대에게 없는 내용을 보낸다 |
| `behind` | 내 기기에 서버가 모르는 연산이 있다 | 작성자별 체인 head를 비교해 상대에게 없는 봉투를 보낸다 |
| `revoked` | 문서 읽기 권한이 회수됐다(서버가 이름을 명시) | vault 단위 회수만 있다. 근거는 권한 기기의 `RemoveDevice`/`RemoveUser` 서명 레코드뿐이다. 문서 단위 회수는 폴더 키(D) 이후 |
| `tombstones` | 소프트 삭제됨 | 서명된 `Tombstone` 연산 |
| `covered` | 서버가 내가 보낸 state vector를 모두 보관했다(삭제 게이트용 확인) | `HeldAck`. 지금 `D/lib/sync/ackedSv.ts:1-14`가 서버 확인 state vector를 문서별로 늘려 가며 기록하는 것과 같은 방식으로, "다른 곳에 영속 저장된 것으로 확인된 state vector"를 기록한다. 단 `ackedSv`는 "서버는 연산을 잊지 않는다"(`ackedSv.ts:13-14`)를 전제로 값이 줄어들지 않는다. P2P 확인은 확인한 기기가 제거되거나 디스크를 잃으면 무효가 되므로, 확인을 기기별로 저장하고 쓸 때마다 다시 계산한다(검증 M6) |

### 7.4 대량 변경 가드
지금 허브 경로의 받는 쪽 가드(`D/lib/sync/inbound.ts:376-398`)를 P2P registry 적용에도 그대로 쓴다. 한 번에 들어온 삭제가 `max(5, 20%)`, 이동이 `max(20, 30%)`를 넘으면 디스크에 반영하지 않고 사용자에게 묻는다. 허브에서는 서버 목록이 잘린 경우를 막는 장치였다. P2P에서는 고장 난 멤버나 실수로 생긴 큰 사고를 늦추는 장치가 된다. registry 상태 자체는 수렴하고, 디스크 반영만 보류한다. 화면에는 "○○님이 노트 120개를 지웠습니다. 이 기기에도 적용할까요?"를 보여 준다.

이 가드는 한 번에 들어온 묶음 단위로 센다. 연결할 때마다 4개씩 지우면 걸리지 않는다. 그래서 **작성자별 누적 상한**을 더한다(검증 M5). 한 작성자의 삭제가 24시간 동안 `max(5, 20%)`, 이동이 `max(20, 30%)`를 넘으면 그 뒤 연산의 디스크 반영을 보류하고 모든 admin에게 알린다. 값은 C1에서 조정한다. 그래도 이 가드는 **악성 멤버를 막는 장치가 아니다.** 상한 아래로 천천히 지우는 멤버는 막지 못하고, 누군가 휴지통 보존 기한(30일) 안에 알아차려야 복원할 수 있다.

### 7.5 삭제·복구 계약
- **삭제:** `Tombstone`을 받으면 파일을 지금과 같은 `.context/trash`(`R/checks.rs:78`)로 옮긴다. CRDT 상태와 봉투는 남긴다.
- **아직 확인받지 않은 로컬 변경:** 삭제할 파일에 `HeldAck`로 덮이지 않은 로컬 변경이 있으면 휴지통으로 옮기기 전에 그 변경을 먼저 내보내고, 복구 사본을 남긴다. 지금 허브의 삭제 게이트와 같은 원칙이다(`D/lib/sync/ackedSv.ts:4-8`). 이 게이트에 쓰는 `HeldAck`는 **권한 기기의 확인이거나 서로 다른 사용자 둘 이상의 기기 확인**일 때만 인정한다. 확인한 기기가 제거되면 그 기기의 `HeldAck`를 무효로 하고 다시 계산한다(검증 M6). 악성 멤버의 거짓 확인 하나로 복구 사본 없이 휴지통에 보내지 않기 위해서다. 노드의 `HeldAck`를 어떻게 셀지는 D에서 정한다.
- **보존:** 휴지통 항목은 기본 30일 뒤 각 기기에서 지운다(PRD §6.2). admin의 `Purge`는 기한 전 영구 삭제다.
- **복원:** `Restore` 연산. 원래 경로가 차 있으면 §7.2의 경로 충돌 규칙을 쓴다.
- **원칙(재검증 N3~N5):** 뒤집힐 수 있는 판정에는 되돌릴 수 없는 자동 조치를 붙이지 않는다. 격리, 무효가 된 가지, 제거는 나중에 분기 규칙(§5.5.1)이나 관리자 판단으로 뒤집힐 수 있다. 그래서 자동으로 하는 일은 멈춤과 보존뿐이고, 지우는 일은 사람이 누른 뒤에만 한다.
- **격리된 봉투:** 제거된 기기의 기준점 이후 봉투, 이중 발행으로 판정된 가지, clientID 충돌, 무효가 된 인수 가지에서 추가된 기기의 봉투는 "확인이 필요한 변경"으로 관리자에게 보여 준다. 관리자가 받거나 버린다. **보존 기한이 지나도 자동으로 지우지 않는다.** r2는 기한 뒤 내용을 지웠다. 그러면 남의 clientID를 주장하거나(N3) 인수를 철회해(N4) 정직한 편집을 격리시킨 뒤 만료로 지우는 경로가 생겼다. 저장 공간은 작성자별 quota(§2.2)로 묶고, 격리 저장소가 quota를 넘으면 관리자에게 정리를 묻는다.
- **제거된 멤버의 기기(재검증 N5):** 서명된 제거 레코드를 받은 정직한 클라이언트는 그 vault를 **봉인**한다. 동기화와 서명을 멈추고, 키·봉투 저장소·outbox·디스크의 Markdown을 그대로 둔다. 자동으로 지우지 않는다. 제거는 뒤집힐 수 있다. 무효가 된 예비 인수의 제거, 복구 인수가 해제한 제거가 그렇다(§5.5.1). r2는 제거를 받으면 키와 봉투를 지웠으므로, 그 제거가 무효가 돼도 미전송 편집을 되살릴 길이 없었다. 합류 폴더는 비어 있어야 해서(§7.6) 다시 넣을 수도 없었다. 봉인한 기기가 제거가 무효가 된 체인을 받으면 봉인을 풀고 outbox부터 다시 보낸다. 키를 남겨도 새로 새는 것은 없다. 그 기기는 이미 그 키들을 가졌고 새 epoch 키는 받지 못한다. 평문은 어차피 회수할 수 없고, 위조되거나 탈취된 권한 기기의 제거로 사용자의 파일을 지우는 위험이 더 크다. 화면에는 "이 vault에서 나갔습니다. 파일은 이 기기에 남아 있습니다 [이 기기에서 지우기]"를 보여 준다. [이 기기에서 지우기]는 보내지 못한 변경이 있으면 개수를 먼저 보여 준다. outbox는 어떤 경우에도 자동으로 지우지 않는다. 허브는 회수된 노트를 로컬에서 지운다(`D/lib/sync/inbound.ts:380-392`의 설명). P2P가 다르게 동작하는 이유를 제거 확인 화면에 적는다(PRD F5.5 "이미 받은 내용은 남는다").

### 7.6 P2P bootstrap 완료 기준 (PRD F5.4)
새 기기는 다음을 모두 만족해야 vault가 준비됐다고 본다.
1. 멤버십 head가 티켓의 head 이상이고 체인 검증을 통과했다.
2. registry head를 권한 기기에서 받았거나, 서로 다른 두 기기(D에서는 노드 포함)가 같은 head를 보고했다. 첫 빈 응답 하나로 끝내지 않는다.
3. registry의 각 문서에 대해 내용을 받았거나 "내용을 가진 기기를 기다리는 중"으로 표시했다.
4. **스냅샷 채택(검증 M11, H4, 재검증 N2):** 원래 봉투가 남아 있으면 먼저 받아서 스스로 재생 검증한다(§6.5-3). 그럴 수 없으면 그 스냅샷 ID와 상태 해시 D에 대한 스냅샷용 `HeldAck`(§7.1)를 다음 중 하나만큼 받아야 채택한다. (a) 권한 기기 하나, (b) 새 기기와 같은 사용자의 다른 기기 하나, (c) **스냅샷 작성자의 사용자가 아닌** 서로 다른 사용자 두 명의 기기. r2는 작성자 자신도 두 명에 넣을 수 있어 악성 작성자 하나와 정직한 기기 하나로 조건이 채워졌다. 이제 `HeldAck`는 재생 결과가 같다는 뜻이므로 정직한 기기는 위조 스냅샷에 보내지 않는다. 그래서 위조 스냅샷을 채택시키려면 작성자 외에 악성 사용자 둘이 담합해야 한다. 새 기기는 채택 전에 받은 본문 바이트로 D를 직접 다시 계산하고(§6.4), 그 값이 D 필드와 `HeldAck`의 D 모두와 같을 때만 채택한다(3차 검증 N16). 정직한 D 필드에 위조 본문을 붙인 스냅샷은 여기서 떨어진다. 채택 전에는 스냅샷을 live doc과 디스크에 넣지 않는다(§6.5-4). 그 문서는 "확인 중"으로 표시하고 내용은 보여 주지 않는다.
5. 작성자마다 최신 checkpoint와 그 뒤 체인을 검증했다(§6.6.1-4).

합류할 폴더는 비어 있어야 한다. 비어 있지 않으면 합류를 거절하거나, 합류 뒤 기존 파일을 새 문서로 가져오는 선택지를 준다. 기존 로컬 파일을 이미 있는 `doc_id`에 시드하지 않는다.

### 7.7 `.context/` 처리
P2P의 봉투 저장소, head, 멤버십 체인, registry 상태, 격리 목록은 `.context/index.sqlite`의 **새 테이블**에 둔다. `.context/` 전체를 동기화하지 않고, 공유하는 것은 위에서 정의한 봉투뿐이다. `.context`는 지금처럼 트리 탐색과 감시에서 빠진다(`R/vault.rs:10`, `R/vault.rs:84`). 파일 신원 맵은 로컬 전용으로 남는다. 키는 `.context`가 아니라 키체인에 둔다(§4.1).

## 8. 기존 브리지 계약 유지 방법 (PRD F5.4, 리뷰 R05)

### 8.1 끼우는 자리
```
디스크 Markdown ⇄ [Rust 감시 150ms] ⇄ NoteBridge(Y.Doc, Y.Text "content") ⇄ 네트워크 어댑터
                                         (바꾸지 않음)
  열린 노트   허브: HocuspocusProvider                        P2P: P2P 문서 세션(신규)
  vault 전체  허브: VaultSyncEngine ─┐                         P2P: P2P vault 엔진(신규) ─┐
                                     └→ DocUpdateSink(VaultDocStore: hot 브리지 / cold 임시 브리지) ←┘
```
지금 허브 동기화는 두 갈래다(검증 M1). 열린 노트는 `HocuspocusProvider`(`D/lib/sync/syncManager.ts:260`)로 붙는다. vault 전체는 `VaultSyncEngine`(`D/lib/sync/vaultSyncEngine.ts:338`)이 `DocUpdateSink` 인터페이스(`vaultSyncEngine.ts:61`)로 `VaultDocStore`(`D/lib/sync/vaultDocStore.ts:133`)에 쓴다. `VaultDocStore`는 최근 노트 100개(`HOT_DOC_CAP`, `vaultDocStore.ts:36`)만 브리지를 상주시키고, 나머지는 원격 업데이트가 오면 임시 headless 브리지를 열어 적용·디스크 쓰기·저장 뒤 닫는다(`vaultDocStore.ts:1-26`). 닫힌 노트를 외부 프로그램이나 AI가 디스크에서 고친 변경은 `docSession.ts`의 `handleLocalFileChanged`(`D/lib/sync/docSession.ts:3426`) 경로로 나가고, 대량 업로드는 `contentUpload.ts`가 한다.

P2P는 **두 자리에 모두** 들어간다.
1. **vault 채널:** P2P vault 엔진이 `VaultSyncEngine` 대신 같은 `DocUpdateSink`에 검증된 원격 업데이트를 넘긴다. hot·cold 분리와 cold 임시 브리지는 그대로 쓴다. 송신은 닫힌 노트의 디스크 변경(cold ingest)도 포함한다.
2. **열린 노트:** P2P 문서 세션이 provider 자리에서 실시간 업데이트와 presence를 맡는다.

`NoteBridge`는 한 줄도 바꾸지 않는 것이 목표다. `docSession.ts`(7,565줄)의 허브 전용 재조정과 `contentUpload.ts`는 P2P에서 재사용하지 않는다. 거기서 지키던 원칙(pull-before-seed, 삭제 게이트, 대량 가드)은 §7과 §8.2에서 P2P용으로 다시 정했다.

### 8.2 지키는 계약
| 계약 | 지금 코드 | P2P에서 지키는 방법 |
|---|---|---|
| 디스크 Markdown이 영속 진실 | Rust 원자적 쓰기, 브리지 egest | P2P 계층은 Markdown을 직접 쓰지 않는다. 받은 내용은 항상 Y.Doc을 거쳐 브리지 egest(300ms)로만 디스크에 간다 |
| `Y.Text("content")`가 실시간 진실 | `D/lib/bridge/noteBridge.ts:190` | 받은 업데이트는 같은 `doc_id`의 **같은 실시간 Y.Doc**에 `applyRemote`(`noteBridge.ts:1267-1268`, origin `remote`)로 적용한다. 별도 Y.Doc에 시드하지 않는다. 스냅샷은 재생 검증할 수 없는 기기가 §7.6-4로 채택한 경우에만 같은 방식으로 적용한다. 기존 기기는 스냅샷을 live doc에 적용하지 않는다(§6.5-4). 재생 검증은 Rust·WebView 어느 쪽이든 live doc과 분리된 임시 문서에서 한다 |
| 에코 가드 1: 디스크 origin은 egest하지 않음 | `noteBridge.ts:249` | 그대로. 이 가드는 디스크로 다시 쓰는 것만 막는다 |
| 디스크 origin은 네트워크로 **보낸다** | 허브 provider는 origin과 관계없이 문서 업데이트를 보낸다 | P2P 세션은 origin이 `remote`이거나 `"persistence"`(로컬 로그 재생)인 트랜잭션만 빼고 모두 보낸다. 디스크, 에디터, AI 변경이 모두 동료에게 간다. 닫힌 노트의 cold 경로도 같다(§8.1). `remote`를 다시 보내지 않는 이유는 에코 때문만이 아니다. 남의 연산을 내 서명으로 보내면 작성자가 바뀌기 때문이다 |
| 에코 가드 2: `lastWrittenHash` | `noteBridge.ts:778`, 쓰기 확인 후 해시 갱신 `noteBridge.ts:1041-1057` | 그대로. P2P는 이 값을 네트워크 ACK나 스냅샷 일치의 증거로 쓰지 않는다. 네트워크 확인은 `HeldAck`다 |
| 동시 디스크 읽기 보호 | `noteBridge.ts:712-728` | 그대로. 원격 업데이트가 디스크 읽기와 겹쳐도 지금과 같은 경로를 탄다 |
| 지연 시간 | 감시 150ms(`R/watcher.rs:46`), 수신 150ms·내보내기 300ms(`D/lib/bridge/types.ts:207-208`) | 바꾸지 않는다. P2P는 **송신 쪽에만** 짧은 묶음 창(가설 50ms, C1에서 측정 후 결정)을 둔다 |
| pull-before-seed | 로그인한 vault의 빈 문서는 받아오기 전에 시드하지 않는다(`noteBridge.ts:340-346`) | P2P vault는 "로그인한 vault"와 같이 다룬다. 받아오기 완료는 §7.6 기준을 쓴다. 로컬 전용 시드는 vault를 만드는 기기의 첫 시드에만 허용한다 |
| `diskBase`와 복구 사본 | `noteBridge.ts:52`, `402-409` | 그대로 |
| `.context/` 비공개 | `R/vault.rs:10` | §7.7 |
| 바이너리는 노트 CRDT에 들어가지 않음 | 확장자 목록 일치(CLAUDE.md) | C는 텍스트 전용. registry도 노트 확장자 문서만 다룬다 |

### 8.3 보내기와 받기의 원자성
- **보내기(검증 M2):** 봉투에는 **이 기기의 로컬 트랜잭션이 만든 업데이트만** 넣는다. 살아 있는 경로는 문서의 트랜잭션별 업데이트 이벤트 중 origin이 `remote`·`"persistence"`가 아닌 것을 받는다. 트랜잭션별 업데이트는 그 트랜잭션이 새로 만든 struct와 새로 지운 범위만 담는다. 디스크 병합 경로(`noteBridge.ts:950`)도 `Y.encodeStateAsUpdate(target, vector)`를 live doc에 `ORIGIN_DISK`로 적용하므로, 봉투에 들어가는 것은 그 적용으로 live doc에 새로 생긴 변경뿐이다.
  r1은 강제 종료 복구에 `Y.encodeStateAsUpdate(doc, 봉투로 만든 state vector)`를 썼다. 이 함수는 sv에 없는 **모든 clientID**의 struct와 **전체 delete set**을 쓰므로(yjs 13.6 `utils/encoding.js`), sv에 빠진 원격 연산이 있으면 남의 연산이 내 서명으로 나간다. §8.2와 모순이고 clientID 고정(§6.3-5)에도 걸린다. 그래서 복구 경로를 바꾼다. 로컬 로그 저장 IPC는 지금 origin 없이 모든 업데이트를 저장한다(`appendUpdate`, `noteBridge.ts:209-219`). 여기에 origin 구분(로컬/원격/재생)을 더하고, Rust가 로컬 업데이트를 평문 로그와 **같은 SQLite 트랜잭션**으로 `p2p_outbox` 테이블에도 넣는다. 봉인과 봉투 저장이 끝나면 같은 트랜잭션에서 outbox 행을 지운다. 재시작하면 outbox에 남은 행만 봉인한다. 키 교체 뒤의 재봉인(§5.3)과 오래 꺼졌던 기기의 재봉인(§9.3)도 outbox 바이트로 한다.
  남는 한계: delete set은 삭제한 사람을 담지 않으므로 서명은 "이 기기가 이 삭제 범위를 보냈다"까지만 증명한다(§2.4-7).
- **받기:** Rust가 검증·복호화한 뒤 봉투와 head를 저장하고, 그다음에 WebView로 평문 업데이트를 넘긴다. WebView 적용 전에 꺼져도 다음 실행 때 저장된 봉투에서 다시 적용한다. Yjs 적용은 멱등이다.
- **저장 공간:** 평문 로컬 로그와 암호화된 봉투 저장소를 둘 다 둔다. 로컬 로그는 지금 계약(빠른 로드, 호환)을 위해, 봉투 저장소는 다른 기기에 전달하기 위해서다. 두 배 가까운 공간이 들 수 있으므로 C1에서 측정한다.

### 8.4 바뀌지 않음을 확인하는 방법
기존 데스크톱 테스트(`pnpm test`, `cargo test`)를 그대로 통과해야 한다. 여기에 C1의 브리지 시나리오(§10.4의 5번)를 더한다. 원격 편집 한 번에 받는 기기의 디스크 쓰기는 한 번 이하이고(egest가 묶을 수 있다), 10분 동안 편집이 없으면 쓰기가 0번이어야 한다(되먹임 없음). 외부 프로그램이 파일을 바꾸면 동료 화면에 반영되어야 한다. 열린 노트와 닫힌 노트(hot·cold) 모두 시험한다.

## 9. 열린 질문 권고

### 9.1 Q1: C0의 기술 선택
§3의 결론대로 **Iroh 1.x 위 직접 구현**을 권고한다. p2panda는 재평가 후보로 두고, NextGraph와 Automerge 계열은 기각한다. C2 착수 전에 §3.3의 재평가 조건을 다시 확인한다.

### 9.2 Q4: 여러 관리자 기기의 동시 권한
**권고: C·D 동안 동시 다중 발행은 하지 않는다. 대신 "예비 권한 기기" 한 대를 지정할 수 있게 한다.**
- 동시 발행을 허용하면 끊긴 상태의 두 관리자가 서로 다른 멤버십과 키를 만든다. 이를 풀려면 p2panda-auth 같은 DAG 해결 규칙이나 MLS의 순서 서비스가 필요하다(리뷰 R01). 2~15명 팀이 얻는 이득에 비해 프로토콜과 검증 비용이 크다.
- 실제 불편은 "권한 기기가 꺼져 있으면 멤버 변경이 멈춘다"이다. 이것은 동시 권한 없이 다음으로 푼다.
  1. 다른 admin의 요청 대기열(§5.4)
  2. 권한 기기의 자발적 이양(`TransferAuthority`)
  3. **예비 권한 기기:** 권한 기기가 `SetStandby`로 다른 admin 기기 하나를 지정한다. 정직한 예비 기기는 인수 공지(`TakeoverNotice`) 후 24시간 뒤에 인수한다. 이 대기는 관례이고 받는 쪽이 강제하지 않는다. 즉시 인수는 복구 키가 함께 서명할 때만 된다. 유효한 인수는 동시인 옛 권한 기기 레코드보다 우선하지만 제거·강등을 되돌리지 못한다. 옛 권한 기기나 복구 키가 확인하기 전까지는 잠정이고, 그동안 권한 기기의 `RevokeStandby`가 있으면 무효다(§5.5.1-8). 예비 기기는 모든 epoch 키를 함께 받으므로 루트 목록(§2.4-3)에 넣는다. 예비 기기는 보안 장치가 아니라 가용성 장치다.
  4. 복구 코드(§4.5)
- **재검토 기준:** C2 베타에서 "멤버십 요청이 24시간 넘게 대기한 비율"과 "예비 권한 기기 인수 횟수"를 기록한다. 대기가 흔하면 E 이후에 DAG 기반 다중 관리자(p2panda-auth의 strong removal 규칙, 또는 감사된 Keyhive)를 다시 평가한다.

### 9.3 Q5: 구 epoch 보존 기한
**권고: 기본 30일을 유지한다. 단, 무엇을 30일 보존하는지 다시 정의한다.**
- **30일 보존 대상은 구 epoch 봉투의 본문**이다. 새 epoch의 스냅샷이 그 봉투들을 덮고(§6.6), 그 스냅샷이 다른 곳에 영속 저장됐다는 `HeldAck`가 있을 때만 30일 뒤에 지운다.
- **epoch 키는 vault 수명 동안 보존한다.** 키는 작다. 현역 기기가 오래 꺼져 있다 돌아와 구 epoch로 만든 미전송 변경을 보내도 열 수 있어야 하고, 이력 보기와 내보내기, F7 전환에도 필요하다. 제거된 기기는 옛 키를 이미 갖고 있으므로 현역 기기가 키를 계속 보관해도 새로 새는 것은 없다.
- **미수령 기기의 `KeyPackage`는 기한 없이 보존한다**(§5.3).
- **그래서 30일은 현역 기기의 오프라인 복귀 한도가 아니다.** 30일 넘게 꺼져 있던 현역 기기도 (1) 자기 미전송 변경을 outbox에서 새 epoch로 다시 봉인해 보내고(§8.3, 남의 연산은 다시 서명하지 않는다), (2) 최신 스냅샷으로 따라잡는다.
- **격리 봉투에는 30일을 적용하지 않는다(r3).** r2는 격리 봉투를 보존 기한 뒤 지워 30일이 데이터 손실 경계였다. 재검증 N3·N4가 이 만료를 악용하는 경로를 보였으므로, 격리 봉투는 관리자가 받거나 버릴 때까지 남긴다(§7.5). 남은 위험은 저장 공간이고 quota로 다룬다. PRD D4·§6.2의 "오프라인 복귀 한도"라는 표현을 이렇게 고친다.
- **관리자 설정 범위:** 7~365일. 디스크가 부족하면 기한 전 정리를 묻는다. legal hold는 범위 밖이다(PRD §6.2).

## 10. C1 같은 망(LAN) 실험 계획

### 10.1 목표
§4~§8의 계약이 실제 기기 2~3대에서 성립하는지, 그리고 비개발자가 같은 Wi-Fi에서 인터넷 없이 서로의 편집을 볼 수 있는지 확인한다. 결과는 `docs/reports/`에 C1 실험 보고서로 남긴다.

### 10.2 범위
| 포함 | 제외(이후 단계) |
|---|---|
| 텍스트 전용 새 vault 하나, 기기 2~3대 | 중계와 인터넷 경로(C2) |
| 기기 키, 복구 코드 생성과 내부 복구 시험 | 저장 노드(D) |
| 초대 티켓(링크·QR)과 승인, 단일 권한 기기 | 첨부(D) |
| 봉투 v1, 작성자 체인, 쓰기 권한 검증 | 게스트(reader) 출시(C2 이후). 단, 강등으로 검증 경로는 시험 |
| 멤버십 체인, 제거 1회와 3단계 키 교체 | 로컬 MCP(D), 허브 전환(F) |
| registry 연산과 충돌 규칙, 대량 변경 가드 | 여러 vault 동시 사용 다듬기, 모바일 |
| 스냅샷, 경쟁, watermark 삭제 | 공개 DNS 주소 게시 |
| 브리지 연결(§8), 화면의 연결 상태 3종 | |

네트워크 설정: `RelayMode::Disabled`, DNS 주소 조회 끔, `iroh-mdns-address-lookup` 켬, 수동 피어 주소 입력 가능.

### 10.3 환경
- 기기: macOS 15와 macOS 27(Apple silicon, 27 정식판에서도 권한 창 미표시 보고가 있다), Windows 11, Ubuntu 24.04 LTS 각 1대 이상. 같은 OS 두 대 조합도 시험한다.
- 망: (a) 인터넷 선을 뺀 가정용 공유기, (b) 기기 간 통신 차단(AP isolation)을 켠 AP, (c) 휴대폰 핫스팟, (d) 방화벽으로 UDP 차단, (e) Wi-Fi와 유선 혼합, (f) 절전 후 재개.
- macOS 로컬 네트워크 권한: macOS 15부터 앱의 같은 망 접근에 사용자 승인이 필요하고, 권한 요청 창이 뜨지 않는 사례가 Apple 개발자 포럼에 보고돼 있다(§13). `NSLocalNetworkUsageDescription`·`NSBonjourServices` 설정(PRD F5.6), 승인, 거부, 창이 뜨지 않음 세 경우를 모두 시험한다. 시험 기기는 깨끗한 상태로 준비한다.

측정 로그에는 본문, 제목, 티켓, 키를 넣지 않는다(PRD §6.7). 가설 값으로 LAN 편집 전파 p95 1초 이하, 발견 10초 이하를 두지만 목표 수치는 C1 기준선 측정 뒤에 정한다(PRD §11).

### 10.6 C1에서 정할 값
송신 묶음 창, 네트워크 스냅샷 기준(봉투 수와 바이트), padding 구간, 봉투·문서 크기 상한, 작성자별 저장 quota, checkpoint 간격과 표 크기, 누적 대량 변경 상한, 휴대폰 핫스팟과 AP isolation에서의 안내 문구, 수동 주소 입력 UX. 그리고 Yjs clientID 충돌 확률 추정(L7)과 `yrs`·JS Yjs v1 인코딩 왕복 결과를 보고서에 넣는다.

### 10.7 중단 기준
다음 중 하나면 C2 계획 전에 설계를 다시 본다. 흔한 가정용 공유기에서 mDNS 발견 실패가 잦다(수동 페어링 UX를 1급으로 올린다). 저장 공간이 평문 로그의 3배를 넘는다(봉투 저장소와 로컬 로그 통합을 검토한다). 2번 시나리오에서 확인된 편집 손실이 한 번이라도 나온다.

## 11. PRD 반영 제안과 리뷰 대응

### 11.1 PRD v2에 반영할 변경 제안
1. **D4:** "멤버십 epoch"를 멤버십 seq와 키 epoch(번호와 `key_id`)로 나눈다.
2. **D4:** 확정 조건을 "전원 ACK, 또는 관리자 선택과 기한 경과"로 바꾸고, 미수령 기기의 감싼 키는 기한 없이 보존한다고 적는다.
3. **D4, §6.2, Q5:** 30일은 구 epoch 봉투 본문의 보존 기한이며 키는 vault 수명 동안 보존한다. "오프라인 복귀 한도"라는 표현을 바꾼다.
4. **D4:** 제거·강등 레코드에 기기별 기준점을 넣고, 기준점 이후 봉투는 격리 후 관리자 확인으로 처리한다.
5. **F5.1:** 기기 키를 vault별로 파생하고, 전송 키를 서명 키와 분리한다. 복구 키를 권한 기기 위의 루트로 명시한다. OS 비밀 저장소가 없으면 P2P를 켜지 않는다.
6. **F5.3:** 제거된 멤버의 기기는 봉인만 한다. 동기화를 멈추고 키·봉투·outbox·Markdown을 자동으로 지우지 않는다. 허브와 다른 이유(제거가 뒤집힐 수 있음, 평문은 회수 불가)를 적는다.
7. **F5.3:** 대량 변경 가드(`D/lib/sync/inbound.ts:376-398`)를 P2P에도 적용한다.
8. **Q4:** 동시 다중 권한 대신 예비 권한 기기 한 대.
9. **D2, D7:** C1과 사내망 전용 모드에서 DNS 주소 조회를 끈다. Iroh 기본 DNS 조회가 EndpointId 기록을 평문으로 게시한다는 사실을 관측 정보 목록에 넣는다.
10. **D4:** 준비 단계의 "새 스냅샷 watermark 기록"을 "제거 기기별 기준점(그 기기의 체인 head)"으로 바꾼다(검증 L3). 스냅샷은 이제 키 교체와 무관하다.
11. **D4:** 감싼 epoch 키는 권한 기기가 서명하고, 받는 기기는 키 확인값을 맞춘 뒤에만 쓴다(§5.3.1). 멤버십 분기에서 제거·강등은 합집합이다(§5.5.1).
12. **F5.1:** 복구 코드 보유자를 기록한다. 복구 코드는 복구 코드로만 바꾼다. 보유자를 제거할 때 코드를 입력하면 같은 교체에서 복구 키를 바꾸고, 입력할 수 없으면 이후 epoch를 복구 키로 감싸지 않으며 "새 vault로 복사"를 안내한다. 퇴사 전에 코드로 교체하는 협조 퇴사를 권한다(§4.5.1). 자동 기기 승인은 C에서 두지 않는다(§4.2).
13. **Q4:** 예비 권한 기기의 인수는 옛 권한 기기나 복구 코드가 확인하기 전까지 잠정이다. 제거를 되돌리지 못하고, 루트 목록에 포함한다(§5.5.1, §9.2).
14. **§6.2, Q5:** 격리 봉투는 자동으로 지우지 않는다. 저장 공간은 quota와 관리자 정리로 다룬다(§7.5, §9.3).
15. **D4:** 스냅샷은 작성자 서명 봉투의 결정적 재생 결과와 상태 해시가 같을 때만 쓴다. 기존 기기는 스냅샷을 live doc에 적용하지 않는다(§6.5).

## 12. 이 문서가 검증하지 않은 것
- 프로토타입, 테스트, 성능 측정, 실기기 네트워크 시험은 하지 않았다. 모든 수치 목표는 C1 이후에 정한다.
- 암호 crate(ed25519-dalek, x25519-dalek, hpke)의 감사 여부는 확인하지 않았다. C2 보안 리뷰에서 확인한다.
- NextGraph의 broker 없는 기기 간 동기화가 코드에 있는지는 확인하지 않았다. 문서와 릴리스 노트만 근거로 했다.
- Iroh mDNS의 Windows·Linux 동작과 macOS 권한 창 동작은 공식 문서에 없어 C1에서 확인한다.
- Yjs 14(`@y/y`)로 올라갈 때 업데이트 형식이 바뀌는지 확인하지 않았다(A6).
- r2·r3에서 넣은 직접 구성(§3.3 목록)은 형식 검증(모델 검사 등)을 하지 않았다. r3 규칙은 재검증 보고서를 다시 받지 않았다. C1의 속성 기반 테스트와 C2 외부 보안 리뷰가 첫 검증이다.
- `yrs` 0.28이 JS Yjs 13.6의 v1 업데이트를 같은 struct로 읽는지 확인하지 않았다. C1에서 왕복 테스트로 확인한다.

## 14. 검증 반영 기록

§14.1~14.4는 1차 반영(r2) 기록이다. 대상: `docs/reports/C0-VERIFY-opus.md`(커밋 d4dc9f8). 판정 "수정 후 승인"의 지적을 모두 다뤘다. 미반영은 없고, 일부는 설계로 닫되 남는 한계를 명시했다. 이 표에 적힌 규칙 중 H3의 두 사람 서명, H4의 checkpoint clientID 목록, Q5의 격리 만료는 r3에서 바꾸거나 지웠다(§14.5).
