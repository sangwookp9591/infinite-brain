# C0 설계 검증: 서버 없는 공유(P2P)

관련 문서: [PRD v2](2026-10-15-team-second-brain-prd.md)(§4 D1~D4·D7, §5.5 F5, §6, §9 C0, §11, §12 Q1·Q4·Q5), [Astra 리뷰](../../reports/PRD-REVIEW-team-second-brain-astra.md), `CLAUDE.md`(불변 조건)

> **이 문서의 역할.** PRD §9의 C0 출시 조건("설계 문서 승인")을 위한 산출물이다. 위협 모델, 기기 신원과 복구, 멤버십 epoch와 키 교체, 스냅샷 경쟁, 암호화된 registry/control 프로토콜, 삭제·복구 계약을 정하고, 구현 기반 기술을 §12 Q1의 기준으로 평가한 뒤 C1(같은 망 실험)의 작업을 나눈다. 코드는 바꾸지 않는다.

경로 약어는 PRD와 같다. `S/` = `app/apps/server/src/`, `D/` = `app/apps/desktop/src/`, `R/` = `app/apps/desktop/src-tauri/src/`. 줄 번호는 이 문서를 쓴 브랜치의 시작 커밋 `c10a7ea` 기준이다.

**표기 규칙.** 문장마다 근거의 종류를 구분한다.
- **[사실]** 저장소 코드(파일:줄)나 공식 문서·저장소(링크와 확인일)로 확인한 것.
- **[설계]** 이 문서가 정하는 계약. C1에서 구현하고 검증한다.
- **[추측]** 확인하지 않은 예상. C1 실험이나 추가 조사로 확정해야 한다.
- **[결정 필요]** 사용자 결정이 필요한 항목. 이 문서는 안전한 기본값을 적어 두고, 목록은 `docs/reports/IMPL-REPORT-C0.md`에 모은다.

## 0. 요약

- **권고:** Iroh 1.x를 연결 계층으로만 쓰고, 봉투·멤버십·registry·스냅샷은 이 문서의 프로토콜로 직접 구현한다(§7). NextGraph는 Yjs 이진 이력을 그대로 보존하는 경로와 브로커 없는 순수 LAN 동작이 확인되지 않아 1차 기반으로 쓰지 않는다.
- **핵심 결정 다섯 가지**
  1. 순서는 **한 대의 권한 기기가 서명하는 해시 사슬 멤버십 로그**로만 정한다. 문서 본문에는 전역 순서가 필요 없다(Yjs가 수렴한다).
  2. 봉투는 **보내기 직전에 봉인**한다(seal-at-send). 로컬 미전송 변경은 평문 Yjs 업데이트로 로컬에만 두고, 보낼 때의 최신 epoch 키로 암호화한다. 그래서 키 교체가 오프라인 편집을 잃게 하지 않는다(R02).
  3. 스냅샷은 **대체가 아니라 합칠 수 있는 체크포인트**다. 경쟁하는 두 스냅샷은 둘 다 적용하면 된다. 업데이트를 지우는 조건은 "로컬에서 포함을 검증한 스냅샷이 있다"뿐이다(R01, R06).
  4. 작성자별·문서별 **연속 카운터**로 누락을 감지한다. 빠진 번호가 있으면 "동기화 미완료"다(R07).
  5. 목록에 없다는 것은 삭제가 아니다. 삭제는 **서명된 tombstone**으로만 일어나고, 지금의 허브 삭제 가드를 그대로 통과해야 디스크에 반영된다(R04).
- **C1 범위:** 텍스트 전용 새 vault, 2~3대, 같은 망, 숨은 개발자 설정. 첨부, 저장 노드, 게스트, 인터넷 경로는 C1에 넣지 않는다(§9).

## 1. 범위와 전제

### 1.1 이 문서가 다루는 것
- P2P 모드 vault 하나의 신원, 권한, 순서, 암호화, 저장, 동기화, 삭제, 복구 계약.
- 지금 코드와의 접점(§8)과 C1 작업 분해(§9).

### 1.2 다루지 않는 것
- 첨부 파일(F5.7), 폴더 키(F5.8), 저장 노드(F5.9)의 상세 설계. 단, 이 문서의 계약이 그것들을 막지 않도록 확장 지점만 적는다.
- 로컬 MCP(F6), P2P → 허브 전환(F7). 전환에 필요한 사용자·기기 대응 관계는 §2에 남긴다.
- 화면 설계. 화면 문구는 PRD §0.1과 F5.5a를 따르며, 이 문서의 기술 용어는 화면에 쓰지 않는다.

### 1.3 규모 가정 [설계]
PRD §3과 리뷰의 가정을 따른다. vault당 사람 2~15명, 사람당 기기 1~3대(최대 기기 약 45대), 문서 수천 개, 몇 주 단위의 오프라인. 수치 상한은 §6.6에 초기값으로 적고 C1에서 측정해 고친다.

### 1.4 지켜야 할 불변 조건 [사실: `CLAUDE.md`]
| 불변 조건 | 이 설계에서 지키는 방법 |
|---|---|
| 안정된 `doc_id`가 정체성 | 봉투, registry, 스냅샷 모두 `doc_id`로만 문서를 가리킨다. 경로는 registry 안의 암호화된 속성이다(§5) |
| 디스크 Markdown이 원본, `Y.Text("content")`가 실시간 원본 | P2P 계층은 디스크를 직접 쓰지 않는다. 받은 업데이트를 같은 실시간 Y.Doc에 적용하고, 디스크 반영은 지금의 브리지 egest가 맡는다(§8.1) |
| 이진 Yjs 업데이트만 | 봉투의 payload는 Yjs 업데이트 또는 `encodeStateAsUpdate` 결과뿐이다. Markdown을 보내지 않는다 |
| 에코 가드 두 개, 150ms/300ms | P2P 어댑터는 새 origin을 하나 더할 뿐 두 가드와 지연값을 바꾸지 않는다(§8.1) |
| pull-before-seed, 삭제·회수·복구·대량 작업 가드 | bootstrap 완료 기준(§6.3)과 tombstone 가드(§6.1)로 같은 보장을 P2P에도 준다 |
| `.context/` 비공개 | P2P 상태는 `.context/` 아래 새 파일에 두되, `.context/`를 동기화하지 않는다. 공유할 메타데이터는 registry 문서로 따로 정의한다(§5) |
| 확장자 목록 일치, 바이너리는 CRDT 밖 | C1은 텍스트 노트만 다룬다. 노트 판정은 지금 함께 맞춰 두는 네 목록을 그대로 쓴다(§8.5) |

## 2. 위협 모델

### 2.1 보호 대상
1. **내용의 기밀성:** 본문, 그리고 D7의 메타데이터(제목, 경로, 폴더 이름, 멤버 프로필, presence, 링크 관계, 검색 snippet).
2. **이력의 무결성:** 누가 어떤 변경을 썼는지, 쓰기 권한이 있었는지.
3. **멤버십의 무결성과 신선함:** 지금 누가 멤버이고 어떤 역할인지, 그리고 그것이 최신인지.
4. **데이터 보존:** 확인 응답(ACK)을 받은 편집은 키 교체, 스냅샷, 장애 후에도 복구할 수 있다(PRD §7).
5. **키:** 기기 키, epoch 콘텐츠 키, 복구 키.

### 2.2 행위자와 대응

| 행위자 | 할 수 있는 일 | 대응 | 남는 위험 |
|---|---|---|---|
| 악성 중계(relay) | 트래픽 관측, 지연, 버림, 재전송 | 연결은 Iroh의 종단간 QUIC/TLS이다(§7.2). 그 위의 봉투도 따로 암호화·서명한다. 재전송은 카운터로 거른다 | IP, 시각, 크기 관측. 가용성 저하 |
| 악성 저장 노드(D 단계) | 봉투 보관, 일부만 제공, 과거 상태 제공 | 노드는 콘텐츠 키가 없다. 작성자별 연속 카운터와 멤버십 해시 사슬로 누락·되돌리기를 감지한다 | 가용성 저하. 모든 경로가 막히면 최신 상태가 있다는 것을 증명할 수 없다 |
| 같은 망 관찰자 | mDNS 광고 관측, 연결 시도 | mDNS에는 기기의 Iroh 공개키와 주소만 실린다. vault ID는 광고하지 않는다(§7.2) | 망 안의 기기 존재가 드러난다(D7) |
| 쓰기 권한이 없는 멤버(읽기 전용 게스트, C2 이후) | 콘텐츠 키로 유효한 암호문 만들기 | 쓰기는 "해당 epoch 멤버십에서 쓰기 역할인 기기의 서명"으로만 인정한다(§3.4) | 없음(읽은 내용을 옮기는 것은 막을 수 없다) |
| 제거된 멤버·기기 | 옛 epoch 키로 옛 봉투 읽기, 옛 epoch로 날짜를 속인 봉투 만들기 | 제거 commit의 cutoff 이후 봉투는 자동으로 받지 않는다(§3.6). 새 epoch 키는 받지 못한다 | 제거 전에 받은 내용, 그리고 제거 소식이 퍼지기 전 짧은 동안 옛 키로 봉인된 봉투 |
| 쓰기 권한이 있는 악의적 멤버 | 정상 서명된 삭제·덮어쓰기, 내용을 뺀 스냅샷 | 서명으로 작성자를 남긴다. 기존 버전 기록과 휴지통으로 되돌릴 수 있다. 다른 기기는 포함을 검증하지 못한 업데이트를 지우지 않는다(§4.4) | **막지 않는다**(PRD D3). Yjs는 BFT CRDT가 아니다 |
| 분실 기기를 주운 사람 | 디스크와 키체인 접근 시도 | OS 로그인과 키체인 보호에 기댄다. 관리자가 기기를 제거하면 새 epoch부터 막힌다 | 디스크 암호화가 없으면 평문 Markdown과 색인이 그대로 읽힌다(PRD §6.7) |
| 디스크 복원·복제된 기기 | 같은 기기 키와 카운터를 두 곳에서 사용 | nonce는 무작위 192비트라 카운터 재사용이 AEAD를 깨지 않는다. 복제를 감지하면 기기 키를 다시 발급한다(§2.4) | 감지 전 짧은 동안의 카운터 충돌은 "동기화 미완료"로 보인다 |
| 권한 기기의 침해 | 임의의 멤버십 변경 | 복구 키로 권한을 되찾고 키를 교체한다(§3.7). 같은 번호의 commit이 둘이면 멤버십 변경을 멈춘다(§3.3) | 침해가 감지되기 전의 변경 |

### 2.3 신뢰 가정 [설계]
- 사용자 기기의 OS와 앱 바이너리는 침해되지 않았다. 앱 자동 업데이트의 서명 검증은 지금의 updater 계약을 따른다.
- 시계는 믿지 않는다. 만료 시각은 보조 신호로만 쓰고, 순서는 멤버십 번호와 카운터로 정한다.
- 공급망(의존 crate·패키지) 공격은 이 문서의 범위 밖이다. 의존성 고정과 감사는 C2 보안 리뷰에서 다룬다.

### 2.4 이 설계가 보장하지 않는 것
- 쓰기 권한이 있는 악의적 멤버의 정상 서명 편집(되돌릴 수는 있다).
- 한 epoch 안의 전방 비밀성(forward secrecy). epoch 키를 얻은 사람은 그 epoch의 모든 봉투를 읽는다. 침해 후 회복은 키 교체로만 얻는다.
- 트래픽 분석 방어. 봉투 크기 덧댐(padding)은 C1에 넣지 않는다 [결정 필요: C2 전 도입 여부].
- 이미 받은 평문의 회수(PRD D1).

## 3. 기기 신원, 멤버십 epoch, 키 교체

### 3.1 신원 구조 [설계]
PRD F5.1의 `사용자 → 승인된 기기 → vault 멤버십과 역할`을 다음처럼 구현한다.

- **사용자(user):** vault 안에서 무작위 128비트 `user_id`와 암호화된 프로필(이름, 색)로만 존재한다. **사용자 키는 두지 않는다.** 사용자 키를 기기 사이에 옮기는 문제와 사용자 키 분실 문제를 피하기 위해서다. 사용자를 묶는 것은 권한 기기가 서명한 멤버십 문서다.
- **기기(device):** 기기마다 세 개의 키 쌍을 만든다.

| 키 | 알고리즘 | 용도 |
|---|---|---|
| 서명 키 | Ed25519 (RFC 8032) | 봉투, 멤버십 commit, ACK 서명. `device_id = BLAKE3(서명 공개키)`의 앞 16바이트 |
| 감싸기 키 | X25519 기반 HPKE (RFC 9180, base mode) | epoch 콘텐츠 키를 이 기기에게 전달 |
| 연결 키 | Iroh 기본 Ed25519 | Iroh `EndpointId`. 연결 계층 인증 전용 |

- **기기 인증서:** `{device_id, 서명 공개키, 감싸기 공개키, 연결 공개키, user_id, 생성 시각, incarnation}`을 서명 키로 자체 서명한다. 권한 기기가 이 인증서를 멤버십 commit에 넣고 서명하면 그 기기는 승인된 것이다.
- **연결 키를 따로 두는 이유:** Iroh는 연결 키를 주소 탐색과 중계에 노출한다. 봉투 서명 키와 분리하면 연결 키만 바꿔 관측을 줄이거나 Iroh 버전을 바꿔도 이력 서명이 유지된다. 연결이 맺어지면 양쪽은 상대의 연결 키가 현재 멤버십의 어떤 기기 인증서에 묶였는지 확인한다. 묶이지 않은 상대와는 초대 처리(F1.2) 외의 대화를 하지 않는다.

### 3.2 키 저장 [설계]
- 비밀키는 OS 키체인에 둔다. 지금 `R/keychain.rs`는 세션 토큰 저장용이므로(§8.4) 같은 OS 비밀 저장소 접근을 재사용하되, 서비스 이름과 항목을 분리한 새 모듈을 만든다. 키는 WebView(TypeScript)로 넘기지 않는다. 서명, 봉인, 열기는 모두 Rust에서 한다.
- 카운터, 수신 기록, 최신 확인 지점, outbox는 키체인이 아니라 `<vault>/.context/index.sqlite`의 **새 `p2p_*` 테이블**에 둔다. 기존 테이블은 건드리지 않는다(PRD F8.5와 같은 원칙). 별도 파일이 아니라 같은 DB에 두는 이유는, 로컬 Yjs 업데이트 저장(`yjs_updates`)과 outbox 기록을 한 트랜잭션으로 묶기 위해서다(§8.3). 이하 이 테이블들을 "P2P 상태"라고 부른다.
- **incarnation:** 키체인에 기기 키를 만들 때 무작위 128비트 incarnation을 함께 만들어 키체인과 P2P 상태에 모두 적는다. 시작할 때 둘이 다르거나, 다른 기기가 "네 기기 ID로 내가 아는 것보다 큰 카운터를 봤다"고 알려 오면 복제로 보고 **새 기기 키로 다시 등록**한다(PRD F5.1의 디스크 복원 항목). 재등록은 같은 사용자의 다른 승인 기기나 권한 기기의 승인을 받는다.

### 3.3 멤버십 로그 [설계]
- vault의 멤버십은 **권한 기기가 서명하는 해시 사슬 commit**의 목록이다. commit `n`은 다음을 담는다.
  - `vault_id`, `epoch = n`, `prev = hash(commit n-1)`
  - 연산 목록: 기기 승인, 기기 제거, 사용자 제거(그 사용자의 모든 기기 제거), 역할 변경, 권한 이양, 복구 키 교체, 키 교체 여부
  - 결과 멤버 표의 해시(받는 쪽이 같은 상태를 계산했는지 비교)
  - 키를 바꾸는 commit이면 새 콘텐츠 키를 남은 기기마다, 그리고 복구 키에게 HPKE로 감싼 값
  - 제거가 있으면 cutoff 벡터(§3.6)
  - 권한 기기의 서명
- **commit 0(genesis)** 은 vault를 만든 기기가 쓴다. 첫 권한 기기, 복구 공개키, vault 설정(사내망 전용 여부 등)을 담는다.
- **epoch 번호는 commit 번호다.** 모든 멤버십 변경이 epoch를 하나 올린다. 콘텐츠 키는 "키 교체" 표시가 있는 commit에서만 바뀌고, 그 외 commit은 직전 키를 그대로 쓴다. 따라서 `key_epoch(e)` = e 이하에서 마지막으로 키를 바꾼 commit 번호다.
- **순서 권한:** 어느 시점에나 권한 기기는 정확히 한 대다(PRD D4, Q4의 1차 답). 권한 이양 commit은 지금 권한 기기나 복구 키가 서명한다.
- **분기 감지:** 같은 번호의 서로 다른 commit이 둘 다 유효한 서명을 가지면, 권한 기기가 복제되었거나 침해된 것이다. 이를 본 기기는 그 사실을 다른 피어에 전하고, 멤버십 변경을 멈추며, 일반 편집은 마지막 공통 epoch로 계속한다. 해결은 복구 키 서명의 이양 commit으로만 한다(§3.7).
- **신선함:** 각 기기는 본 commit 중 가장 높은 번호를 P2P 상태에 기록하고 낮은 번호로 돌아가지 않는다. 연결할 때 서로의 최신 commit 해시를 먼저 주고받는다. 새 기기와 복원된 기기는 권한 기기나 서로 다른 두 기기에게서 같은 최신 commit을 확인한 뒤에야 bootstrap 완료로 본다(§6.3).

### 3.4 쓰기 권한 검증 [설계]
받은 영속 봉투(업데이트, 스냅샷, registry 변경)는 경로와 관계없이 다음을 모두 통과해야 Yjs에 적용한다.
1. 봉투 서명이 봉투에 적힌 작성 기기의 서명 공개키로 검증된다.
2. 봉투에 적힌 epoch `e`의 멤버십 상태에서 그 기기가 승인되어 있고, 역할이 쓰기 이상이다.
3. 그 기기가 `e` 이후의 commit에서 제거되었다면, 봉투의 카운터가 그 제거 commit의 cutoff 이하다(§3.6).
4. 봉투가 `key_epoch(e)`의 키로 열린다.
5. 카운터가 이미 받은 것이 아니다. 같은 카운터에 다른 내용이 오면 거부하고 복제 의심으로 기록한다.

멤버십 commit 자체는 권한 기기 서명과 해시 사슬로 검증한다. **이 검증이 없으면 읽기 전용 게스트를 출시하지 않는다**(PRD D4, R03). C1은 모든 멤버가 쓰기 역할이지만, 이 검증은 C1부터 넣는다.

### 3.5 키 교체 3단계 [설계]
PRD D4의 준비·배포·확정을 다음처럼 정한다.

1. **준비:** 권한 기기가 새 콘텐츠 키(무작위 256비트)를 만들고, 키 교체 commit을 완성해 키체인과 P2P 상태에 **먼저 적은 뒤** 내보낸다. 장애 후 다시 시작하면 적어 둔 같은 commit을 다시 보낸다. 새 키를 다시 만들지 않으므로 같은 번호의 commit이 둘 생기지 않는다(idempotency).
2. **배포:** commit 안에 감싼 키가 이미 들어 있으므로, 배포는 commit을 퍼뜨리는 것으로 끝난다. commit을 받은 기기는 키를 풀어 저장하고, 서명된 수신 확인 `{device_id, epoch}`를 보낸다. 권한 기기는 확인을 모은다.
3. **확정:** 남은 모든 기기가 확인했거나 확인 대기 한도(초기값 30일, Q5)가 지나면 권한 기기가 "확정" 표시를 내보낸다. 확정은 **옛 epoch 봉투를 정리해도 되는 시점**만 정한다. 쓰기는 확정을 기다리지 않는다. 기기는 새 commit을 아는 순간부터 새 키로만 봉인한다.

- **오프라인 편집 보존(R02):** 로컬 편집은 평문 Yjs 업데이트로 로컬 outbox에 두고, 보낼 때 봉인한다(seal-at-send). 오래 오프라인이던 기기가 돌아오면 먼저 멤버십을 따라잡고(§3.3 신선함), 자기 쓰기 권한이 아직 유효한지 확인한 뒤 미전송 변경을 최신 키로 봉인해 보낸다. Yjs 업데이트는 교환 가능하므로 새 스냅샷 위에 그대로 합쳐진다. 권한이 사라졌으면(제거나 읽기 전용 강등) 보내지 않고 로컬 복구 사본으로 남긴다(§6.2).
- **옛 epoch 보존 기한의 의미:** 이 설계에서 옛 epoch 봉투의 보존은 정확성 조건이 아니다. 현역 기기는 새 스냅샷을 새 키로 받을 수 있고, 자기 미전송 변경은 평문으로 갖고 있기 때문이다. 보존 기한은 (1) 오래된 기기가 전체 스냅샷 대신 차이만 받게 하는 대역폭 최적화, (2) 제거된 기기의 격리 봉투를 관리자가 검토할 기간, 두 가지에만 쓴다. 그래서 Q5의 기본값 30일을 바꿀 이유가 약하다 [결정 필요: 30일 유지].
- **새 멤버의 옛 이력:** 새 기기에게는 현재 키만 준다. 옛 이력은 현재 키로 봉인된 최신 스냅샷으로 받는다. 옛 epoch 키는 주지 않는다. 버전 기록(과거 상태 보기)은 스냅샷 안의 Yjs 상태에서 만든다. 단, 스냅샷의 Yjs GC 설정에 따라 지워진 내용의 과거 보기 범위가 달라진다(§4.5).

### 3.6 제거와 기준 시점 [설계]
- 제거 commit에는 **cutoff 벡터**를 넣는다. 제거되는 기기마다, 권한 기기가 그 순간까지 받은 그 기기의 문서별 최대 카운터다.
- 제거된 기기의 봉투 중 카운터가 cutoff 이하인 것은 제거 전에 이미 퍼진 것으로 보고 받는다. cutoff를 넘는 것은 epoch 표기와 관계없이 **격리**한다. 제거된 기기는 옛 키를 갖고 있어 옛 epoch로 날짜를 속인 봉투를 만들 수 있기 때문이다.
- 격리된 봉투는 권한 기기(관리자)에게 "나간 팀원이 남긴 변경 n건"으로 보여 주고, 관리자가 받기를 고르면 관리자 기기가 그 내용을 자기 서명으로 다시 써서 새 epoch로 보낸다. 받지 않으면 보존 기한 뒤에 지운다. 이것이 PRD D4의 "그 전에 작성된 변경은 관리자 확인을 거쳐 받을 수 있다"의 구현이다.
- **알려진 틈:** 권한 기기가 아직 받지 못한, 제거 전에 정직하게 작성된 변경도 cutoff를 넘어 격리된다. 자동 수용과 즉시 차단을 동시에 보장할 수 없다는 리뷰 R02의 지적을 받아들여, 기준을 "권한 기기가 본 것"으로 정한다.
- **제거 소식이 퍼지기 전의 틈:** 제거 commit을 아직 모르는 두 기기가 서로 직접 주고받는 봉투는 옛 키로 봉인된다. 제거된 기기가 그 암호문을 얻으면 읽을 수 있다. 연결 시 멤버십 최신 해시를 먼저 교환하므로 한쪽이라도 알면 바로 좁혀진다. 남는 위험으로 문서화한다.

### 3.7 기기 추가, 승계, 복구 [설계]
- **같은 사용자의 기기 추가:** 새 기기가 기기 인증서를 만들고, 사용자의 기존 승인 기기가 QR이나 링크로 그것을 확인해 서명한 "기기 추가 요청"을 권한 기기에 보낸다. 권한 기기가 commit한다. 권한 기기가 오프라인이면 "승인 대기"다.
- **새 사람의 합류:** PRD F1.2의 초대 티켓을 따른다. 티켓 소비는 권한 기기가 원자적으로 확정하고, 승인은 요청 기기의 서명 공개키에 묶는다.
- **기기 하나 제거와 사용자 전체 제거**는 서로 다른 연산이다. 둘 다 키 교체를 일으킨다.
- **마지막 관리자 제거 금지:** 권한 기기의 사용자를 제거하는 commit은 권한 이양 연산을 함께 담아야만 유효하다.
- **복구 키:** vault를 만들 때 256비트 시드를 만들어 "복구 코드"로 보여 준다(PRD §0.1의 "복구 코드 저장하기" 화면). 시드에서 Ed25519 서명 키와 X25519 감싸기 키를 만든다. 공개키는 genesis에 들어간다.
  - 키 교체 commit은 새 콘텐츠 키를 복구 공개키에게도 감싼다. 그래서 복구 코드와 암호문 백업만 있으면 모든 epoch의 내용을 열 수 있다(PRD §6.1의 운영 백업 전제).
  - 복구 코드는 권한 이양 commit에 서명할 수 있다. 권한 기기를 잃었거나 침해되었을 때 새 기기에서 복구 코드를 입력해 권한을 되찾고, 바로 키 교체와 복구 키 교체를 한다.
  - 복구 코드가 새면 vault 전체가 노출된다. 그래서 복구 코드로 권한을 되찾으면 반드시 새 복구 코드를 발급한다.
- **복구 코드도 권한 기기도 잃은 경우:** 남은 기기는 지금 키로 편집을 계속할 수 있지만 멤버십은 영원히 바꿀 수 없다. 이때는 "새 vault로 옮기기"를 제공한다. 남은 기기의 평문 상태로 새 genesis를 만들고 다시 초대한다. 같은 `doc_id`를 유지하고 Yjs 상태를 이진으로 옮긴다. 만들 때 이 결과를 고지한다(PRD F5.1).

[결정 필요] 복구 코드 형식(단어 24개 또는 영숫자 묶음), 건너뛰기 허용 여부, 복구 코드를 vault마다 둘지 사람마다 둘지. 기본값: vault마다, 건너뛸 수 없음, 영숫자 묶음(대소문자 구분 없음).

## 4. 봉투와 스냅샷

### 4.1 봉투 형식 [설계]
secsync 명세에서 봉투의 구성만 참고하고, 순서와 복구는 이 문서의 규칙을 따른다(PRD D3).

| 필드 | 평문/인증 대상(AAD) | 내용 |
|---|---|---|
| `v` | AAD | 프로토콜 버전 |
| `kind` | AAD | `update`, `snapshot`, `registry`, `ack`, `quarantine-accept` |
| `vault_id`, `doc_id` | AAD | 불투명 ID. registry는 예약된 `doc_id` 하나를 쓴다 |
| `epoch` | AAD | 봉인할 때의 멤버십 epoch |
| `parent` | AAD | 스냅샷이면 부모 스냅샷 ID 목록, 업데이트면 작성자가 아는 최신 스냅샷 ID |
| `device_id`, `counter` | AAD | 작성 기기와 (기기, 문서)별 1부터 연속 증가하는 카운터 |
| `payload_hash` | AAD | 평문 payload의 BLAKE3 해시 |
| `nonce` | 평문 | 무작위 192비트 |
| `ciphertext` | — | XChaCha20-Poly1305로 봉인한 payload |
| `sig` | — | 위 모든 필드에 대한 작성 기기의 Ed25519 서명 |

- **봉투 ID:** `hash(device_id, doc_id, counter)`. 같은 ID에 다른 내용이 오면 거부한다(§3.4의 5).
- **nonce:** 무작위 192비트를 쓰므로 카운터가 복제되어도 AEAD 키·nonce 재사용이 일어나지 않는다. 카운터는 순서와 누락 감지에만 쓴다.
- **문서 키:** epoch 콘텐츠 키에서 `HKDF(epoch_key, "doc" ‖ doc_id)`로 문서별 키를 만든다. 나중에 폴더 키(F5.8)를 넣을 때 이 자리를 바꾼다.
- **payload:** `update`는 Yjs 업데이트 바이트, `snapshot`은 `Y.encodeStateAsUpdate` 결과와 포함 범위(§4.3), `registry`는 registry 문서의 Yjs 업데이트다. 압축은 봉인 전에 하고, 받는 쪽은 압축 해제 크기 상한을 둔다(PRD §6.4).
- **일시 메시지:** presence와 동기화 협상(have/want)은 저장하지 않는 일시 메시지다. 같은 epoch 키로 암호화하고 연결 계층 인증에 기댄다. 카운터를 쓰지 않는다.

### 4.2 누락과 되돌리기 감지 [설계]
- 각 기기는 문서마다 **frontier** = `{device_id → 받은 최대 연속 카운터}`를 유지한다. 중간 번호가 빠지면 그 번호 위의 봉투는 보관하되 "구멍"으로 기록한다.
- 동기화할 때 양쪽은 frontier를 교환하고, 상대가 가진 더 큰 번호를 요청한다. 상대가 자기 frontier보다 낮은 상태만 주면 되돌리기 시도로 보지 않는다. CRDT 병합은 단조라서 이미 가진 상태가 줄어들지 않기 때문이다.
- 되돌리기가 실제로 해로운 경우는 두 가지다. 상태가 없는 새 기기, 그리고 멤버십이다. 새 기기는 §6.3의 bootstrap 완료 기준으로, 멤버십은 §3.3의 해시 사슬과 최신 번호 기록으로 막는다.
- 구멍이 남은 문서, 또는 상대가 "가지고 있다"고 한 번호를 끝내 받지 못한 문서는 "동기화 미완료"로 표시한다. 조용히 성공으로 처리하지 않는다(PRD D3).

### 4.3 스냅샷 [설계]
- 스냅샷 payload는 `Y.encodeStateAsUpdate(doc)`이다. Markdown에서 다시 만들지 않는다(PRD D4, R06).
- 스냅샷은 **포함 범위**를 함께 담는다. 포함 범위 = 문서 frontier(위 §4.2) 와 Yjs 상태 벡터. 스냅샷 ID = `hash(payload_hash, 포함 범위)`.
- 스냅샷을 만들 수 있는 기기: 해당 epoch에서 쓰기 역할인 모든 기기. 스냅샷도 쓰기다. 읽기 전용 기기는 만들 수 없다.
- 만드는 조건(초기값, C1에서 측정 후 조정): 마지막 스냅샷 이후 업데이트 500개 또는 1 MiB, 그리고 키 교체 직후.

### 4.4 스냅샷 경쟁 [설계]
리뷰 R01의 시나리오(두 기기가 같은 부모에서 서로 다른 스냅샷을 만든다)를 다음 원칙으로 푼다.

1. **스냅샷은 대체가 아니라 합칠 수 있는 체크포인트다.** Yjs 상태는 서로 합칠 수 있으므로, 경쟁하는 스냅샷 S1과 S2를 받은 기기는 둘 다 적용한다. 결과는 둘의 합집합이다. 어느 쪽을 "정본"으로 고를 필요가 없다.
2. **업데이트 삭제 조건은 로컬 검증뿐이다.** 기기는 업데이트 U를, U가 로컬에서 검증한 어떤 스냅샷에 포함될 때만 지운다. 포함 검증은 두 가지를 모두 본다. 스냅샷의 포함 범위가 U의 (기기, 카운터)를 덮는다. 그리고 `Y.diffUpdate(U, 스냅샷 상태 벡터)`가 빈 업데이트다. 다른 기기의 주장만으로는 지우지 않는다. 이것이 지금 `save_yjs_snapshot`의 `id <= up_to` 원리(§8.3)를 봉투 저장소에 옮긴 것이다.
3. **새 기기에게 줄 스냅샷 선택:** 포함 범위가 가장 넓은 것을 준다. 넓이가 같으면 스냅샷 ID가 작은 것을 준다. 선택은 효율의 문제이지 정확성의 문제가 아니다. 받은 쪽은 그 위에 남은 업데이트를 합친다.
4. **스냅샷 작성자가 오프라인이어도:** 다른 쓰기 기기가 같은 frontier를 가지면 같은 상태의 스냅샷을 만들 수 있다. frontier가 다르면 각자 만들고 1번 원칙으로 합친다. PRD D4의 "같은 검증된 이력" 조건은 정확성 조건이 아니라 "스냅샷을 중복으로 만들지 않는" 최적화 조건으로 바뀐다.
5. **키 교체와의 경쟁:** 권한 기기만 키를 바꾸므로(§3.3) 서로 다른 새 키로 봉인한 두 스냅샷은 생기지 않는다. 같은 epoch의 경쟁만 있다.
6. **악의적 쓰기 멤버의 빈 스냅샷:** 내용을 뺀 스냅샷을 받아도 다른 기기는 그 스냅샷이 포함하지 않는 업데이트를 지우지 않는다(2번). 새 기기는 잘못된 상태로 시작할 수 있지만, 이후 다른 기기의 업데이트가 합쳐진다. 위협 모델에서 받아들인 위험이다(§2.2).

### 4.5 Yjs GC와 이력 [사실 + 추측]
- [사실] Yjs의 삭제 내용 GC는 압축과 별개다. 과거 상태 보기(Yjs snapshot)는 `gc: false`인 문서에서만 정확하다(§10 참고 자료의 Yjs 문서).
- [추측] GC가 켜진 기기와 꺼진 기기가 섞여도 문서는 수렴한다. 그러나 GC가 켜진 기기가 만든 스냅샷을 받은 새 기기는 지워진 내용의 과거를 볼 수 없다. [사실] 지금 브리지는 `new Y.Doc()`을 기본값(GC 켜짐)으로 만든다(`D/lib/bridge/noteBridge.ts:189`). `D/lib/sync/crdtGc.ts`는 Yjs GC가 아니라 죽은 CRDT 문서를 정리하는 모듈이다. C1은 지금 설정을 그대로 따르고, 섞인 설정에서의 수렴을 테스트로 확인한다.
- [설계] 수년 편집된 문서의 상태 크기 상한(초기값 문서당 16 MiB)을 넘으면 "이력 정리"를 별도 기능으로 제안한다. 이력 정리는 새 `doc_id`가 아니라 같은 `doc_id`의 새 세대로 기록하고, 오프라인 기기의 옛 업데이트는 복구 사본으로 돌린다. C1 범위 밖이다.

## 5. 암호화된 registry/control 프로토콜

### 5.1 registry 문서 [설계]
- vault마다 예약된 `doc_id` 하나를 **registry 문서**로 쓴다. 내용은 Yjs 문서이고, 다른 노트와 같은 봉투·서명·쓰기 검증·스냅샷 경로를 탄다. 따라서 메타데이터도 본문과 같은 수준으로 암호화된다(PRD D7).
- registry 문서의 구조(Yjs `Y.Map("docs")`, 키 = `doc_id`):

| 속성 | 의미 |
|---|---|
| `path` | vault 안의 상대 경로(NFC 정규화). 이름 변경과 이동은 이 값을 바꾸는 것이다 |
| `kind` | `note` (C1). D 단계에서 `binary` |
| `created` | `{device_id, epoch}` |
| `tomb` | 없음, 또는 `{device_id, epoch, at}`. 휴지통으로 보낸 상태 |
| `restored` | 마지막 복구 `{device_id, epoch}` |

- 폴더는 문서 경로에서 파생하고, 빈 폴더만 `Y.Map("folders")`에 둔다.
- 멤버 프로필, 기기 이름은 registry가 아니라 멤버십 commit 안의 암호화 필드에 둔다(권한 기기만 쓴다).

### 5.2 지금 허브 신호와의 대응 [설계]
지금 허브 프로토콜의 `ready` 제어 메시지에는 다섯 신호가 있다(§8.2). P2P에서는 같은 판단을 다음 근거로 내린다.

| 허브 신호 | 허브에서의 의미 | P2P의 같은 근거 |
|---|---|---|
| `empty` | 서버에 내용이 없는 문서. 올려야 한다 | 상대 frontier에 내 기기의 카운터가 없거나 낮은 문서. 상대가 요청한다 |
| `behind` | 내가 서버보다 앞선 문서 | 같은 frontier 비교. 내가 가진 더 큰 번호를 보낸다 |
| `revoked` | 내가 가진 문서 중 더는 읽을 수 없는 것 | vault 단위 권한이라 문서별 회수는 없다. 내 기기가 제거된 멤버십 commit 하나가 vault 전체 회수다(§6.4) |
| `tombstones` | 휴지통에 있는 문서 | registry의 `tomb` 속성 |
| `covered` | 서버가 내 상태를 다 갖고 있음(삭제 게이트의 ACK) | 서명된 ACK 봉투: `{doc_id, frontier}`를 받은 기기가 서명해 돌려준다. **권한 기기나 저장 노드의 ACK만** 삭제 게이트의 "보존됨" 근거가 된다(§6.1) |

### 5.3 충돌 규칙 [설계]
PRD F5.3이 요구하는 경우마다 정한다. 원칙은 "registry는 그대로 두고, 디스크 표현만 결정적으로 정한다"이다. 모든 기기가 같은 registry에서 같은 디스크 결과를 계산해야 디스크가 갈라지지 않는다.

| 경우 | 규칙 |
|---|---|
| 같은 `doc_id`의 동시 이름 변경 | Yjs Map의 마지막 쓰기 규칙을 따른다(모든 기기가 같은 값을 고른다). 진 이름은 버전 기록에 남는다 |
| 같은 경로, 다른 `doc_id` | 둘 다 남긴다. `doc_id`가 작은 쪽이 원래 이름을, 큰 쪽이 `이름 (충돌 <doc_id 앞 6자>).md`를 디스크에 쓴다. registry는 바꾸지 않고 사용자에게 충돌로 보여 준다(PRD §6.6) |
| 대소문자나 Unicode 정규화만 다른 경로 | 비교 키 = NFC 정규화 + 대소문자 접기. 비교 키가 같으면 위 "같은 경로" 규칙을 쓴다. 대소문자를 구분하는 Linux에서도 같은 규칙을 써서 기기마다 결과가 같게 한다 |
| 폴더 삭제 중 새 파일 | 폴더 삭제는 "그 순간 폴더 안에 있던 `doc_id` 목록"의 tombstone 묶음이다. 경로 접두어로 지우지 않는다. 동시에 생긴 새 파일은 목록에 없으므로 남고, 폴더는 디스크에 다시 생긴다 |
| tombstone과 동시 편집 | 편집은 받아서 보관한다. 문서는 휴지통 상태를 유지하고, 사용자가 복구하면 편집이 보인다. 지금 허브 휴지통의 동작과 같다(`S/trash/access.ts`, §8.6) |
| tombstone과 동시 이름 변경 | tombstone이 이긴다. 복구하면 바뀐 이름으로 돌아온다 |
| 바이너리 충돌 | C1은 바이너리를 다루지 않는다. D 단계에서 사본으로 남긴다 |

### 5.4 `.context/`와의 관계 [설계]
- registry 문서의 Yjs 상태는 다른 노트의 CRDT 상태와 같은 방식으로 로컬에 저장한다.
- 지금 `.context/`의 identity map(경로 ↔ `doc_id`)은 **로컬 파생 상태**로 남는다. registry가 원본이고, identity map은 registry와 디스크를 맞추는 로컬 색인이다. `.context/` 파일 자체는 어떤 경로로도 내보내지 않는다(§8.3).

## 6. 삭제·복구 계약

### 6.1 삭제 [설계]
- 삭제는 registry의 서명된 `tomb` 설정으로만 일어난다. **어떤 피어의 목록에 문서가 없다는 것은 삭제의 증거가 아니다.**
- 받은 tombstone을 디스크에 반영하기 전에 지금의 inbound 삭제 가드를 그대로 통과시킨다(§8.2). 한 번에 많은 문서를 지우는 묶음은 지금의 대량 삭제 확인 기준을 그대로 쓴다.
- 로컬 사용자가 삭제할 때의 게이트: 그 문서의 내 마지막 변경이 권한 기기나 저장 노드의 ACK(§5.2)로 "보존됨"이 아니면, 지금처럼 "아직 다른 기기에 저장되지 않음"을 알리고 확인을 받는다.
- **영구 삭제(purge):** 휴지통 보존 기한(지금 허브 휴지통 기본값을 따른다) 뒤에 관리자만 한다. purge는 봉투를 지우라는 서명된 요청일 뿐이며, 다른 기기와 노드가 실제로 지웠다고 보장하지 않는다. 화면에 그렇게 알린다.

### 6.2 복구 사본 [설계]
다음 경우 데이터를 버리지 않고 지금의 복구 사본 경로(§8.1의 `diskBase`와 복구 사본)로 남긴다.
- 쓰기 권한을 잃은 뒤 남은 로컬 미전송 변경(§3.5).
- 제거된 기기의 격리 봉투 중 관리자가 받지 않은 것(보존 기한까지).
- 경로 충돌로 디스크 이름이 바뀐 문서의 원래 이름 기록.
- 디스크와 실시간 Y.Doc이 동시에 바뀌어 지금 브리지가 복구 사본을 만드는 경우(변경 없음).

### 6.3 bootstrap 완료 기준 [설계]
새 기기, 복원된 기기, `.context/`를 잃은 기기는 다음이 모두 참일 때만 "받아오기 완료"로 본다. 완료 전에는 빈 문서를 시드하지 않고, 어떤 부재도 삭제로 해석하지 않는다(pull-before-seed).
1. 멤버십 최신 commit을 권한 기기에서, 또는 서로 다른 사용자의 기기 두 대에서 같은 해시로 확인했다.
2. registry 문서의 frontier를 같은 출처에서 확인했고, 그 frontier까지 구멍 없이 받았다.
3. registry의 모든 살아 있는 문서에 대해 상대가 알린 frontier까지 받았다. 받지 못한 문서는 "아직 받는 중"으로 남기고, 그 문서의 경로에 로컬 빈 파일을 시드하지 않는다.

[결정 필요] 2대 기준. 기본값: 권한 기기 1대 또는 다른 사용자의 기기 2대. 저장 노드가 생기면(D 단계) 노드 1대도 인정한다.

### 6.4 vault에서 제거된 기기 [설계]
- 자기 기기가 제거된 commit을 받은 정직한 앱은 동기화를 멈추고 "이 vault에서 나가게 되었습니다"를 보여 준다. 이미 받은 노트를 디스크에서 지울지는 결정 사항이다.
- [사실] 지금 허브는 회수된 노트의 로컬 파일을 `.context/trash` 사본 없이 지운다. 사본을 남기면 회수의 의미가 없어지기 때문이다. 단, 한 번에 50%(최소 20개)를 넘는 회수는 막고 파일을 남긴다(`D/lib/sync/inbound.ts:379-395`).
- [설계] P2P도 허브와 같게 한다. 제거된 기기의 앱은 vault의 노트를 지우고, 같은 회수 상한을 적용한다. 단, **그 기기의 미전송 변경은 그 사람이 쓴 것이므로** "보내지 못한 내 변경" 복구 사본으로 따로 남긴다.
- [결정 필요] 위 기본값(허브와 같이 지움 + 내 미전송 변경만 남김)을 승인할지. 어느 쪽이든 이미 받은 평문을 회수할 수 없다는 사실은 같다(PRD D1).

### 6.5 확인 응답과 보존 상태 [설계]
- 화면의 세 상태(PRD F5.9)는 다음 근거로 정한다.
  - "이 기기에만 저장됨": 다른 기기의 ACK가 없다.
  - "다른 기기가 받음": 같은 vault의 다른 기기 하나 이상이 서명한 ACK가 내 frontier를 덮는다.
  - "노드에 보존됨"(D 단계): 저장 노드의 durable ACK.
- PRD §7의 "확인 응답을 받은 데이터는 복구 가능"은 "다른 기기가 받음" 이상을 뜻한다. ACK를 보낸 기기는 그 봉투를 디스크에 fsync한 뒤에만 ACK를 서명한다.

### 6.6 용량 상한 초기값 [설계, C1에서 측정]
| 항목 | 초기값 |
|---|---|
| 봉투 하나 | 압축 해제 후 4 MiB |
| 문서 상태 | 16 MiB (넘으면 "이력 정리" 제안) |
| 문서별 미압축 업데이트 | 500개 또는 1 MiB 넘으면 스냅샷 |
| vault 기기 수 | 64대 |
| 미승인 연결 | 기기당 분당 10회 |

## 7. 기술 평가 (PRD §12 Q1)

### 7.1 평가 기준
PRD §12 Q1의 여섯 기준을 그대로 쓴다. 각 기준의 통과 조건은 다음과 같다.

| 기준 | 통과 조건 |
|---|---|
| Yjs 이진 이력 보존 | 지금 저장된 Yjs 업데이트를 바꾸지 않고 그대로 싣고, 같은 `doc_id`의 같은 Y.Doc에 적용할 수 있다 |
| 순수 LAN 오프라인 | 인터넷이나 상시 서버 없이 같은 망의 기기 2~3대가 서로 찾고 동기화한다 |
| 라이선스 | 앱 배포와 양립한다(MIT, Apache-2.0, BSD 계열이면 통과) |
| 지원 플랫폼 | macOS, Windows, Linux 데스크톱의 Rust(Tauri)에서 쓸 수 있다 |
| 게스트와 회수 | 읽기와 쓰기를 나눌 수 있고, 제거 후 새 내용을 막는 키 교체가 가능하다. 이 문서의 단일 권한 기기 모델(§3)과 충돌하지 않는다 |
| 데이터 내보내기 | 사용자가 Markdown과 이진 CRDT 상태를 기반 기술 없이 꺼낼 수 있다 |

### 7.2 후보별 사실

**NextGraph** [사실]
- 라이선스는 Apache-2.0 또는 MIT 중 선택이다. 스스로 alpha라고 밝힌다. Rust crate `nextgraph`·`ng-repo`·`ng-net`은 0.1.1-alpha.2(2025-05-01), `ng-broker`는 0.1.0-preview.6(2024-05-23)이다. JS 패키지 `@ng-org/orm`은 0.1.2-alpha.23(2026-09-28)이다.
- Repo 형식 명세에 `YText`, `YMap`, `YArray`, `YXml` 거래가 있고, 각각 "yrs::Update의 직렬화"다. 즉 Yjs 이진 업데이트를 담는 경로는 있다.
- 모든 앱은 브로커를 설정해야 하고, 지금 제공되는 공개 브로커는 nextgraph.eu 하나다. 브로커 종류는 Core, Edge(사무실이 직접 띄워 LAN 사용자가 씀), Local이다. 클라이언트는 브로커와 클라이언트-서버 방식으로만 통신한다. 전송은 WebSocket 위의 Noise이고 QUIC은 계획 단계다.
- 문서마다 하나의 E2EE 그룹(Repo)이다. 내용은 ChaCha20 수렴 암호화(convergent encryption)이고, 전방 비밀성은 일부러 쓰지 않는다. 멤버를 제거하면 `RootCapRefresh`/`BranchCapRefresh` commit으로 읽기 권한을 갱신하며, 권한 제거에는 quorum의 서명이 필요하다고 명세하지만 문서에는 "곧 더 쓴다"로 남아 있다.
- 데이터 내보내기는 CRDT 표에 JSON 가져오기·내보내기만 있다.
- 확인하지 못한 것: 브로커 없는 기기 간 직접 동기화, mDNS 탐색, 앱이 Tauri 기반인지.

**Iroh** [사실]
- `iroh` 1.3.0(2026-09-28), MIT 또는 Apache-2.0. 1.0(2026-06-15) 발표에서 wire 프로토콜과 API의 안정성을 선언했다. 공개키가 곧 `EndpointId`이고 연결은 QUIC 표준대로 TLS로 암호화된다.
- `RelayMode::Disabled`와 `presets::N0DisableRelay`로 중계를 완전히 끌 수 있다. 같은 망 탐색은 `iroh-mdns-address-lookup` 0.6.0(2026-09-28, MIT 또는 Apache-2.0)이며 기본 preset에 들어 있지 않아 따로 붙인다. 공식 문서는 "중계 없이 로컬 네트워크로 직접 연결할 수 있다"고 쓴다. 같은 문서가 소개하는 `iroh-mdns-peer-lookup`은 n0가 아닌 제3자 저장소이고 라이선스가 "non-standard"라 쓰지 않는다.
- n0 공개 중계는 무료지만 rate limit이 있고 SLA가 없으며 "개발과 테스트용"이다. `iroh-relay` 1.3.0으로 직접 띄울 수 있다. 중계는 트래픽을 읽지 못한다.
- `iroh-gossip` 0.101.0, `iroh-blobs` 0.103.1, `iroh-docs` 0.101.0은 아직 0.x다. `iroh-docs`는 값이 BLAKE3 해시인 키-값 저장소이고 README에 암호화 설명이 없다.
- Iroh는 인증된 암호화 전송만 준다. 그룹 암호화, 멤버십, 회수는 위에서 직접 만들어야 한다.

**p2panda** [사실] (PRD 후보 외 추가)
- `p2panda-core`·`-net`·`-auth`·`-encryption` 0.7.1(2026-08-21), MIT 또는 Apache-2.0. `p2panda-net`은 선택 기능으로 `iroh-mdns-address-lookup`을 쓴다.
- `p2panda-encryption`은 침해 후 회복과 선택형 전방 비밀성을 주고, 멤버 제거 시 키를 교체한다. `p2panda-auth`는 "탈중앙, 오프라인 우선 그룹 관리와 멤버별 세밀한 권한"을 준다. crate들은 원시 바이트 위에서 동작해 어떤 CRDT와도 쓸 수 있다고 밝힌다.

**그 밖의 후보** [사실]

### 7.4 권고 [설계]
1. **Iroh 1.x를 연결 계층으로 쓰고, 이 문서의 봉투·멤버십·registry·스냅샷 프로토콜을 직접 구현한다.** 이유는 세 가지다.
   - 지금 Yjs 업데이트와 브리지를 바꾸지 않는다. CLAUDE.md 불변 조건을 지키는 가장 짧은 길이다.
   - 순수 LAN, 사내 중계, 공개 중계를 설정 하나로 고를 수 있고, 연결 계층이 1.x로 안정되어 있다.
   - 순서 권한(§3.3)이 이 제품의 판단이다. 기반 기술의 그룹 모델에 맞춰 바꾸지 않아도 된다.
2. **NextGraph는 1차 기반으로 쓰지 않는다.** 브로커가 필수이고 브로커 없는 LAN 동작을 확인하지 못했으며, alpha이고, 회수 문서가 미완성이다. 문서마다 그룹인 모델은 vault 단위 멤버십과 맞지 않는다 [추측]. C2 전에 1.0이 나오면 다시 본다.
3. **p2panda는 관찰 후보로 둔다.** C1의 C1-4(봉투)와 C1-9(키 교체) 작업에서 `p2panda-encryption`의 "data encryption" 방식을 우리 설계와 나란히 읽고, 그대로 쓸 수 있는 부품이 있으면 그 시점에 결정한다. `p2panda-auth`의 탈중앙 그룹 관리는 Q4(여러 관리자 기기)를 다시 열 때 첫 후보다.
4. **Iroh의 상위 crate(`iroh-docs`, `iroh-gossip`, `iroh-blobs`)는 C1에서 쓰지 않는다.** 아직 0.x이고, `iroh-docs`는 암호화를 다루지 않는다. 동기화는 Iroh 연결 위의 자체 ALPN 프로토콜로 한다. 첨부(D 단계)에서 `iroh-blobs`를 다시 본다.
5. **Yjs 처리는 TypeScript(`yjs` 13.6.x)에 둔다.** Rust는 봉투를 바이트로만 다룬다. 스냅샷 포함 검증(`Y.diffUpdate`)도 TS에서 한다. [사실] `yrs` 0.28은 기본 ClientID를 53비트로 바꿨고, yjs 14 이전과 맞추려면 `small-client` 기능이 필요하다. Rust에서 Yjs를 파싱해야 하는 일이 생기면 그 기능을 켜고 저장된 업데이트로 상호 운용 테스트를 먼저 한다.
6. **암호 부품:** Ed25519는 `ed25519-dalek` 3.0.0, HPKE는 `hpke` 0.14.1(RFC 9180, 유료 감사는 없음), AEAD는 `chacha20poly1305` 0.11.0의 XChaCha20-Poly1305(NCC Group 감사 1회). XChaCha20은 IETF 초안이 만료되어 RFC가 없다는 점을 C2 보안 리뷰에 남긴다. 해시와 KDF는 BLAKE3와 HKDF-SHA256 [결정 필요 아님, C1에서 고정].
7. **MLS(`openmls` 0.9.1, MIT)는 계속 제외한다**(PRD §2.2). 단일 권한 기기 모델에서는 commit 순서를 이미 권한 기기가 정하므로, Q4를 열 때 함께 재검토한다.

### 7.5 연결 계층 설정 [설계]
| 모드 | Iroh 설정 | 비고 |
|---|---|---|
| 기본 | `presets::N0` + `iroh-mdns-address-lookup` | 공개 중계는 "개발과 테스트용"이라고 공식 문서가 밝힌다. C2 전에 직접 운영하는 중계를 둘지 정한다 [결정 필요] |
| 사내망 전용 | `N0DisableRelay` 또는 `RelayMode::Custom(사내 중계)`, 공개 주소 조회 끔, mDNS 켬, 수동 피어 주소 | PRD D2. C1은 이 모드로만 실험한다 |
| mDNS 광고 | 기기의 연결 공개키와 주소만 실린다. vault ID, 사용자 이름은 싣지 않는다 | 같은 망에서 앱이 켜져 있다는 사실은 드러난다(D7) |
- 동기화 프로토콜은 자체 ALPN(`infinitebrain/p2p/1`)을 쓴다. 버전이 다르면 연결 단계에서 기능 협상을 한다(PRD §6.5).
- [사실] macOS 15부터 로컬 네트워크 개인정보 보호가 강제된다. 터미널에서 실행한 명령줄 도구는 자동으로 허용되므로, 권한 요청 창 확인은 패키지된 `.app`으로만 할 수 있다(Apple TN3179). `NSLocalNetworkUsageDescription`과 `NSBonjourServices`는 macOS 11부터의 Info.plist 키다. [추측] Rust에서 직접 쓰는 mDNS 멀티캐스트에도 `NSBonjourServices` 선언이 필요한지는 확인하지 못했다. C1에서 확인한다.

### 8.4 키체인
- [사실] `R/keychain.rs:29` `SERVICE = "com.infinitebrain.desktop"`, `SecretStore` trait(`:32-36`), 메모리 대체 저장소 감지(`:43`, `:53`), Tauri 명령 `keychain_set/get/delete`(`:110-121`). 지금은 세션 토큰, 기억한 비밀번호, AI 제공자 키를 저장한다(`D/lib/auth/authManager.ts:38`, `D/lib/rememberedPassword.ts:6`).
- [설계] P2P 키는 같은 `SecretStore`를 쓰되 Tauri 명령으로 노출하지 않는다. WebView가 `keychain_get`으로 기기 비밀키를 읽을 수 없게 Rust 안에서만 접근한다. 메모리 대체 저장소가 감지되면(Linux 비밀 저장소 없음) P2P vault를 만들지 않고 PRD F5.6의 안내를 보여 준다.

### 8.6 서버(참고)
P2P vault는 서버를 쓰지 않지만, 같은 판단을 옮겨 오기 위해 참고한다.
- `S/sync/hocuspocus.ts:228-318` `onAuthenticate`: 토큰의 문서·vault 일치를 확인하고 DB 권한을 다시 확인한다. 실패하면 닫힌 쪽으로 판정하고, `edit` 미만은 읽기 전용이다. → P2P의 §3.4 쓰기 검증에 해당한다.
- `S/sync/vault-channel.ts:740-781`: `ready`의 tombstone, 회수, `covered` 계산.
- `S/trash/access.ts:36-46` `syncPermission`: 휴지통 기간 안의 문서에도 편집을 받는다. → §5.3의 "tombstone과 동시 편집" 규칙의 근거.
