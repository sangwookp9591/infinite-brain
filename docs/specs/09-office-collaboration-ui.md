# 09 · 사내 협업 화면 흐름 제안

**구현 전 화면 계약.** 06 PRD와 07~08 기술 제안을 직원·관리자가 실제로 따라갈 수 있는 화면으로 구체화한다. 이 문서는 화면 구현이나 현재 지원 상태를 뜻하지 않는다. 직원은 IP 주소·포트·지문·DB·명령어를 입력하거나 볼 필요가 없다. 별명은 표시용이며 인증 주체는 승인된 기기 키다. `organizationId`와 `vaultId`는 별개의 식별자이며 화면 또는 전이에서 자동으로 같다고 가정하지 않는다.

## 1. 제품 원칙과 전역 상태

- 별명은 최초 사내 협업 설정에서 한 번 묻고, 이후 프로필에서 변경할 수 있다. 별명으로 로그인하거나 사람·권한을 자동 연결하지 않는다. 같은 이름은 `민수 · 7K2P`처럼 고정 보조 표식으로 구별한다. 표식은 비밀이 아니고 인증 수단도 아니다.
- ‘내 근처 작업자’는 발견 후보 목록이다. 발견은 물리적 근접, 회사 소속, 허브 신뢰를 증명하지 않는다. 후보 행에 항상 “아직 확인되지 않은 작업 공간”을 붙인다. 승인 전에는 문서·폴더·팀원 명단을 표시하지 않는다.
- 작업 공간 신뢰는 별도 전달된 초대/기존 신뢰 또는 아래 양 화면 확인을 거친다. SAS가 맞아도 참여 요청만 제출된다. 관리자 승인과 기존 계정·기기 권한 검사가 추가로 필요하다.
- 어디서든 연결 상태 필은 `연결됨`, `승인 대기`, `이 컴퓨터에만 저장됨`, `회사 공유 대기` 중 현재 상태와 저장 위치를 함께 표현한다. 서버가 저장을 확인한 경우에만 `회사에 저장됨`으로 말한다. 요청 대기와 회사 저장은 같은 의미가 아니다.
- 연결이나 승인이 실패해도 로컬 메모를 지우거나 덮어쓰지 않는다. 오프라인 수정은 “이 컴퓨터에 저장됨 · 회사 공유 대기”로 남기고 복귀 뒤 권한을 다시 확인한다.

## 2. 직원 흐름

### 2.1 첫 설정: 별명

제목 “동료에게 어떻게 표시할까요?” 한 줄 별명을 받고 예시를 제공한다. 안내는 “별명은 화면에 표시돼요. 회사 계정과 기기 확인에는 사용되지 않아요.”다. 값은 trim하고 빈 값/제어문자/과도한 길이는 안내한다. 기기 별명은 선택이며 OS 사용자명은 가져오지 않는다. 저장 뒤 개인 메모로 바로 갈 수 있고 나중에 ‘사내 공유’에서 참여를 시작한다.

### 2.2 내 근처 작업자

화면 제목은 “내 근처 작업자”, 보조 설명은 “목록은 연결 후보예요. 확인 전에는 신뢰하거나 참여하지 않아요.”다. 항목은 중립적인 작업 공간 이름, 공개 동의된 별명(예: `기획팀 · 민수`), “확인 전”, 발견 시각만 보여 준다. 같은 이름은 확인 후 허용되는 디렉터리에서 `민수 · 7K2P`처럼 구별한다. 검색·필터는 이미 보이는 후보에만 적용하며 후보가 없으면 초대 링크/파일 열기 방법을 안내한다. 자동 발견이 안 될 때 IP를 입력하는 대체 경로는 두지 않는다.

### 2.3 허브 확인과 합류 요청

후보를 선택하면 허브의 별도 전달 초대와 신원을 검증한다. 최초 신뢰 경로에서 양쪽 확인을 선택했다면 신청자 화면과 관리자의 같은 pairing 요청 행에 동일한 확인값을 표시한다. 값은 인증 자체가 아니라 사용자가 중간자 연결을 알아차리도록 돕는다. 값이 다르거나 상대가 확인할 수 없다면 즉시 취소하고 재시도 횟수 제한에 걸린다.

숫자가 일치한 뒤에만 “참여 요청 보내기”가 활성화된다. 신청자는 별명, 이 기기 이름, 운영체제의 넓은 구분, 요청 만료 시각과 `승인 대기` 상태를 확인한다. IP·포트·지문·서버 키 전문은 노출하지 않는다. 화면을 닫아도 요청은 대기함에 남고 취소할 수 있다. 승인 전에는 세션, 폴더/문서 목록, vault 권한이 생기지 않는다.

### 2.4 상태 필과 저장 위치

| 화면 상태 | 필 문구 | 설명/다음 행동 |
|---|---|---|
| 기기 승인 전 | `이 컴퓨터에만 저장됨` | 개인 저장은 가능. 회사 자료에 접근하려면 연결과 승인이 필요 |
| 요청 제출 후 | `승인 대기` | 요청은 관리자 확인 중. 개인 메모는 이 컴퓨터에 저장 |
| 연결된 상태, 허브 저장 전/오프라인 | `회사 공유 대기` | 변경은 이 컴퓨터에 저장됐고 회사 반영 확인을 기다림 |
| 허브 durable ACK 후 | `연결됨` / `회사에 저장됨` | 허브가 저장을 확인한 상태. 다른 사람의 기기 저장까지 보장하지 않음 |
| 연결 끊김 | `이 컴퓨터에만 저장됨 · 회사 공유 대기` | 편집은 유지. 다시 연결하면 권한을 확인한 뒤 전송 |

필은 색상만으로 구별하지 않고 아이콘과 텍스트를 함께 쓴다. 툴팁/접근성 이름은 “연결됨. 회사 작업 공간이 변경 내용을 저장했어요.”처럼 상태와 저장 위치를 읽는다.

## 3. 관리자 승인함

관리 권한이 실제로 확인된 사용자만 연다. 탭 또는 필터 `대기`, `승인`, `거절`, `취소`를 제공하고 상태·최근 요청 순으로 정렬한다. 각 행은 요청자 별명, 기기 별명, Windows/macOS, 요청 시각, 만료, SAS 일치 여부, 기존 계정 연결 상태처럼 최소 정보만 보인다. 키 지문 전문, IP, OS 로그인 이름, 문서/폴더/파일 수는 표시하지 않는다. 동명이인은 승인된 디렉터리 정보가 공개 가능한 시점에만 보조 표식으로 구별한다.

행을 열면 “이 사람이 실제 동료이고 이 기기를 승인해도 되나요?”를 확인한다. SAS 일치 여부는 전송 대상 확인의 보조 증거일 뿐 요청자의 직장 신분을 증명하지 않는다. 승인자는 별도 수단으로 요청자를 확인해야 한다. 승인/거절에는 명시 확인을 요구하고 본인 요청 승인 금지 등 서버 권한 규칙을 따른다. 승인 후에도 기존 user/member와 ACL을 재검사하며 pairing이 vault 권한을 넓히지 않는다. 거절·취소는 이유 코드를 기록하고 비밀 정보나 자유 서술을 요청하지 않는다. 행은 `대기 → 승인`, `대기 → 거절`, `대기 → 취소`를 한 번만 전이하며 만료된 요청은 처리할 수 없다.

## 4. 호스트 시작·중지와 광고

### 4.1 공유 시작

설정의 “사내 공유”에서 “이 컴퓨터를 공유 작업 공간으로 사용”을 선택한다. 시작 전 카드에 “이 컴퓨터가 켜져 있고 회사 네트워크에 연결돼 있을 때 동료가 연결할 수 있어요. 상시 운영에는 회사의 상시 켜진 컴퓨터를 권장해요.”라고 설명한다. 최초 시작자는 임시 관리자가 되며 정식 관리자 이전과 복구 담당자 지정이 필요하다는 안내를 표시한다. 앱이 호스트를 시작하고 준비 상태를 확인한 뒤에만 `공유 중`을 보인다. 시작 실패는 원인과 다음 행동으로 표시하고 기술 진단 복사본은 직원 문구와 분리한다.

### 4.2 내 호스트 광고 on/off

“근처 작업자 목록에 이 작업 공간 표시” 스위치는 명시 opt-in, 기본 off다. 끄면 발견 광고만 멈추며 기존 승인 기기의 연결을 끊거나 공유를 중지하지 않는다는 의미를 설명한다. 켜도 광고에는 최소 후보 정보만 담는다. 회사명/팀명/별명 공개 여부를 별도 동의로 제어한다. 광고 off 상태에서 초대 링크는 계속 사용할 수 있다.

### 4.3 공유 중지

“공유 중지”는 확인 대화상자에서 연결 중인 사람과 공유 대기 변경이 영향을 받음을 설명한다. 중지해도 다른 사람 기기에 이미 저장된 자료는 지워지지 않는다. 사용자가 확인하면 호스트를 중지하고 상태를 갱신한다. 앱 종료 시 호스트가 함께 종료되는 정책도 같은 위치에서 알린다. 단순히 광고 off를 공유 중지처럼 표현하지 않는다.

## 5. TOFU와 SAS 보안 평가

발견은 공격자가 위조할 수 있는 후보일 뿐이다. 허브 TLS 공개키 pin은 별도 전달된 초대나 사람이 확인한 절차로 고정한다. 후보의 공개키나 확인값만으로 pin을 저장하지 않는다. 양 화면 확인은 신청 앱과 관리자 화면이 같은 허브와 pairing을 보고 있는지 알아차리게 돕고, 회사 소속이나 요청자 신원을 증명하지 않는다.

### 대안 비교와 권고

기존의 `SAS = H(허브 지문, 세션, 양쪽 nonce)`는 nonce가 모두 공개된 뒤 계산할 경우 안전하지 않다. 공격자는 허브 지문을 본 뒤 자신이 조절할 nonce를 바꾸며 해시를 반복해 두 화면의 짧은 숫자를 일치시킬 수 있다. nonce 또는 출력 자릿수만 늘리는 것으로는 이 선택 공격을 없앨 수 없다.

| 대안 | 안전성 및 비용 | 화면 표현 |
|---|---|---|
| 1. nonce commit-reveal | 한쪽이 nonce의 해시 커밋을 먼저 보내고 상대가 커밋한 뒤 원 nonce를 공개한다. 양쪽 커밋 검증 후에만 허브 지문, 세션, 양 nonce가 묶인 transcript에서 SAS를 계산한다. nonce 사후 선택을 막고 매 세션 새 값을 쓰지만, 커밋 상태·재전송 방지·타임아웃을 서버와 Rust 양쪽에서 일치시켜야 한다. | 여섯 자리 숫자를 두 화면에서 대조. “두 화면의 확인 숫자가 같나요?” |
| 2. 지문 기반 40비트 확인값 | 양쪽이 동일하게 검증한 허브 지문만으로 40비트 이상을 파생한다. nonce 사후 선택은 없고 구현은 단순하지만, 세션 결합을 표시하지 못하며 지문 출처를 이미 신뢰해야 한다. 단어 목록/정규화와 지문 비교 규칙도 고정해야 한다. | 양 화면에 같은 단어 네 개를 표시하고 “두 화면의 단어가 모두 같나요?”라고 묻는다. |

**권고: 대안 1, commit-reveal과 여섯 자리 숫자.** 세션별 신선도를 유지하면서 현재 pairing transcript를 비교할 수 있다. 숫자는 전화나 대면으로 짧게 전달하기 쉽다. 여섯 자리는 온라인 인증 강도나 신원 확인으로 표현하지 않으며, 실제 보호는 유효한 허브 pin, 기기 키 서명, 한 번만 처리되는 세션, 관리자 승인과 강한 시도 제한에 달려 있다. commit-reveal을 완전히 구현하기 전에는 이 화면을 보안 완료로 간주하거나 프로덕션에서 pairing을 활성화하지 않는다.

### 필수 프로토콜 단계와 시도 제한

서버와 Rust pairing 구현은 같은 버전이 고정된 단계 전이를 강제해야 한다.

1. 서버가 무작위 session ID와 만료 시각을 발급하고, 양쪽 기기는 역할·session ID·hub fingerprint·프로토콜 버전이 들어간 canonical transcript에 각자의 무작위 nonce를 만든다.
2. 양쪽 기기는 길이 구분 인코딩한 nonce와 transcript의 SHA-256 커밋을 서명해 전송한다. 서버는 각 역할에서 커밋 하나만 허용하고 둘 다 받기 전에는 어떤 nonce도 공개하지 않는다.
3. 양쪽 기기가 nonce를 공개한다. 서버와 각 Rust 클라이언트는 커밋을 상수 시간 비교로 검증하고, 값·역할·세션·허브 지문이 transcript와 맞지 않거나 중복 공개면 세션 전체를 실패 처리한다.
4. 양쪽이 검증에 성공한 뒤 transcript hash에서 편향 없는 방식으로 여섯 자리 숫자를 파생한다. 서버는 확인 결과만 세션에 한 번 기록하고 같은 세션의 재확인·재사용을 거부한다.
5. 양 화면에서 모두 일치 확인을 제출한 다음에만 참여 요청을 만든다. 관리자는 요청자와 기기를 별도로 확인하고 승인한다. 어느 한쪽 불일치, 서명 불일치, 만료 또는 취소도 즉시 폐기한다.

세션마다 최대 **3회** 확인 실패를 허용하고 실패 후 1초, 2초, 4초 지연을 적용한다. 네 번째 실패는 해당 pairing session과 invite token을 폐기하고 새 초대가 필요하게 한다. 제한은 서버가 session, invite, 기기 키를 기준으로 원자적으로 적용하며 Rust는 서버 응답을 우회해 재시도하지 않는다. 성공·실패·취소 뒤 nonce와 커밋은 메모리에서 제거한다. 상세 키·nonce·커밋 값은 직원 화면이나 일반 로그에 보이지 않는다.

관리 화면과 참여 화면의 안내는 각각 “두 화면의 확인 숫자가 같나요?” / “두 화면의 숫자를 서로 확인해 주세요.”로 한다. 동료에게 값을 읽어 줄 때 주변에 들릴 수 있다는 짧은 안내를 둔다. 같지 않거나 상대가 확인할 수 없으면 “숫자가 달라요. 연결을 멈추고 관리자에게 새 초대를 요청해 주세요.”를 표시한다. SAS를 확인하지 못해도 계속할 수 있는 건너뛰기 경로는 제공하지 않는다.

### officeFlow reducer 후속 변경 목록

현재 reducer는 `SAS_RECEIVED`/`SAS_CONFIRMED` 두 이벤트로 확인을 표현하므로 실제 프로토콜 UI에 연결하기 전에 다음을 반영해야 한다. 이번 UI 작업에서는 테스트된 reducer를 최소한으로 유지하고, 프로토콜 미구현 상태를 출시 준비 완료로 표현하지 않는다.

- 단일 `sas` 필드 대신 `commit-waiting`, `reveal-waiting`, `sas-waiting` 단계와 세션 만료·프로토콜 버전을 표현한다.
- `COMMIT_RECEIVED`, `REVEAL_RECEIVED`, `SAS_READY`, `SAS_CONFIRMED` 전이를 추가하고 순서가 바뀌거나 세션이 다른 이벤트를 거부한다.
- 확인 횟수와 서버가 결정한 잠금/초대 폐기 결과를 상태에 반영한다. UI 시계나 로컬 카운터가 제한의 권한자가 되지 않게 한다.
- 기존 `sas_mismatch` 오류 문구를 확인 숫자 용어로 고정하고, 확인 전에는 `JOIN_REQUESTED`가 불가능한 invariant와 승인 만료 검사를 유지한다.

SAS는 기기 키 서명, 별도로 검증한 hub pin, 계정 연결 또는 관리자 승인을 대체하지 않는다.

## 6. 창 크기와 플랫폼 규칙

모든 화면은 동일한 정보 순서와 동작을 유지하고 OS별 차이는 창 프레임/안전 여백에만 둔다. 좁은 창은 세로 단일 열, 넓은 창은 목록+상세 패널을 사용한다. 아래 폭은 설계 기준이며 실제 simulator에서 조정한다.

## 7. 접근성

- 모든 동작은 키보드만으로 가능하다. Tab 순서는 제목 → 설명 → 입력/목록 → 주요 버튼 → 취소/도움말이다. 후보 행은 버튼 하나의 명확한 이름으로 묶고 화살표 키 이동은 선택 기능이 구현된 경우에만 제공한다.
- 포커스 표시를 제거하지 않는다. 모달은 열릴 때 제목으로 포커스를 이동하고 닫힐 때 호출한 버튼으로 돌려준다. 승인/거절/공유 중지 확인은 `dialog` 이름과 설명을 제공한다.
- 발견 결과 갱신은 `aria-live="polite"`로 “후보 2개를 찾았어요”처럼 알린다. 새 후보마다 포커스를 빼앗지 않는다. 오류는 제목/원인/다음 행동을 읽고 입력 오류는 해당 입력과 연결한다.
- SAS는 숫자를 시각적으로 그룹화할 수 있어도 스크린리더에는 자릿수를 또렷이 읽히게 하고, 숫자만이 아니라 “두 화면의 확인 숫자”라는 맥락을 제공한다. 화면 낭독 중 숫자 비교와 맞음/다름 버튼이 혼동되지 않게 한다.
- 상태 필 접근성 이름은 연결/저장 위치를 모두 포함한다. 아이콘이나 색상에만 의존하지 않는다. 동명이인 표식도 별명과 함께 읽힌다.
- 조작 대상은 최소 44×44 CSS px를 목표로 하며 200% 확대와 Windows 고대비 모드에서 텍스트/포커스가 보인다. 애니메이션·자동 갱신이 있으면 줄이기 설정을 따른다.

## 10. 화면 상태 계약과 구현 경계

`officeFlow.ts`의 순수 reducer는 별명 필요 → 목록 탐색 → 후보 선택 → SAS 대기 → 승인 대기 → 연결됨 또는 오류를 표현한다. reducer에 시간값을 전달해 만료 경계를 결정적으로 다룬다. `OfficeDiscoveryPort`, `OfficeLinkPort`, `PairingPort`는 타입 계약뿐이며 실제 IPC/Rust 연결·화면/CSS·저장소는 후속 작업이다. 발견 후보는 항상 `untrusted-candidate`다. 외부 이벤트/응답을 reducer에 넣기 전 어댑터가 검증하고, 관리 승인 상태를 UI만 믿고 권한 부여하지 않는다.

저장 필은 UI 표시 모델이며 ACL이 아니다. 상태기계의 `company-shared`는 앱이 서버 durable ACK를 받은 이벤트에서만 설정한다. approval granted만으로 팀 저장 완료를 표시하지 않는다. SAS 비교는 허브 pin, 세션 transcript, 양쪽 nonce commit-reveal에 묶여야 하고 별명으로 인증하지 않는다. 실제 pairing 서버가 단계 전이·속도 제한·한 번 승인 규칙을 구현하기 전에는 화면 흐름을 출시 완료로 간주하지 않는다.

### 어댑터 계약: 승인 세션에서 동기화 시작

세션/relay는 구현되어 있으며 화면의 전역 session/vault 선택 및 SyncManager enable 연결은 다음 UI 작업이다. `createOfficeJoin(onEvent, ports?, api?)`의 세 번째 인자로 동기화에 사용할 ApiClient를 명시 주입한다. 기본값으로 전역 API를 바꾸지 않는다. simulator는 기존 가짜 ports를 그대로 사용한다. 실제 Rust status가 `approved`를 반환할 때는 기기 서명 세션이 origin별 비공개 keychain에 저장되어 있고 공개 `origin`, `serverId`가 포함된다. JS에 session bearer는 없다.

1. 기존 provider와 SyncManager를 먼저 정지하고 로컬 bridge의 저장을 마친다. 다른 허브의 API/세션·vault 선택과 섞지 않는다.
2. 선택한 ApiClient를 주입해 아래 순서로 join을 수행한다. 승인 폴링은 join이 소유한다.
3. `APPROVAL_GRANTED`를 받은 뒤에만 `getConnection()`으로 relay를 사용하고 `api.getSession()`과 `api.listVaults()`로 실제 user/organization과 허용된 vault 목록을 받는다. 목록의 `id`가 vaultId, `organization_id`가 organizationId다. 두 값을 복사해 같게 만들지 않는다.
4. 사용자가 vault를 고른 뒤 기존 store session 설정과 SyncManager enable 경로를 호출한다. 그 경로의 server pull-before-seed와 bridge echo/deletion/revocation guards를 유지한다. 승인은 durable 저장 ACK가 아니다.
5. 창 닫기/허브 전환/세션 회수 때 provider와 SyncManager를 먼저 정지한 뒤 `join.close()`를 await한다. 실패를 무시하고 다른 허브로 넘어가지 않는다. relay 종료 실패는 재시도할 수 있고 ApiClient의 이전 URL·토큰은 종료 성공 때 복원된다. `join.close()`는 discovery와 pending pairing도 정리한다. 승인 뒤에는 pairing 취소로 기기를 회수할 수 없으므로 관리자의 회수 API가 필요하다.

```ts
import { ApiClient } from "./api";
import { createOfficeJoin } from "./officeJoin";

const api = new ApiClient();
// UI owner: await the existing syncManager/provider shutdown before switching.
const join = createOfficeJoin((event) => {
  if (event.type === "APPROVAL_GRANTED") void connectSelectedVault();
}, undefined, api);
await join.begin(invitationInput, {personId, displayAlias, deviceLabel, platform}, candidateId);
// After the human compares SAS, and only from their explicit button action:
await join.confirm(true);

async function connectSelectedVault() {
  const link = join.getConnection(); // OfficeLink | undefined
  if (!link) throw new Error("Office relay is not ready");
  const session = await api.getSession();
  const vaults = await api.listVaults();
  // UI owner: choose vaults[i].id, install session, invoke existing enable path.
  // ApiClient is already at link.httpBaseUrl. Existing managers derive both
  // /sync and /vault-sync from api.getBaseUrl(); direct providers can use:
  const {syncUrl, vaultSyncUrl} = link;
}
// UI owner: stop all providers BEFORE releasing the transport.
await join.close();
```

서버가 차단하는 기능(MCP/OAuth 자격 발급, 계정/멤버 관리, presigned blob intent)은 계정 인증을 별도로 요구한다. office 세션은 기존 계정 토큰을 대체하여 keychain의 `session-v2`에 쓰지 않는다. 현재 relay는 10분 이하 기기 세션을 사용하고 만료 시 소켓을 닫는다. UI는 정지·재연결 시 `openOfficeLink({origin, serverId}, api)`로 Rust의 새 서명 challenge/세션을 받아야 하며 generic keychain으로 토큰을 읽어 갱신하지 않는다. 갱신 UI와 앱 재시작 후 허브 선택 복원은 다음 UI 작업에서 다룬다.
