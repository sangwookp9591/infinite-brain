# 06 · 직장인을 위한 사내 협업 PRD

**상태: 구현 전 제안.** 사용자가 요청한 방향은 회사 내부 사용, IP·개발 지식 없는 참여, 초기 별명으로 동료 알아보기, 팀 그룹별 폴더 지정·업데이트 동기화·형상관리 경험이다. 아래 단일 허브, 파일럿 규모, 권한·이력·운영 정책은 이를 구체화한 제안이며 사용자 승인이나 구현 완료를 뜻하지 않는다. 근거: [조사 보고서](../reports/사내%20협업%20동기화%20설계%20조사.md). 기술 계약: [07 아키텍처](07-office-collaboration-architecture.md).

## 1. 해결할 문제와 제품 기준안

지금 가입 화면은 서버 주소와 계정 생성을 먼저 요구한다. 개발 서버가 없는 직원은 `localhost:3010`에서 막히며 무엇을 운영해야 하는지도 모른다. 목표 경험은 **앱 설치 → 별명 설정 → 근처 회사 작업 공간 선택/초대 열기 → 승인 → 내 팀 폴더로 작업**이다. 이메일·공용 계정·IP 입력·Node/Postgres 설치 명령은 사내 모드의 직원 흐름에 없다.

한 명이 앱에서 ‘사내 공유 시작’을 누르면 앱이 허브 실행을 관리한다. 정식 회사 운영은 상시 켜진 사내 장비를 권장하고 동일 회사 신원과 자료를 유지해 이전한다. 직원 앱끼리 모두 연결할 필요는 없다. 인터넷 없이 회사 내부에서 발견·인증·동기화가 가능해야 한다. 앱 전체의 무외부 통신은 별도 ‘엄격 오프라인 정책’으로 제공하고 검증한다. 외부 AI 사용이나 업데이트를 회사 내부 사용 요구만으로 금지됐다고 가정하지 않는다.

파일럿 가정은 **한 회사 경계, 한 허브, 2~3개 팀, 직원 5~15명, Windows/macOS 혼합, Markdown 수천 개와 일부 Office 첨부**다. 사용자가 확정한 인원·한도가 아니며 동시 편집자 수·첨부 크기·오프라인 기간을 조사 후 부하 시나리오를 조정한다. 이 수치는 지원 상한이나 성능 보장이 아니다.

## 2. 사람과 데이터의 단위

| 개념 | 제품 의미 | 경계 |
|---|---|---|
| 회사 | 직원·승인 기기·운영 정책 관리 | 제안하는 회사 디렉터리 경계. 기존 organization 관계는 migration gate에서 확정 |
| organization | Better Auth 소속과 기존 권한 경계 | `organizationId`. 기존 데이터에서 vault와 사실상 1:1인 경우를 보존 |
| vault | 열고 공유하는 노트 모음 | `vaultId`. organization과 동일 ID로 취급하지 않음 |
| 팀 그룹 | 기획팀·디자인팀 등 직원 집합 | 회사 범위 그룹을 만들고 각 organization에 명시적으로 연결. 비가입 vault 접근을 만들지 않음 |
| 폴더 | vault 내부 정리·권한·동기화 선택 대상 | 임의 PC 폴더의 재귀 공유를 허용하는 기능이 아님 |
| 사람 / 기기 | 구성원 / 승인된 PC | 별명·팀·아바타는 표시, 안정된 ID와 키는 인증·이력 |

일반 직원은 받은 권한으로 메모하고, 팀 담당자는 위임받은 범위의 그룹·폴더를 관리하며, 회사 관리자는 초대·기기 취소·허브·백업 정책을 관리한다. 관리 권한이 모든 비공개 내용을 읽는 권한을 뜻하지 않는다. 기존 owner/admin 예외와 deny·lock을 보존한다. 최초 공유 시작자가 임시 관리자가 되며, 정식 운영 전 회사 관리자로 이전하고 복구 자격을 보관하도록 안내한다.

## 3. 주요 사용자 여정

### 3.1 별명으로 시작하고 근처 동료에게 참여한다

첫 실행은 ‘어떻게 불러드릴까요?’에서 별명과 선택적 기기 별명을 받는다. 개인 메모는 즉시 쓸 수 있다. ‘근처에서 찾기’를 누르면 공개에 동의한 공유자만 `기획팀 · 민수 · 공유 중`으로 보인다. 발견됐지만 아직 승인받지 않은 후보이며 문서·폴더·팀원 명단은 없다. 별명·팀 공개를 끄면 중립적인 작업 공간 이름으로 표시한다. 다른 직원 PC 전체를 항상 광고하거나 물리적 근접을 추정하지 않는다.

참여자는 허브 확인 정보를 대조하고 요청한다. 관리자는 `지수 · 회사 노트북 · 새 기기`를 실제 동료인지 확인해 승인하고 그룹과 vault 소속을 지정한다. 동명이인은 `민수 · 7K2P`로 구별한다. 짧은 표식은 보조값이며 키 지문 검증을 대체하지 않는다. 승인 뒤 ‘같은 팀의 접속 중인 사람’에서 승인된 별명·팀·기기와 접근 가능한 공유 대상을 고른다. 별명을 바꿔도 작성자와 권한은 유지된다. 두 번째 PC는 ‘기존 구성원으로 기기 추가’를 통해 같은 사람에 연결한다.

### 3.2 자동 발견이 안 되어도 IP 입력 없이 참여한다

자동 발견 → 기억한 허브 재연결 → 초대 링크/파일 열기 순으로 제공한다. 초대에는 연결 위치와 허브 지문이 포함된다. 카메라 없는 PC를 위해 QR은 보조다. 멀티캐스트가 막혀도 허브에 직접 연결 가능하면 초대로 참여한다. 단말 격리·허브 포트 차단이면 참여가 불가능하며 ‘발견했지만 연결되지 않음’과 관리자용 진단 복사를 제공한다. 초대나 짧은 코드가 방화벽을 우회한다고 안내하지 않는다.

### 3.3 팀 그룹에 폴더를 배정하고 필요한 것만 받는다

관리자는 vault 안의 `/기획`, `/디자인`, `/공통`을 선택하고 그룹에 보기/편집 권한을 준다. 여러 그룹 가입은 허용하고 V1 그룹 중첩은 제외한다. 폴더 권한은 자손에게 상속되며 기존 사용자 deny·private·lock 규칙을 함께 적용한다. 직원은 접근 가능한 폴더 중 ‘이 컴퓨터에 보관’을 고른다. 이 선택은 저장 공간과 수신 범위를 바꿀 뿐 권한을 주거나 회수하지 않는다. 다른 팀 경계로 폴더를 옮길 때 변경되는 열람 대상과 끊어지는 접근을 먼저 보여 주고 확인한다.

### 3.4 자동으로 공유하고 중요한 순간에 버전을 남긴다

메모를 쓰면 로컬에 저장되고 허브가 영속 저장을 확인하면 ‘팀에 반영됨’으로 바뀐다. 다른 사람의 수신·디스크 저장까지 확인한 것과 구별한다. 허브가 꺼지면 ‘이 컴퓨터에 저장됨 · 회사 공유 대기’로 표시하고 로컬 작업을 계속한다. 복귀하면 최신 권한과 삭제 정보를 먼저 받은 뒤 허용된 변경만 병합한다.

‘버전 남기기’는 폴더 또는 vault 범위의 이름 있는 확정 시점이다. ‘분기 기획 확정’과 현재본을 비교하고 작성자·변경 파일·추가/삭제를 확인한다. 자동 공유한 내용은 이미 팀원이 볼 수 있다. ‘검토받기 전 비공개’라는 의미는 없다. 복원은 영향 범위를 미리 보여 주고 복원 직전 버전을 남긴 뒤 새 변경으로 적용한다. Office 파일 동시 저장은 두 버전을 보존하고 선택을 요청한다.

### 3.5 퇴사·분실·호스트 교체를 처리한다

구성원 또는 기기를 취소하면 열린 연결과 후속 다운로드·업로드를 차단한다. 회수 전에 내려받은 평문을 원격으로 없앨 수 있다고 약속하지 않는다. 회수된 기기의 미전송 작업은 공유 원본에 넣지 않고 로컬 복구 사본으로 보존하며 회사 정책과 잔여 접근 권한에 따라 내보내기를 안내한다.

호스트 종료 시 ‘이 컴퓨터가 켜져 있을 때 공유됨’을 명확히 보여 준다. 상시 장비로 이전은 관리자가 실행하며 구 호스트와 새 호스트가 동시에 확정 쓰기를 받지 않게 한다. 호스트 분실은 백업과 복구 자격으로 명시 복구한다. 자동 승격은 없다.

## 5. 범위와 안전한 기본값

V1은 단일 authoritative hub, 사내 디렉터리, 그룹 폴더 grant, 자동 live sync, 로컬 오프라인 작업, binary 충돌 보존을 제공하는 범위다. 확정 버전·백업·상시 호스트 이전까지 통과해야 정식 회사 운영으로 부른다. 개인 PC 호스트 파일럿은 가용성 한계를 표시하고 운영한다.

다중 마스터·자동 리더 선출·공용 relay·인터넷 협업·SSO/사내 IdP·모바일·승인 전 branch·배포 승인·임의 외부 폴더 감시·원격 평문 회수는 후속이다. 기기 간 TLS를 제공하더라도 허브는 내용을 읽는 신뢰 경계다. E2EE나 사내 디스크 암호화를 구현됐다고 주장하지 않는다.

수동 확정 버전은 기본 90일 보관하고 관리자가 ‘계속 보관’을 지정할 수 있는 정책을 제안한다. 자동 버전·휴지통·tombstone은 별도 보존 정책이며 저장 용량 경고와 GC 보호를 둔다. 정확한 기간은 회사 보존 정책 확인 후 확정한다. 기존 checkpoint 최대 5개 정책을 기업 요구에 충분하다고 간주하지 않는다.

| V-07 | OC-13 | discovery/auth/sync/업데이트/AI/모델/원격 리소스의 egress 캡처. 엄격 정책에서 외부 패킷 0 |
| V-08 | OC-01,09,15 | 이름 변경·중복, 기기 취소·추가 뒤 이력 비교. 불완전 버전을 완성으로 표시하지 않는지 확인 |

합격 기준은 위 안전성 시험에서 **검증 대상 변경의 누락·침묵 덮어쓰기 0건**이다. 아직 달성한 수치나 모든 장애에서의 손실 0 보장이 아니다. 사용성은 IP·터미널 설명 없이 참여 가능한지 우선 확인하고 파일럿에서 성공률·관리자 개입·시간의 기준선을 만든다. 성능 목표는 실제 문서량·동시 사용자·호스트 사양 측정 뒤 정한다. UI는 시뮬레이터 양 플랫폼 검토와 별도로 native 테스트를 수행한다.

## 7. 의존 단계와 미결정

| 단계 | 선행 gate와 산출물 | 다음 단계 진입 조건 |
|---|---|---|
| G0 · 설계 확정 | 회사 관계·기기 신원·그룹 권한 표·위협 모델, 파일럿 망/규모 확인 | 현재 ACL와 신규 그룹 조합의 판정표 및 migration 검토 |
| G1 · 제품 런타임 실험 | 실제 Postgres + Node/native deps 패키징, Rust TLS pin/WS 연결, mDNS·초대 | Windows/macOS 배포 앱에서 설치/재시작/권한 실패/복원 재현 |
| G2 · 직원 파일럿 | 승인·그룹 ACL·선택 sync·outbox·binary·감사 | V-01~05·07~08 통과, 실제 업무 자료와 분리된 파일럿 |
| G3 · 회사 운영 | 불변 확정 버전·백업·상시 host·fencing·운영 문서 | V-06과 복원 drill, 운영 담당자와 RPO/RTO 확정 |
| G4 · 후속 검토 | 승인 전 초안·공식 배포본·IdP·대규모 운영 | 별도 PRD/ADR, V1의 자동 공유 의미와 분리 |

미확정 항목은 실제 직원 수·vault 수·망 분리·회사 IT 설치 권한·복구 책임자·보존 기간·VPN 허용 여부·외부 AI/업데이트 정책이다. 플랫폼 런타임을 묶기 어렵다는 결과가 나오면 비개발자에게 명령을 떠넘기지 말고 관리자 배포형 상시 허브를 우선하는 대안을 검토한다. 기존 [C0](../superpowers/specs/2026-10-17-p2p-c0-design.md)는 텍스트 전용 2~3대 실험 설계로 유지한다. 이 PRD는 회사 운영 기본 경로의 제안이며 C0가 구현됐다거나 기존 아키텍처를 전부 대체했다는 선언이 아니다.
